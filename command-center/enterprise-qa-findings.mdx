## AUDIT 1 — INBOX / TASKS / CALENDAR / NOTIFICATIONS  (returned 8/12, verified via grep + prod DB)

### P0-1 · Inbox "mark as read" is a dead path — unread count can only ever grow
- **Where:** the `'read'` action exists (`app/api/inbox/triage/route.ts` → `lib/inboxes/triage.ts:markConversationRead` → writes `hl_inbox_conversation_read`) but **nothing in the UI ever calls it**. Grep finds `'read'`/`markConversationRead` only in those two files. `app/(crm)/inbox/page.tsx` + `components/inbox/ConversationList.tsx` only ever call `action:'assign'` and `action:'status'`.
- **Proof:** `hl_inbox_conversation_read` has **0 rows** in prod.
- **User sees:** opening a conversation never clears its blue unread dot; the per-scope pill counts + header "N unread" only grow, never shrink. The inbox is permanently "unread."
- **Structural fix:** fire `POST /api/inbox/triage {action:'read'}` when a conversation row is opened — mirror the existing lead-notifications bell pattern (`app/api/notifications/read-all/route.ts`). One door, already exists; just wire the caller.

### P1-1 · Bulk task actions bypass the one-door (no activity log, no clone-cancel) — SAFETY
- **Where:** `app/api/tasks/bulk/route.ts` writes straight to `hl_tasks` (`UPDATE/DELETE … WHERE id IN (…)`) with **no `logActivity`** and **no `cancelCloneTaskActions`** — both of which the single-task path (`app/api/tasks/[id]/route.ts`) treats as mandatory.
- **User sees / risk:** (1) bulk complete/delete never appears in the lead's Activity Log / All feed (violates ALL_FEED_IS_EVERYTHING); (2) **an AI-clone scheduled fire for a bulk-dismissed task stays queued — the clone could text a lead about a task the human just dismissed** (same class as the Faduma clone-unauthorized-send incident).
- **Structural fix:** route bulk actions through the same service functions the single-task path uses (loop or shared helper) — not a second raw-SQL door. Textbook BEDROCK one-door violation.

### P1-2 · Silent empty-vs-failed conflation (2 places)
- `components/tasks/TasksPage.tsx` `loadTasks()` — `if (res.ok) setTasks(...)` with no else; a failed fetch looks identical to "no tasks."

- **Structural fix:** explicit error state, copy the good pattern already in `components/calendar/CalendarPage.tsx` `loadEvents` (distinguishes non-2xx/non-JSON from a true empty array, surfaces `fetchError`).

### P2-1 · Third private copy of task-status vocabulary

## AUDIT 2 — OUTBOUND TEXT / SMS GOVERNANCE  (returned 8/12, file:line + grep verified)

### S1 · P0 · The AI-send authorization SEVER is bypassed on the PRIMARY lead channel
- `lib/ai/authorized-send.ts` convicts only when `actorRole==='ai_agent'` or actorUserId resolves AI. The three AI iMessage sends — `lib/ai/lead-conversation.ts:1044`, `lib/workflows/execute-step.ts:271`, `lib/coordination/mediation.ts:39` — pass NEITHER, so `looksAi=false → ALLOW`. The Twilio FALLBACK right below each DOES pass `ai_agent` and is correctly refused — so the law fires only on the dead emergency path and waves through the main road. Since BlueBubbles is the primary lead text channel, **essentially every AI text to a real lead skips the sever.** 4th instance of this exact bug.
- **Fix (structural):** make `SendBbArgs.actorRole` REQUIRED; pass actorRole/actorUserId/intentId into `sendIMessageRaw` on all three paths; run the sever inside the wire function, one door.

### S2 · P0 · `/api/bb/send` is a second, ungoverned door
- `app/api/bb/send/route.ts:142` POSTs BlueBubbles directly — no `authorizeWireSend`, no leak-guard, no dedupe. Reachable w/ internal secret; scheduled iMessages route through it. Also `sendHandle` defaults to an EMAIL (`myli@houseloop.ai`) written as `sender` while the text physically leaves from +19132081633 → identity resolves wrong.
- **Fix:** route it through `sendIMessageRaw` (the one door); never a raw fetch.

### S3 · P0 · Lead-facing sends fail silently AND are recorded as done
- `lib/leads/handoff.ts:175` (+ `:61,:139,:144`, `mediation.ts:39`): `await sendSmsRaw(...).catch(()=>{})` — but `sendSmsRaw` returns `{ok:false}` as a VALUE, never throws, so `.catch` never engages and the result is discarded. A Twilio outage / missing token → no text, no `hl_messages` row, no error — then `logHandoff` records the handoff COMPLETE. **The lead is told (in CRM) Myli introduced their new agent; their phone never rang; nothing knows.**
- **Fix:** check the returned `{ok}`; on failure do NOT log the step complete — surface it.

### S5 · P0 · No opt-out. We can text someone who replied STOP (TCPA exposure)
- Grep: ZERO `opt_out`/`dnc`/`do_not_text`/STOP-keyword handling anywhere on the outbound path. `lib/phone/blocklist.ts` is consulted only at the INBOUND webhook, never before a send. Twilio handles STOP at the carrier — but leads are texted over BlueBubbles, where there is NO carrier opt-out. A lead who says STOP keeps getting iMessages from 1633 indefinitely. Email has suppression machinery; text has none.
- **Fix:** a suppression check inside the wire functions (`twilioSend`/`sendIMessageRaw`), keyed on digits10, before the wire + a STOP-keyword capture on inbound.

### S6 · P1 · Unresolved merge token reaches a lead as a BLANK hole
- `lib/merge/engine.ts:89` send-mode renders an unknown token as `''` (its own header cites the shipped "You're all set for  on !" incident). `applyMergeVerbose`/`unresolvedScopeTokens` exist to block/annotate but have ZERO callers. Preview shows `⚠missing:` so review looks clean while the send is broken.
- **Fix:** the send path uses the verbose form and blocks/annotates on unresolved tokens.

### S7-S12 · P1/P2 · double-log dropping AI attribution + duplicate green-SMS cards (S4); `APP_URL` unset → scheduled texts POST to localhost:3020 (S7); BB handle used as Twilio From (S8); GSM-7/em-dash scrub on only one path → 3× segment cost (S9); dedupe on 1 of 6 send paths (S10); BB password unencoded in query string (S11).
