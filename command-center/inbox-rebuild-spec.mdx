## 0. THE MODEL, IN ONE PARAGRAPH

FUB has exactly **one first-class object: the inbox.** A phone number is not a thing that has
behavior — it is a *door* that must be assigned to exactly one owner, and **all behavior lives on the
owner.** An owner is one of three kinds: the **Company Number** (account-level), a **Shared Inbox**
(FUB's internal name for what the UI calls a Team Inbox — the code leaks it in
`?sharedInboxId=1`), or a **User** (whose personal inbox is implicit and always exists). A number in
no owner's hands sits in the **Parking Lot**, where it can neither make nor receive calls. Configuring
"the phone system" therefore means configuring inboxes, and the Phone Numbers page is only a
directory + an assignment tool.

Two things sit deliberately ABOVE the inbox, at account level, because they are legal/company facts
rather than routing choices: **office hours** and **call recording + disclosure**. The inbox only
decides what to do *outside* those hours — it never defines them.

## 2. SCREEN — Phone Number Management (`/2/phone-numbers`)

Shot: `shots/02-phone-numbers.png` · Zach's reference: `fub-6-25-25.png`

Page title "Phone Number Management" with a **View Business Registration** button top-right (A2P/10DLC
compliance, gated separately at `/2/company-settings/phone-registration`). Four stacked sections:

### 2.1 Number Ports
Blurb: *"Once your number is ported into Follow Up Boss, it will stop working with your old
provider."* + **New Port Request** button. Empty state renders as a full-width notice: *"You currently
have no active porting requests…"*. No table when empty — the empty state replaces it.

### 2.2 Number Parking Lot
Blurb, verbatim and load-bearing: *"These numbers will not be able to make or receive calls until
assigned to a user or inbox. Once a number is released, you will no longer have access to it."*

Segmented control **Parked | Released** switches the table. Columns: `Phone Number` (with a
help-circle icon) · `Date Parked` · `Status` · `Actions`.

- `Status` is a lifecycle, not a flag: **`Parked`** or **`Releasing in 2 days`** (a countdown — release
  is scheduled, reversible until it lands, then the number is gone for good).
- `Actions` differs BY status: a `Parked` row gets a single **→ arrow** (assign it); a `Releasing` row
  gets the **⋯ menu** instead. The affordance encodes the state.
- 7 numbers parked at walk time.

**The arrow opens the "Move Number" dialog** (shot `shots/04-move-number-dialog.png`) — this is the
single most important screen in the walk, because its picker IS the ownership taxonomy:

> *"Please select the inbox or user you would like to move **(913) 355-6785** to:"*
> A searchable dropdown (`Search…` box) grouped into three headings:
> - **Company** → `Company Number`
> - **Shared Inboxes** → `Company`, `Past Agents`
> - **Users** → `Zach Spradling`
>
> Buttons: `Cancel` · `Move Number`.

So: **one number → exactly one owner, and the owner is a company/inbox/user union.** There is no
many-to-many, and no number without an owner except in the parking lot.

### 2.3 Team Inboxes
Header with a **Manage Inboxes** button (→ `/2/inbox-new/settings`). Columns: `Name` · `Phone Number` ·
`Actions`. **One row per NUMBER, not per inbox** — the `Name` cell reads `Inbox (Label)`, e.g.
`Past Agents (Melanie Clark)`, `Company (Default Buyer's Agent # - OLD)`. 40+ rows across only **two**
inboxes. This is the single most misread thing on the page: *"Past Agents (Melanie Clark)" is not an
inbox.* It is the Past Agents inbox holding a number labelled "Melanie Clark".

Per-row `⋯` menu — six actions (read verbatim from the opened menu's accessibility tree; the element
screenshot of the floating menu came back empty, so the label list below is the record):

| Action | Meaning |
|---|---|
| **Change Number** | swap this line for a different available number, keeping the assignment |
| **Swap Number** | exchange the assignment with another owned number |
| **Move Number** | re-assign to a different inbox/user (same dialog as §2.2) |
| **Set as Inbound-Only** | the number receives but is never used as an outbound caller ID |
| **Remove Number** | send it back to the Parking Lot |
| **Edit Label** | rename the label — the parenthetical in `Inbox (Label)` |

### 2.4 Team Members
Columns: `Name` (avatar + email) · `Phone Number` · `Actions`. Each user's personal line. Zach Spradling
→ (913) 490-2988. This section is why a user is a peer of an inbox in the Move picker.

## 4. SCREEN — Update a team inbox (`/2/inbox-new/settings/<id>`) — THE MAIN ONE

Shot: `shots/06-inbox-update-company.png` · Zach's reference: `fub-6-26-42.png`

Breadcrumb `All Team Inboxes > Manage > Update` (the first crumb goes to the inbox's *messages*, not
the list — `/2/inbox-new/1`). One card, three labelled bands (`CALL SETTINGS`, `EMAIL`), a
label-left / control-right two-column grid throughout, and a sticky footer `Cancel` · `Save`.
**Nothing autosaves.**

### 4.1 Identity
| Field | Behavior |
|---|---|
| **Inbox name** | free-text input. The only naming control. |
| **Phone numbers** `(Manage)` | read-only list of `(number) (label)`, bolded; `(Manage)` → `/2/phone-numbers`. Below it a **`+ Add Number`** link. |

**`+ Add Number` opens a modal** (shot `shots/07-add-number-click.png`) titled **"Add phone number to
Company"** — it names the target inbox in the title:
- *"Enter your area code or starting six digits"* → text input (pre-filled `913`) + **Find available
  numbers** button. Hint: *"Currently we support phone numbers in US and Canada"*.
- *"Select a phone number"* → radio list of provisionable numbers as `+19133953505 - Olathe, KS`
  (E.164 + city/state; some rows only resolve to `- US`).
- **Label** `(Optional)` → text input, placeholder "Add label".
- `Cancel` · `Add Number` (**disabled until a number is selected**).

That modal is the proof that **the label is a property of the number's assignment**, set at the moment
of assignment, and that provisioning is search-by-area-code → pick from live inventory.

### 4.2 CALL SETTINGS — the routing table (the heart of it)

A 4-column grid: **`Team Member` · `Ring Desktop` · `Ring Mobile` · `Press 1 to Answer`**, one row per
routing target, with **`+ Add Team Member or Phone`** beneath it.

A row is one of two kinds, and the kind changes which cells are even *available*:

| Row kind | Ring Desktop | Ring Mobile | Press 1 to Answer |
|---|---|---|---|
| **A raw phone** — e.g. `(913) 675-9877`, generic avatar | **red ✗** — impossible, there's no app | checkbox (checked in prod) | checkbox (unchecked) |
| **A user** — e.g. `Zach Spradling`, initials avatar | checkbox | checkbox | **cell is empty** — not applicable |

The semantics: **all checked targets ring simultaneously**, and the first to answer takes the call.
`Press 1 to Answer` exists only for raw phones and is the anti-voicemail guard — without it, the
callee's own carrier voicemail can answer the call and swallow the lead; requiring a keypress proves a
human picked up. That it is *absent* for users is the tell that FUB models "a user" as an app session
it controls, and "a phone" as a dumb endpoint it does not.

**`+ Add Team Member or Phone`** (shot `shots/08-add-team-member-or-phone.png`) opens a popover with
ONE control: a combobox placeheld *"Search team members or enter a phone number"*, listing the team
members not already in the table (Ana Spradling, Ben Froeschl). **One ➕, two paths** — pick a known
person or type an arbitrary number. This is exactly the pattern our own editable-row law already
mandates (`EditablePickerRow`), which makes it cheap to replicate.

### 4.3 CALL SETTINGS — the rest

| Control | Type | Behavior |
|---|---|---|
| **Voicemail** | link **`Record new voicemail`** | per-inbox greeting. On the CREATE screen this is replaced by the text *"Please save this team inbox before recording a voicemail"* — the inbox must exist first. |
| **Do not disturb** | checkbox | *"If enabled, no team members will be called."* A master kill-switch for the whole routing table; calls fall straight through to the fallbacks. |
| **If outside office hours** `(Edit)` | radio | `Go to inbox voicemail` (default) \| `Forward to number`. `(Edit)` links OUT to `/2/company-settings` — **the hours themselves are not editable here**. |
| **If there's no answer** | radio | `Go to inbox voicemail` (default) \| `Forward to number` |

Selecting **`Forward to number`** reveals a **`+ Add Number`** link under the radio (shot
`shots/09-forward-to-number.png`) — the forward target is chosen, not typed inline. Both fallbacks are
independent and can differ.

The full call decision, as the screen states it: *DND on?* → voicemail. *Outside office hours?* → the
outside-hours choice. Otherwise ring every checked target at once; *nobody answered?* → the no-answer
choice.

### 4.4 EMAIL
**Connect Email** → a **Sign in with Google** button (→ `/settings/betaConnectGoogle?sharedInboxId=1`)
`or` **Microsoft 365** (→ `/settings/connectMicrosoftFub2?sharedInboxId=1`). Blurb: *"We will use your
email account to send, receive and manage email directly in Follow Up Boss, sync email history with
your leads and report on lead source performance."*

**The mailbox is bound to the INBOX, not the user** — `sharedInboxId` in both OAuth URLs. A shared
inbox can own a real mailbox. On CREATE this band reads *"You will be able to connect an email address
to this team inbox after it is created."*

### 4.5 Create vs Update parity
Shot: `shots/15-new-team-inbox.png`. Breadcrumb `… > Create`. Identical form MINUS: no Phone numbers
section at all, voicemail deferred, email deferred. Routing table renders its empty state: *"No team
members selected. Add one or more using the button below."* Defaults: DND off, both fallbacks = `Go to
inbox voicemail`. **Everything that needs an id is deferred to after the first save** — a create is
just a name + routing.

### ⚠ THE HAZARD TO FIX FIRST — ring config lives in TWO stores

`hl_inboxes.ring_chain` (0390) and `hl_routing_groups.ring_targets` (0362) both describe "who rings."
**The one the runtime actually obeys is the OLD one:** `InboxCallRoutingModal.tsx` writes
`hl_routing_groups` and stamps `hl_phone_numbers.routing_group_id`, and the live webhook reads it at
`app/api/phone/webhooks/voice/route.ts:135` (with `no_answer` at `:118-119` and `dial-status/route.ts:13`),
while `InboxDetail.tsx` *displays* `ring_chain`. 0390 declared `hl_routing_groups` "DEPRECATED in
place… until the C3 code cutover ships" — **that cutover never shipped.** So `ring_chain` is largely
display while `ring_targets` is behavior: **the screen and the phone can disagree, and the phone wins.**

A third deprecated-but-live signal rides along: `hl_phone_numbers.answer_mode` (0382), also marked
superseded by 0390 and **also still honored**. Three signals, one question.

This is exactly the disease `ONE_ANSWER_TABLE` names: one fact, two homes, and the surface reading the
one that isn't the answer. **Collapse these into one store before adding a single new control** —
otherwise every gap closed below gets built twice and the two copies drift.

A second instance of the same disease: a number's owner is recorded in **three** places —
`hl_phone_numbers.inbox_id` (0390), `hl_phone_numbers.assigned_user_id` (0269), and
`hl_dialer_assignments.user_id` (0016, UNIQUE per user). FUB has exactly one. That single-owner rule is
the thing most worth replicating.

**And the design question the two stores disagree on:** FUB rings every checked target
**simultaneously**; our `ring_chain` is **ordered/sequential**. Zach picks; the schema follows.

**Our vocabulary is already better and stays.** A number is a **door**; an inbox has a **manager**
(which may be an AI); the number's name is the **friendly name** (one field, one truth, pushed to
Twilio). We do not adopt "Team Inbox" (ours is **shared inbox**), "Shared Inbox" as a hidden internal
name, or "Move Number" as a menu item — ours is **which inbox does this door feed**.

| FUB screen / control | HouseLoop surface | Status |
|---|---|---|
| `/2/phone-numbers` → Team Inboxes + Team Members tables | **Numbers → Our Numbers** (`FEEDS INBOX` column) | **have** — ours is better: one row per number with an explicit inbox picker, rather than a name mashed as `Inbox (Label)` |

### What WE have that FUB does not
1. **A door can be an email OR a phone.** FUB bolts a mailbox onto an inbox through OAuth; ours is one
   uniform door list, so "who owns this address" and "who owns this number" are one question.
2. **An inbox manager can be an AI.** `Myli · all channels` is a manager in the same column a human
   occupies — FUB has no slot for a non-human answerer, which is why its whole routing model is
   "which humans ring."
3. **Provider + source on every number** (`Twilio`, `SOURCE`, `Sync from Follow Up Boss`) — we model
   where a line came from; FUB assumes it owns everything.
4. **The activity log.** Every message/call lands in `hl_activity_log` through one writer with a signed
   actor — FUB's inbox is a mail client, ours is a projection of the ledger (`BEDROCK_LAW` layer 5).
5. **Personal inboxes are first-class rows** (`hl_inboxes.kind='personal'`, one per user enforced by a
   partial unique index) in the same table as shared ones, so they can be listed, audited and
   configured. FUB's personal inbox is implicit and has no configuration screen at all (§6).
6. **A number carries its meaning**: `creates_event`, `workflow_id`, `lead_source_id` — calling a
   specific line can fire a specific playbook and attribute a specific source. FUB's number knows only
   which inbox it rings.
7. **Port pipeline as real state** — `hl_number_ports` has a 7-state status plus a human `next_step`;
   FUB shows a request or an empty box.
8. **A per-inbox AI prompt layer** (`hl_inboxes.prompt_layer`) — steers the AI for *that inbox's*
   callers, under the agent's persona.
9. **AI voicemail triage** — cold/unknown voicemails don't blast the admin
   (`webhooks/recording/route.ts:118-123`).
10. **Per-inbox notification subscriptions with channel choice** (`hl_inbox_subscribers`, email/sms,
    independent of lead assignment) — solves the visibility problem FUB's blunt all-leads toggle can't.
11. **Caller-based forwarding rules with priority** (`hl_phone_forward_rules`) and an inbound
    **blocklist at the webhook door** (`hl_blocked_numbers`) that drops before lead mint while still
    recording the raw inbound for audit.
12. **Anti-number-leak call screening** — `answerOnBridge` plus the screen whisper means the caller
    never lands in an agent's personal cell voicemail. FUB forwards raw.

Full detail with file:line pointers: `.claude/reports/inbox-rebuild-spec/houseloop-inbox-estate-map.md`.

### The one structural lesson to copy
**Behavior belongs to the inbox; the number is only a door.** FUB never lets you configure a phone
number — you configure the thing it points at. Our Numbers page already says this out loud (*"All
behavior lives on the inbox"*), so the rebuild is: put the routing/voicemail/DND/fallback block on the
inbox detail screen, and leave Numbers as a pure directory. Do not scatter call behavior across both.

### What this implies for the rebuild, in order
0. **Decide inbox membership** (GAP 0) — it is the prerequisite for the routing table, the `Team`
   column, and any per-seat notification rule. Membership and "who rings" are two facts, not one.
1. **Collapse the ring stores into one** (`ring_chain` vs `ring_targets` vs `answer_mode`) and settle
   simultaneous-vs-sequential in the same pass. Nothing else should be built on top of a fact with
   three homes, and the store the runtime obeys is currently one of the two marked deprecated.
2. **Collapse the three number→owner paths into one** (`inbox_id` · `assigned_user_id` ·
   `hl_dialer_assignments.user_id`). FUB's single-owner rule is the shape to copy.
3. **Wire what already exists** before adding anything: surface the `ring_desktop` flag the schema
   already carries, make the global press-any-key screen configurable, and let the phone webhooks read
   `lib/business-hours.ts`. Three of the biggest-looking gaps are wiring, not building.
4. **Then add the genuinely missing call-behavior columns to the inbox**: DND and a per-inbox voicemail
   greeting. Both belong on `hl_inboxes` — behavior lives on the inbox.
5. **Unify personal and shared routing** into one model before building either screen (GAP 10) — a
   personal inbox is N=1, not a second system.
6. **Give the inbox a workqueue** (GAP 11 + 13): triage states and an unmatched-inbound panel. This is
   the largest UX delta and the one Bedrock actually depends on.
7. **Last:** per-inbox email OAuth (GAP 9), compliance switches (GAP 8), number lifecycle (GAP 1/2/3).

### The one thing NOT to copy
FUB names a number's assignment by string-concatenating `Inbox (Label)` and then shows that string as
the row's `Name` in a table headed "Team Inboxes" — which reads as 40 inboxes when there are two. Keep
our two explicit columns (`FRIENDLY NAME`, `FEEDS INBOX`). Same information, no lie.
