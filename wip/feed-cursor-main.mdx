### The defect
`ORDER BY occurred_at DESC` alone is not a total order, and the paging predicate was a strict
`occurred_at < before`. A page ending on a shared instant asked for everything strictly older than
it, so every tied sibling was skipped by that request AND by every request after it. No stall, no
error: hasMore went false on schedule and the feed looked whole. 126 rows across 11 of the 12
deepest leads; ties cluster on second-granularity FUB-import timestamps.

### The fix (in the order the law requires — a cursor over an unstable order points at nothing)
- **`lib/activity/feed-cursor.ts` (new)** — the order and the predicate declared ONCE, as each
  other's mirror, plus the JS mirrors the test drives. The route imports the SQL builders instead
  of retyping them beside the query.
- **`app/api/leads/[id]/activity/route.ts`** — `ORDER BY (occurred_at DESC, id DESC)`; the
  DISTINCT ON representative gains `a.id DESC` (an identical request must dedup identically);
  accepts `beforeId`; returns `nextBeforeId`.
  ⭐ **The cursor moved OUTSIDE the dedup.** Inside, it could filter away the primary lead's copy of
  a household event and promote the twin — one event returning as a second card on a later page.
  Cost measured, not assumed: 2218 → 2260 ms/page.
- **`lib/activity/compose-feed.ts`** — `nextPage()` returns `beforeId`; both halves come off ONE
  source (reader cursor, else the screen's tail) and never one from each.
- **`CenterLane.tsx`** — sends the pair; `mergeDesc` sorts in the same total order; each row
  carries **`data-activity-id`** so the screen half of the completeness equation is countable at all.
