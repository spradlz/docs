### THE URL-SERVICE VERDICT (argued, keep it)
**Right for the web, wrong for the CRM.**
- **Web: YES**, already built. Her face is drawn inside CLIENT components; a server-resolved prop
  would have to be threaded through every one and missed by the next surface someone adds.
- **CRM: NO.** Every CRM surface already receives the avatar URL inside the JSON it already fetches.
  The walked feed carries **62 person-avatars on one lead** — a service would turn one payload into
  62 extra round-trips, each doing a DB read, to deliver a URL the payload already carried. It buys
  nothing: the payload regenerates on every refresh, so edits already fan out with zero re-renders.
- Cache-busting is a non-issue **by design**: the door stores a URL, so an edit CHANGES the URL.
  Replacing bytes behind a fixed path is the stale-cache trap; we don't do that.

### THE IMMUTABLES (correct, not violations — say so in the doc)
- A **sent email** bakes its photo at send. History is history. (The signature bakes `<img src=avatar_url>`,
  so it follows a change to the BYTES at that path but not to the row. Semi-baked, fine.)
- The **sign-off board** bakes at promote; regenerates on the next promote.
- The **contact-card PNG** and the **vCard** bake at generation (the vCard embeds base64 because iOS
  refuses a URI photo). Re-issued cards pick up the new face; ones already on a phone do not. Physics.
- **Mobile `/m`** draws LEADS only (initials + name-hash color). No actor faces. Scoped gap, not a bug.
