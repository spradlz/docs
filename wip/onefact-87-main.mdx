### THE ONE THING TO KNOW

**The Twilio Message SID IS the identity of an inbound text — always, group or 1:1. The Conversation
Message SID is an ATTRIBUTE of that fact, never a second identity.** Now law (desk ruling, 8/15).

`/webhooks/sms` is the ONE WRITER. `/webhooks/conversations` is an ENRICHER that claims the row the
SMS path wrote and stamps the group truth onto it + its card. It does not insert.

### ⭐ WHY THE IDENTITY WAS CHOSEN, NOT DISCOVERED — DO NOT RE-LITIGATE THIS WITHOUT NEW EVIDENCE

Twilio delivers a group reply TWICE (~130ms apart) under two ids and **links them nowhere**. Proven
three ways on the live specimen (`IM605677cd…` in `CH6b63b447…`), not assumed from docs:

| probe | result |
|---|---|
| `GET …/Messages/{IM}/ChannelMetadata` | **`{"data": null, "type": null}`** — populated for WhatsApp-class channels, EMPTY for an SMS-originated conversation message |
| the Conversations Message resource (account- AND service-scoped, identical) | no field naming the carrier message; `delivery: null` on an inbound |
| `GET /Messages/{MM}` | no field naming the conversation |

`onDeliveryUpdated` **does** carry `ChannelMessageSid` — but it fires for OUTBOUND delivery only,
never for an inbound reply. If someone "finds" the linkage later, re-run these three before building
on it.

**The double-delivery is structural, not an accident:** `+19132861761` carries BOTH an Address
Configuration (`auto_creation.enabled=false`) AND its own `sms_url` → `/api/phone/webhooks/sms`; a
matching inbound fires both. Deliberately NOT cured by Twilio config — correctness must not rest on
provider settings. ⚠ My first probe reported "zero address configurations"; that was **my JSON
