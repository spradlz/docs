## 📌 The one sentence

A lead answers **two independent questions**, and they must never share a control:

- **Stage** — *where is it in the funnel?* (New Lead → Closed, plus Nurture). Per-pipeline. Stays exactly as it was.
- **Disposition** — *why is it set aside?* (Active · Incoming · Has Other Agent · DNC · Blocked · Trashed). **One field, both pipelines, user-configurable.**

Before this engine, "why a lead was set aside" lived in six places that disagreed — a `status` column
(`active/hidden/trashed/staged`), a **Trash stage** *and* a **trashed status** for the same idea, a DNC stage,
a blocklist. Zach 8/8: *"stage = progress, disposition = why parked."* The engine collapses all of it onto one
axis.

## The table — `hl_dispositions` (mig 0708)

Configured exactly like stages (**Settings → Dispositions**), but flatter: no pipeline, no sections. Add →
name + color + icon + **Behavior** + **Enabled**. Nothing is hardcoded — every surface reads this table.

| column | meaning |
|---|---|
| `name` · `color` · `icon` | how it renders (a colored dot + Lucide icon) |
| `position` | display + reorder order |
| `is_active` | shown in the UI as **Enabled** — a disabled one isn't offered for new assignment |
| `behavior` | **what it DOES** — `none` \| `hide` \| `trash` \| `block` (the whole point; chosen in the builder, never hardcoded) |
| `is_system` | `Active`/`Blocked`/`Trashed` own real machinery → can't be deleted, and their behavior is locked |

`hl_leads.disposition_id` is the FK (`ON DELETE SET NULL` — removing a disposition never deletes a lead; the
lead falls back to Active). Seeded 6; `status` was backfilled (`active→Active`, `trashed→Trashed`).

### The four behaviors — each wires to real machinery

| behavior | on the working list? | what setting it does |
|---|---|---|
| **none** (Active) | shown | a normal working lead; also un-trashes if it was in the bin |
| **hide** (Incoming · Has Other Agent · DNC) | hidden | parked — drops off the list, kept for later |
| **trash** (Trashed) | hidden | the recycle bin: soft-trash (`status='trashed'` + `deleted_at`), reversible |
| **block** (Blocked) | hidden | blocklists the number (calls/texts rejected) **and** parks it |

## Where it shows

- **Lead detail** (`LeadLane` → `DispositionPill`): a small pill on the far right of the AI-Clone line —
  `● Active ▾` (green) by default, no ribbon. A parked lead colors the pill and raises a thin **ribbon** under
  the navy header. The menu lists the enabled dispositions live from `/api/dispositions`.
- **Leads table** (`LeadsTable`): the quick **Disposition** filter (was "Status") — live options with color
  dots, filters `disposition_id`. The standalone trashcan quick-icon is replaced by a **Set Disposition**
  icon (the bin is now the *Trashed* filter). The Advanced Search `disposition` field maps the same way.

## The write path — `PATCH /api/leads/[id]/disposition` + bulk

Setting a disposition is one action; the behavior read from `hl_dispositions` decides what happens:
`trash` → soft-trash, `block` → blocklist the number, else → active (un-trash). Every change logs the
**`lead_dispositioned`** activity kind (mig 0711 — the lead lifecycle is disposition now, replacing the old
`lead_trashed`/`lead_restored` as the general case). Bulk: `POST /api/leads/bulk` `action:'set_disposition'`.

## The filter engine — the default gate (`lib/leads-query.ts`)

The table's default view = **working leads only**: not in the bin **and** not set aside.

```sql
l.deleted_at IS NULL
AND (l.disposition_id IS NULL OR l.disposition_id IN (SELECT id FROM hl_dispositions WHERE behavior = 'none'))
```

A subquery, not a join, so the bare count query stays valid. The moment you filter on a disposition, the gate
steps aside and `l.disposition_id = ANY(...)` does the work — including surfacing the recycle bin when
**Trashed** is picked (those rows carry `deleted_at`). A legacy `status` handler is kept only so pre-existing
saved searches don't break.

## What was retired (mig 0711)

- The empty **DNC** + **Trash** *stages* (both pipelines, 0 leads) — those were dispositions pretending to be
  funnel steps.
- `status='staged'` (0 rows, and the name collided with "stage") folds toward the **Incoming** disposition.

## The rule

Every surface reads `hl_dispositions` — the pill, the ribbon, the bulk menu, the filter. **No hardcoded
disposition list anywhere.** A new disposition is a row a human adds in Settings, and it flows everywhere the
moment it's enabled. Companion: [Stages](/crm/pipeline-workflow-stages) · [Leads Table](/guides/leads-table).
