## The locked model (Zach, 2026-07-27)

**A trigger event was never a separate object — it is an activity with automation switched on.**
The Trigger Events page and the Activity Catalog are ONE page over ONE table (`hl_activity_catalog`);
Trigger Events is that table filtered to the rows whose automation toggle is on. An automation can run a
workflow, a playbook, or a notification.

**The four nouns:** Integration = the pipe a lead arrives through · Source = the brand that produced them ·
Activity = a fact that happened · Tool = a capability the AI can use. The loop: the Toolbox performs →
an Activity records it → some activities are Triggers → Triggers run Playbooks → Playbooks use the Toolbox.

**Sections never collapse across pipes.** "Registered on HouseLoop" and "Registered via Zillow" are two
rows, even when they run the same playbook — *"the lead source says who introduced them, the activity says
where they are now."* Collapsing them destroys the number that proves HouseLoop is earning its keep.

**Follow Up Boss is the Zillow connector, not an integration in its own right.** Zillow owns FUB; nothing
else flows through it. Its section is Zillow — swap the connector later and the section keeps working.

## The two-natures law (Zach, 2026-08-04)

Every catalog row now carries an `origin` marker, because the rows come in two natures:

| Nature | `origin` | What it means |
|---|---|---|
| **Facts Zillow defines** | `zillow_mapped` | Tour request, in-app message, the Zillow insights (high-intent buyer, new area, viewed 10x…). Zillow invents these; we painstakingly *mapped* them. Their names are **read-only** — only what they trigger is ours to configure. |
| **Activities we built** | `ours` | Everything HouseLoop emits — website activity, comms, our native insights, and the registration activities. Fully ours to name, toggle, and extend. |

## The vocabulary — there are no doors (Zach, 2026-08-04)

> "There are no registration doors. There are no trigger door events. There are no inbox doors.
> There are no doors. There's an activity. There's an inbox. There's an activity log."

Three nouns carry the whole automation model. An **activity** is a fact (`sms_received`,
`phone_call_received`). An **inbox** is where it landed — a real line or mailbox with real links
(`hl_inboxes`, `hl_phone_numbers`), never a marker column. An **automation trigger** is a named
activity-times-inbox pair that fires an automation, filed under its integration — "Past Client
Inbound Text" is `sms_received` on the past-client line, filed under Follow Up Boss. Nothing walks
through anything. The word `door` is banned language in code and docs; the `door-zero` cage check
(8/8, shrink-only floor) enforces it on every push.

## The registered_* family — first-class registration activities

Registration events are **first-class catalog rows, one row per registration activity** — never collapsed into a generic
"registered" (the per-activity counts are the whole point). Born 2026-08-04 (migration 0612, phase 1):

`registered_like_home` · `registered_saved_home` · `registered_shared_home` · `registered_saved_search` ·
`registered_tour_request` · `registered_contact_request` · `registered_get_seller_report` ·
`registered_seller_get_started` · `registered_manual_entry`

Each carries its own Trigger / Creates-Lead / Notify toggles and its own fire counts. The old
`*_registration` spellings still route during the transition and retire in phase 2 once rename-readiness
reads zero.

## The scale switch — `requires_registration`

A register-first action used to be **hardcoded twice**: the website carried a hardcoded list of "actions
that pop register-first," and each action fired a hardcoded token. That does not scale — a new one meant
a deploy.

Now: **a register-first action = a catalog row with `requires_registration` switched ON.** Eight rows
carry it today (like, save, share, saved search, seller report, seller inquiry, tour, contact). The
website will read that list *from the catalog* (arc item 504) — after that, a new register-first action
is a row, never a deploy. Same config-table-and-UI law as colors.

## The arm collapse (2026-08-04, board #527)

A **registration-band row mints a NEW lead by definition**, so it carries exactly ONE automation slot —
the New-Lead arm; the Existing-Lead arm never renders on those rows. The collapse **derives from the
row's band** (the catalog's own filing), not a hand-kept key list — the earlier single-key hardcode had
already drifted stale against the band. Activity-band rows keep their dual arms, and every toggle on the
page writes the real seat columns through `/api/lead-flow` (round-trip proven in the receipt).

## One owner for the notification binding (2026-08-04, board #525)

The **NOTIFICATION column reads THROUGH the Activity Catalog** — `hl_activity_catalog.notify` +
`notify_class` are the owner (mig 0630 backfilled them through the alias closure, canonical-wins on the
10 measured collisions). One save from Configure writes the catalog and keeps a transitional mirror on
the old trigger table until the swap; no read touches the mirror.

## The FUB inbound-text toggle

An inbound text from an unknown number on the FUB side can mint a lead — governed by the
`text_message` row in `hl_fub_webhook_settings` (Settings → Integrations → Follow Up Boss). The
creates-a-lead toggle is currently **off by choice**: an existing lead's inbound text logs as plain comms
activity; flip the toggle and an unknown sender mints. The in-app (Zillow) message row has the same switch,
currently on.

## How a FUB signal becomes an activity card — the converter (Zach 2026-08-08)

FUB is a **hub, not a source.** It hands us signals — insights, in-app messages, tours, saves, pre-approvals —
however it wants, and it often disguises an event as a **note.** The thesis Zach signed: *"point to ONE
pre-mapped place and say — here are the FUB events we mapped, and here is what they do,"* and **never match a
note body or a TypeScript regex to figure out a FUB signal again.**

**There is NO new table — and there was never meant to be one.** `ONE_ANSWER_TABLE.md` settles it: FUB vs
HouseLoop are two SOURCES of one fact (an automation trigger), so the difference is a **column
(`integration`) on one table, never a second table.** And the table already exists — `hl_trigger_events`
(one row per activity × integration; the FUB Sync section IS its `integration='follow_up_boss'` rows, with
`creates_lead` · workflow · playbook · notify already on each row).

**The three layers, and where each fact lives:**

| Layer | Table | Grain | Owns |
|---|---|---|---|
| **Dictionary** | `hl_activity_catalog` | one row / **kind** | the sentence, color, `card_layout` — what it IS |
| **Automation triggers** | `hl_trigger_events` | one row / **(kind × integration)** | `automation` · `creates_lead` · workflow · playbook · notify — what it DOES, per pipe |
| **Activity cards** | `hl_activity_runlog` | one row / **instance** | the rendered card — carries kind + integration + source |

So a `property_inquiry` **via FUB** (`integration=follow_up_boss · source=zillow`) and a `property_inquiry`
**via HouseLoop** (`integration=houseloop · source=houseloop.ai`) are the **same catalog kind, two different
things** — separated by the `integration` on the row, each with its own automation-trigger row. That is the
atomic law, physically.

**The one hand-coded piece, and why it stays code:** `lib/fub/convert-fub-signal.ts` maps each raw FUB signal
(note, event, tag, message, saved search, home activity) to its catalog kind and **parses** the payload (one
Zillow-Insights note carries N homes with prices + zpids). The *mapping* is data (the catalog + the
`hl_trigger_event_alias` spellings); the *parsing* is genuinely code — a table of regexes would be worse. The
converter emits the catalog kind, `logActivity()` writes ONE `hl_activity_runlog` row with
`integration=follow_up_boss`, and the card reads the **kind** (catalog paints it) + the **source pill** (row).

### Current state vs the locked target

**Live today:** the converter maps the FUB signals; the catalog carries every control (`automation`,
`creates_lead`, `notify`/`notify_class`, `status=locked`, `platforms`); `hl_trigger_events` holds the
per-(activity × integration) trigger rows; the catalog paints every card (`card_layout` now set on all 187
kinds — mig 0712, so nothing falls back to un-declared TypeScript).

**Building towards (the "never again"):**
- **Converter wins** (`backfill-fub-comms.ts`, 2026-08-08): every FUB note runs through `convertNote()` first;
  a note the converter claims (a Zillow insight, a property save/view) is **skipped** as a note — it's already
  logged as its true kind by `backfillFubBehavior`. Only a genuine human note (`convertNote` → `[]`) becomes
  `note_added`. This is the fix for the *"Jeremy David created a note"* bug — a FUB insight can never
  double-import as a note again.
- **Data cleanup** (mig-era, Rule #0, Zach-approved): 157 duplicate `note_added` rows (a `zillow_insight_*`
  twin already existed) deleted from `hl_activity_runlog` with a reversible receipt; the remaining sole-copies
  are flagged for a converter re-run.
- **Anti-drift gate:** a parity check so a FUB note cannot silently become `note_added` and every catalog kind
  carries a card shape.
