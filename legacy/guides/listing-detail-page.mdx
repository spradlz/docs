Every listing on HouseLoop has a detail page at `/listings/{address-slug}/{hlid}/`. This page
documents the data-driven sections added in the May 2026 marathon: Offer Insights v3, Market
Estimate v3, the Tax card, Schools, and the HOA/Community rollup.

## Page composition

The root component is `components/listing/ListingDetail.tsx`. All sections below the hero
are composed in this order on **desktop**:

1. Hero (photos + address + price)
2. Property facts (beds/baths/sqft/lot)
3. About (public remarks)
4. Features (interior / exterior / parking / community)
5. Offer Insights
6. Market Estimate
7. HOA / Community
8. Schools
9. Tax
10. Price history

**Mobile reorders sections 5-6 to appear directly after About**, before features and downstream
detail blocks. Section nav pills are desktop-only; mobile relies on native scroll.

## Offer Insights

**Component:** `components/listing/OfferInsights.tsx`
**Source:** `lib/listings/resolve-market-stats.ts` -> `lib/listings/market-bands.ts`

Offer Insights gives buyers a market-context band for the listing's price relative to recent
sold comps. It renders four pills (Strong / Solid / Fair / Weak) plus a Zillow-parity
probability blurb.

### How bands are computed

The resolver `resolveMarketStats(hlid)` walks a proximity ladder:

```
neighborhood (>= 10 sold)  ->  zip (>= 30)  ->  city (>= 50)  ->  county (floor)
```

It reads from `hl_geo_market_stats` (daily) and `hl_geo_neighborhood_stats` (nightly). The
`sellToListPct` at the matched level feeds `deriveBandsFromRatio()`:

| Band | Label | Mobile label | Probability copy |
|---|---|---|---|
| `competitive` | Very Competitive | **Strong** | "Over 90% chance of a winning offer" |
| `moderate` | Competitive | **Solid** | "70 to 90% chance" |
| `soft` | Somewhat Competitive | **Fair** | "50 to 70% chance" |
| `buyers` | Buyer's Market | **Weak** | "Under 50% chance" |

<Note>
Mobile pill labels are 6 characters or fewer (`Strong / Solid / Fair / Weak`) — the longer semantic
slugs live only in code for analytics stability. Do **not** display `Competitive` / `Moderate`
on mobile; they truncate at 8 characters on small screens.
</Note>

### Architecture constraint — client-safe split

`deriveBandsFromRatio()` and all band types live in `lib/listings/market-bands.ts`. This file
has **no Node.js imports** (no Prisma, no `pg`, no `fs`). The component imports from here;
the server route imports from `resolve-market-stats.ts`. This split is required because
Railway's Next.js build fails if any `"use client"` component transitively reaches `pg`
(which pulls `tls` / `net` into the client bundle).

### Probability blurb

The static text under the pills is **not LLM-generated**. It reads directly from a
`PROBABILITY_COPY` lookup keyed to the band slug. Cost: $0. Speed: 0ms.

### Source citation

The bottom of the widget cites the geo page as its data source:

```
"Data from {level} market report · {date}"  ->  /kansas/johnson-county/overland-park#market-trends
```

The `#market-trends` anchor scrolls the geo page to the 8-card Market Trends hero. The
constant `MARKET_TRENDS_ANCHOR` in `resolve-market-stats.ts` holds the fragment string so it
cannot silently drift from the actual section `id`.

## Market Estimate

**Component:** `components/listing/ListingDetail.tsx` (`<MarketEstimateBlock>`)
**Source:** `lib/listings/resolve-market-stats.ts`

The Market Estimate block shows the listing's context within its local market and provides a
"Compare nearby" link to the geo page.

- **Median price** — pulled from the same proximity-ladder result as Offer Insights.
- **Price vs. median** — the listing's list price expressed as `+X%` or `-X%` relative to the
  local median sold price.
- **Compare-nearby deep-link** — links to the geo page at `#market-trends` (same anchor as
  the Offer Insights citation).

Prices are displayed as **full numbers** (`$1,160,000`), never compact (`$1.16M`). Mobile
uses `text-hl-subhead`; desktop `md:text-hl-h2`.

## Tax

**Component:** inline card in `ListingDetail.tsx`
**Source:** `Listing.annualTaxAmount` (Prisma column, adapter `raw.TaxAnnualAmount`)

The Tax card shows the most recently reported annual property tax for the listing.

```
Annual tax   $4,891 / year   (source: MLS — may not reflect current assessment)
```

- Column `annualTaxAmount` is populated by the listing-catalog Inngest function from
  `raw.TaxAnnualAmount` on every sync.
- A backfill event (`listing-catalog-backfill/run`) refreshes all ~15K active listings.
  Coverage rises from near-zero to ~80%+ as the backfill completes.
- Listings with no tax data omit the card entirely (no "N/A" placeholder).

## Schools

**Component:** inline card in `ListingDetail.tsx`
**Source:** stub from listing data (school district field + nearby school lookup)

The Schools card shows the listing's school district and up to three assigned schools:

```
School District   Blue Valley USD 229
Elementary        Wolf Creek Elementary
Middle            Harmony Middle
High              Blue Valley High
```

School data is populated from the `Listing` record's school district field plus a geo-based
school match. Coverage is ~46% at launch, improving to ~80%+ after the listing-catalog
backfill propagates. Listings with no school data omit the card.

## HOA / Community

**Component:** inline card in `ListingDetail.tsx`
**Source:** `hl_geo_neighborhood_stats.amenities` (nightly Inngest job)

The HOA/Community card shows subdivision-level amenities aggregated from active listings in
the same subdivision. Amenities displayed: Pool, Tennis, Clubhouse, Gated, Exercise Room,
Walking Trails (plus any others from the `amenities` JSONB column).

```
Community   Mills Farm  ·  Pool  ·  Tennis  ·  Clubhouse  ·  Gated
```

- **0ms render cost** — data comes from `hl_geo_neighborhood_stats` (nightly batch), not a
  real-time Repliers fetch.
- **Render-time fallback** — if the nightly row is missing, a UNION query builds the amenity
  set on-demand from active `Listing` records in the same subdivision.
- HOA fee, if available, is shown from `Listing.associationFee` + `associationFeeFrequency`
  (adapter: `raw.AssociationFeeFrequency` normalizes the display string).

The nightly job is `lib/inngest/functions/geo-neighborhood-stats.ts`. Its runs are visible
in the CRM Run Log under the "Geo / SEO" category.

## FAQ, Similar Listings & the geo tail (shipped 2026-09-08)

Every listing now carries a stored FAQ, rendered as an accordion below the Tax/Schools/HOA cards,
followed by a run of related content before the page's closing "what's your home worth" and Myli
sections. Live order (both mobile and desktop trees): photos/sticky bar → features/HOA/schools/tax →
[mortgage calculator slot] → **FAQ** → **Similar Listings** → **city paragraph** → **geo directory +
popular searches** → "what's your home worth" → HouseLoop value + Offer Insights → Myli's bar
(trimmed, no pill row) → sources.

- **The FAQ is composed once and stored, never generated at request time.** `Listing.faq` (jsonb) +
  `faqSource` + `faqGeneratedAt` hold up to 13 question/answer pairs, written by
  `lib/seo/listing-faq.ts` — a pure, deterministic function (no LLM, $0) that reuses the page's own
  readers (tour slots, tourability, status). A question with no underlying data (no HOA fee, no tax
  figure, an implausible list date) is **omitted**, never guessed or padded.
- **Every answer follows one standard** (ruling #257.317, the desk's read of a competitor's FAQ depth):
  two short paragraphs, 45-90 words — paragraph one states the listing's own numbers plus the market
  number beside them (median $/sqft in the zip, sell-to-list %, days to offer) where we have it;
  paragraph two says what the number means for this buyer and names the one control to use next
  ("Tap Request a tour", "Ask Myli", "Tap Talk to a lender"). A sold price is never named (Heartland
  MLS rule §12.3(b) — a "still for sale, now sold" answer states only the sale date). Attribution
  ("Listing data: Heartland MLS, distributed by MLS GRID… Market numbers: HouseLoop analysis…") rides
  once under the whole FAQ, not per answer.
- **The refresh runs on Inngest** (`lib/inngest/functions/listing-faq-refresh.ts`, registered in
  `app/api/inngest/route.ts`): a nightly cron (dry-run by default, priority order
  active → pending → coming_soon → sold → off_market, never-generated-first) and a real-write path
  that fires on the `houseloop/listing.catalog` event so a newly synced listing gets its FAQ the same
  night. A manual `houseloop/listing-faq.refresh` event exists for a targeted dry-run-then-apply. As
  of the 2026-09-08 build, 0 of 17,006 active/pending listings were missing an FAQ.
- **`FAQPage` JSON-LD** is emitted once per page (in `HomeDetailView.tsx`, not inside
  `ListingDetail`, which renders twice in the DOM for the mobile/desktop trees).
- **Similar Listings** (`components/listing/SimilarListings.tsx`) reuses `ListingRow` — the site's
  one horizontal card component (`HOME_RENDER_LAW`), never a bespoke card.
- **The city paragraph** (`components/listing/CityParagraph.tsx`) and the **geo directory + popular
  searches** tail read the same nightly-cached `hl_geo_market_stats` table the geo landing pages
  already use — no new queries.
- **Not built in this pass:** the on-page mortgage calculator and lender modal for mobile/desktop —
  a marked slot sits between the Tax card and the FAQ for that work; a per-listing city-average
  $/sqft comparison clause in the FAQ is wired to accept the data but nothing computes it yet.

Related: [Home Page](/legacy/website/home-page) (the FAQ engine's sibling SEO work — sitemap +
structured data) · [The Myli OS](/guides/myli-os) (the listing-page Myli bar and its chat tools).

## The right rail, the one word, the activity row and the two timestamps (shipped 2026-09-08)

Zach ruling #257.344 and its amendment #257.344a, from his own screenshots of the live page.

### The right rail's order is the lock's order

The rail on desktop reads, top to bottom: **Request a tour** (with the coming-soon sentence above it
and the "as early as ..." line inside it) → **Ask a question** → mortgage calculator → the "Already
own a home?" /sell card → Offer Insights → HouseLoop Value. Two signed wireframes draw this and they
agree: the 2026-08-27 engagement lock states "the rail holds the tour CTA and Offer Insights only —
as drawn", and the 2026-09-08 website wireframe states the stack "under Request a tour / Ask a
question".

A desk ruling on 2026-09-04 had moved the tour button out of the rail because three tour controls
were visible in one fold. That is **superseded** for the desktop rail by #257.344; the concern it
raised is honoured a different way, by there being exactly **one tour button per width** — the
rail's on desktop, the sticky bar's on the phone. Both read the same `comingSoonBandCopy`,
`tourTimeCopy` and `isTourable` values, so the two widths cannot drift apart.

### One action, one word, one control per width, and it opens Myli

Exactly one "Ask a question" control renders per width — the right rail's button on desktop, the
sticky bar's on the phone. The desktop LEFT COLUMN used to carry a second "Ask a question" button
(under `ListingTourBooker`, duplicating the rail's); it is deleted (ruling on #257.344's residuals,
2026-09-08). Every one of the three call sites in source (the rail + the phone's two status
branches) opens **Myli**, never the lead-capture form (`#257.337c`/`#257.346`) — the divergence the
previous pass left open ("on desktop the button still opens the form") is now closed.

The sentence Myli hears is composed **once**, in `ListingDetail.tsx`, and reused at all three call
sites: `Hey Myli, I have a question about <street>, <city>, <state>`. Before this pass, `askMyli()`'s
first argument — passed through verbatim as the buyer's opening bubble — was the literal button
label `"Ask a question"`, which is a label, not a sentence a buyer would ever type.

`ContactAgentModal` stays imported and mounted (nothing sets its open state any more) — retired BY
CALL SITE, never deleted, because the form re-enters later as a pill Myli offers. The file and prop
names still say `ContactAgentModal`, which no user reads.

The ratchet's arms G1-G4 (`listing-detail.test.ts`) hold this shape: exactly three "Ask a question"
strings in source, zero calls to `setContactModalOpen(true)`, the composed-sentence const present at
every call site, and the modal still mounted.

### The HouseLoop user activity row

The crowd line — views, saves, likes, shares — renders on the detail page again, in both trees,
directly under the price/beds/baths/sqft headline and above the description. It is the **same
component the house cards render** (`components/listing/HouseLoopUserActivity.tsx`), fed the same
single `listing.engagement` object; it is read-only and nothing in it is tappable.

It had been missing since 2026-09-07, when a cut list naming "the pill row under Myli's bar — What
should I offer, What's the payment, HouseLoop user activity" was read as one block and the row was
removed along with Myli's bar and her pills. The row is its own read-only section in the lock, not
part of her pill row.

### Two timestamps, two facts, two sources

The attribution block at the foot of the page carries both, and never conflates them:

| Line | Source | Shape |
|---|---|---|
| **HouseLoop last checked** | the last successful `listing-cache-sync` Inngest run | relative, ticking on the client |
| **Listing updated** | `Listing.mlsUpdatedAt`, the MLS modification clock | absolute, Central |

**"HouseLoop last checked" deliberately does not read `Listing.cachedAt`,** the column that looks
like this fact. Two measured reasons, both recorded in `lib/listings/last-checked.ts`. First, the
only cron that writes it is a delta sync that upserts only listings that actually changed, so on a
home polled hourly that has not moved in three weeks it would read "3 weeks ago". Second, the page's
own read path writes it after a TTL-lapsed refresh, which makes it a page-render time — the one
thing #257.344a bans by name. The line the page shipped before this change was that banned line.

The honest source is the sync's watermark row in `hl_app_config`, and specifically **the row's
`updatedAt`, not its stored value**: the sync deliberately stores the watermark as its run start
minus a ten-minute overlap so the next scan re-reads a few already-seen minutes. Measured on the
live web database on 2026-09-08, the row's `updatedAt` was 41.4 minutes old while its value was
51.4 minutes old — exactly that offset. The offset is right for scanning and wrong for reporting.

A missing row or a read error renders **nothing**. There is no fallback and no "just now".

### The page's one heading is visible

The `<h1>` is the address, and it is the phone peek's own visible address line rather than a
screen-reader-only element. The bottom sheet renders its peek before its children, so the heading is
still the first in the document and the SEO cage's heading-order rule still passes. At desktop
widths that heading belongs to the phone rendition and the breakpoint hides it; it says exactly what
the visible desktop address says. A heading visible at both widths would mean moving the address out
of two locked layouts, which the desk declined.

### The sold rendition — no close price anywhere, ever (#257.348f)

Kansas and Missouri are non-disclosure states, and Heartland §12.3(b) forbids publishing a
per-address close price. The sold rendition is built entirely on facts that are **not** the price:

- **Title / description say sold and when.** `listingPageTitle()` (`lib/listings/format-address.ts`)
  titles a genuinely closed listing with a recorded sale date `"<addr>, <city>, <state> <zip> —
  Sold <M/D/YY> | HouseLoop"` — a compact numeric date, deliberately not the site's usual verbose
  format, so it survives the existing 60-character ladder. A sold row with no recorded close date,
  and every off-market/withdrawn row, keeps the pre-existing "Property History" fallback. The page's
  `generateMetadata` builds a matching description naming the sale date, never a price.
- **RealEstateListing JSON-LD drops the price, carries the date.** For a closed listing, the
  `offers` block omits `price` entirely (the last ASKING price is a stale number a crawler could
  read as "what it sold for") and reads `availability: OutOfStock` +
  `validThrough: <soldDate>` — schema.org's own "the offer ceased to be valid on this date," the
  closest standard field to "when it sold."
- **The FAQ's status answer** (`lib/seo/listing-faq.ts`, item 13's `closed` case) states the sale
  date, then folds in two facts that are not the price: **days list-to-contract** (computed from a
  REAL `pendingDate` only — omitted, never guessed, when the row carries none) and the
  **neighborhood's recent-sales context** (`stats.soldCount12mo` / `stats.scopeLabel` — an area
  aggregate, never this home's own close number).
- **Two questions retired for a sold home.** "Can I negotiate the asking price" and "How long has
  it been on the market … N days and counting as of today" both used to fire for `status ===
  "closed"`, which reads as nonsense beside the same page's "sold and no longer available." Both
  now skip entirely once a home is sold ("What is a good offer" is gated the same way).
- **The team line is a named gap, not built.** `lib/seo/team-record.ts` exports only PLACE-level
  facts (`teamPlaceFacts`, `soldByPlace`, `recentTeamSales`) — nothing that answers "did the team
  represent a side on THIS home." Matching this listing's own MLS number against
  `recentTeamSales()`'s recent-N list would risk a false negative on any team sale outside that
  window, which is not a risk worth taking on a compliance-adjacent claim. Flagged, not guessed.
- **FAQ coverage is by design, not a backfill target.** 311 of 347,014 sold rows carry a generated
  FAQ (0.09%) against 100% of active/pending/coming_soon — the refresh job's own declared priority
  order (`lib/inngest/functions/listing-faq-refresh.ts`). The road is on-demand generation for the
  specific sold HLIDs the team's latest-sales block links to, via the existing
  `houseloop/listing-faq.refresh` event's `hlid` parameter — never a 347k sweep.

<Note>
  **A stored FAQ does not regenerate itself when a listing's status changes.** The FAQ shown on a
  page is whatever `Listing.faq` held at last write — a listing generated while ACTIVE and later
  sold will keep saying "is active" until it is regenerated (`houseloop/listing-faq.refresh`,
  `{dryRun:false, hlid:"..."}`). The composer's `closed`-branch logic above is correct and tested;
  seeing it on a specific address requires that address's FAQ to have been (re)written after it sold.
</Note>

<Note>
  **The SEO page-structure cage's census does not yet declare a sold-state row.** Measured directly
  against the cage's own `evaluate()`: the probe sold URL passes every rule except `LINK_TAIL` — its
  geo tail carries 6 crawlable links against the declared minimum of 12, a pre-existing thin-market
  gap in `GeoSearchTail.tsx`, unrelated to this build. Adding the row requires bumping the shared,
  shrink-only `listing` floor from 0 to 1 in `tools/seo/page-structure.floor` — a call left to the
  desk given the floor gates every lane's push. The ready-to-apply census entry is in
  `.claude/reports/grinder/website-home-rows/RECEIPT-listing-detail-2026-09-08.md` Part 6.

## KCRAR is retired

The legacy `hl_market_snapshot` table (KCRAR data) is **no longer read** on the listing
detail page. All market context comes from `hl_geo_market_stats` (daily) and
`hl_geo_neighborhood_stats` (nightly). `hl_market_snapshot` remains in the DB for sold
archive purposes but the listing page never queries it.

<Warning>
Do **not** add `hl_market_snapshot` reads back to `ListingDetail.tsx` or
`resolve-market-stats.ts`. If you need historical sold comps, read from `ListingHistory`
(the Repliers backfill) instead.
</Warning>
