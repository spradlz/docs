Every SEO surface — `/listings`, every county / city / zip / neighborhood page — renders the
**same** React component. There is no per-page template to drift. This page explains how that
works and how to add a new SEO page.

## One shared page

`components/listings/SearchResultsPage.tsx` is the single listings UI. Geo routes are thin
shells that resolve the URL params, then hand off:

```tsx
// app/[state]/[county]/[city]/page.tsx  (county, zip, neighborhood are identical shape)
export const dynamic = "force-dynamic";
export async function generateStaticParams() { return allCityParams(); }

export default async function CityPage({ params }) {
  const { st, co, ci } = resolveGeo(params);
  const qp = new URLSearchParams({ city: ci.name, state: st.abbr });
  return <SearchResultsPage sp={qp} geo={{ basePath: `/${st.slug}/${co.slug}/${ci.slug}` }} />;
}
```

The shell only does three things: resolve the slug to a real place, build the search params,
and pass a `basePath`. All header, results, map, and SEO rendering live in the shared page.

## The dynamic SEO block

Inside `SearchResultsPage`, the SEO section is **resolved from the URL on every surface** — so
`/listings?city=Fairway` gets the exact same breadcrumb + sections as `/kansas/johnson-county/fairway`.

```
resolveLocation(searchParams)   →  lib/geo/resolve-location.ts
   ↓  ResolvedLocation { level: state|county|city|zip|neighborhood, ... }
<LocationSeo location={resolved} />   →  components/geo/LocationSeo.tsx
   ↓ renders: breadcrumb → amenity → property type → popular searches
     → nearby cities ($) → neighborhoods ($) → zips ($) → estimate proceeds → price bands
```

- `resolveLocation` reads `city / county / zip / state / neighborhood` off the params and
  resolves them against the geo taxonomy. It returns `null` for a bare metro search, so we
  render just the directory — never a false city SEO block.
- `locationH1()` produces the server-rendered `"{Place}, {ST} Real Estate & Homes For Sale"`.
- Neighborhood dollar figures come from `getNeighborhoodValues(city, state)`
  (`lib/geo/neighborhood-stats.ts`), backed by the nightly job — see
  [SEO background jobs](/guides/seo-background-jobs).

## Rendering strategy

Geo pages are `export const dynamic = "force-dynamic"` — server-rendered on every request, so
they always reflect live inventory and live counts. `generateStaticParams` enumerates the full
taxonomy so the route set is known and the sitemap is complete. (Roadmap: flip to ISR
`revalidate` once crawl budget justifies it — see the overview's roadmap.)

## Sitemap

`app/sitemap.ts` emits a chunked sitemap via `generateSitemaps()`:

- **Chunk 0** — static pages + market-data + the whole geo tree (county → city → zip →
  neighborhood) + active listings.
- **Chunks 1..N** — remaining listing URLs (50K-URL cap per file).

The geo + neighborhood URLs are generated by walking the same taxonomy the routes use, so the
sitemap can never list a page the routes can't serve (or vice-versa).

### `lastmod` is a real data-change clock (shipped 2026-09-08)

Every entry used to emit `lastModified: new Date()` — the render clock, so 5,879 geo/static/
collection URLs shared one identical timestamp on every fetch, telling Google nothing had ever
changed. Listings and the sold archive already read their own real `updatedAt`/`soldDate` columns
(unchanged). Geo pages (county/city/zip/neighborhood) now read the newer of the geo's newest
`Listing.updatedAt` or its stats-row `updatedAt`, computed once per sitemap chunk in a batch of
grouped-aggregate queries — never one query per page. A geo with neither signal, or a static/
collection page that isn't a row in any table, omits `lastModified` entirely rather than inventing
one. `changeFrequency`/`priority` were removed from every entry — Google documents that it ignores
both, and this sitemap carried 22,200 of each doing nothing. Measured after the fix: two live
fetches 65 seconds apart returned 20,020 of 22,202 URLs with a distinct timestamp, and 99.7% of
neighborhood URLs were byte-identical between the two fetches (the handful that moved matched a
real MLS write landing in that window).

## The geo taxonomy

The directory tree is one generated file:

- `lib/geo/heartland-geo.generated.json` — `STATES → counties → cities → { subdivisions, zips }`,
  each node carrying `avgValue` (avg **active** list price) + counts.
- Read through `lib/geo/geo.ts` (`STATES`, `findCityByName`, `geoSlug`, `findSubdivisionByName`).
- Rebuilt by `scripts/build-geo-taxonomy.ts`. `geoSlug()` is the canonical slug function — any
  code that derives a neighborhood/city slug must use it so URLs match the taxonomy.

## How to create a new SEO page

Because everything is data-driven, you rarely write a new route:

1. **New place (city / zip / neighborhood)** — it appears automatically once it's in the geo
   taxonomy. Re-run `scripts/build-geo-taxonomy.ts` to regenerate `heartland-geo.generated.json`;
   the route and its sitemap entry come for free.
2. **New SEO section** (e.g. "Homes with a Pool near {city}") — add it to
   `components/geo/LocationSeo.tsx` with its icon. It then renders on every surface at once.
3. **New page *type*** (a genuinely new route, e.g. facet pages) — add a thin shell under
   `app/.../page.tsx` that resolves params and renders `<SearchResultsPage>`, add its URLs to
   `app/sitemap.ts`, and confirm `LocationSeo` handles the new level. Never fork the results UI.

<Note>
After any `houseloop-web` deploy that changes routes or the sitemap, the change is live on the
next request — no extra step. Only **Inngest function** changes need the re-register step (see
[SEO background jobs](/guides/seo-background-jobs#operating-the-job)).
</Note>


## Market Trends hero on every variant (2026-05-29)

Every geo page — county, city, zip, neighborhood, **and every property-type / status / facet
variant** (Single Family, Townhouse, Condo, Open Houses, Coming Soon, etc.) — renders the same
8-card Market Trends hero (county/city/zip from `hl_geo_market_stats`; **neighborhood tiers have NO rows there by design** — their heroes render from the live profile / `hl_geo_page` artifact):

```
Homes for sale · Median sale price · Sold (last 12 mo) · Sale $/sqft
Sell-to-list   · Days to offer     · Coming soon       · Under contract
```

The hero anchors at `<section id="market-trends">` in `components/geo/GeoSeoContent.tsx`.

### Don't strip liveReport on facet pages

There was a long-standing bug at `components/geo/LocationSeo.tsx` line 157:

```ts
if (facet) liveReport = null;  // ❌ NEVER do this
```

That truncated every facet/variant page (Single Family, Open Houses, Coming Soon, etc.) to a
4-card stub and dropped the median sold / sell-to-list / days-to-offer block — even though the
data was already populated in `hl_geo_market_stats`. **The fix is to always render `liveReport`
when it exists.** Facet-scoped active counts still flow through `getEnvelopeStats(query)` for
the cards below the hero; the city baseline shows above. Headline copy still includes the facet
("Overland Park, KS Single Family Residence Homes Market Trends") so the variant context is
preserved visually.

### Heartland §15 compliance — aggregate sold IS permitted

The footer disclaimer must say:

> *Aggregate market statistics from Heartland MLS · as of {date} · per-address sold prices
> excluded per Heartland §12.3(b).*

Do **not** render legacy phrasing like "sale prices are not displayed, per Heartland MLS rules"
as a blanket guard — that was wrong copy. Heartland §15 explicitly permits aggregate sold
display at neighborhood / zip / city / county / property-type level. Only **per-address** sold
price is restricted, and that's only relevant to `app/home/[slug]/page.tsx` (the per-house
detail).

### Citation deep-links from listing detail

The listing detail page's Offer Insights + Market Estimate widgets cite their source with a
deep-link to the geo SEO page. All source URLs append `#market-trends` so the click scrolls
straight to the 8-card hero instead of dumping the user at the top:

```
/kansas/johnson-county/overland-park#market-trends                   ← city scope
/kansas/johnson-county/overland-park/n/mills-farm#market-trends      ← neighborhood scope
/missouri/jackson-county/blue-springs/64015#market-trends            ← zip scope
/missouri/jackson-county#market-trends                               ← county scope
```

The constant lives in `lib/listings/resolve-market-stats.ts` (`MARKET_TRENDS_ANCHOR`). The
section has `scroll-mt-32` so the heading is visible below the sticky header.

## The geo page body and the data bank (shipped 2026-09-08)

Ruling #257.342 added a **data bank** to the bottom of every non-listing collection page: an overview
paragraph, the counted facet bank, the listing-overview tiles, and the feed's own Last Updated stamp.
It renders on the city, county and zip pages through `components/geo/GeoPageBody/`, mounted by one
line inside `LocationSeo` — which is already the shell's single geo block, so no route and no shared
shell file changed.

### One read, one predicate

`lib/geo/facet-bank.ts` is the whole data layer. It runs **two scans**, not one per module: a single
row of `count(*) FILTER (…)` expressions unpivoted with `jsonb_each`, plus one `VALUES`-driven
`LATERAL` covering every JSON feature column at once. The first build wrote one `UNION ALL` arm per
value and cost 1,055 ms warm for Overland Park; the two-scan shape costs 279 ms cold and 56-70 ms
warm. **The arm count, not the row count, was the bill.** No per-place stats table was created.

The bank counts the same set the grid above it shows, reproducing all six clamps `searchFromDb`
applies — `deletedAt IS NULL`, `quarantinedAt IS NULL`, `status IN (active, coming_soon)`,
`photoCount >= 1 OR coming_soon`, `propertyType IN CONSUMER_PROPERTY_TYPES`, and
`(county,state) IN CORE_HEARTLAND_COUNTIES` — drawing the two list-shaped ones from the same
constants that file imports. Measured against prod: Overland Park 457, Johnson County 1,905,
66213 32, each equal to the page's own rendered count.

### What each module reads

| module | source | linkable? |
|---|---|---|
| Construction dates | `yearBuilt` | yes — `minYearBuilt` / `maxYearBuilt` |
| Square footage | `sqftAboveGrade` | yes — `minSqft` / `maxSqft` |
| Lot sizes | `lotSizeAcres` | yes — `minAcres` / `maxAcres` |
| Stories | `hasSingleStory` | single story only — `story=1` |
| HOA fees | `hasHoa`, `hoaMonthly` | yes — `maxHoa` (ceilings, since there is no `minHoa`) |
| Bedrooms | `bedrooms` | yes — `minBeds` / `maxBeds` |
| Bathrooms | `bathroomsFull` | yes — `minBaths`, cumulative (gte-only) |
| Garage | `garageSpaces` | yes — `minGarage`, cumulative |
| Pool, waterfront, 55+ | `hasPool`, `hasWaterfront`, `isSeniorCommunity` | yes — `pool=1`, `wf=1`, `senior=1` |
| Flooring, Basement, Community features, Patio, Parking, Interior, Lot features, Rooms, Security, Water source, Sewer | the matching JSON feature array | **no** — counted text |

**Square footage groups `sqftAboveGrade`, not `sqftTotal`,** because that is the column the search
filters. Grouping the other one would have shipped a chip whose count no page could ever show.

**The feature arrays carry no links, deliberately.** `?feature=finished_basement` is a vision-tag
predicate, not the MLS `basementFeatures` array the module groups. They are different facts sharing a
word, so linking them would put a wrong number under a right-looking chip.

**Roof, view, furnishing and ADA do not render.** They are not columns, and probing all four feature
arrays across Overland Park's whole active set returned zero rows. A module lights up on its own the
day the feed carries it.

### The rules that keep the numbers honest

- A value describing fewer than three homes is omitted; a module whose every value is omitted does not
  render. Verified with a real control: Lake Quivira (5 homes) drops the pool/waterfront/55+ module
  entirely while Overland Park renders it.
- Every linked value's SQL predicate is the literal twin of the URL params in its `href`
  (`>= lo AND <= hi` on both sides). Eight sampled links were probed against the page they open and
  all eight counts matched exactly.
- `lotFeatures` is keyed `lotfeat`, never `lot`. Heartland's feature array carries the literal strings
  `"1/4 to 1/2 acre"` — the same labels the scalar lot-size buckets use — so a shared key silently
  overwrote the typed column's counts with the array's. It passed the link probe anyway, because the
  two agree in Overland Park today.

### The sixteen FAQs

`lib/geo/geo-faq-16.ts` builds up to sixteen questions from the page's own live count, its market
report, and the bank. They are handed to the existing FAQ block in `GeoSeoContent` — never rendered as
a second section, because two FAQ sections would put two `FAQPage` JSON-LD scripts on one URL.

Eighteen questions are written and the first sixteen that have their numbers are kept: a question whose
number the feed does not carry for this place is dropped rather than padded, so a thin zip honestly
renders fewer.

**These sixteen are exempt from `reconcileSegments`.** That reconciler re-seats any homes-count-shaped
number onto the page's one live count, because every other prose road carries a number that was true
when it was written. These are computed at render, and half of them state a legitimate subset — run
through the reconciler, "117 homes were built in 2020 or later" became "457", and "242 homes have a
three-car garage" became "457". A source that owns no frozen number needs no reconciliation.

### Last Updated

The stamp under the bank is `max(mlsUpdatedAt)` **for that place**, printed in Central. The site-wide
compliance footer answers "when did we last hear from the feed at all"; this answers "when did anything
in this city last change", which is the only version of the question a per-place page can answer.
