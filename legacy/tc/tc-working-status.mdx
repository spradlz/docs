## 📌 Summary — what is true today

**TC Working Status is what the COORDINATOR is doing** with a file — not where the deal stands. Four
rows: **Processing · Paused / Blocked · Waiting for Closing · Complete.**

⚠ **This surface was called "Transaction Status" until 2026-08-05**, while delivering the coordinator's
workload. The status that actually describes the deal is
**[Transaction Status](/tc/transaction-status)**. The two wore each other's names for months; Zach:
*"the loop status is really the transaction status."*

**It is a STATUS, not a stage — and one row proves it.** You do not pass *through* **Paused / Blocked**
on the way to Waiting for Closing: you get blocked, sit, get unblocked, and go **back** to Processing.
Round trips make it a status. Stages do not do round trips, which is why "Buyer Agreement Signed →
Attempted Contact" never happens on the buyer pipeline. So **"stage" stays reserved** for the
buyer/seller pipeline (`hl_stages`, 55 rows) that renders as the stepper under the loop band — and for
`hl_tc_stage`, dropped 2026-08-04 for exactly this class of confusion.

| | |
|---|---|
| Vocabulary | `hl_tc_working_status` — `id` · `name` · `color` · `icon` · `position` · `is_active` · `transaction_status_advance_to_key` |
| Stored value | `hl_transactions.working_status_id` FKs to `id` |
| Automation | `transaction_status_advance_to_key` — when set, changing the working status also moves the **transaction** status, visibly, and logs it |

<Warning>
**⚠ This table is id-PK / `name` / `position`, while the rest of the TC estate is key-PK / `label` /
`sort_order`.** So "transaction status" is key-based and "working status" is id-based, and a reader has
to remember which is which from the name alone — a smaller version of the confusion the 0632 rename
just fixed. **Recorded on the freeze exception list, dated, not yet fixed**: moving it to the key
convention is its own change and was deliberately kept out of 0632's scope.
</Warning>

### 2026-08-05 · benji
**Renamed FROM `hl_tc_transaction_status` in migration 0632** — step 1 of the swap, the step that frees
the name for the vocabulary that actually describes a deal. Four rows, unchanged. The page label moved
from "Transaction Status" to "TC Working Status"; the route path `/tc/configure/status` is unchanged.

**Found — the two statuses were labelled backwards on the loop band.** "Transaction Status" showed the
coordinator's workload and "Loop Status" showed where the deal stood. Both now say what they are.

**Found — a guard checked one field and rendered another.** `LoopDetailModal` and `MilestoneBand` both
guarded on the *deal's* status and then rendered the *working* status pill, so a loop with a deal status
but no coordinator status would pass the guard and hand the pill a null. It was first silenced with a
non-null assertion; the compiler was right and the assertion was me telling it to stop talking. Both now
guard the field they render.

**Verdict:** pass.
