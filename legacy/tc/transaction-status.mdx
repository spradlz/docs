## 📌 Summary — what is true today

**Transaction Status is where the DEAL stands**: Pre-Listing · Pre-Contract · Under Contract · Closed ·
Contract Fell Through · Listing Not Won · Listing Expired · Listing Cancelled · Offer Not Accepted ·
Buyer Cancelled. Ten rows, one stored column, and every legal value is a row on this page.

⚠ **This surface was called "Loop Status" until 2026-08-05.** Zach: *"the loop status is really the
transaction status."* The table it reads was renamed in the same pass — see the run log below. If you
find `loop_status` anywhere in code or docs, it is stale.

**It is not the same as [TC Working Status](/tc/tc-working-status)**, which is what the *coordinator*
is doing (Processing · Paused / Blocked · Waiting for Closing · Complete). Those two wore each other's
names for months and that is the confusion this rename ended.

| | |
|---|---|
| Vocabulary | `hl_tc_transaction_status` — `key` · `label` · `color` · `icon` · `sort_order` · `is_active` · `is_terminal` · `section_key` |
| Sections | `hl_tc_transaction_status_section` — the group bands (Active · Closed · Archived), flat since 0622 |
| Stored value | `hl_transactions.transaction_status_key` FKs to `key` |
| API | `/api/tc/loop-statuses` (route path not yet renamed — tracked) |

**What the page does:** add, rename, recolour, reorder and section statuses through the same shared
builder as every other TC config surface. The LOOPS column counts live transactions on each status, and
the delete guard refuses to remove one while transactions still point at it. `is_terminal` marks the
statuses that end a transaction's life.

## 📋 Run log

### 2026-08-05 · benji
**THE GREAT RENAME — the status confusion ends.** Zach ruled it: *"the loop status is really the
transaction status."* Two tables had been wearing each other's names since the TC estate was built.
Migration **0632** swapped them in one transaction:

```
hl_tc_transaction_status  →  hl_tc_working_status       (4 rows — what the TC is doing)
hl_tc_loop_status         →  hl_tc_transaction_status   (10 rows — where the DEAL stands)
hl_tc_loop_status_section →  hl_tc_transaction_status_section
```

**Found — it is a SWAP, not two renames, and the order is load-bearing.** `loop_status` had to *become*
a name the other table still held. Step 1 frees it, step 2 takes it, one migration one transaction — so
there is never a moment where two tables claim one meaning. There was also a cross-FK: the table renamed
in step 1 held a key *into* the table renamed in step 2.

**Found — the blanket rename MERGED TWO SIGNED ACTIVITY KINDS.** `loop_status_changed` and
`transaction_status_changed` are distinct catalog rows; the mechanical pass rewrote the first into the
second across three live activity writers and the Deals feed filter. On prod that logs every status
change under the wrong kind — no error, the row writes fine, and it only surfaces weeks later as a
history that is quietly wrong. Caught by the push cage, which blocked on a regenerate: the rename had
hand-edited a *generated* file, and regenerating it from the catalog exposed the collapse. All four
sites restored.

**Found — the typecheck cannot see a broken route.** The sidebar's route *string* was renamed but the
route *folder* was not, so "Loop Status" pointed at a 404 in a commit whose message said "tsc exit 0". A
route string is a string; the folder is a filesystem fact, and nothing checks between them. Caught by
resolving all five sidebar routes against the filesystem.

**Verdict:** pass. 0632 applied and ledgered; 10 rows in transaction status, 4 in working status;
`hl_transactions.milestone` and `.transaction_type` deliberately untouched (the seller-engine ledger
reads both).

### 2026-08-05 · benji
**THE LOOP BAND BECOMES NINE EDIT CARDS.** Zach: *"Why are we making these drop-down pills anyway?…
you just click on it and you edit it… everything's equal across the top."*

**Found — shape was communicating string length, not meaning.** The band had four pill dropdowns beside
five value cards, on the theory that *pills are controls, cards are readings*. But each pill was
`inline-flex` and sized to its own **text**, so "Sale" rendered as a stub beside "Listing Not Won". One
card shape with one affordance says the true thing: every field is editable and equally important.

**Found — the row had the space, it was distributed wrong.** Nine *equal* columns forced the long
values to wrap while the price and date cards sat half empty. `repeat(4, 1.3fr) repeat(5, 1fr)` gives
the long text its room. Verified by measuring every label and value against its own card's inner width
in a real browser: **9 cards, zero overflowing, all identical height, no scroll.**

**Found — "Transaction Coordinator" does not fit**, by measurement rather than opinion: 142px needed
against 125px available, with every other label sitting exactly at its limit and nothing to borrow.
`TC Coordinator` instead.

**Verdict:** pass.

### 2026-08-04 · benji
**Loop Status became a stored column with its own config page.** Until mig 0599 it was **derived** by a
45-line read-time precedence ladder — you could not *set* a status, only cause one. Zach: *"i dont need
those weird derived stuff, it should just be a simple drop down."* Mig **0620** cut the vocabulary
(`listing_withdrawn` → `listing_cancelled`, `fell_through` → `contract_fell_through`, deleted
`terminated` and `lost`); **0621** added sections; **0622** flattened them per his filter argument —
*"show me all active loops or all closed loops, versus sorting through 15 different archive sections."*

**Found — `listing_cancelled` already existed** in `hl_tc_stage`, the dead parallel vocabulary. The word
Zach asked for was sitting in a table nobody read. That table was dropped 2026-08-04.

**Verdict:** pass.
