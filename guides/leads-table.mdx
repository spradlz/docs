### The sort key — inbound or website, never our own outbound

```
last_touch_at = GREATEST(created_at, last INBOUND conversation, last website activity)
```

Zach: *"it reorders by what comes first, either last communication **inbound from the lead**, or last website
activity."* **Inbound-only is the point** — if our own outbound counted, every message you send would re-sort
your own table, and the order would stop meaning *"who needs me"* and start meaning *"who did I last talk at."*

A new registration floats to the top on its own, because **the registration IS the newest touch** — no pinning
special-case fighting the sort forever.

## Filtering & smart filters

The table has **one filter engine, and it is SQL.** Filtering never happens in the
browser. Every filter — a smart-filter tab, the Advanced Search builder, the
quick "All Statuses / All Agents" dropdowns — resolves to the SAME
`FilterCondition[]`, is written to the **URL**, and is applied by
`buildLeadsQuery` / `buildLeadsCountQuery` in `lib/leads-query.ts`. Because one
engine computes both the visible rows and the smart-filter tab badge, the two can
never disagree.

<Note>
Before 2026-07-24 there were **two** engines — SQL for the tab badges and a
partial JavaScript re-implementation (`applyFilterConditions`) for the visible
rows. They drifted: the JS side silently did nothing for 12 shipping fields
(every `sig_*`, `has_task`, `followup_*`) because the row payload carries no
column for them, disagreed with SQL on `stage` for leads in both pipelines, and
used 30-day months vs Postgres calendar intervals. Adding a second condition
could make the result set *grow*. The JS engine was deleted; this section
documents the single-engine design that replaced it.
</Note>

### The registry is the one source of truth

Every filterable field is defined once in **`lib/leads/filter-fields.ts`**
(`FILTER_FIELDS`), imported by both the picker UI and `condToSql`. A field has a
`key`, a `label`, a `group`, and its `operators`. Adding a field is two edits in
the same pass — the registry entry **and** its `condToSql` branch — and a test
(`lib/leads/filter-parity.test.ts`) fails the build if they drift apart. That
test is what makes a "field that silently does nothing" impossible to ship.

- **Only built fields are shown.** Fields flagged `comingSoon` stay defined (so the
  intent isn't lost) but are hidden from the picker — `VISIBLE_FILTER_FIELDS` is
  what renders. A field you can pick is a field that actually filters.
- **Conditions AND together.** Multiple conditions narrow the result; adding one
  can only ever *reduce* the count. If a count grows when you add a condition,
  that's a bug upstream (a condition being dropped), not the semantics.
- **Legacy keys are normalized, not rejected.** Old saved filters and bookmarks
  that used the retired keys (`open_task`, `task_due_today`, `text_message`, …)
  are rewritten to the canonical field on read by `normalizeCriteria`, so they
  keep working while `condToSql` keeps exactly one branch per concept.

### Operators

| Field type | Operators |
|---|---|
| **Multiselect** (Stage, Source, Assigned To, Tags) | include · exclude · is empty · is not empty (Tags also: include any / all, exclude any / all) |
| **Boolean** (Has Email, Has Phone, Has Task, Task Due Today, …) | yes · no |
| **Number** (Lead Score, Open Task Count, …) | is greater than · is less than · is empty · is not empty |
| **Date** (Last Communication, Last Text Sent, Created At, …) | was less than · was more than *(N minutes/hours/days/weeks/months/years)* · is empty · is not empty |
| **Signal** (Tour Request, Any Inbound, …) | not replied to · replied to · occurred (ever) · never occurred · occurred in the last N · occurred more than N ago |

A **date** field's "was more than N" matches only leads where it *happened* but
longer ago than N — a never-happened lead is reached with **is empty**, not with
a date operator. A **signal**'s "not replied to" means the most recent occurrence
has no real outbound reply after it (a notification ping never counts).

<Warning>
`stage` names repeat across pipelines — "New Lead" exists in both the Buyer and
Seller pipelines as different rows. The picker qualifies the ambiguous ones
("New Lead · Buyer" / "New Lead · Seller"). SQL matches with `EXISTS` over
`hl_lead_pipeline_memberships`, so a lead in either pipeline's chosen stage
matches — a lead can sit in both pipelines at once.
</Warning>

### The URL contract

| Param | Meaning |
|---|---|
| `?sf=<id>` | A saved smart filter is active; its tab is highlighted. The server applies that filter's stored criteria. |
| `?criteria=<json>` | Ad-hoc / in-progress builder criteria. Takes **precedence** over `?sf=` so an edit previews immediately; `?sf=` stays in the URL to keep the tab lit. |
| `?edit=<id>` | Opens the Advanced Search builder seeded with that filter's criteria **and previews them** (it does not load the whole unfiltered book). |

The builder writes `?criteria=` on a short debounce; the server component re-runs
`buildLeadsQuery` and returns correctly-filtered rows. The client adopts whatever
the server applied, so the URL is the single source of truth and the two never
fight.

### Smart filters

Smart filters are saved `FilterCondition[]` sets stored in `hl_smart_filters`.
- **System filters** (`is_system`) are the built-in queue — All Leads, New Leads,
  Not Contacted, No Task Scheduled, Task Due Today, Task Overdue, No Emails Sent,
  No Texts Sent. **They are fully editable (Zach 2026-07-24):** rename, re-scope,
  update, or delete them the same as your own. The one guardrail — **"All Leads"
  (empty-criteria reset view) can't be deleted**, or the tab bar loses its
  "everything" fallback.
- **Every filter shows Save / Update / Delete.** Open **Advanced Search** on ANY
  active filter — system or user — and all three buttons appear and work:
  **Save as Smart Filter** (saves current criteria as a NEW filter), **Update
  Smart Filter** (overwrites this one), **Delete Smart Filter** (removes it, with a
  confirm). They stay visibly enabled — a greyed-out button reads as a missing one.
- **User filters** are created from **Advanced Search → Save as Smart Filter**, and
  can be updated, duplicated, deleted, and reordered (drag the pills, or use the
  **Edit Smart Filters** screen at `/leads/smart-filters`).
- **The tab bar shows `is_default` filters** plus whichever one is active; the rest
  live on the Edit Smart Filters screen. Each tab's **red badge** is that filter's
  live match count (`/api/smart-filters/counts`, the same SQL that draws the rows).
- **Writes are validated + authenticated.** Every smart-filter route requires a
  session, and `POST`/`PUT` reject criteria the SQL engine can't filter — an
  unknown field can no longer be saved as a filter that silently matches everyone.

### Editing committed criteria in place (2026-07-24)

Criteria that have been added to the Advanced Search builder are **editable in place** — they are
not locked static bands. Each committed row shows a **field dropdown** (▾) and an **operator dropdown** (▾);
clicking either opens an inline picker so you can change the field type or operator without removing and
re-adding the condition. Values update live and the `?criteria=` URL param re-runs the SQL immediately.

The edit-in-place UI sits on top of the same registry (`lib/leads/filter-fields.ts`) as the add-new
flow — changing a field to another type swaps the value control (text → date, multiselect → boolean, etc.)
and clears the stale value so the condition is never partially valid.

### The 500-row window

`buildLeadsQuery` returns at most **500 rows**; `buildLeadsCountQuery` counts the
whole match set. When a filter matches more than 500, the toolbar reads
"500 shown · N match" rather than pretending the page is the whole result.

## Unread alerts (mission control)

The **red icon-chip badge means UNREAD for the current user** — not the total
(the total lives in the label underneath). Unread is computed per-user in the
same aggregation against `hl_notification` (`read_at IS NULL`, scoped to the
session user via the `userP` bind):

| Badge | Event keys | Status |
|---|---|---|
| **Texts** unread | `new_message` | Live |
| **Requests** unread | `tour_request` / `saved_search` / `contact_form` | Live |
| **Calls** unread | — | Pending Gate 5 (Twilio voice ingest) |
| **Emails** unread | — | Pending Gate 5 (inbound-email ingest) |

**Clear-on-open:** opening a lead `POST`s `/api/notifications/lead-badges`
with `category: 'all'`, marking that lead's notifications read so its badges
clear. Calls/Emails light up once inbound call-logging + email ingestion land.

## Clickable metric icons

Every metric chip is a link to that lead's detail with the matching iPad panel
pre-opened: `/leads/[id]?tab=<Tab>` (Calls→Calls, Texts→Texts, Email→Emails,
Requests→Requests, Listings/Visits→Homes, Registered/Agent Action→All). The
page validates `?tab` server-side against the `ActivityTab` union.

## Agent Action — what & who

Agent Action reads the most recent real action against the lead through a
`LATERAL` union over outbound messages, notes, tasks, and appointments. It shows
the verb + relative time + **who** did it. The actor is derived honestly from
`hl_messages.actor_role`, `hl_notes.source`, and `hl_tasks/appointments.created_by`
— so a system/automation action reads "HouseLoop System" and a human action reads
the agent's name. Never fabricated.

## Layout system

- **Icon chips** — every column uses one shared round icon chip sized by the
  `--hl-stat-chip-size` token (the "cannon"), so all icons match and line up.
- **Proportional growth** — `ColumnDef.grow` (fr weight) lets columns expand at
  different rates as the table widens (Agent Action grows far faster than Visits)
  instead of every column growing equally.
- **Full width** — the page opts into `<PageShell wide>` (`.hl-page-inner--wide`)
  to lift the global 1400px content cap so the table fills the browser.
- **Truncation** — every metric value clips with an ellipsis when its column is
  too narrow; no cell can ever bleed into its neighbor.

## Relative time

All relative timestamps use minutes / hours / days only — never "about", never
months or years (a 400-day-old lead reads "400 days ago"). Times are Central.
