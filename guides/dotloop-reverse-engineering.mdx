## 3 · The document line — the unit that matters

**The line is the unit.** Two row types share one grid:

| Column | Folder row | Document row |
|---|---|---|
| **Status label** (left, gray small-caps ~11px) | — | `NOT SUBMITTED` · `OPTIONAL` · `PDF` |
| **Checkbox** | ✓ | ✓ |
| **Name** | 📁 blue icon + **BOLD CAPS** folder name | document name (`#393939`, ~14px) |
| **Right side** | `ADD DOCUMENT` + ⋮ | share-state · people chip · comment icon · ⋮ |

### The share-state and the people chip — this is the whole point

Each document row's right side carries, in order:

- **Share state** — `NOT SHARED` (gray) · `SIGNED` (gray) · **`WAITING ON OTHERS`** (orange `#FF7964`)
- **A people chip** — a person icon with a **superscript count**
- **A comment icon**
- **A kebab**
- **`SHARE`** appears as a link on row hover

Hovering the people chip shows a tooltip naming them:

> **SHARED WITH CHRIS, JOHN, ANA, GINA, AND GINA**

**Measured on ONE listing loop (5711 Highland Ave), the counts differ per document:**

| Document | State | Shared with |
|---|---|---|
| Cancellation Agreement - Listing Contract | SIGNED | 5 |
| PropertyDetails_5711_Highland_Ave… | **NOT SHARED** | 3 |
| Exclusive Right to Sell Contract | SIGNED | 5 |
| Sellers Disclosure and Condition of Property | SIGNED | **4** |
| Lead Based Paint Disclosure Addendum | SIGNED | **4** |
| EXP Wire Fraud Advisory Notice - Seller | SIGNED | 5 |
| ABA Disclosures - Seller | SIGNED | 5 |

<Warning>
**Read that table again — it is the finding.** Same loop, same people list, and the share count is
**5 / 3 / 5 / 4 / 4 / 5 / 5**. Access is a property of the **document**, not of the loop. A loop-wide
"these are the signers on every document" model cannot express this, and ours currently claims exactly that.
</Warning>

Rows with an `OPTIONAL` status and a greyed name are **placeholder slots** — a document the loop expects but
that has not been added yet. They carry only a kebab: no share state, no people chip.

## 4 · Sharing — the two-faced Share modal

Sharing is one modal with a front and a back. Clicking `SHARE` on a document row (or `SHARE` in the open
document's toolbar) opens the **front**.

### Front — the fast path

```
┌─ Share Document ─────────────────────────── ✕ ─┐
│ DOCUMENT                                        │
│ Exclusive Right to Sell Contract                │
│                                                 │
│ WHO HAS ACCESS                                  │
│ Chris Cribb, John Otradovec, Spradling …        │
│                        RESHARE AND MORE OPTIONS │
│                                                 │
│ ADD PEOPLE              + ADD ANOTHER PERSON    │
│ [ADD NAME] [ADD EMAIL] [ROLE ▾] [VIEW ONLY ▾]  │
│                                                 │
│ ☐ ATTACH PDF TO EMAIL              [ DONE ]     │
└─────────────────────────────────────────────────┘
```

- **DOCUMENT** — names the one document being shared. Not the loop.
- **WHO HAS ACCESS** — a flat summary line of current names.
- **ADD PEOPLE** — one row: name · email · **role** · **permission**, plus `+ ADD ANOTHER PERSON`.
- **ATTACH PDF TO EMAIL** — off by default.

### Back — "Reshare and more options"

The modal flips. Same header, a `‹ BACK` link, and now every person is a row you can act on:

```
┌─ Share Document ─────────────────────────── ✕ ─┐
│ ‹ BACK                                          │
│ WHO HAS ACCESS                                  │
│ Spradling Realty Group (Admin), Gina…           │
│                            CAN EDIT IN PRIVATE  │
│ ☐ Chris Cribb (Managing Broker)   CAN SIGN ▾ ✕ │
│      ┌──────────────────────┐                   │
│      │ VIEW ONLY            │                   │
│      │ CAN SIGN         ▓▓▓ │ ← selected        │
│      │ CAN FILL & SIGN      │                   │
│      │ CAN EDIT IN PRIVATE  │                   │
│      └──────────────────────┘                   │
│ ☐ John Otradovec (Seller)         CAN SIGN ▾ ✕ │
│                                                 │
│ ☐ ATTACH PDF TO EMAIL           [ RESHARE ]     │
└─────────────────────────────────────────────────┘
```

**The two controls are independent, and this is the part that matters:**

| Control | Means |
|---|---|
| **Checkbox** | *Do they get emailed on THIS send?* Unchecked = still has access, just not notified now. |
| **Permission dropdown** | *What may they DO with it?* |
| **✕** | Revoke access entirely. |

The owner row (Spradling Realty Group Admin) has **no checkbox and no dropdown** — it is `CAN EDIT IN PRIVATE`
and cannot be removed.

### The permission ladder

| dotloop permission | Meaning | Ours (MVP) |
|---|---|---|
| `VIEW ONLY` | Can open and read | ✅ ship |
| `CAN SIGN` | Can sign the fields assigned to them | ✅ ship |
| `CAN FILL & SIGN` | Can also complete form fields | ⬜ later |
| `CAN EDIT IN PRIVATE` | Full edit, changes invisible until shared | ⬜ later |

<Note>
**MVP is two, not four** (Zach 2026-08-03: *"the minimum viable product is probably view only or can sign"*).
Fill and edit change who may alter a legal document — they are real features, not dropdown entries, and must
not be faked with options that do nothing.
</Note>

## 7 · The gap — measured 2026-08-03

An audit of our own code against the above found four concrete divergences.

### 7a · Our People list is a fixed 4-slot roster

`resolveLoopSigners` (`lib/esign/resolve-sender.ts:187`) returns a **hard-coded 4-element array**:
`buyer_1 · buyer_2 · buyers_broker · designated_agent`.

- The empty **`BUYER 2 — No co-buyer`** row renders whether or not a co-buyer exists
  (`LoopDetailModal.tsx:221`), because the slot always comes back.
- `Add Person` opens pre-set to `buyer_2` (`LoopDetailModal.tsx:154`) and its role picker offers only three
  options (`AddPersonModal.tsx:19-23`).
- **There is no way to add a lender, title rep, inspector, or seller.** `hl_tc_loop_participant.role` is free
  text and *could* hold them, but the participants API hard-rejects anything outside the three override roles.

### 7b · Per-document sharing does not exist

`hl_tc_loop_document` has no recipient column, and there is **no share / access / permission table anywhere**
in the schema. Recipients exist only inside Documenso, reachable via `esign_doc_id`. Locally, a document knows
its status and nothing about who can see it.

### 7c · The send selection is thrown away

`SendForSignatureModal` builds `includeParties` from local React checkbox state at send time and posts it.
Nothing persists it. The only DB write after a send is
`UPDATE hl_tc_loop_document SET status='sent', esign_doc_id=…`.

**Consequence:** the loop can say a document is `sent` but can never say **to whom** — so we cannot build
dotloop's people chip, and we cannot prove after the fact that the broker was not emailed.

### 7d · The footer makes a false promise

> "These are the signers on every document in this loop. \* required before a document can be sent."

There is no per-document concept for this to be true of. It is the sentence that causes the confusion.

## 8 · The target — wireframe

Locked source: `docs/wireframes/loop-people-and-share.html`.

### 8a · People card

**People = everyone associated with the loop.** Not "signers". Signing and editing are per-document
permissions, so the `Signs` label leaves this panel entirely.

```
┌ People · on this loop                    [+ Add Person] ┐
│ (T) BUYER *          Timothy R Wilkinson    Edit Remove │
│ (C) BUYER'S BROKER   Chris Cribb            Edit Remove │
│ (A) DESIGNATED AGENT * Ana Spradling        Edit Remove │
│ (L) LENDER           Dana Reed              Edit Remove │
│                                                          │
│ People on this loop. Who receives a document is chosen   │
│ per document, on that document's Share.                  │
└──────────────────────────────────────────────────────────┘
```

- **No `BUYER 2 — No co-buyer` slot.** A co-buyer is just another person you add.
- **Any role** — buyer, co-buyer, seller, lender, title, inspector, other.
- **Adding someone on a document adds them here too** (Zach 2026-08-03). One address book per loop.

### 8b · Document row — dotloop's line, our tokens

```
STATUS      DOCUMENT                          SHARE-STATE   PEOPLE      ⋮
draft       Exclusive Buyer Agency Contract   Not shared      —      Share ⋮
sent        Single Property Buyer-Broker      Waiting on 2   👤3     Share ⋮
```

Hovering the people chip lists the names, exactly as dotloop does.

### 8c · Share modal — the ONE door

<Warning>
**Share replaces "Send for signature" entirely** (Zach 2026-08-03). There must be exactly one place that

Front = document name · who has access · add people (name · email · role · permission) · attach-PDF · Done.

## 10 · Edit, reshare, and the MVP scope — measured 8/3/2026 · 4:05 PM

Walked live in dotloop (loop 306998806, a real executed listing loop) after Zach asked how dotloop handles
editing a document that has already gone out. This section is what was **observed**, then what we build.

### 10a · dotloop has NO void / resend — the model is "edit in private, then reshare"

Opening a **SIGNED** document shows **`EDIT IN PRIVATE`** under the title, and **the fields are still
editable**. Changes go nowhere until you press **SHARE** again. That is what *"Anything you add is private
until shared"* has meant the whole time.

So the loop is: **edit privately → save → share again.** There is no envelope to void, no "resend", no
cancel. The button says **RESHARE** because the document is a living, versioned thing with a share state —
not an envelope that gets sealed and mailed.

**The document toolbar, measured:**

| Menu | Items |
|---|---|
| **FILE** | Save · Print · Download · Split document · Rotate · Apply template · Save as template |
| **ADD** | Add signature · Add initials · Add strikethrough |
| **MORE** | Review notes · Show tasks · **Document history** · Host in person signing |
| | **AUTOFILL** · **SAVE** · **SHARE** |

`Document history` is the version trail that makes editing-after-signing survivable.

### 10b · The stamp — the parity target, on a real executed document

On the signature line itself, in green, sitting **in the DATE column**:

```
Chris Cribb          ┌ dotloop verified          ┐
                     │ 12/17/25 1:02 PM CST      │
BROKER SIGNATURE     └ QYP5-5XQB-EMTI-UVWZ  DATE ┘
```

Name in cursive · a verified label · timestamp **with timezone** · a 4×4 verification code. Three signers,
three distinct codes. Page top carries `dotloop signature verification: https://dtlp.us/1pBL-oHDs-IzTC`.
An unsigned slot still reads **`SELLER SIGN HERE`** — the same placeholder idea as our G0 tags.

<Note>
**We already match this.** `lib/esign/stamp-verification.ts` renders `HouseLoop verified` + the same
timestamp format + a 4×4 grouped code derived from Documenso's `field.secondaryId` — the same value printed
on the signing certificate, so the code genuinely cross-references. Shipped as G1. It says *HouseLoop
verified*, never a false "dotloop verified" claim.
</Note>

### 10c · Where our architecture genuinely differs — and why we do NOT copy them

| | dotloop | HouseLoop (Documenso) |
|---|---|---|
| A document is | living, versioned, edit-in-private | an **envelope**, sealed on send |
| Edit after send | just edit, then reshare | **impossible** — `throw 'already sent'` |
| A signature is | a stamp applied in place | a cryptographic seal |

Copying dotloop wholesale would mean giving up envelope sealing, which is the stronger legal position. We
keep the envelope and close the hole a different way (10d).

### 10d · THE MVP — Zach 2026-08-03: *"make this an mvp for what we need dont boil the ocean"*

His list, verbatim: *"the ability to add a person, does that person sign or not, reshare the doc, just send
the pdf, or whatever … i still need that dotloop parity with the code and the date and time stamp on the
date field."*

| # | MVP capability | State |
|---|---|---|
| 1 | **Add a person to a document** — name · email · role | ✅ built (`hl_tc_loop_document_share`, mig 0581) |
| 2 | **Do they sign?** — `view_only` \| `can_sign`, per document | ✅ built |
| 3 | **Reshare** — re-notify chosen people, document unchanged | ⬜ modal built; needs wiring to the send engine |
| 4 | **Just send the PDF** — a copy, no signature request | ⬜ to build |
| 5 | **The stamp** — code + timestamp in the DATE column | ✅ built (G1) |
| 6 | **Deliver the STAMPED copy** | ⬜ **G2 — the real gap** |

<Warning>
**#6 is why Zach thinks the stamping does not work.** The stamp has been correct since G1 — but Documenso
emails the **unstamped** copy, and our stamped one sits in the loop where nobody looks. He opened the wrong
copy and drew the obvious conclusion. Fixing the DELIVERY is worth more than any further stamp work.
</Warning>

**Explicitly OUT of the MVP** — named so nobody quietly builds them:

- Edit-after-send / envelope voiding / document versioning
- `Document history`
- `Can fill & sign` and `Can edit in private` permissions (they change who may ALTER a legal document)
- Split · Rotate · Apply template · Save as template · Host in person signing · Review notes · Fax

### 10e · The one hole the MVP still leaves open

`lib/esign/send-loop-document.ts:73` — `if (doc.status === 'sent') throw new Error('already sent')`, and
there is **no void, no resend, no new-version path anywhere in the codebase**. Send a document with a typo
today and you are stuck.

That is deliberately NOT in the MVP, but it must not be forgotten. When it is built, the rule is the line
dotloop's own model implies:

- **Nobody has signed** → void the envelope, unlock the fill, send fresh links. The old links must die, or
  a signer signs a stale version.
- **Someone has signed** → editing produces a **new version** with its own envelope; the signed one stays
  sealed in history. A signed document is immutable — that is what makes the signature mean anything.
