## THE MODEL — gate on AUDIENCE, not on actor (BUILT 2026-08-04)

> **You can lie about what you are. You cannot lie about who receives it.**

The recipient is in the payload. Keying the gate on **audience** is what makes it un-dodgeable: a workflow
cannot escape by not being an AI, because **it is not being asked what it is.** As of 2026-08-04 this is not
a design — it is **Altitude 0 of the one evaluator**, asked before even the master switch.

| Class | Reaches | Gate — and where it is enforced |
|---|---|---|
| **① COMPUTATION** | **nobody** — facts, summaries, lead context, scoring, vision tags, SEO drafting | **NONE.** Nothing leaves the building. A computation that asks the send gate is denied `WRONG_LANE` — it has no business there. |
| **② INTERNAL** | **our team** — notifications, alerts, run log | **ALWAYS ON.** *A pause that silences your own alerts hides what it stopped.* Declared in data: `hl_notify_classes.audience = 'team'` on all 58 classes (mig 0618), and the registry audit's axis 5 fails the push if any class misdeclares. The notification router never consults an AI switch — structurally, not accidentally. |
| **③ A PERSON** | lead · past client · lender · partner | **THE GATE.** The only class that splits. The only audience the evaluator serves — everything else bounces to its own lane. |
| **④ PUBLIC** | SEO articles published · social posts · listings | **Its own switch.** Real risk (brand, a wrong price on a public page) but **nobody's phone buzzes.** Pausing lead outreach must not stop an article. |

### ③ splits on one question — and that is the whole model

> **Why does this message exist?**

**THEY ASKED FOR IT → it flows.** A receipt for something they just did. A **saved search they subscribed
to**. An appointment confirmation. Deterministic, template, no judgment.

<Info>
**This class must NOT be blocked by an AI pause.** If turning off AI also breaks "here's your confirmation,"
the pause gets turned back on — and then there is no working switch at all.
</Info>

**WE CHOSE TO SEND IT → the gate.** Follow-up, nurture, re-engagement, "just checking in." **This needs a
playbook** — judgment, context, timing.

**Two buckets. Everything else is detail.**

### ⏱ "They asked for it" has a shelf life — the Monica rule

Her email **was** a receipt. The problem was that it arrived **twelve days late**.

> **A receipt is only a receipt if it is immediate. Past that it is outreach wearing a receipt's clothes.**

An asked-for message on an event older than ~15 minutes **reclassifies to chosen**, and the gate catches it.

<Warning>
**Nothing else would have caught Monica.** It was not AI. It had a legitimate template. It was bound to a
real event. **It was just stale — and nothing anywhere asks how old the triggering event is.**
</Warning>

### An AI writing INSIDE a message does not reclassify it

A saved-search alert with an AI-written top paragraph is **still a subscription**. The AI is an **ingredient,
not a sender**.

> **AI off → the alert still goes, without the paragraph.**
> An AI **component** fails soft. An AI-**initiated** message fails closed.

**Verified fleet-wide 2026-08-04** (the era-3 #89 census): every AI-initiator error path terminates without a
provider call, and every AI ingredient inside a deterministic send degrades instead of dying — the voicemail
triage is the exemplar (transcribe/classify failures still alert the team with *"Couldn't auto-read it —
worth a listen"*). The scheduled lane's choke gate is keyed on the actor's **nature**, fail-closed: a future
AI actor type is gated by default, not by someone remembering to widen a literal.

## THE LAW (the AI lane — still accurate, now one class of four)

> **No playbook, no voice.** Every AI communication — text, email, or (when the lane ships) a phone call, to a
> lead **or to a teammate** — is proposed, authorized, and re-authorized before it reaches a provider.

An AI outside a playbook has no goal, no state, and no history. It is a model guessing with a phone. The
playbook is the only thing that makes it *not* guessing, so **the playbook run is the authorization scope.**

## Why the old model kept failing

An AI **clone deliberately sends as a human** — the same number, the same inbox, the same name. That is a
feature, not a bug. And a clone is **not a user row**: it is a mode on a human
(`hl_agent_clone_config`, keyed by the human's id).

So every previous design did one of two impossible things:

| Approach | Why it failed |
|---|---|
| **Infer** AI-ness from the sending identity | Impossible — it is identical to the human by design |
| **Ask the caller** to declare it | Fails the moment any code path forgets |

That is not three separate bugs. It is **one unanswerable question, asked three times.** The fix was to stop
asking it.

<Warning>
**The real incidents this exists to prevent.** **Faduma** — a clone texted a live lead while clones were
"off." **Allison** — a muted lead was nudged at 9:52pm and cooled off. **Nickolas Loring** — a clone task
texted a muted lead with the master off. Every one of them was a send path that skipped a check nobody knew
was separate.
</Warning>

## THE SEVER — nothing AI can send, and that is the correct state

<Warning>
**Verdict, 2026-07-27: every AI send path in this codebase was built before the playbook model existed
and none of them is usable.** Not "needs gating" — **unusable.** There is no workflow, no playbook, no
goal, no context and no permission behind any of them. Auditing them one at a time and patching
whichever forgot to declare itself is whack-a-mole with a nicer vocabulary.
</Warning>

So the wire was **severed**, not gated. `lib/ai/authorized-send.ts` runs inside every provider module —
Twilio, BlueBubbles, Resend, Gmail — and refuses any AI-attributed send that cannot present a
**committed communication intent**. There is no parameter left to forget: **absence of the slip is
absence of permission.**

```
AI → SMS        ⛔ no_intent
AI → iMessage   ⛔ no_intent          ← this wire had NO actor context at all until today
AI → email      ⛔ no_intent
AI, no role     ⛔ no_intent          ← the actor lookup convicts it regardless
HUMAN → SMS     ▶ allowed
SYSTEM notify   ▶ allowed
```

**Essentially nothing the AI does can send today.** That is intended. None of it should have been
sending. Each path earns its voice back when it is rebuilt behind a playbook — and not one moment
sooner. **The rebuild landed 2026-08-04:** all five AI compose→send roads now propose through the
evaluator and dispatch only through the gateway (see WHAT IS REAL above).

**Unaffected, deliberately:** humans clicking send, and system notifications to our own team
(`kind: 'notification'`). An alert to an agent is not an AI talking to a customer.

## THE GROUND TRUTH — the AI is always inside a playbook

> **An AI is never idle and never freelancing. It is always operating out of a playbook, and the
> authorization to communicate lives INSIDE that playbook — what it may send, to whom, as whom, how
> many times, and for how long.**

This is why "no playbook, no voice" is not a slogan. The playbook step **is** the permission. A step
does not grant "may send texts" — it grants a **narrow, expiring capability**:

```json
{
  "key": "buyer_tour_request",
  "label": "Secure the showing",
  "goal": "A confirmed, calendared showing with the agreement out",
  "steps": [
    {
      "id": "acknowledge",
      "goal": "Confirm the requested time still works",
      "authorization": {
        "allowedActions":            ["sms.send"],
        "allowedRecipients":         ["playbook_lead"],
        "allowedPresentationModes":  ["human_clone"],
        "maxSends":                  1,
        "expiresAfterMinutes":       15
      }
    },
    {
      "id": "coordinate_partner",
      "goal": "Confirm availability with the showing partner",
      "authorization": {
        "allowedActions":            ["sms.send"],
        "allowedRecipients":         ["routing_rule_partner"],
        "allowedPresentationModes":  ["ai_identity"],
        "maxSends":                  2,
        "expiresAfterMinutes":       60
      }
    }
  ]
}
```

Read that second step carefully: Myli may text **the showing partner**, **as herself**, **twice**,
**within an hour**. She may not text the lead from that step. She may not present as Zach. She may not
send a third time. **The scope is the grant.**

### What must be true for a single message to leave the building

| # | Condition | Where it is enforced |
|---|---|---|
| 1 | A playbook run is **open** for this lead | `hl_playbook_runs`, unique index: one open run per lead |
| 2 | The run is on the **step** that permits this action | the step's `authorization` block |
| 3 | The action is in `allowedActions` | the evaluator |
| 4 | The recipient is in `allowedRecipients` | the evaluator |
| 5 | The presented identity is **delegated** for this channel | `hl_ai_identity_delegation` |
| 6 | `maxSends` for this step is not exhausted | `hl_communication_intent` idempotency |
| 7 | The grant has **not expired** | `expiresAfterMinutes` from step entry |
| 8 | Every switch is on — roster · lane · employee · lead mic · playbook | the evaluator |
| 9 | An **intent** was proposed and recorded | `hl_communication_intent` |
| 10 | It **re-authorized at commit**, against current policy | the gateway |
| 11 | The content passes constraints + the leak guard | the evaluator |

**Eleven conditions. Miss any one and nothing leaves.** And the eleven live in *one* evaluator, so a
new rule is one change in one place and applies to every channel at once.

## The actor model

Four things that used to be blended into one. **Separating them is the fix.**

| Concept | Answers | Example |
|---|---|---|
| **Actual actor** | Who is really causing this? | Myli — **always the AI**. The authorization principal. |
| **Role** | What class of employee? | Inside Sales Agent |
| **Playbook run** | **Why**, and in what scope? | Tour Request, step `acknowledge` |
| **Presented identity** | Whose name does the recipient see? | Zach's SMS line — **never the principal** |

<Warning>
**The presented identity must never become the authorization principal.** Resolving a clone to Ana's user row
and evaluating *Ana* is **privilege escalation by impersonation** — if Ana is an admin, her clone inherits
admin. The clone is an envelope, not an actor.
</Warning>

Every audit line reads: *actual actor* Myli · *under playbook* Tour Request · *presented as* Zach Spradling ·
*channel* SMS. **Two columns, never conflated.**

## The six altitudes

Two questions, in order: *who receives this?* — then *is this AI allowed to act?* — asked at six scopes.
**Deny overrides: a child can only ever be more restrictive than its parent, never less.**

| # | Scope | Where it lives |
|---|---|---|
| **0** | **The audience — who receives** | `CommRequest.audience`, required; asked before the master. Only 'person' proceeds — everything else is `WRONG_LANE` |
| 1 | The whole roster | `hl_settings.ai_master` |
| 2 | A lane | `hl_settings.ai_clones` · `ai_conversations` |
| 3 | One employee | `hl_users.is_active` · `hl_agent_clone_config.enabled` |
| 4 | One lead — **the mic** | `hl_leads.ai_responder = 'none'` — honored by text, email **and the phone lane** |
| 5 | One playbook | `hl_playbooks.enabled` + an **open run** |

Plus the delegation check: **may this actor present as this identity, on this channel?**
(`hl_ai_identity_delegation`). An absent row is a denial — which is why **voice is off today**: nobody has
written a voice delegation row.

<Info>
**Fail-closed, always.** Missing context, an unknown row, a malformed value, or a thrown query all **deny**.
There is no `?? true` anywhere in this path, and no way to ask for fail-open — the parameter was deleted so it
cannot be reintroduced. A missing `ai_master` row means **off**.
</Info>

## The flow

```
AI actor
   │  proposes
   ▼
CommunicationIntent  ──►  authorizeCommunication()   ← the ONE evaluator
   │                          (proposal-time decision)
   ▼
AICommunicationGateway  ──►  authorizeCommunication()  ← AGAIN, at commit
   │                          (current policy, not the old decision)
   ▼
SMS · Email · iMessage · Voice
```

**Nothing sends that was not written down first.** The intent row exists before any provider is contacted, so
"what was it about to say, and was it allowed?" is always answerable — including for messages we blocked,
which are the most valuable rows in an audit.

### Commit-time re-authorization

<Warning>
**An authorization decision is evidence of a past decision, never standing authority.** Myli drafts → the gate
approves → you flip the master off → the queued job fires two minutes later. Without a re-check at the
provider boundary, **it sends.** So the evaluator runs twice: once at proposal, once immediately before the
wire.
</Warning>

## Voice — why it is a separate codebase, and why that changes nothing

The voice agent (`apps/myli-voice-agent`) is **Python** — Pipecat + LiveKit, containerised, deployed to
**Pipecat Cloud** rather than Railway. That separation is legitimate engineering:

- A live call needs a **persistent bidirectional audio stream** at sub-second latency. Next.js route
  handlers are request/response and cannot hold a streaming audio session.
- The realtime-voice SDKs are mature in Python.
- It ships as a container, on its own release cycle, to a different platform.

**A voice bot genuinely cannot run inside the CRM process.**

<Warning>
**But a different runtime justifies a different PROCESS — never different RULES.** The bot already calls
`https://crm.houseloop.ai` at call start to fetch its persona. The pipe to ask permission has existed the
whole time. **It asks "who am I?" and has never once asked "may I speak?"** That is not a technical
limitation; it is a missing HTTP call.
</Warning>

### How voice joins the law — the protocol

The evaluator cannot be imported across a process boundary, so it is **served**. `POST /api/ai/authorize-call`
is live (`app/api/ai/authorize-call/route.ts`).

**Auth** — the same two doors as the persona route: the in-app internal secret
(`x-hl-internal-secret`), or the DB-stored voice secret (`x-myli-voice-secret`, from
`hl_settings.myli_voice`). The DB secret exists because a Railway env var and a local `.env` drifted
once and 403'd every worker call.

**The worker asks BEFORE it answers:**

```json
POST /api/ai/authorize-call
x-myli-voice-secret: ••••

{
  "callerPhone": "+19135551234",
  "actorUserId": "…myli…",
  "direction":   "inbound"
}
```

**Allowed:**

```json
{
  "allowed":          true,
  "reasonCode":       "ALLOWED",
  "leadId":           "…",
  "playbookRunId":    "…",          // THE CALL IS THIS RUN
  "playbookKey":      "buyer_tour_request",
  "expiresAt":        "2026-07-28T01:20:00Z",
  "stampOnEveryTurn": { "playbook_run_id": "…", "lead_id": "…" }
}
```

**Denied:**

```json
{
  "allowed":     false,
  "reasonCode":  "NO_ACTIVE_PLAYBOOK",
  "explanation": "…",
  "leadId":      "…"
}
```

### The worker's obligations

| Rule | Why |
|---|---|
| **Ask before answering.** Never after. | A denial must be able to prevent the call becoming an AI call at all |
| **On `allowed: false`, do not answer as AI** — forward to a human or take a voicemail | A denial is a routing instruction, not a warning |
| **Stamp `playbook_run_id` on every turn** written back | A voice conversation that left no record did not happen |
| **Never cache an allow across calls** | The grant is call-scoped. A new call is a new question |
| **Treat a non-200 as DENY** | The CRM being unreachable is not permission |

<Warning>
**An unknown caller is not authorized here.** If no lead matches the caller ID the endpoint returns
`LEAD_MISSING` — an AI does not hold a conversation with someone it has no record of. The cold-receptionist
path is a separate decision and is deliberately **not** covered by this endpoint.
</Warning>

**Today every call denies**, two ways over: `hl_ai_identity_delegation` has no `voice` row for any actor, and
there are no open playbook runs. Both are correct. Voice earns its voice back when someone writes the
delegation row on purpose and a playbook is running.

**The call IS the playbook run.** A live conversation cannot round-trip the database per sentence, so
permission is asked **once, at answer-time**, and the run scopes the entire call. A denial means it never
becomes an AI call at all — it forwards to a human or to voicemail.

**Provenance is non-negotiable:** every call opens a run and every turn lands in the trace, exactly as text
does. A voice conversation that left no record did not happen as far as the audit is concerned.

<Info>
**Today, voice is denied by construction** — `hl_ai_identity_delegation` has no `channel = 'voice'` row for
any actor. Nobody wrote one. **The absence of the row is the denial**, which is what fail-closed-by-design
looks like: a new channel is off until someone turns it on deliberately.

**And the per-lead mic reaches the phone lane** (era-3 #87, 2026-08-04): before dialing the bot, the inbound
webhook resolves the caller by phone and reads their mic — `ai_responder='none'` means the AI does not
answer and the human forward chain / voicemail takes the call. An unknown caller has no lead and no mute.
A lookup error fails closed.
</Info>

### One request, one decision — never a function per event

There is exactly one request shape and one decision shape. There is deliberately **no**
`canSendNewLeadText()` / `canSendFollowUpEmail()` / `canCallAfterShowing()`. That abstraction guarantees
whack-a-mole: a new event means a new function and a new place to forget a rule.

Reason codes: `ALLOWED` · `AUDIENCE_UNDECLARED` · `WRONG_LANE` · `MASTER_AI_DISABLED` ·
`CLONE_LANE_DISABLED` · `EMPLOYEE_DISABLED` · `NO_ACTIVE_PLAYBOOK` · `PLAYBOOK_NOT_RUNNING` ·
`PLAYBOOK_WRONG_LEAD` · `PLAYBOOK_DISABLED` · `IDENTITY_NOT_DELEGATED` · `LEAD_MUTED` · `LEAD_MISSING` ·
`QUIET_HOURS` · `DUPLICATE_ACTION` · `POLICY_CONTEXT_MISSING`.

## Runbook — how to actually stop the AI

| You want to stop… | Do this |

The twelve cover: master off blocks everything · **the happy path still works** · no playbook denied ·

<Info>
**Test 2 matters as much as the denials.** It asserts the happy path *works* — a wall that blocks everything

**The schema guard** reads `information_schema` and fails the build if the security path references a column
that does not exist. It exists because the authorization code once queried

swallowed, and the send was allowed** — a fail-open hiding inside a fail-closed function, invisible to
TypeScript because SQL is just a string. "Be more careful" is not a fix; a failing build is.
