## 📌 Summary

`/leads/[id]` is where an operator works a single lead. It is a **single-scroll, Follow-Up-Boss-style page**:
three lanes that scroll as ONE (the old independently-scrolling lanes and the self-scrolling "iPad" with its
bottom dock are gone), the centre feed is the tall column, and the iPad frame grows with the conversation.
The **composer is inline at the TOP of the iPad** — no modals — and the old bottom dock is now an **icon
filter row of read-only feed lenses**. Two mode bands render above the lanes when they apply: **TC Dashboard**
and **Referral Dashboard**. This page is the hub; each surface it names has its own deep-dive doc.

<Warning>
**THE ONE THING TO KNOW BEFORE YOU DEBUG ANYTHING HERE: the Messages tab does not read `hl_messages`.**

It reads the run-log, `hl_lead_activity`, which `logMessage()` writes as a **second, separate step** via
`logActivity()`. So a text can land in the comms table with a correct body, a correct lead and a correct
`conversation_key`, fire a notification to your phone, and **still never appear on the lead** — because the
write that this page renders is a different write, and it can fail on its own.

**When a message is "missing", query the run-log FIRST, not `hl_messages`.** Zero rows there with the message
present in `hl_messages` means the message is not lost, it is **unrendered** — and it can be replayed
(idempotent on `source_table` + `source_id`). This is not hypothetical; it cost seven silent hours on
2026-07-31 with zero errors logged anywhere. The full incident, the query, and the law that came out of it
(*coerce, don't reject*) are in the run log below.
</Warning>

## 🚧 IN-PROGRESS CUTOVER — the Messages tab, and how a message goes missing

<Warning>
**A message can be captured PERFECTLY and still be invisible on this page.** That is not a hypothetical —
it happened on 2026-07-31 and Zach found it in the product within hours.

**THE NON-OBVIOUS DEPENDENCY:** the Messages tab does **not** read `hl_messages`. It reads the run-log
(`hl_lead_activity`), which `logMessage()` writes to as a *second, separate* step via `logActivity()`. So a
text can land in the comms table with a correct body, a correct lead, a correct `conversation_key` — fire a
notification to your phone — and **still never appear on the lead**, because the run-log write is what the
tab renders and that write can fail independently.

**When a message is "missing," check the run-log FIRST, not `hl_messages`:**
```sql
SELECT a.kind, a.occurred_at, left(a.body,40)
  FROM hl_lead_activity a
 WHERE a.source_table = 'hl_messages' AND a.source_id = '<the hl_messages id>';
```
Zero rows with the message present in `hl_messages` = the run-log write failed. The message is not lost, it is
**unrendered** — and it can be replayed (idempotent on `source_table` + `source_id`).
</Warning>

### The 2026-07-31 incident — one message, seven hours, zero errors

| | |
|---|---|
| **Symptom** | Lucy Hartman's inbound text notified Zach's phone but was **missing from her Messages tab**, and she did not rise to the top of an activity-sorted leads table. |
| **Cause** | A `NOT NULL` constraint added to `hl_lead_activity.integration` that morning. A column **DEFAULT does not apply to an explicit NULL** — only to an *omitted* column. `logActivity()` names `integration` in its INSERT list and `logMessage()` supplies none, so every activity write inserted an explicit NULL and was **rejected**. |
| **Why nothing caught it** | The call is `void logActivity(...)` — **fire-and-forget**. The rejection was swallowed: no log, no throw, no error count. The schema-lock cage stayed green the whole time, because the constraint doing the damage was faithfully recorded. |
| **Fix** | Mig **0527** — a `BEFORE INSERT` trigger that **coerces** a NULL integration to its derived value instead of rejecting the row. It applies whether the column is omitted *or* explicitly NULL, which a DEFAULT cannot do. |
| **Recovery** | The one lost row was replayed and verified rendering. |

**The rule that came out of it:** *coerce, don't reject — when the value is DERIVABLE, an absent one is a
thing to fill, not a reason to lose the row.* `NOT NULL` is right when a value is genuinely unknowable and a
caller must decide; it is wrong when the system can derive it, because there it turns a harmless omission
into silent data loss.

<Note>
**Still open:** `logMessage()` does not pass an `integration` at all — the trigger fills it. That is a
band-aid on the writer, not a fix to it. The writer should state the pipe it wrote through. Tracked with Lee
alongside the `actor` → `user` cutover, since both touch the same INSERT.
</Note>

## How a message row renders (the Messages lens)

**A message row's job is to show the words.** Everything else — the house card, the badge, the headline — is
furniture around the words. That sounds obvious; it was violated four different ways at once (Lee, 2026-07-27,
found on Renita Ford, whose feed showed a wall of empty "Text Received" cards while FUB held a full negotiation).

| Rule | Why it exists |
|---|---|
| **The body always renders.** A row carrying an address shows **the message AND the house card** — never the house instead of the message. | The renderer treated an address as "this is a property row, the body is redundant". Every Zillow message carries a house, so **every one rendered blank**. |
| **Never truncate a message.** Quotes wrap (`pre-wrap` + `wordBreak`), they don't ellipsis. | The message IS the record. A negotiation clipped mid-sentence is not a record of a negotiation. |
| **Never render the body twice.** If the body is already showing as the quote, the preview slot takes the search criteria or nothing. | The first pass at "always render the body" produced a double-render — the fix caused the bug it was fixing. |
| **The headline names the actual speaker.** Outbound → the agent; inbound → the lead's first name. | It hardcoded the lead's name onto every row, so the agent's own replies read *"Renita sent an in-app message."* |
| **A Zillow message wears the Zillow mark** — its own chip (`'inapp'`), not the purple request hand. | The hand is the *request* icon; an in-app message is a conversation, not a request. Same portal asset the home cards use. |

<Note>
**Every comms row now names WHO acted and TO WHOM — native and FUB, one way (Zach 2026-08-08).** A row reads
"Zach Spradling sent a text to Marcell Hendrickson" (agent→lead) or "Marcell Hendrickson sent a text to Jessica
Coggins" (lead→agent). This is the [§5 composed sentence](#the-composed-sentence-5-one-who-did-what-line), and
the recipient resolves the SAME way for native and imported rows — a data fix, not a second render path:
- **Native** carries the recipient on the row (the writer stamps it; the receiving agent resolves via
  `our_identity_user_id`, never the raw phone number).
- **FUB legacy** was recovered **at the source**: the earlier "the card says Agent" state existed because FUB's
  export dropped the sender/recipient on inbound. `tools/fub-sync/resolve-comms-actors.mjs` (idempotent) fills
  the mirror's blank inbound from/to (the lead's phone → the conversing agent's line, resolved from the mirror's
  own outbound roster) and propagates `recipient_name`/`recipient_role` onto the run-log rows. An unresolved
  recipient renders an honest blank — never a guessed name. See [the FUB Master Scraper SSOT](/fub/master-scraper-ssot).
</Note>

## The composed sentence (§5) — one who-did-what line

Every non-hero row leads with ONE sentence — **`{actor} {verb-phrase} {relation} {counterparty}`** —
composed server-side at the one reader, never hand-rolled per surface. It is **catalog-driven**: the grammar
is DATA on the [activity catalog](/guides/activity-catalog) (`hl_activity_catalog`), not a map in the
component.

- **`composeSentence(row, grammar, portal)`** (`lib/activity/render-activity.ts`) is pure. The verb phrase is
  the catalog's `sentence` ("sent a text", "called", "saved a home"); `relation` (`to` · `about` · `for` ·
  `via` · `''`) is the catalog column that decides how the actor joins the counterparty.
- The **actor** is the run-log row's `by_kind` / `by_name` (the [actor model](/schema-lock/overview)); a lead
  acting on their own behalf reads "{lead} {phrase} [via {source}]".
- The **counterparty** is resolved by DIRECTION: an agent→lead row names the lead; an inbound lead→agent comms
  row names the RECIPIENT agent (see the [note above](#how-a-message-row-renders-the-messages-lens)). Add a
  badge/grammar to the catalog → it composes correctly everywhere, with no code change.

<Note>
Signed wordings that are NOT the plain sentence are preserved deliberately: a **call** reads "Outbound call to
{lead}" / "Call received from {lead}" (Zach 2026-08-06); a **fully-executed document** reads "Document fully
executed". Everything else is the composed sentence. The acceptance test
(`render-activity.sentence.test.ts`) loads the REAL catalog grammar and pins every signed sentence.
</Note>

## The card catalog — hero vs compact, every card the feed can render

**Two densities, one component.** `ActivityHeroCard` renders both: a **hero** card (big photo tile, address,
links) and a **compact** row (a small ROUND accent icon + the black who-did-what headline + a gray facts line
+ the body underneath — exactly like a text message). **A card is chosen by the row's CANONICAL event token**,
resolved through `canonicalEventType()` from `lib/leads/activity-badges.ts` — never a raw string in a
component. Renderers: `CenterLane.tsx` (the lead feed) and `PixelFeedStream.tsx` (website activity).

**Hero is reserved for a house-bearing first-class event** (Zach 2026-08-08): a **Zillow in-app message with a
home**, or a **registration**. Everything else — texts, **calls**, notes, website behavior — is a compact row
with a round icon. A **phone call reads like a text**: round phone icon, "Outbound call to {lead}", a gray
line "from {agent}'s old line · (number) · duration", then the recording player / AI summary / transcript
underneath (Zach 2026-08-08; calls were removed from `isHero`).

### The in-app card contract (Zach, locked across three sessions)

1. **2026-07-16 — the body is the point.** An in-app message carries a home, but its *point* is the MESSAGE.
   It routes to the hero row (photo + home + **the quoted message**), never the bare home card that drops the text.
2. **2026-07-23 — one action.** No "Look up on HouseLoop" (the address doesn't resolve) and no "View on Zillow"
   (Zillow has no per-lead page). The ONE action is **"View in Follow Up Boss"** → the lead's FUB profile.
   Falls back to no link row when the lead has no FUB id.
3. **2026-07-27 — a message with no house reads like a message** (found on Renita Ford). "Hi Dean, could you
   reach out to me?" — a plain sentence with nothing attached — must NOT render as a giant card with a Zillow
   logo where the photo should be. No home ⇒ the ordinary message row, still headlined "… sent an in-app
   message" with the VIA chip.

<Warning>
**⚠ THE SILENT RENDER REGRESSION — found 2026-07-28, and why a renamed token must break the BUILD.**

All three rules above stopped working and **nothing failed, threw, or logged.** The card simply went quiet:
no message body, no Zillow-circle branch, and the wrong link row.

**Root cause — one token, seven dead comparisons.** The event was renamed `in_app_message` →
`in_app_message_received` under the `object_verbPast` naming law, and the `ALIAS` map was correctly pointed at
the new name. But `canonicalEventType()` therefore **always** returns the new token, while seven UI comparisons
still tested the old literal:

```js
canon === 'in_app_message'          // ← can never be true again
a.kind === 'in_app_message'         // ← same, in CenterLane
```

Each dead branch removed one signed-off behaviour:

| Dead comparison | What the user lost |
|---|---|
| `PixelFeedStream:690` `buyerMessage` | **The message body.** The quote block had nothing to render — rule 1 gone |
| `PixelFeedStream:856` `heroLinks` | The "View in Follow Up Boss" action — rule 2 gone; fell through to HouseLoop/Zillow |
| `CenterLane:2305/2307` `inAppWithHouse` / `isHome` | The no-house message row — rule 3 gone |
| `PixelFeedStream:728`, `CenterLane:2205/2346` | Hero routing + the source chip |

**The fix, and the law it establishes:** compare against the exported constant **`IN_APP_MESSAGE`** from
`lib/leads/activity-badges.ts`, and canonicalize raw kinds (`canonicalEventType(a.kind) === IN_APP_MESSAGE`)
before comparing. **A renamed token must produce a compile error, not a card that quietly stops showing what
the lead said.** A string literal compared against a catalog-derived value is invisible drift — this is the
same class of bug as the FUB in-app sweep outage the same week (green signal, dead behaviour). See
[the FUB Master Scraper SSOT](/fub/master-scraper-ssot).

**The lesson for reviewers:** when you rename an event token, `grep` the OLD literal across `components/`,
`app/`, and `lib/` before shipping. The alias map keeps *data* working; it does nothing for *comparisons*.
</Warning>

## Activity architecture — one store, one writer, one catalog, one reader

The feed above is not assembled from a dozen fetches. Everything that ever happens to a lead — texts, emails
(sent/opened/clicked), notes, tasks, appointments, calls, website activity, saved searches, stage/contact
changes, AI actions — is **one append-only row** in the canonical run-log, and every lead-detail surface (and
Myli's dossier) reads the **one** endpoint. There are no parallel sources of truth. The kinds, their
sentences, and their grammar are the [Activity Catalog](/guides/activity-catalog); the whole model is locked
in the [Schema Lock](/schema-lock/overview).

| Layer | What | Where |
|---|---|---|
| **One store** | `hl_activity_runlog` — one row per event (renamed from `hl_lead_activity`, mig `0632`). Carries `kind` (a catalog key), `occurred_at`, `by_kind`/`by_name` (the [actor](/schema-lock/overview)), `direction`, `title`/`body`/`photo`, `source`/`source_table`/`source_id`, and `meta` (jsonb — listing, criteria, from/to numbers, `recipient_name`, old→new values). Idempotent on `(source_table, source_id)`; append-only. | migration `0632` |
| **One writer** | `logActivity()` — the only function that writes the run-log. Best-effort (a log failure never breaks the real action) and fires a realtime frame so open feeds update with no refresh. Every source double-writes through it right after its own insert (`logMessage`, workflow/manual email, the Resend + pixel webhooks, notes/tasks/appointments, lead-record edits, voice). | `lib/activity/log-activity.ts` |
| **One catalog** | Every kind → `{ label, color, Icon, category }` **and its sentence grammar** (`sentence` · `relation` · `sentence_subject` · `via_source`). The code catalog (`activity-badges.ts`) paints the tile; `hl_activity_catalog` carries the grammar that drives [§5](#the-composed-sentence-5-one-who-did-what-line). **The one place to recategorize or reword anything.** | `lib/leads/activity-badges.ts` · `hl_activity_catalog` |
| **One reader** | `GET /api/leads/{id}/activity?limit=&kinds=&savedSearchId=` — reads only the run-log, newest first, composes the sentence server-side, and returns `label`/`color`/`request`/`sentence` beside the raw row. `?kinds=` is a lens (a catalog subset). | `app/api/leads/[id]/activity/route.ts` |

**Adding a new event = two steps, no per-surface edits:** (1) call `logActivity({ leadId, kind, … })` at the
source with `sourceTable`+`sourceId`; (2) add the kind to the catalog (label/color/icon + sentence grammar).
It then appears — correctly labeled, colored, and phrased — in the All feed, the right lens, and the dossier.

<Warning>
**A LENS IS A CLAIM — measure it, never review it.** A tab that filters on a token the data does not use
renders **empty forever**, and an empty tab is indistinguishable from a lead with no activity — nothing errors.
Reading lenses one at a time cannot find this; a tool must: `node apps/houseloop-crm/scripts/audit-lenses.ts`
scores every lens on three questions — is every token a real kind (after alias resolution), how many rows its
predicate actually matches, and which kinds have data **no** lens shows. (Zach 2026-08-06, the transaction-lens
audit: Pending/Closed/Lost had always rendered zero because they filtered on non-kinds.)
</Warning>

**AI cost rides on the row, not a second table.** An AI action's token cost is two columns on its run-log row
(`input_tokens`/`output_tokens`); dollar cost is derived at read time from the model's $/M (never frozen).
"What is the AI costing" is a VIEW over the one catalog (`WHERE by_kind`/type = AI), split per agent. The one
allowed exception to append-only is `stampActivityTokens()`, which annotates ONLY those two cost columns of an
already-written self-logged AI row — never an identity field. Full model: [Activity Catalog](/guides/activity-catalog).

**History backfill** — `leadActivityBackfill` (Inngest, event `hl/lead-activity.backfill`) replays the source
tables into the run-log, idempotent and re-runnable, visible in the [Run Log](/guides/run-log).
