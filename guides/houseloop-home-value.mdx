## What this is

Every home on houseloop.ai has a **HouseLoop Value** and a **HouseLoop Home Value History** — our equivalent of
Zillow's Zestimate + "Zestimate history." The value is a single current number; the history is a **monthly series**
of that value going back as far as the data allows, rendered on the home page as a **graph** or a **table**.

The current value is not one algorithm — it's a **fork**. Which branch a home takes depends on what data it has,
and two different monthly jobs feed the two branches. Getting this right is the difference between a dead-on
Zillow-grade number and a rough index estimate.

## HouseLoop Value — TWO monthly engines + one live state (Zach LOCKED 2026-07-03)

Computed at read time in `lib/listings/get.ts`, chosen by **data presence, not a per-home flag**. The old "5–6 bucket"
framing collapses to exactly this — **every home's value is one of these:**

| # | Engine | When | Value | Monthly engine |
|---|---|---|---|---|
| **①** | **Past-Client Home Value · Ninja Monthly** | `sold` **AND** past-client (has a cached Zestimate) | `Zestimate × 1.005` — `zestimateHouseLoopValue` | re-fetch the Zestimate from OpenWeb Ninja (26th) → persist (27th). **Zestimate is used ONLY here.** |
| **②** | **Sold Home Value · ZHVI Monthly** | `sold` **AND** (not a past client **OR** no Zestimate) | `sold price × ZHVI[now]/ZHVI[soldMonth]` — `soldValueFromAppreciation` | recompute from the fresh ZHVI index (24th) → persist (27th) |
| — | **Active** (live, no cron) | `active` / `coming_soon` / `pending` | `list price × 1.005` — `activeValueFromList` | live at render; **on close flips to ① if past-client, else ②** |

**Engine ② is the default — ALL property types fold in: single-family, condo, apartment, AND land.** There is **no
separate land / native / self-sourced bucket.**
- **Land is NOT held flat.** Land appreciates on the same zip → city → county → metro ZHVI ladder as homes. ZHVI has
  no land-specific series, so **land stays lockstep with single-family** for its area — if the zip appreciates, the
  land appreciates the same.
- **Self-sourced / new-construction not on Zillow:** Zillow carries no Zestimate for it → it runs **②** on its sold
  anchor price. We **cannot** get a Zestimate for a self-sourced home.
- **The only "held flat" case** is a home with **no anchor date at all** (an organic new-build minted from scratch,
  e.g. `12111 W 165th Ter`). The moment it has any sale/list date, Engine ② takes over. Held-flat is the *anchorless*
  exception, never a property-type rule.

<Warning>

**The fork ORDER is the contract (Zach LOCKED 2026-07-03).** The branches are evaluated in this exact
priority, and the order matters:
1. **active/pending/coming-soon** → `list × 1.005`
2. **Zestimate present** → `zestimate × 1.005` (ninja_monthly — dead-on)
3. **sold + `closePrice` + `soldDate`** → `soldValueFromAppreciation` = `closePrice × ZHVI[now]/ZHVI[soldMonth]`
   (zhvi_monthly / native / self_sourced — the appreciation branch)
4. **stored `hlEstimate`** → LAST-RESORT fallback ONLY (raw land held at sale price, or a home missing a `soldDate`).
Branch 3 (appreciation) **must** run before branch 4 (stored value). Previously the stored-`hlEstimate` branch was
evaluated first and short-circuited the appreciation — so every no-Zestimate sold home rendered **flat at its raw
close price** (e.g. 3025 NW 95th showed $596,813 forever; 10908 E 35th sold $135k in 2021 still showed $135,675).
The formula was correct but unreachable. Verified by `tools/houseloop-cards/audit-value-buckets.mjs` (independent
ZHVI recompute vs the live render; must report `FLAT_BUG = 0`).

</Warning>

<Info>**The switch is the cached Zestimate's presence.** Past-client homes get a real Zillow Zestimate pulled onto
their `Listing` each month → Engine **①**. Everything else — every non-past-client sold home, plus any home Zillow
doesn't carry a Zestimate for (new-construction, land, off-Zillow organic cards) — runs Engine **②** (ZHVI on the sold
price). No per-home flag and no `native`/`self_sourced`/`land` sub-buckets: **the data decides, and ② handles every
property type the same way.** Canonical spec: `GT/GT - ACTIVE/GT_HOUSELOOP_HOME_VALUE_ENGINE.md`.</Info>

### Out-of-area homes

A home that **closed with SRG but sits outside our display MLS** (e.g. Richland, MO — a different board) still gets
a **past-client card + ZHVI value** — the relationship is the asset. But it does **not** render as a live IDX
listing, because we lack display authority from that source MLS. The empty IDX feed for such an address is the
*signal* it's out-of-area, not a data error.

### The value fields on `Listing` (centerbeam DB)

| Field | Meaning |
|---|---|
| `zestimate` (+`zestimateLow/High`) | raw Zillow Zestimate (via **OpenWeb Ninja**), cached only on homes that get the Ninja refresh |
| `redfinEstimate` (+`redfinEstimateLow/High` · `redfinEstimateUrl` · `redfinEstimateAt`) | raw **Redfin Estimate**, scraped by ADDRESS off the Redfin property page (past-client homes only — see the Portal-value spread below) |
| `hlEstimate` (+`hlEstimateLow/High`) | **the HouseLoop Value** = `zestimate × 1.005` (or list/ZHVI per the fork), persisted for seated homes |
| `hlEstimateAt` · `hlEstimateSource` | when it was computed · which branch produced it |

⚠️ **A stale `zestimate` = a stale value.** If a home's `zestimate` still holds an **old sale price** instead of a
fresh Ninja Zestimate, `× 1.005` just inflates the wrong number (e.g. a $215k old sale shows $216,075 even though
Zillow says $333k). The fix is a **Ninja refresh** for that home (the 26th job below) — not a code change.

## The refresh jobs — three monthly + one daily backstop

Four registered Inngest functions keep the value fresh. Three run on a staggered **monthly** cron (each feeds a
different branch of the fork), and one runs **daily** to reconcile close prices and backstop any sold home that never
got dispositioned:

| Day (UTC) | Function | id | Feeds |
|---|---|---|---|
| **24th** 09:00 | Zillow Research — monthly **ZHVI** ingest | `zillow-research-ingest` | the **MASS / ZHVI** branch — downloads Zillow's free ZHVI CSVs (county/city/zip/metro) → `hl_market_index`. Powers value + history for **all ~354k homes** |
| **26th** 10:00 | Past-Client Zillow Cache — dead-on Zestimate | `past-client-zillow-cache` | the **PAST-CLIENT** branch — fans out one **OpenWeb Ninja** call per past-client home → caches the real **Zestimate** (+ tax/price history) onto the `Listing`. Worklist = `hl_past_client_homes`, so new past clients auto-enroll |
| **27th** | Value-History Persist | `value-history-persist` | calls `getListing(hlid)` (so it reuses the ONE value fork above — no second formula), writes the current month's value + back-seeds the full monthly series into `hl_value_history`, **and refreshes the stored `Listing.hlEstimate` column** so the CRM seller-report/exports that read it directly stay current (target: `hl_past_client_homes`) |
| **Daily** 08:00 | Sold data reconcile + **disposition backstop** | `sold-data-reconcile` | fills any missing `closePrice` from Repliers, then re-emits `listing.sold` for **genuinely-flat** sold homes so nothing stays flat (see [Disposition](#disposition--no-sold-home-renders-flat-hardened-2026-07-03)) |

The monthly order matters: ZHVI (24th) lands first so the mass tier is fresh, then the Ninja Zestimates (26th) refresh
the past-client tier, then the value/history persist (27th) reads the now-current numbers and writes the monthly point.

<Info>Each is a real registered Inngest function — trigger manually via the dashboard **Invoke** button, never a
one-off script (see [Listing intake pipeline](/guides/listing-intake-pipeline)). `value-history-persist` also takes
the event `value-history/persist.run` (`{ limit?, hlids?[] }`) for targeted back-seeds/re-runs. Files:
`apps/houseloop-web/lib/inngest/functions/{zillow-research-ingest,past-client-zillow-cache,value-history-persist,sold-data-reconcile}.ts`.</Info>

## Portal-value spread — Zillow + Redfin, HouseLoop Estimate on top (Zach LOCKED 2026-07-21)

For the **Home Value Report / Homeowner's View**, a past-client home shows a **row of portal values** — **Zillow**
(`zestimate`, already cached via Ninja) and **Redfin** (`redfinEstimate`) — with **our HouseLoop Estimate on top**
("we weigh all of these plus our own algorithm"). Only two portals, by Zach's call: **Zillow via the OpenWeb Ninja
API, Redfin via scrape.**

**Why scrape Redfin, and why NOT the MLS tools (scouted + rejected 2026-07-21):** the value must be **address-based and
current**. Cloud CMA needs live MLS *comps* → fails on off-market homes (every past client who still owns). Remine is
parcel-based but its listing/owner/sale record is **stale** (anchored to the last MLS listing) and it carries no
Zillow. The Redfin Estimate is address-keyed and current, so we read it straight off the Redfin property page.

| Piece | Where |
|---|---|
| The scraper | `tools/houseloop-photos/redfin-estimate-scraper.mjs` (Camp David) — worklist = `hl_past_client_homes` JOIN `Listing`, stalest-first; human-search Redfin (reuses `redfin-human-scraper`'s zero-block recipe: real Chrome, type the address, autocomplete, Enter → land on `/home/<id>`); extract the estimate (brand-label `Redfin Estimate` anchor + `predictedValue` JSON fallback); write `redfinEstimate` back to `Listing`. |
| Monthly cron | `tools/houseloop-photos/redfin-estimate-cron.sh` on Camp David (`0 1 1 * *`) — single-instance guarded (file lock **and** a live-process `pgrep` guard). Resumable: skips homes with a fresh `redfinEstimateAt` (&lt; 25 days). |

**Why Camp David, not an Inngest fn:** Redfin blocks datacenter IPs. The scrape must run from Camp David's residential
IP in a real headful Chrome — Railway/Inngest can't reach Redfin. So this one value source is a **Camp-David cron**, not
a registered Inngest function (the address-based AVM exception to "Inngest or it doesn't exist"). It writes its durable
output straight to `Listing` (the table is the truth), single-threaded + human-paced (~15–20s/home, ~11h for the full
~1,900-home cohort → an overnight monthly run), and **self-stops on Redfin challenge detection** (never hammers).

**The sanity band:** a real home value is ~$20k–$50M — anything the extractor grabs outside that (a rent/mo or
price-per-sqft mis-grab) is dropped, not written. Coverage gaps (Redfin has no estimate for a home) are stamped and
skipped, not retried every run.

## The seller report's number — the two-rung ladder (shipped 2026-08-25)

The `/sell` **Home Valuation &amp; Demand Report** (`components/sell/DemandReportModal.tsx` →
`app/api/demand-report/route.ts`) carries the home's own number. It does **not** call `getListing`'s
fork, because that fork can return a MARKET-derived value and Zach's
**Seller value-source ruling (8/24)** removed exactly that from this surface. Two rungs:

| Rung | Source | When | `source` |
|---|---|---|---|
| **1** | **Live Zillow** via Open Web Ninja, × 1.005 | we have street + ZIP (the Zillow search key) | `zillow_live` |
| **2** | The **Zestimate-derived value we already hold** (`lib/valuation/stored-home-value.ts`) | rung 1 returned nothing, but the address resolves to a home | `zillow_cached` |

**Rung 2 is not a softening of the ruling — it is the same law reading a cached copy.** The gate keys on
the raw **`zestimate`** column, never on `hlEstimateSource` (that column is free text and has drifted to
36 distinct values including per-home strings like `zillow-zpid-80876319-reenrich`; a guard on a string
that open-ended silently narrows as new writers invent spellings). Anything ZHVI / sold-price /
list-price derived is **refused** and the report renders its honest no-number state. Measured yield on
the 2,102-home watch list: **2,016 pass** on the raw Zestimate, 1 on a stored Zestimate-sourced value,
**85 correctly refuse**.

<Warning>**A cached number must never say "updated today".** The response carries `asOf`, and the
header renders "as of {'{'}Month Year{'}'}" for a `zillow_cached` value. 1,976 of the 2,102 watch-list homes
were last stamped a full month ago, so this is not a rounding error in the copy.</Warning>

**The door that was losing the number:** the listing-page "Is this your home?" CTA
(`ClaimHomeCta.tsx`) sent `hlid` + city/state/zip and **no `street`**, so the old first line
(`if (!street || !zip) return null`) refused before it ever looked at the home — a seller standing on
their own listing page, whose Zestimate we had cached, was told we had no value. Fixed by passing the
part it already had. The `AddressAutocomplete` **Enter race** (submitting inside the 120 ms debounce, so
the suggestion list was still empty and the address travelled with no parts) now re-asks Places once
before falling back.

### The demand half — Google Search Console (`lib/demand/gsc-area-demand.ts`)

Answers Zach's E29 *"+ Google Search Console demand"*. Reads `searchAnalytics/query` on
`sc-domain:houseloop.ai` for queries **containing the city name**, 90-day window, and returns
impressions + distinct-query count. Auth takes the service-account road on prod
(`HOUSELOOP_GCP_SA_KEY_JSON`, Railway-only) and falls back to `GSC_REFRESH_TOKEN` locally, so the
feature is verifiable in dev instead of 503-ing into a silence that looks like "no demand".

- **CITY grain only, by measurement.** 90-day totals: Kansas City 703 · Overland Park 383 · Leawood 302
  · Shawnee 272 · Olathe 249 · Prairie Village 53 — but **ZIP 66224 is 8 and ZIP 66212 is 14.** A
  ZIP-grain number is noise, so `MIN_IMPRESSIONS = 25` refuses anything below the floor and the line
  simply does not render.
- **The wording is load-bearing.** An impression is *a search that surfaced a HouseLoop page* — not a
  person and not a visit. City-level **clicks are 0–1** over 90 days, so any copy saying "N buyers
  looked at your area" would be false by orders of magnitude.
- Best-effort throughout: no credentials, a failed call, and a below-floor measurement are
  indistinguishable to the caller, and all three mean "no demand line". It never costs the seller
  their valuation.

### The seller road

**How a home value gets built, from a typed address to a valued home. The mechanism as shipped
2026-09-10 (Zach #257.478: "i need the actual mechanism for how this gets built").**

Everything in this section is **live on prod at push #23** (`3d44ab4a7a`). Measured before writing:
`git diff 3d44ab4a7a HEAD` over the seven files named below returns zero lines, and none carries an
uncommitted edit, so there is no "in HEAD, awaiting a push" paragraph here. The build record behind
every number is the lane receipt
`.claude/reports/grinder/home-value-report/RECEIPT-sell-home-value-2026-09-10.md` (cited below by
round, e.g. R29.3). The "off-market front" section further down this page describes the ladder as it
stood on 2026-09-08 (Ninja first); the order in THIS section is the one that runs today.

#### 1. The entrance

`/sell` has ONE door: the address bar (`components/sell/SellerAddressInput.tsx`), fed by Google Places
through `AddressAutocomplete.tsx`, which hands over structured parts (street · unit · city · state ·
zip · lat · lng), never a free-text string. Picking a suggestion opens `DemandReportModal.tsx`
straight onto its loading state and calls `GET /api/demand-report` with those parts. The second door
is the dashboard's **+ Add a property / Update address** (`POST /api/home/address`), which runs the
same resolve → mint → enrol functions and returns a destination, never a number. The listing-page
"Is this your home?" CTA is the third, arriving with an `hlid` and no street.

#### 2. The resolver, and the address veto

`resolveHome()` (`lib/listings/resolve-home.ts`) answers "which home is this?" before any value
question is asked. Three rungs, cheapest first:

1. **The identity key** — `canonicalStreet + unit + zip5`, city excluded. `canonicalStreet` already
   normalises suffix (St/Street), directional spelling (W/West), case, punctuation and spacing, so
   nine of ten spelling drifts adopt here and never see a coordinate.
2. **Coordinate CANDIDATES, then an address DECISION** (Zach #257.399, built 2026-09-10). The lat/lng
   box (about 25 m) only narrows the catalog to the rows this address might be related to, up to 50
   of them. `sameAddress()` then compares the complete house number as a STRING (`123`, `123A` and
   `123 1/2` are three addresses), the unit, and the remaining street tokens with a directional set
   aside. Any mismatch is a **veto**, and the verdict carries its named reason
   (`house_number_mismatch` · `unit_mismatch` · `street_mismatch` · `no_house_number`). Geometry lost
   its authority because six rooftops sit inside one box on W 95th Street and four different houses
   on River Hills Drive share one exact lat/lng; the old `LIMIT 1` adopted whichever neighbour recency
   surfaced first.
3. **Mint** — nothing owned matches, so this is a new home.

The trade is deliberate: a false split leaves two rows somebody can merge later; a false merge
commingles valuations, owners, photos and history and cannot be unpicked. One shape got worse on
purpose: a genuinely re-numbered corner lot now mints a second row instead of adopting.

<Warning>**The veto also CORRECTS old contamination.** `10009 W 95th St` carried the identical
Zestimate as `10011` (a coordinate-collision artifact) until a seller re-submitted it; the new road
resolved its own zpid and wrote its own number (R29.6). Do not "clean up" stale duplicate values by
hand; the next enrich does it with provenance.</Warning>

#### 3. The mint

`mintHomeForAddress()` (`lib/listings/mint-home.ts`, Zach-signed 2026-08-24) creates the `Listing`
row only when four guards pass: resolve first (a match adopts, never forks) · a verified Places
result of premise type with a street number and a postal code (a street, city or ZIP centroid never
mints) · a plausible Heartland coordinate · mint-once via `ON CONFLICT (identity_key)` with a
sequence-backed HLID. A refusal is logged by reason and the report still renders its market half. On
a successful mint the SAME function fires the enrich event (`mint-home.ts:274`), which is why the
report route must not fire it again for a fresh mint (section 5).

#### 4. The number on the report: held value first, live only when we hold nothing

`resolveHomeValue()` in `app/api/demand-report/route.ts` runs in this order (R32.2, measured
before and after):

| Rung | What | Source label | Outbound value calls |
|---|---|---|---|
| resolve | `resolveHlidFromAddress` → the hlid, and whether it was just minted | | 0 |
| **1** | `fetchStoredHomeValue(hlid)` — the Zestimate-derived value already on the row | `zillow_cached` | **0** |
| **2** | `fetchLiveZestimate(parts)` — reached ONLY when rung 1 holds nothing | `zillow_live` | 1 |
| tail | no number: the honest no-value state, the HOME still resolved, still claimable | | 0 |

Until 2026-09-10 the live call was the function's FIRST statement, so a fully built home paid a
2 s provider call on every view (cold 3,989 ms, warm 4,008 ms: a 19 ms difference). Reversed, a held
home renders in about 1.4 s with zero value calls, and a valueless home pays once ever, because rung
2 persists what it found and the next view hits rung 1 (R32.3, the "road heals" arm).

**The provider switch.** Rung 2 no longer names a vendor. `lib/valuation/live-zestimate.ts` owns the
choice through `LIVE_VALUE_PROVIDER` (`"ninja"` or `"apify_address"`, env override
`HL_LIVE_VALUE_PROVIDER` for proofs only). **Today it is Ninja.** Zach #257.438 retires Ninja from
the seller road; the Apify ADDRESS leg replaces it once the coverage proof
(`lib/valuation/apify-address-coverage.proof.ts`, ten frozen off-market KC homes) reads **at least
7 of 10** carrying a Zestimate. The run on 2026-09-10 was INCONCLUSIVE because the daily run cap was
already spent (ten refusals, zero measurements, and a refusal is never counted as a miss); the
adoption run is scheduled after the 00:00 UTC reset, and flipping the constant is a desk act with the
number in the commit message. So #257.438 is satisfied on the enrich ladder (section 5) and NOT yet
on the report's live rung. Each provider builds its own key: Apify takes
`street, city, ST zip`; Ninja takes street + ZIP with the city deliberately left out.

<Warning>**The Apify address leg returns a point estimate and no band.** `zestimateLow` and
`zestimateHigh` are written as NULL when it answers, never coalesced over a stale band on the row,
and the surface already has a no-range rendition. A missing band beats a fabricated one.</Warning>

**What rung 1 costs, named.** A held value is not refreshed by opening the report; the monthly
writer owns that cadence. On the one home measured, the stored Zestimate was 15.4% below the live
read (R32.2). The Zillow columns carry no timestamp by construction, so `asOf` on a `zillow_cached`
value is the best honesty the row can offer.

#### 5. The enrich ladder: Inngest `listing-mint-enrich`

The report renders FIRST; the house is built BEHIND it by one Inngest function
(`lib/inngest/functions/listing-mint-enrich.ts`, id `listing-mint-enrich`, Run Log slug
`houseloop-listing-mint-enrich`, concurrency 5, retries 2, event `listing-mint/enrich` with an
`hlid`). It has exactly two dispatchers, and which one fires is decided by the `minted` flag:

- **A fresh mint** — `mint-home.ts` fires it. The report route sees `minted: true` and stays silent
  (R31.3: a fresh mint dispatches exactly once; before the dedupe, two runs raced the read-then-write
  guards and one house cost $0.2062 instead of $0.1031).
- **An existing thin row** — `route.ts:524`: when the home resolved without minting and its record
  is missing a photo, a Redfin estimate, or a value, the report route fires it. This is the common
  case and it landed 2026-09-10 (`b6f82d7c56`): most KC sellers who type their address are already
  one of the ~354k `Listing` rows, and until that commit the ladder fired ONLY on a mint, so a home
  we held as an MLS listing got the facts we happened to have and nothing the ladder would find
  (R19, `11504 Noland St`: zestimate NULL, Redfin NULL, photos 0). ⚠ The dashboard door
  (`POST /api/home/address`) mints and enrols but has no existing-row dispatch of its own; a thin home
  added there is enriched only if the /sell report is later opened on it.

The four steps, in order, every one fill-only (`COALESCE`, never an overwrite) and each guarded by
its OWN token in the run ledger so a re-fire costs one Inngest run and zero dollars:

| Step | Function | Actor / provider | Fills | Ledger token |
|---|---|---|---|---|
| 1 | `zillowApifyFill` | `one-api~zillow-scrape-address-url-zpid` (address → zpid), then `delicious_zebu~zillow-property-details-scraper` (zpid → details) | `zpid` (persisted the moment it is known, so future calls skip the address leg), `zestimate` + low/high, `photos` when empty | `apify_zillow` · `apify_zillow_absent` · `apify_zillow_failed` |
| 2 | `repliersFill` | our MLS, by structured address (streetNumber + streetName + city) | whatever step 1 left null: beds, full/half baths, sqft, lot, year, type, lat/lng, MLS photos | `repliers` · `repliers_absent` · `repliers_failed` |
| 3 | `apifyFill` | `one-api~realtor-property-scraper`, then `sian.agency~redfin-property-detail-scraper` | facts + per-field `*Source` stamps, the Realtor AVM into `avmEstimate`/`avmSource`/`avmAt`, Realtor photos when still empty, `redfinEstimate` + url + at | `apify_realtor` · `apify_absent` · `apify_failed`, each `+apify_redfin` when Redfin answered |
| 4 | `writeListingPriceHistory` | Repliers, MLS number resolved BY ADDRESS when `mlsId` is null | `priceHistory` (section 7) | its own column, idempotent |

Then, if any step filled photos, the function sends `houseloop/photos.cache` so the R2 copy travels
the same road real listings use.

**Two provenance vocabularies live on one row, deliberately.** `enrichmentSource` is a RUN LEDGER
keyed on the transport (`apify_zillow+repliers_failed+apify_realtor+apify_redfin` reads as one
history), appended through the ONE writer `appendSourceOnce()`, at most once per token. The seven
`*Source` columns (`bedroomsSource` … `photosSource`, migration `ee75cdce20`) answer "who knows this
fact" and are PROVIDER-named (`realtor`, `zillow`), never vendor-named. A `*Source` stamp fires only
when the column was NULL before the statement AND the incoming value is not NULL.

**Redfin is not gated on Realtor** (desk ruling 2026-09-10). A Realtor-absent home still asks Redfin
and stamps `apify_absent+apify_redfin`. Redfin declines active listings (`isAvailable:false`), which
suits a /sell home, and batches five addresses per run. It is a point estimate with no band.

**The Realtor AVM is captured and displayed nowhere.** THE ONE VALUE LAW (Zestimate × 1.005, index
and sold price the only fallbacks) does not contemplate a third-party AVM; whether it may feed a
displayed value is Zach's open ruling, and the harness asserts `avmEstimate` has zero readers as a
tripwire.

**Photo hygiene.** A Zillow record with no gallery substitutes a Google satellite tile; the client
filters those out (R24.2, proven with a 24-photo control), so an empty gallery and a map tile never
read the same. `photoCount` is `@default(0)` and never NULL, so the ladder's `COALESCE` on it never
fires: a row with 33 photos can read `photoCount = 0` (R29.5). Read `photos`, not the count.

**The spend guard** (`lib/enrich/apify.ts`, the ONE Apify client). Every actor call passes
`spendGuard()`, which reads month-to-date USD and today's run count from Apify's own API, never a
local counter. Defaults: **$4 a month** (`APIFY_MONTHLY_USD_CEILING`) and **40 runs a day**
(`APIFY_DAILY_RUN_CAP`), both env-overridable, both set below the account's platform cap so our
refusal fires first and says why. A refusal is LOUD and UNSTAMPED: the log line reads
`[apify] REFUSED reason=daily_run_cap actor=… observed=41 limit=40`, the run's return carries the
reason and numbers, and the row is left untouched so "we ran out of budget" and "this address has no
data" never share a trace (R31.2). The ledger fix is a ledger fix only: two truly concurrent runs can
still both call an actor, and the authority on what was paid is Apify's `/v2/actor-runs`, not the
`enrichmentSource` string.

## Disposition — no sold home renders flat (hardened 2026-07-03)

A sold home only gets its value **minted** (and its AI overview written) when the `listing-sold` Inngest function
runs. Two gaps used to leave homes **flat** (no value / raw close price):

**1. The webhook trigger only fired on a status TRANSITION.** `apps/houseloop-web/app/api/repliers/webhook/route.ts`
required `previous.lastStatus` to be present before sending `houseloop/listing.sold`. A metadata **re-sync** of an
already-sold record carries `previous.lastStatus = null`, so if the webhook missed the *original* `Sld` transition the
sold chain never ran and the home stayed flat forever (the "1011 Fontana" bug). **Fix:** fire `listing.sold` whenever
the record is `Sld` and the row is **not already archived** — the `listing-sold` idempotency-check
(`status='sold' AND soldDate AND enrichmentSource='repliers_webhook'`) makes an already-archived re-emit a cheap
no-op, so re-firing is safe. Only genuinely-archived rows keep the `sold_resync_skipped` label.

**2. No backstop for the historical backlog.** `sold-data-reconcile` (daily) now has an `emit-missing-disposition`
step that finds the **genuinely-flat** sold homes and re-emits `listing.sold` for each. "Flat" is precise — a home
renders a value from EITHER a stored `hlEstimate` OR a `closePrice` (× ZHVI appreciation, computed read-time in
`get.ts`), so it is only flat when it has **neither**:

```sql
status = 'sold' AND "hlEstimate" IS NULL AND "closePrice" IS NULL
```

<Warning>"Flat" is **NOT** "no `hlEstimate`". ~346k sold homes carry no stored estimate on purpose and render fine
from their close price × ZHVI. Scoping the backstop to `hlEstimate IS NULL` alone matched **345,882** homes (the whole
catalog); the real genuinely-flat set is **~29**. Step 1 of the same job fills `closePrice` from Repliers first, so
only the truly-broken tail remains. Emitting is idempotent — dispositioned homes no-op via `listing-sold`.</Warning>

## HouseLoop Home Value History (the monthly series)

### Where it lives — `hl_value_history`

A dedicated table in the website DB, **one row per HLID per month**, append-only:

| Column | Meaning |
|---|---|
| `hlid` | the home's HLID (permanent id) |
| `month` | first-of-month bucket (e.g. `2012-01-01`) |
| `value` (+`value_low`/`value_high`) | the HouseLoop value that month |
| `source` | `backseed` (historical) · `current` (the latest month) |
| `created_at` · `updated_at` | audit |

Primary key `(hlid, month)` — every monthly write is idempotent (re-runs never duplicate a month). A real
relational table, not a JSON blob, so the series is queryable, immutable per point, and cheap to append at scale.

### How it's built — the universal history builder

**One algorithm** (`flooredHistory` in `get.ts`, shared with the live graph and the persist job) builds the line
for **every** tier: start at the home's **oldest real sale** (which can predate 2012), otherwise floor at **2012**
using the **ZHVI** (`hl_market_index`), then climb monthly to today's HouseLoop value. The percentage shown spans
the whole line ("+X% since {year}"). The back-seed is **free** — pure index math, no Zillow API call.

### How it renders

`getListing(hlid)` reads `hl_value_history` as the source once a home is seeded (falling back to the computed line
for any home not yet seeded), and exposes it as `houseLoopValue.history`. On the home page the **HouseLoop Value**
hero shows the value range plus a **HouseLoop Home Value History** section with a **Graph ↔ Table** toggle:

- **Graph** — an interactive line + scrubber.
- **Table** — the Zillow-style monthly table: Date | HouseLoop Value, newest first, with "+X% since {year}".

| Symptom | Likely cause | Fix |
|---|---|---|
| A **no-Zestimate** sold home shows a **flat value = its raw close price** (never appreciated) | the value fork evaluated the stored-`hlEstimate` branch before the appreciation branch (the pre-2026-07-03 bug) | fixed in `get.ts` (fork order); re-persist via `value-history/persist.run { hlids }`. Verify with `audit-value-buckets.mjs` → `FLAT_BUG = 0` |
| Value = an **old sale price** (× 1.005) | `Listing.zestimate` holds a stale sale price, not a fresh Ninja Zestimate | re-run **`past-client-zillow-cache`** for that hlid (26th job) to pull the current Zestimate |

## Field provenance — the `*_source` columns + the Repliers ↔ Ninja fallback split

Every enriched field carries a `*_source` tag so we always know where a value came from:

- `value_source` = `zestimate | zhvi | algo` · `price_history_source` · `schools_source` · `tax_source`.
- Distinguish coverage with e.g. `SELECT source, count(*) FROM hl_value_history GROUP BY source` (⚠ there is NO `hl_home_value` table — the persisted series lives in `hl_value_history` + the ZHVI anchor in `hl_market_index`; fixed per the Fable 5 audit 2026-07-06).

**Repliers gives the CURRENT facts; Zillow / OpenWeb Ninja gives the RICH HISTORY + ratings.** The per-field fallback order:

- base fields (address / beds / baths / current price) + **current tax (single)** = **Repliers**.
- **tax HISTORY (multi-year)** = **OpenWeb Ninja / Zillow** → fallback Repliers current tax.
- **GreatSchools** = **OpenWeb Ninja / Zillow** ratings → fallback Repliers schools (only if the listing agent provided them).
- **price / listing history** = **default OpenWeb Ninja / Zillow** full history → fallback Repliers (partial).
- **home value** = OpenWeb Ninja Zestimate × 1.005 → fallback ZHVI → fallback the monthly algo.

The `*_source` column records which one ACTUALLY filled each field.
