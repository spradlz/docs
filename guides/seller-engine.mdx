**3 · ⚠ SISU `status` IS MUTABLE — "not Closed" NEVER means "never closed".** SISU is a per-PERSON CRM

reset to `Appt Set` and the closing is gone.** Proven: **30 clients in the book with a real canonical
closing now read `Pending` / `Lost` / `Appt Met` in SISU** (e.g. *Aj Nardi — closed May 20 — SISU says
"Pending"*). Worse, Logan Fritts' **2019** $225,000 purchase is not in SISU **at all**; the earliest row
is dated **2024-04-13**, logged as a fresh appointment **on the very house we sold them.**

→ `status='Closed'` is a TRUE POSITIVE (a closing happened). **The absence of it proves nothing.** For
"did this person ever close with us", **dotloop is the immutable record** — loops are ARCHIVED, never
overwritten. See [dotloop Integration](/guides/dotloop-integration) §"Using dotloop as a confirmation source".

**4 · SISU IS ONLY TRUTH WHERE `status = 'Closed'`.** 11,636 rows, **1,945 closings.** Everything else is
Appt Met (5,178) / Appt Set (3,388) / Signed (417) / Lost (309) / Pipeline (282). Omitting that filter is
**the single most expensive mistake in this system** — it counts *appointments* as closings and
manufactures a crisis every time. `build-deal-ledger.mjs:55` filters correctly; hand queries did not.

**5 · `hl_srg_canonical` is the deal SSOT.** `hl_srg_book` is the client-level view of it.

**5b · A HUMAN VERDICT CAN NOW CREATE A DEAL — the path that never existed** (fixed 7/29/2026).
`hl_srg_deal_overrides` was keyed `pc_id:sisu_id` and applied INSIDE the SISU loop, so a verdict could only
**edit a deal SISU already found — never add one SISU never saw.** 150 override rows existed and not one

## How a past client resolves — the whole flow, once

```
SISU (closings, frozen)  ─┐
Heartland MLS deals      ─┼─►  hl_srg_deal_ledger  ─►  hl_srg_canonical  ─►  hl_srg_master_houses
dotloop contracts        ─┤    (the MATCH: mls#,       (the RESOLVED         (same truth, per HOUSE)
human overrides          ─┘     hlid, side, price,      answer, 1/deal)
                                date, agent, tier,             │
                                verified_sources[],            │  hlid
                                contradiction)                 ▼
                                                        WEB db: Listing / hl_property
                                                        (value · photos · price history)
```

- **The ledger MATCHES** (`match_method`, e.g. `price-date-unique`; `verified_sources[]`; `contradiction`).
- **Canonical is the ANSWER** — one resolved row per deal.
- **`hlid` is the ONE key** that crosses from the CRM to the website. There is no other join.
- **`bucket` is the only thing you fetch from the parent**, joined on `pc_id`.

<Note>
**Why it is not one single table** — and it cannot become one. HouseLoop is **exactly two databases**
(constitutional): people/deals in CRM, homes in WEB. You cannot join across them in SQL. And a *person*,
a *deal*, and a *house* are three different grains — "one row" would have to pick one. So the real
architecture is **one resolved table per grain, and ONE key (`hlid`) between the two databases.**
That is already built and already 100% populated.
</Note>

### The deal ledger — match deals, not addresses (locked 2026-07-03)

floorplans, fat-fingered streets). The right question is **"which DEAL is this?"** — a deal fingerprints as
**client name + price + close date**, and independent ledgers of the same deals join deterministically.

**The five edges, in matching order:**

1. **SISU↔MLS name edge** — `sisu_transactions` ↔ `hl_srg_mls_deals` by last name + price ±$3k + close date ±20d.

3. **Price+date-unique (cross-side)** — when exactly ONE listing in the book carries the fingerprint, **with
   the ADDRESS-CONTRADICTION VETO** (differing street numbers reject the match — this un-glued 27 silent
   mispins the day it landed).
4. **The FUB person-ID link** (`hl_fub_sisu_link`) — immune to name-spelling drift.

Sphere Of Influence. The distribution shows exactly what it marks — **Ana's personal sphere**:

| Bucket | has pcsoi |
|---|---|
| ana-only | **349 / 432** |
| ana-handoff | **82 / 83** |
| team | 126 / 1,249 |

**Nothing branches on the value** — it is a marker, not a driver — which is what made normalizing safe.
105 rows (`true`, `PCSOI`) → `yes`. Two states now: `yes` (560) and empty (1,219). Any query filtering
`pcsoi='yes'` was previously missing 105 people.
</Warning>

### 2026-07-27 · Task 40 — empty-render cards, and WHY A HOUSE GETS TWO HOUSELOOP IDs

**Result: empty-render cards 16 → 8.** The 8 repaired now carry real value and photos ($972,438 · $609,030 ·
$513,555, all with galleries). The remaining 8 have **no live listing at all**, so they are a data-availability
problem now, folded into tasks 46-47.

**The bug had two layers.** `hl_property.identity_key` was written with a **double-suffix**
(`14813 w 150th pl place`, `9627 kessler street street`), so a home and its own listing were keyed to two
different addresses. Then when de-fork merged the listings for that address it quarantined the loser — and if
that was the only listing under *this* property, the property was left pointing at a dead row. `getListing()`
skips quarantined rows, so the card rendered blank while a perfect listing sat a few rows away.

<Warning>
**⚑ ROOT CAUSE OF DUPLICATE HOUSELOOP IDs — settled 2026-07-27. It is the MLS feed, not our normalizer.**

`hl_property.identity_key` is **UNIQUE** — but **a malformed key does not COLLIDE with the correct one**, so
the constraint never fires and a **second HouseLoop ID is minted for one house, silently.** The malformed
string arrives straight from Heartland, verified in `hl_srg_mls_deals`:

| What the MLS sent | What we minted | Its twin |
|---|---|---|
| `14813 W 150TH PL PLACE` (MLS#2583791) | **HLID100257** | HLID149137 — "14813 w 150th place" |
| `9627 KESSLER STREET STREET` | **HLID100280** | HLID326937 — "9627 kessler street" |

**The fix is to collapse a repeated suffix at INGEST** — but only MATCHING pairs (`pl`+`place`,
`st`+`street`). ⚠️ **`TERR COURT` and `ST COURT` are REAL Kansas City street types** and must never be
collapsed.

**And stop exact-string matching.** `tools/houseloop-cards/resolve-address.mjs` narrows the way a search box
does — house number → street stem → unit — and stops at ONE home. When two rows survive for one address it
**reports the duplicate instead of minting a third**.
</Warning>

**Zach's merge rule (locked):** when two IDs describe one house, **the CORRECT address wins; among equally
correct, the OLDEST wins** (it has been in the wild longest — shared links, Google, old emails). The loser
**always** aliases forward via `hl_hlid_alias` so no URL 404s. For a condo, the record carrying the real unit
is the correct one even if it is newer.

**Repaired from MLS truth** (`hl_srg_mls_deals` — MLS# is address ground truth):

- **7 garbage unit hashes.** Two leaked template variables — `#F320a52c6` and `#776f18ccb` — had been parsed
  as unit numbers and keyed into home identity, forking the homes. The MLS had every real unit:
  Herder **230** · Cuddy **1208** · Helmich **307** · Peterson **904** · Rojas **103** · Calmus **410**.
  Zero garbage hashes remain; `15900 Granada St #230` now resolves to exactly **HLID101348**.
- **4 property ZIPs**, each MLS-confirmed. 2 more were vetoed by the guard below.

<Note>
**Two near-misses worth keeping on the record.**

**A query escaped its scope.** The ZIP repair was about to rewrite **772 property rows** across the whole
358k-row table — including cross-state jumps like `66083 → 64083`. Caught in the dry run and scoped to
past-client homes: 6.

**Then a guard saved a correct record.** Taking the most common ZIP among a property's listings is **not
safe** — a mis-attached listing poisons it. `8 NE 110 Terrace` had the MLS **and** its own listing both at
64155 (already correct) while a stray row pulled the average to 64114. Nothing is rewritten now unless the
**MLS deal agrees**: 4 applied, 2 vetoed.
</Note>

### 2026-07-27 · Task 36 — the 65 quarantined home pins

**Symptom:** 97 past-client pin rows (65 distinct targets) pointed at a `Listing` row whose
`quarantinedAt` was set, so the card rendered value-less. Named clients affected: Megan L. Hawks,
Therese Foster, Erin Odom, Rick Lucas, Colby Peterson, Abagale Brown.

**Why it recurred nine times.** Archaeology found **nine separate one-off repair passes since 2026-07-02**
— unquarantine-batch, defork-keeper, ledger-repoint, card-history-recover, thin5, Aaron-Johnson-adopt,
active-listing-repoint, rich-keeper-swap, Bergin-keeper-swap. Every one a scratch script; most no longer
exist in the tree, only their reversal receipt survives.

The mechanism nobody closed:

1. Quarantine is a **WEB-local event**. `lib/listings/defork.ts` merges a fork pair, sets the loser's
   `quarantinedAt`, and logs `loser_hlid → winner_hlid` in `hl_dedup_quarantine` — with **zero CRM
   awareness** (no CRM connection exists in that file).
2. The CRM's `website_hlid` columns are **static text snapshots** written once by a backfill and never
   re-resolved. The Seller Report renders from those columns.
3. So every merge silently stranded a card, and a human re-found it later.

<Warning>
**A correction to the previous guidance.** This guide used to say "flip the `pastclient-rooftop-guard`
cron" was the structural fix for recurrence. **It was not, for this bug.** Steps ①-③ of that guard maintain
`hl_property.active_listing_hlid` (WEB side). The Seller Report reads `website_hlid` (CRM side). Different
pointers — the cron alone would never have fixed a single value-less card.
</Warning>

**Why hand-fixes kept failing:** the winner usually lives under a **different `identityKey`**, because the
merge was across address variants — `604 W 90th Ter` → a Heartland row, `818 N 84th Dr` vs `818 NE 84th St`,
`14813 W 149th Ter` keyed as `…149th court`. Anyone hunting a keeper *within* the loser's identityKey finds
zero live rows and concludes the data is gone. It is not — the forward pointer was in the quarantine trail
the whole time, and it has to be followed **transitively** (a winner can itself be merged later).

**What shipped:**

| | |
|---|---|
| `tools/houseloop-cards/repoint-quarantined-pins.mjs` | The repair. Dry by default, `--write` gated, writes a reversal to `.claude/reports/`. Two recovery paths: the dedup trail (transitive, cycle-guarded), then a fallback to the richest live sibling under the same identityKey (value → photos → not-archive — the Bergin keeper rule). |
| `pastclient-rooftop-guard` — quarantine filter | `resolve-keepers` had **no** `quarantinedAt` filter, so a quarantined row could rank #1 and *become* the keeper. That is the Bergin mechanism. Filtered now. |
| `pastclient-rooftop-guard` — new `sync-crm-pins` step | The loop nobody closed. Follows the quarantine trail transitively and repoints **both** CRM pin columns onto the live winner. Idempotent — 0 repoints on a healthy book. |
| **Cron ON** — `0 6 * * *` | Zach's typed sign-off 2026-07-27. Event trigger kept for manual re-runs. |

### 2026-07-27 · Tasks 37 + 39 — the sell score and the suppression list

`tools/houseloop-cards/sell-score.mjs` — turns 1,779 names into a ranked call list. Read-only by default;
`--write` stamps `hl_srg_past_clients.sell_score`, `--csv` exports.

**The score is 0-100 across four explainable parts — never a black box:** TENURE 0-40 (peaks at 6-10 years
owned, the strongest signal) · EQUITY 0-30 (blends % gain and absolute dollars) · MOMENTUM 0-20 (real
12-month year-over-year) · REACHABLE 0-10 (contactable, and do we know them well enough to sound human).
Every row prints its own breakdown (`T40 E30 M17 R9`) so a human can argue with it.

**Suppression is a hard gate applied BEFORE scoring** — a landmine is **removed with its reason printed**,
never merely ranked low, so nobody can accidentally work one: quarantined pin · negative equity · no
purchase price · absurd appreciation (>300%) · not a current owner · no email · agent-dnc/internal.

Result after the pin repair: 1,271 owners → **126 suppressed** → **1,145 scored** · 167 HOT (75+) · 142 WARM.

<Note>
**A bug worth remembering.** The first version read `Listing.valueHistory` — the *column*, which is empty on
most homes. It silently defaulted ~75% of rows to "no trend" and quietly collapsed the score into
tenure+equity. The real series is the **`hl_value_history` table** (345k rows). Reading a column that looks
right but is empty is the kind of failure that produces a plausible, wrong answer.
</Note>

### 2026-07-27 · Task 1/35 — Redfin column verified against the live site

Zach checked **3730 Ditzler Ave** and reported Redfin had no value for it, while our database held
**$336,621**. Verified on Camp David's warm Chrome: Redfin prints *"Unfortunately, we don't have enough data
to generate an accurate Estimate at this time"* and the page carries **zero** `predictedValue`. **We stored a
fabricated number.**

Two defects, root cause first:

1. **Settle too short (the cause).** The estimate JSON hydrates well after `domcontentloaded`, but the
   scraper extracted ~2.2s after landing. On slower pages the primary read **missed** and fell through to the
   text fallback. Measured: `11443 W 105th Ter` read null at 3.8s and the correct **$503,150** at 5.2s. Now
   waits for a **terminal signal** — the value is present *or* Redfin states it has none — capped at 9s. This
   also recovers legitimate values the monthly sweep has been silently missing.
2. **Unanchored fallback (the symptom).** The regex matched *any* "Redfin Estimate" occurrence followed by a
   `$` within 80 characters, so on a no-estimate page it scanned past the apology into another module.
   Returns null immediately now when Redfin states it has no estimate.

**Verified live, 5 cases:** both Ditzler homes → null (fabrication killed); `11443 W 105th Ter` $503,150,
`4809 W 70th St` $419,666, `5523 Sutton Ave` $287,153 all preserved exactly. **Context: 28 of 28 other
sampled homes matched Redfin exactly**, so the column is broadly sound — this was a narrow but real defect on
no-estimate homes. A full re-scrape with the fixed extractor is running on Camp David.
