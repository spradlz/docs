## 1 · The end goal (Zach, locked 2026-07-20 — verbatim)

**Every SRG past client, completely reconciled, becomes a living monthly relationship:**

1. **ONE perfect HouseLoop ID card per client home** — 100% reconciled data (transactions, agents,
   dispositions, dossier), a fully hydrated + current public `/home` page, guarded forever (one HLID, every

     seller-report card. (Separate surface from lead-detail.)

   - **Website · OWNER'S VIEW** — owner mode on the client's own `/home` page: their report + full history,
     value growth since purchase (the public view stays public).

   Runs itself on Inngest; Ana's workflow rides on top.

**Why we win:** Homebot shows value + equity + appreciation. HouseCanary shows a range + confidence + comps.

## 4 · The value model

### The locked source stack (Zach 2026-07-21)

The homeowner sees a portal-value row — **Zillow + Redfin** — with the **HouseLoop Estimate ON TOP**.

- **Zillow** — cached on `Listing.zestimate` via the OpenWeb Ninja pipeline.
- **Redfin** — scraped to `Listing.redfinEstimate` (+`Low`/`High`/`Url`/`At`) by
  `tools/houseloop-photos/redfin-estimate-scraper.mjs` on Camp David's **warm** Chrome (never headless),
  self-healing monthly.
- **HouseLoop Estimate** — `Listing.hlEstimate` (+`Low`/`High`/`Source`/`At`), the headline number.
- **HouseLoop Home History** — the real sold price → today trajectory.

**Cloud CMA and Remine were scouted and REJECTED** — stale and MLS-listing-anchored. Value must be
address-based and always-current; every past client who still owns is off-market, so a listing-anchored tool
returns nothing.

<Warning>
**🚨 THE BLOCKING FINDING — the unfair advantage is not built yet.**

Measured 2026-07-27: **1,583** past-client homes carry `hlEstimateSource = "zestimate"`. **84.6%** of
HouseLoop Estimate values sit **within 1%** of the Zillow number; only **1.9%** diverge by more than 5%.
**Redfin is scraped on 1,600 homes and used in the estimate on exactly one.**

Today the HouseLoop Estimate is **Zillow's Zestimate, relabeled.** Showing a homeowner three numbers where
ours is visibly a copy reads as padding, not an advantage.

**The fix:** blend the two portal AVMs against the three things no portal has — the **real purchase price**
(our own closing), our **MLS-receipted sold comps** (`hl_srg_mls_deals`), and the **ZHVI trajectory**
(`hl_market_index`, 401,118 rows) — and publish the weighting. That is the moat, and it is a build, not a scrape.
</Warning>

### The value fork ORDER (locked 2026-07-03 — order matters)

1. Active / pending / coming-soon → list price × 1.005
2. Zestimate present → zestimate × 1.005
3. Sold + closePrice + soldDate → **ZHVI appreciation** from the real sale
4. Stored `hlEstimate` → **LAST RESORT ONLY**

Branch 3 must run before 4 — reversing them caused a "flat forever" bug.

### The value-history floor law (locked 2026-07-23)

**The line can never start before the home existed.** The owner's line anchors on the **REAL purchase**
(`% = (current − purchase) / purchase`); with no sale on record it floors at the **build year**, never earlier.

*The Bergin case:* 15584 S Church #1600 was built 2020 and bought 2020 for $359,900. The graph claimed
**+112% "since 2012"** — a fabricated pre-existence line. It now reads **+32% since 2020**. Book-wide
regeneration took fabricated histories from 196 → 24 → **0 (verified 2026-07-27)**.

⚠️ **66 past-client homes still have a null build year**, so the floor cannot be enforced on them. That is
the root cause of recurrence — fix the data, not the symptom.

### Divergence — an open design decision

On **73 homes the three sources disagree by more than 25%.** Worst case: HouseLoop **$132,761** · Zillow
**$132,100** · Redfin **$412,081** (a 211% spread). Redfin diverges from Zillow by more than 5% on **657
homes (42%)** — it is a genuine independent signal, not noise.

**Needs Zach's call before pixels lock:** show the range and say why? Suppress the weakest source? A
confidence badge? Whatever we choose, the report must be able to answer *"why is your number different from
Zillow's?"*

## 5 · The reconciliation engine (the data foundation)

**North star:** every SRG past client → ONE accurate card: person + household + every transaction we did
(with the agent who worked it, even if they left) + their current home (deed-confirmed) + lost opportunities
+ a relationship dossier. **Accuracy is the only benchmark. The table is the truth.**

### The pipeline — three stacked layers (newest is canonical)

1. **Layer 1 — the canonical MLS#-anchored resolver.** `resolve-from-mls.mjs` keys every deal on its **MLS#**
   (not the typed address) → MLS# → HLID → the WEB `Listing` rooftop life → disposition vs the SRG roster.
   Writes **`hl_srg_canonical`**. Then `regenerate-notes-from-canonical.mjs` pushes the resolved
   disposition/value onto the child so the audit cards and FUB notes render the truth.
2. **Layer 2 — the deal ledger.** `build-deal-ledger.mjs` materializes **`hl_srg_deal_ledger`** (the
   deterministic client×deal match, 5 edges, GREEN/YELLOW/RED tiers, `verified_sources[]`).
   `build-master-houses.mjs` rolls it into the **`hl_srg_master_houses`** VIEW (one row per house + nested
   transactions = the Zillow-style history).
3. **Layer 3 — the WEB cards.** `sync-pastclient-worklist.mjs` mirrors the child → WEB
   `hl_past_client_homes`; `enrich-pastclient-listing.mjs` + `hl-photo-engine.mjs` fill the WEB `Listing`;
   `build-resolution-table.mjs` rebuilds the **`hl_pastclient_resolved`** VIEW (coverage flags).

### The identity model — one home, one ID, many transactions

```
identity_key = "<street>::<zip5>"          ← the ADDRESS is the home key
      │ (one row per key)
      ▼
hl_property.hl_property_id = HLID######     ← THE canonical, permanent home id (in the /home URL)
      │  .active_listing_hlid ───────────►  names the KEEPER Listing row
      ▼
"Listing"  (MANY rows per home — one per sale)
      .hlPropertyId = HLID######            ← back-link every listing → its home
      .hlid = hl_<source>_<slug>            ← the per-LISTING id (NOT the home id)
```

A person points at their current home via `hl_srg_past_clients.website_hlid`; the child
`hl_srg_past_client_homes` holds every home, pinned by both `hl_property_id` (HLID) and `website_hlid`.

### The deal ledger — match deals, not addresses (locked 2026-07-03)

**The insight that ended three weeks of resolver pain: we were answering the wrong question.** *"Whose house
is this ADDRESS?"* is unanswerable — addresses lie (dropped units, colliding slugs, repeating condo
floorplans, fat-fingered streets). The right question is **"which DEAL is this?"** — a deal fingerprints as
**client name + price + close date**, and independent ledgers of the same deals join deterministically.

**The five edges, in matching order:**

1. **SISU↔MLS name edge** — `sisu_transactions` ↔ `hl_srg_mls_deals` by last name + price ±$3k + close date ±20d.
2. **The MLS row's own client name** (`client_first`/`client_last`).
3. **Price+date-unique (cross-side)** — when exactly ONE listing in the book carries the fingerprint, **with
   the ADDRESS-CONTRADICTION VETO** (differing street numbers reject the match — this un-glued 27 silent
   mispins the day it landed).
4. **The FUB person-ID link** (`hl_fub_sisu_link`) — immune to name-spelling drift.
5. **Child-row fingerprint placement** for off-market deals, with the **corrupt-date rule** (pre-2010 child
   dates are a known corrupt class → price must be unambiguous within the client).

**Tiers:** both name edges agree → GREEN · one edge → YELLOW · none → RED (off-market/referral = expected,
not an error). **PENDING = CLOSED** (SISU died 2026-06-19; pending rows froze).

**The three hops — no similarity matching anywhere:**

> **CLIENT** →(name+price+date)→ **MLS#** →(history stamp)→ **HLID** → the card.

**The LLM law:** an LLM **never assigns identity** — keys assign identity. Its jobs are the dossier prose,
fact extraction from raw sources, and structured verdict *proposals* on residue. **It proposes, code
disposes, a human confirms.**

### The verification engine — trust you can see

Every `build-deal-ledger.mjs --write` run ends with a verification pass that stamps, per placed row:

- **`verified_sources[]`** — which INDEPENDENT sources confirm the client↔house pin (`sisu-addr` ·
  `mls-name` · `sisu-name` · `override` · `zach-verified`).
- **`contradiction`** — set verbatim when SISU's own street number disagrees with the pinned house.

A contradicted house is **NOT fully resolved** — it moves to Needs Resolution with a proposed fix, its
receipt, and a **Verify ✓** button. **SISU failure classes the engine catches:** address typos (transposed
digits) · wrong-field entries (the client's residence typed as the deal address) · signing-price ghosts (a
second row at list price on the contract date) · $0 referral-tracking ghosts · pending-frozen dates.

### The no-dogfood input contract (locked 2026-07-03)

> Zach: *"Make sure it doesn't eat its own dog food… it would render, I'd make fixes, I'd run it again, and
> it would just make fixes upon its rendering before."*

- **ALLOWED inputs:** the deterministic tables · **RAW** comms (`fub.*` texts, emails, calls, notes, stages,
  tags — every one, unabridged) · **HUMAN** verdicts (override reasons, Zach notes).
- **BANNED inputs:** `personality_paragraph`, `transaction_paragraph`, `dossier_facts`, prior stage2 outputs,
  the quarantined `resolver_block`, rendered card notes — **any prior LLM artifact, even "for context."**

Re-runs REPLACE prior LLM fields wholesale. Identity comes ONLY from the ledger.

### Attribution + disposition law

- **The agent waterfall (locked 2026-06-27):** *"NO AGENT = NOT RESOLVED. NEVER 'SRG', NEVER the MLS-listing
  agent, NEVER a placeholder."* Order: SISU agent → dotloop contract licensee → FUB Team Exit tag+notes →
  investigation. **Ben Froeschl is never the agent of record.** We keep the departed agent — SRG owns the
  client relationship.
- **The MLS-ID attribution law (locked 2026-07-18)** — supersedes all name-matching on the sale side. The
  ours-test is the **list-side MLS agent ID** ∈ `{ANASPRAD, SPRADLINGGP}`. **Any other lister = lost listing,
  including a departed SG agent.**
- **The disposition engine (locked 2026-07-18):** four deterministic tokens computed from SISU dates + the
  MLS sheet across Residential + Multifamily + Land.
- **The Bazalgette rule:** a lost listing is ONLY a home *we bought for them* that they later sold via a
  non-SRG agent. If we sold it, it is never lost.

### 2026-07-27 · Task 40 — empty-render cards, and WHY A HOUSE GETS TWO HOUSELOOP IDs

**Result: empty-render cards 16 → 8.** The 8 repaired now carry real value and photos ($972,438 · $609,030 ·
$513,555, all with galleries). The remaining 8 have **no live listing at all**, so they are a data-availability
problem now, folded into tasks 46-47.

**The bug had two layers.** `hl_property.identity_key` was written with a **double-suffix**
(`14813 w 150th pl place`, `9627 kessler street street`), so a home and its own listing were keyed to two
different addresses. Then when de-fork merged the listings for that address it quarantined the loser — and if
that was the only listing under *this* property, the property was left pointing at a dead row. `getListing()`
skips quarantined rows, so the card rendered blank while a perfect listing sat a few rows away.

<Warning>
**⚑ ROOT CAUSE OF DUPLICATE HOUSELOOP IDs — settled 2026-07-27. It is the MLS feed, not our normalizer.**

`hl_property.identity_key` is **UNIQUE** — but **a malformed key does not COLLIDE with the correct one**, so
the constraint never fires and a **second HouseLoop ID is minted for one house, silently.** The malformed
string arrives straight from Heartland, verified in `hl_srg_mls_deals`:

| What the MLS sent | What we minted | Its twin |
|---|---|---|
| `14813 W 150TH PL PLACE` (MLS#2583791) | **HLID100257** | HLID149137 — "14813 w 150th place" |
| `9627 KESSLER STREET STREET` | **HLID100280** | HLID326937 — "9627 kessler street" |

**The fix is to collapse a repeated suffix at INGEST** — but only MATCHING pairs (`pl`+`place`,
`st`+`street`). ⚠️ **`TERR COURT` and `ST COURT` are REAL Kansas City street types** and must never be
collapsed.

**And stop exact-string matching.** `tools/houseloop-cards/resolve-address.mjs` narrows the way a search box
does — house number → street stem → unit — and stops at ONE home. When two rows survive for one address it
**reports the duplicate instead of minting a third**.
</Warning>

**Zach's merge rule (locked):** when two IDs describe one house, **the CORRECT address wins; among equally
correct, the OLDEST wins** (it has been in the wild longest — shared links, Google, old emails). The loser
**always** aliases forward via `hl_hlid_alias` so no URL 404s. For a condo, the record carrying the real unit
is the correct one even if it is newer.

**Repaired from MLS truth** (`hl_srg_mls_deals` — MLS# is address ground truth):

- **7 garbage unit hashes.** Two leaked template variables — `#F320a52c6` and `#776f18ccb` — had been parsed

- **4 property ZIPs**, each MLS-confirmed. 2 more were vetoed by the guard below.
