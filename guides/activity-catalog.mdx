**In the app:** Settings → **Activity Catalog** (new — sits directly above Trigger Events)

<Info>
**THE LAW (Zach, 2026-07-27): the Activity Catalog is the superset. Trigger Events is a filtered view of it.**
Every single thing that can happen in the CRM — a lead saving a home, an agent adding a note, Myli learning a
fact, a deal going under contract — is ONE row here. A per-row toggle promotes it into a **Trigger Event**; a
trigger's **category** runs a **Playbook**. There is no second table and no second list. If it is not in this
catalog, it cannot be automated, and today that is why 35 real activities are dead ends.
</Info>

## The model in four lines

```
ACTIVITY CATALOG      every single thing that CAN happen          69 rows
      │               (lead · agent · Myli · transaction)
      │  toggle: "can this start automation?"
      ▼
TRIGGER EVENTS        the subset that can                          34 today
      │               each carries a CATEGORY
      ▼
PLAYBOOK              the category's playbook runs
      │
      ▼
TOOLS                 the playbook's hands (send, book, tag…)
```

The last two layers are the machines Adam is building (`playbooks, not workflows`). This page owns the **first**
one — the inventory those machines draw from.

<Note>
**Why this page had to exist (the autopsy, 2026-07-27).** "Trigger event" was used as the name for *the thing*,
but it is really the name for *the wiring on the thing*. So anything without wiring had nowhere to live — and a
second, parallel list grew in code to hold what actually happens. Measured live: **69 activity kinds in code, 90
trigger events in the database, and only 17 share a name.** `save_home` and `property_saved` are the same event.
So are `property_view`/`property_viewed`, `behavior_high_intent_buyer`/`insight_high_intent_buyer`,
`deal_closed`/`tc_closed`. **Five hardcoded code maps exist purely to translate between the two lists.** Merging
them into this one catalog deletes those maps.
</Note>

## Where it sits in the menu

Each item depends on the one above it — you cannot toggle a trigger for an activity that is not listed, and an
activity cannot arrive through a pipe that does not exist. The menu is the model, read top to bottom.

| # | Menu item | What it is |
|---|---|---|
| 1 | **Lead Integrations** → **Lead Sources** *(nested)* | The pipes, and the brands that arrive through them |
| 2 | **Activity Catalog** | Everything that can happen. The toggle lives here |
| 3 | **Trigger Events** | The toggled subset + its category and per-pipe rules |
| 4 | **Playbooks** | One per goal. Categories point here |
| — | ~~Workflows~~ | Retiring into Playbooks |
| 5 | **Stages** · 6 **Tags** | Lead attributes — they describe the *lead*, not the system |

**Lead Sources is nested under Lead Integrations, never a sibling.** A brand arrives *through* a pipe. Creating a
source from inside its integration is what prevents `fub_zillow` and `zillow_com` existing as two rows for one
brand (the live bug this ordering fixes).

## How to read a row

Every activity carries three facts. **The sections below are generated from them — they are never hand-maintained.**

| Field | Values | Why it exists |
|---|---|---|
| **Who** | `lead` · `agent` · `system` (Myli/derived) | Drives the "what a lead can do" vs "what an agent can do" split |
| **Where** | which integrations can deliver it, or `internal` | An activity we generate has no pipe — nobody sent it, we did it |
| **Trigger?** | on / off + category | On = it appears in Trigger Events and can run a playbook |

Add Realtor.com as an integration and every activity tagged to it appears in the right section **automatically**.
That is the whole point of deriving sections instead of authoring them.

## 📞 Inboxes — the row explosion, and the fix

**Yes: an inbound call, text or email IS an activity.** "Something happened to us" is exactly the test. But the
Trigger Events board today renders **one row per line per event type**, and that is where it breaks down:

```
Zach Spradling (inbox)
  ├ Phone Call Received — Zach's HL Twilio Line
  ├ Phone Call Received — Zach's FUB Twilio Line
  ├ Text Received       — Zach's HL Twilio Line
  ├ Email Received      — zach@houseloop.ai
  └ Email Received      — zach@spradlingrealtygroup.com
```

Eight inboxes × three event types × multiple lines each = **dozens of rows to hand-maintain**, and a new phone
number means new rows in every one of them.

<Warning>
**"The channel is just data" is WRONG, and it was the first answer given here (Zach caught it, 2026-07-27).**
A call to the **sign-call line** and a call to the **transaction coordinator's line** are not the same event with
a different label — they have *different goals*. A model that collapses them cannot ever answer "was this a sign
call or a TC call," which is the whole reason those numbers exist.
</Warning>

### The resolution: the ACTIVITY is one row; the TRIGGER EVENT is (activity × channel scope)

Two different layers, and the distinction lives in the second one:

| Layer | Rows | Example |
|---|---|---|
| **Activity** — the fact type | **3** (`call_received`, `text_received`, `email_received`) | "a call came in" |
| **Channel** — the endpoint, first-class, never collapsed | one per number/mailbox | Sign Call Line · TC Line · Zach's HL Twilio · GMB number |
| **Trigger Event** — activity **scoped to** a channel | as many as you need | "Call received **on the Sign Call Line**" |

**A trigger event names its scope**, and the scope is your choice per case:

| Scope | Reads as | Use when |
|---|---|---|
| **One specific number** | Call received on the Sign Call Line | that number has its own goal |
| **A group of numbers** | Call received on any agent line | they share a goal |
| **Any channel** | Call received | the default that covers everything else |

So you can create an individual trigger event per number **or** group many numbers into one — which is exactly the
requirement. The catalog does not multiply; the **rules** do, and only where behaviour genuinely differs.

<Note>
**Every number is its own door, but not its own lead source.** Zach's framing: *"every single number is almost
like its own lead source — you're not going to call it a lead source, it'll be just the pipe that delivered it."*
Exactly. The number is a **channel**. See [The three fields](#the-three-fields-that-fight-over-one-column) below —
a channel can *carry a default source*, which is how a sign call gets attributed without anyone asking.
</Note>

### What the receptionist playbook actually receives

Because the trigger is scoped, the playbook is handed the specifics and can hold a **per-number goal**:

```
{
  "activity":    "call_received",
  "channel":     { "name": "Sign Call Line", "number": "…", "kind": "phone" },
  "inbox":       { "name": "Company Inbox", "assigned_to": "…" },
  "integration": "houseloop",
  "source":      "Sign Call",          // the channel's default attribution
  "lead":        null                   // unknown caller — this call may mint one
}
```

One playbook (**AI Receptionist**), many goals, selected by channel: a sign call needs the address they are
standing in front of; a TC line call needs the file it is about; an agent's line needs a message taken. **Same
playbook, different goal per door** — which is what makes it a playbook rather than a workflow.

### Your AI receptionist, end to end

This is the closed loop, and it works without a single new table:

| Step | What happens |
|---|---|
| **1. Toggle** | Turn `call_received` ON in the catalog → it becomes a trigger event |
| **2. Scope** | One default rule: **any channel** → the *AI Receptionist* playbook. (Add a per-line rule ONLY where a line should behave differently — most won't) |
| **3. Payload** | The trigger hands the playbook the facts: which **channel**, which **inbox**, who is **assigned**, the **caller**, and the lead if we know them |
| **4. Goal** | The playbook owns the judgment: *answer, qualify, disposition, book* |
| **5. Tools** | The playbook draws from the **Toolbox**, bounded by its permissions |
| **6. Loop** | Every tool call writes an **activity** — which can itself be a trigger |

**One toggle covers every number you own**, because the rule is scoped to "any channel" by default. You are not
turning on thirty things; you are turning on one thing and letting the channel ride in the payload. That is the
difference between a system that scales to a hundred lines and one that needs a row per line.

## The three fields that fight over one column

Channel, integration and source are **three different questions**. Today they are crammed into one `source`
column, which is why the sources list has phone lines sitting next to Zillow, and why 5 of 34 leads already
carry a label that contradicts what they actually point at.

| Field | The question | Examples |
|---|---|---|
| **Channel** | *Where did they reach us?* | Sign Call Line · zach@houseloop.ai · the website |
| **Integration** | *Which system carried it?* | HouseLoop · Follow Up Boss |
| **Source** | *How did they hear about us?* | Zillow · ChatGPT · Referral · Sign |

### Worked example — the ChatGPT call

Someone rings the company line. You ask how they heard about you. They say ChatGPT.

| Field | Value |
|---|---|
| Channel | Company Line (913-320-0906) |
| Integration | HouseLoop — we took the call ourselves, no Follow Up Boss involved |
| Source | **ChatGPT** |

**A source does not need an integration.** ChatGPT is pure attribution — nobody integrates with it, you simply
asked. That is legitimate, and the current schema fights it by forcing every source to belong to a platform.
Note also: **"Company phone number" is not a source** — it is the channel. It is filed as a source today, which
is why phone lines appear in the source list.

### The channel supplies a default source

This is what makes attribution work without interrogating anyone:

| Channel | Default source | Overridable? |
|---|---|---|
| Sign Call Line | Sign | rarely |
| Google My Business number | Google My Business | rarely |
| Company Line | *(none — ask)* | **yes → "ChatGPT"** |
| Website | HouseLoop Organic | yes |

A call to the sign line is attributed to **Sign** automatically. A call to the general line has no inherent
source, so you ask — and the answer **overrides** the default. One rule, no guessing.

### Why this makes Zillow-direct free

Zillow arrives through Follow Up Boss today. When a direct integration is added later:

- **Source** stays **one row** — Zillow. Same row, same reports, same history.
- **Integration** on new leads flips from Follow Up Boss to HouseLoop.
- **Zero new rows, zero code changes**, and *"show me everything from Zillow"* keeps working across both eras.

That is impossible today, because the source key is literally `fub_zillow` — the pipe is welded into the brand's
identity, so a second pipe needs a second brand row (`zillow_com`, which already exists, orphaned).

# The rules that keep it true

## 1. One name per thing

**The 17 duplicate pairs are the bug.** An activity and its trigger must share a key. Where they differ today, the
**activity's name wins** — it is what the feed, the badges and the lead timeline already read, and it is the one a
human recognises (`save_home`, not `property_saved`).

<Warning>
**Do the foreign keys BEFORE any rename.** The event dictionary has **zero foreign keys** — every reference to an
event is unvalidated text. **244 notifications (17%) already point at events that no longer exist**, and nothing
ever errored. A rename today adds silently to that pile. Keys first, then renames become a database operation
that either succeeds completely or fails loudly.
</Warning>

## 2. Categories are derived, never invented

A **category is a goal**, and a goal is a playbook. Categories are named **from the catalog**, when a playbook
actually needs one — never designed as a separate list, which is how a third vocabulary starts.

**Today there is exactly ONE category**, because there is exactly one playbook being built:

> **Tour** — the goal is *"get them in a house."* It covers `tour_request` from HouseLoop, `tour_request` from
> Follow Up Boss, and `virtually_toured`. **One category, three activities, one playbook.**

This is also the test of the model: if the tour playbook can be driven by a **category** rather than by three
separate wirings, the design holds. Better to prove that on one playbook than on twelve.

## 3. The maintenance rule

- **New activity** → add ONE row here, with its who / where. It appears in the right section automatically.
- **Want to automate it** → flip the toggle, give it a category. It appears in Trigger Events.
- **New integration** (Realtor.com direct) → tag the activities it can deliver. **No new table, no new page.**
- **Never** create a parallel list of event kinds in code. That is the exact defect this catalog replaces.

## 4. What a section is NOT

Sections are **generated** from `who` + `where`. Do not hand-author a section, and do not add a `section` column —
that is a second place to remember, and it will drift the way the two event lists did.
