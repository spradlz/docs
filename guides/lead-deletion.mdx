## What is true today

A lead can leave your view three different ways, and they are **not** the same thing.

| | What it does | Who | Reversible |
|---|---|---|---|
| **Trash** | `status = 'trashed'`. Gone from your world. History kept. Never blocks anybody. | Any agent | Yes |
| **Hidden** | `status = 'hidden'`. Not a separate job — but still fully reachable. | Any agent | Yes |
| **Block** | The number cannot call, text, or iMessage you. Deliberate, for harassment. | Any agent | Yes |
| **Hard delete** | The record is destroyed. Cannot be restored. | **Owner only** | **No** |

<Warning>
**Hidden is not a quiet trash, and the difference is the whole point.** Trash means *gone from your
world*. Hidden means *not a second job*: it removes somebody from the leads table, the queues, the
counts and workflow enrolment, and it removes them from **nothing else**. A hidden person still
receives texts, email, search alerts and home-value reports; their tour requests, replies and property
views still arrive, still notify, and land on the **primary lead's** page attributed to them.

Zach, 2026-08-06: *"i still need these leads to receive comms, to make comms, to receive search alerts,
to receive home value alerts. basically the only thing they need to be is HIDDEN FROM VIEW FROM A
LEADS TABLE, but i have to be able to text, email, etc."*

The two questions live as two predicates in `lib/leads/workable.ts` and must never be collapsed into
one: `workableLead()` (may we put WORK on them — active only) and `contactableLead()` (may we SEND to
them — active **and hidden**). Applying the first to a send path silences exactly the alerts a hidden
household member is switched on for, and it looks like a broken toggle rather than a wrong gate.
</Warning>

The model deliberately mirrors Follow Up Boss, because FUB is the system of record and the two must never
disagree about what "deleted" means: in FUB, trash hides and restores, and a real delete is permanent and
owner-only.

**Trash never blocks, and blocking never trashes.** They are separate deliberate acts. A trashed lead who
calls or texts again **resurfaces** — trash means hidden, not gone.

<Warning>
**Trash hides a lead from your TABLE, never from the matcher.** If a trashed person comes back, the system
must still recognise them so they land on their own record with their history. A gate on the matching path
turns a returning person into a **duplicate** while the original sits orphaned. This is the single most
important rule on this page.
</Warning>

## Trash — the reversible one

Trash sets `hl_leads.status = 'trashed'` **and** `deleted_at`. Nothing is destroyed. The trash bin lives
at `/m/trash` (`app/api/m/trash/route.ts`) and supports list, restore, delete-one-permanently, and
empty-trash; the desktop CRM reaches the same endpoint through the trash-can icon on the leads toolbar.

<Note>
**Trash became a real STATUS on 2026-08-06 (migration `0680`).** It had been a timestamp that several
surfaces *read as* a status while the status dropdown offered "Trashed" as though it were one — Zach:
*"why isn't trash a status? it needs to be a fucking status, otherwise this is vibe coded, because it
is in the status dropdown."* He was describing one word in the UI standing for two different questions
in the code, which is the same defect class as the notification `new_message` outage the same week.

The two columns can never disagree, because the migration added the invariant rather than trusting
writers to keep them in step:

```sql
ALTER TABLE hl_leads ADD CONSTRAINT hl_leads_trashed_pairs_with_deleted_at
  CHECK ((status = 'trashed') = (deleted_at IS NOT NULL));
```

**Hidden deliberately does NOT pair with a timestamp.** A trashing is an event and has a moment; hiding
is a household arrangement and has none. Inventing a `hidden_at` would be a second column carrying a
fact the status already holds.
</Note>

**Nothing in the trash ever expires** — Zach, 2026-07-25: *"let's not do the auto delete… I don't want
that."* There is no retention window and no sweeper. A trashed lead sits untouched until a human acts.

Trashing is `DELETE /api/leads/[id]?soft=1` (optionally `&block=1`), which lives on the main leads route so
the mobile app and the desktop CRM share one code path and can never disagree about what "deleted" means.

<Note>
**The desktop trash shipped 2026-08-06.** The leads toolbar carries a trash-can icon with a live count;
opening it lists every trashed lead with the date it was trashed and a **Blocked** chip where the number
is also on the blocklist, and offers Select-all, Restore and Delete-permanently. Filtering the leads
table to **Status: Trashed** shows the same two facts as a view-scoped **Trashed** column — restoring
somebody whose number is still blocked should never be a surprise.
</Note>

## Block — stopping contact

Blocking writes the number to `hl_blocked_numbers` (`lib/phone/blocklist.ts`). It is enforced at the three
**contact** doors:

| Door | What a blocked caller gets |
|---|---|
| Inbound call (`app/api/phone/webhooks/voice`) | TwiML `Reject` — the call never connects |
| Inbound SMS (`app/api/phone/webhooks/sms`) | Empty TwiML — silently dropped, no lead minted |
| Inbound iMessage (`app/api/bb/inbound`) | Dropped, no lead minted, no notification |

Unblock in Settings → Phone. When the contact has a real name, the confirm names them, so blocking an
actual lead is always deliberate rather than a reflex (`lib/leads/blockable.ts`).

<Warning>
**Blocking only half-works today, and this is the known gap.** It is checked at the three contact doors
above and at **zero** of the four doors that CREATE a lead — website registration, the Follow Up Boss
import, `mint-phone-lead`, and the manual add. So a blocked spam caller genuinely cannot ring you, and
still lands back in the table on the next FUB sync. Measured 2026-08-06.
</Warning>

## Hard delete — owner only, permanent

Hard delete destroys the record. It is gated to the `owner` role (migration `0648`), one tier above admin.

<Warning>
**Rule #0 applies.** A hard delete is destructive by design and the owner gate is the product. Any
**backfill or sweep** that hard-deletes in bulk needs Zach's typed approval naming the target — the owner
gate covers a human deleting one lead, not a script deleting many.
</Warning>

### The two tombstones

A hard delete must write **both** guards, or the person resurrects through whichever one was forgotten.

| Tombstone | Database | Keyed on | Guards against |
|---|---|---|---|
| `hl_deleted_leads` (mig `0649`) | CRM | `fub_person_id`, phone, email — any signal | The **FUB import** re-creating them |
| `hl_deleted_web_emails` | Website | email | **Magic-link** resurrection |

**The CRM tombstone is not about barring humans.** You cannot delete a person in Follow Up Boss, so when a
lead is destroyed here the next sync sees them, finds no match, and re-creates them with every field
intact. The tombstone tells the import to skip them permanently. Barring a human is what **Block** is for.

A hard-deleted person who returns under their own steam comes back as a **stranger with a blank record**,
which is honest — the old one was destroyed.

<Note>
`hl_deleted_web_emails` guards a subtler hole: a magic-link token is a forever `HMAC(email)` with no
expiry, so a purged user's old link would silently re-create the account. The tombstone is written
**before** the delete for exactly that reason.
</Note>

## The purge sequence — `purgeLead()`

All purge logic lives in one function, `lib/leads/purge-lead.ts`. **Never hand-roll a lead purge with raw
SQL** — a hand-written `DELETE FROM hl_leads` skips every step that has no lead FK, which is exactly how a
"deleted" lead leaves an orphaned website identity that blocks re-registration.

Callers today: `app/api/leads/[id]`, `app/api/leads/bulk`, `app/api/m/trash` (delete-one and empty-trash),
and the test harness `lib/test-harness/audit.ts`.

1. **Snapshot** the lead's `id`, `email`, `phone` — these drive the explicit steps.
2. **Pixel tables, anonymously aware.** `hl_pixel_event` and `hl_pixel_visitor` have no FK to `hl_leads`
   (a visitor is anonymous-first). Deleting `WHERE lead_id = $id` alone **misses the anonymous events**
   recorded before signup, which then re-link by email on the next registration and show as ghost views on
   a brand-new lead. The purge deletes by the lead's email-linked visitor ids, anonymous rows included.
3. **Polymorphic tables.** `hl_notes` keys on `entity_type` + `entity_id`, not a FK.
4. **Phone-matched inbound.** `hl_inbound_messages` links by phone, not `lead_id`. Normalised to the last
   10 digits — the same normalisation `hl_blocked_numbers` and `hl_deleted_leads` use. **One phone rule in
   this estate, not three that drift.**
5. **`DELETE FROM hl_leads`** — every FK referencing `hl_leads.id` is `ON DELETE CASCADE`, so one delete
   wipes the dependents. 51 `hl_` tables carry a `lead_id`; the guard confirms all are covered.
6. **Cross-database website purge** — `deleteWebUserByEmail()` against `HL_WEB_DATABASE_URL`, which
   tombstones the email first, then deletes the `User` (whose own FKs cascade).

<Warning>
**An orphaned website `User` row is not harmless — it silently blocks re-registration.** If a leftover row
carries a name and phone, the site treats the next sign-in as a returning complete user, skips the
complete-profile step, and never calls the CRM lead-intake. The person gets a website account, **no CRM
lead, and no registration door fires**. Step 6 is not optional cleanup; it is what makes re-registration
work. Learned 2026-07-08 when a raw-SQL purge skipped it.
</Warning>

## The guard — why you never have to remember

`tools/lead-purge-audit.mjs` reads `information_schema` and **fails (exit 1)** if any `hl_` table has a
`lead_id` covered by neither an `ON DELETE CASCADE` FK nor the explicit allow-list handled inside
`purgeLead()`. It runs on every migration. A new lead-referencing table can never silently orphan.
