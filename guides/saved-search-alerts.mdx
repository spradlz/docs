### Login: the binding problem is BUILT, and there are now two doors

The doc below calls the magic-link binding fix *"solved on paper"* and gates sending on it shipping.
**It shipped.** Read the sections below with that in mind:

- **Magic link is now one-time and burned server-side.** Redemption happens only inside the NextAuth
  `magic-token` provider's `authorize()`; `GET /api/auth/magic/preflight` is a read-only status oracle
  (`valid | used | expired | invalid`) so the landing page can route to silent login, the identity-conflict
  interstitial, or a friendly expired page — without redeeming. A forwarded or bookmarked URL is dead, which
  was the precondition this doc set before anything could be mailed.
- **A second door shipped 2026-08-12: phone-code (SMS one-time-code) login.** `POST /api/auth/phone/start`
  → `/verify` (`lib/auth/phone-otp.ts`, `phone-ticket.ts`). Only the SHA-256 **hash** of the 6-digit code is
  stored, 10-minute expiry, 5-attempt cap, consumed exactly once, 30-second per-phone resend cooldown,
  `crypto.randomInt`. **Phone is a contact point, not an identity** — the CRM owns the `hl_leads`
  disambiguation and the website User is resolved/minted only after a code checks out.

So where this doc says a lead can only own a search with a website account, note the account can now be
established by a code to their phone — no email, no password, no forwarded-link risk.

updated faster, with the tour button pointing at us. An agent builds the search on the real website in
under a minute, the lead gets it by text, and **they never register, never pick a password, never see

paper: **the link becomes a one-time ticket and the session becomes the credential** (rolling 90 days,
per-device, revocable) — so a forwarded or bookmarked URL is dead rather than a permanent key. And the
sequencing that follows from it: **minting silent accounts is free and unblocked; SENDING anything is
gated on one-time + expiry shipping first.** We do not mail 1,710 permanent bearer tokens.

### 🔒 Laws locked — do not re-litigate

**IDENTITY** (full write-up: artifact `9f951cca`)
- **A phone number is a CONTACT POINT, not an identity.** Identity is an opaque minted id; contact points
  resolve TO it — the same principle as HLID for homes.
- **NEVER a unique constraint on a phone number, anywhere.** `guides/lead-deduplication` is explicit that
  shared numbers are legitimate. A first attempt DID add one and would have permanently blocked a second
  spouse from having an account — caught by Zach, reverted, and proven fixed.
- **The cross-database join is `User.leadId` = `hl_leads.id`.** The website account stores **no copy** of
  any contact value for identity purposes. No copy, no drift.
- No lead MERGE machinery exists, so `hl_leads.id` never dies. **If merge is ever built it needs an alias
  table mirroring `hl_hlid_alias`.**

**TAXONOMY** (Lee's, enforced in code — mig 0464-0472)
- `hl_trigger_events` is THE list; 6 FKs enforce every reference; `logActivity({kind})` is typed to it so
  **an invented kind does not compile**; `npm run test:event-kinds` fails on drift.
- **Adding a kind = add the ROW, then `npm run gen:event-kinds`. That is the only door.**
- **Naming law: `object_verbPast`** — never `property_`. ⚠ The example keys here are STALE: the live
  catalog key is **`saved_search_created`** (`lib/activity/catalog.generated.ts:147`), not `search_saved`.
- **Ping Lee before touching the render catalog or `hl_trigger_events`** — he rebuilt both. ⚠ `activity-badges.ts`
  no longer exists; the ONE reader is now `apps/houseloop-crm/lib/activity/catalog.ts`, fed from
  `hl_activity_catalog` (see [Activity Catalog](/guides/activity-catalog)).

### The locked design (Zach 2026-07-27)

1. **`Create Search` is an ACTION, not a place** — the 6th tab in the lead-detail composer row, after
   Create Note (`LeadComposer.tsx:21`). Inline, no modal. Captures **name + frequency** only.
2. **It opens the real website** — `houseloop.ai/listings?forLead=<id>`, the same map/filters a buyer uses.
   A fixed banner reads *"Creating saved search for Norma Herra."* **No magic link, no lead session** — the
   lead is named in the URL, never in the session. That is the structural fix.
3. **Save → Verify → Save Search as Agent** — the verify screen reads back name, frequency, criteria and a
   live match count. Saving writes server-side via `createSavedSearchForLead()` with `createdBy='agent'`.
4. **Send-now lives at the END** (there is nothing to link to before the search exists) — a prefilled,
   editable text carrying the magic link, plus optional "email the N matches now" via the existing
   `/api/leads/saved-searches/send`.
5. **Website Activity keeps the saved-search card, view-only** — Edit / Send now / Duplicate / Delete all
   stay. Only the "Create Saved Search as Agent" button and its route are removed.
6. **Phone becomes the account key.** `phone` gains a normalized unique index; `email` becomes nullable.
   The account is minted silently (`findOrCreateWebUserForLead`) — the lead never sees a signup form.
   **Password is set only from inside an already-authenticated session** (arriving via the texted link
   proves phone ownership); setting a password from a bare phone number would let anyone claim a lead's
   account. "Text me a link" is the fallback for anyone who never sets one.

### The thesis (Zach, 2026-07-26) — say it out loud before designing anything

Zillow inquiries arrive through Follow Up Boss. **Those people have never visited houseloop.ai and have
never registered.** The saved search is the lever that moves them off Zillow and onto our platform:

1. The agent creates a saved search **for** the lead, on HouseLoop.
2. The agent sends the lead a **magic link**.
3. The lead clicks it and is signed in **as themselves** — no registration, no password, no friction.
4. They see their search: often **more homes than Zillow, updated faster**.

**So the magic link is the PRODUCT, not a bug.** Structurally the lead never needs to create an account.
That was the whole thesis and it is sound.

### What is actually broken (narrow, not the whole flow)

The **agent** rides the **lead's** magic link in order to author the search. `Create Saved Search as Agent`

### ✅ 2026-08-04 — DECIDED: the link is a TICKET, the session is the credential

<Warning>
**THE BUG, NAMED PROPERLY: our token IS the credential.** Magic tokens are `HMAC(email)` with **no expiry
and unlimited reuse** (`apps/houseloop-web/lib/auth/magic-token.ts`), so the URL itself is a permanent
key — forwarded emails, shared screens, browser history. Anyone holding it *is* that person, forever.

Zach, 2026-08-04, from having it happen to him: *"I had one attach to my browser and it was like a
horsefly I couldn't get off me."* He was not carrying a session — he was carrying the password in his
URL bar. Acceptable-ish internally; **not** acceptable mailed to 1,710 past clients.
</Warning>

**THE DECIDED ARCHITECTURE — separate the LINK from the SESSION.** This is what Substack, Notion and
Slack do, and it kills the horsefly by construction:

| | Today (broken) | Decided |
|---|---|---|
| **The link** | permanent credential, unlimited reuse | **one-time exchange ticket** — short-lived (24h by text, 7d by email) and **burned the instant it is used** |
| **The session** | does not exist as a separate thing | **the credential.** A rolling 90-day cookie, refreshed on every visit |
| **Forwarded link** | the recipient becomes that person, permanently | dead — *"this link has already been used"* |
| **Getting unstuck** | impossible, the URL still works forever | log out. The session is per-device and revocable |

**"Stay logged in" needs no native app.** A rolling 90-day session pushes its own expiry out on every
visit, so a client who checks their home value monthly **never sees a login screen again** — the same
reason nobody re-logs-in to Amazon.

**And a PWA beats an app for this.** *Add to Home Screen* gives an icon, full-screen chrome and a
persistent session: roughly 95 percent of the app benefit, no App Store, and nobody has to install
anything. **A native app is worth building for exactly one thing — push notifications** (*"your home
went up $4,000 this month"* on the lock screen). Ship the PWA first; let the engaged clients prove
whether push earns the build.

## The origin taxonomy (`createdBy`: system | client | agent)

Every saved search carries exactly one **origin** — who created it. It drives the CRM grouping,
the copy, and the per-lead counts. (Zach 2026-07-01 — replaces the old `lead | agent`.)

| Origin | Who made it | How |
| --- | --- | --- |
| **`system`** | HouseLoop, automatically | The registration auto-seed (`seedStarterSavedSearch`) derives a starter search from the homes the lead actually viewed and inserts it silently. *(Was mislabeled `agent`.)* |
| **`client`** | The buyer themselves | They clicked **Save Search** on `/listings`. *(Was `lead`.)* |
| **`agent`** | A HouseLoop agent, FOR the client | The **Create Saved Search as Agent** flow (below). |

In the CRM lead-detail **Searches** tab, the three render as **Agent Searches / Client Searches /
System Searches**. `GET /api/leads` returns `agent_search_count`, `client_search_count`,
`system_search_count` (legacy `lead`/NULL rows count as client).

## The match engine (the `firstSeenAt` law)

`sendSavedSearchAlert(savedSearchId, opts)` in
`apps/houseloop-web/app/api/saved-searches/alert/logic.ts` is the ONE engine every path uses.

1. Loads the `SavedSearch` row + the owner's email (JOIN on `User`). Skips if inactive, no
   delivery email, or no user email.
2. Parses the search's own `searchUrl` through the **exact** engine the website uses
   (`parseSearchParams` + `searchFromDb`), so the alert matches what the buyer sees on
   `houseloop.ai` — including feature filters (`feature=pool`, etc.).
3. **Digest floor (`effSince`):** keeps only homes whose **`firstSeenAt >= effSince`** — i.e. the
   homes that arrived in *our feed* in this window. **Not `listDate`.** `firstSeenAt` is set once
   on create and never updated; it is the source of truth for "newest." `listDate` is the MLS
   market date (date-only) and must never gate alerts (see Dev Log 2026-06-28).
4. Resolves cover photos from `Listing.photos` (`{ primary, all, count }`).
5. **`skipSend` (the default for every automated path):** compute the matches and **return** them
   — send nothing, stamp nothing. The CRM workflow owns the email. The legacy direct-Resend send
   (`HouseLoop <updates@houseloop.ai>`) remains only for the manual `/api/saved-searches/alert`
   HTTP wrapper.
6. On a real send (non-`skipSend`): updates `lastAlertSentAt`, `lastMatchCount`, `totalMatchesSeen`.

<Note>
The alert always queries our **own `Listing` table** (centerbeam DB), never Repliers live. Results
reflect our cached MLS data, as current as the last Repliers webhook/sync. The `/listings` **"Newest
Listed"** sort orders by `firstSeenAt` (feed-arrival) with no status tier, so the newest home — even
a coming-soon one — always leads. Same clock everywhere.
</Note>

## The send chain (compute → emit → workflow)

`emitDigestDue()` (in `saved-search-alert.ts`) runs the match query with `skipSend`, and if there
is at least one new match, emits:

```
houseloop/saved-search.digest-due
  { email, match_count, search: { name, url, criteria, matches[] } }
```

`match_count` is the **new-since-last** count; `search.matches[]` is those **exact** homes (the
`topMatches`, up to 4). The CRM consumes this in
`apps/houseloop-crm/lib/inngest/functions/saved-search-digest-due.ts`, resolves the lead by email,
and fires the **`sys_saved_search_digest`** ("Saved Search Listing Alerts") workflow — whose
branded email step is the only thing that actually sends. After emitting, the watermark advances
(`lastAlertSentAt = now()`, `lastMatchCount = matches`) so the next tick only picks up newer homes.

<Note>
**Count == cards (Zach 2026-07-01).** The digest subject says "N new homes." The branded email's
`{{search.matches}}` cards render from the carried **`matches_json`** (the exact new-since-last homes),
NOT a re-query of the full criteria — so the count and the cards are the same set. The full-criteria
`total` still drives the "See all {total} homes that match your search" footer, and the omit-zero
"explore the rest" block (`{{search.other_results}}`) links to *Listed in the last 24 hours*,
*Coming soon*, etc. Card rendering: `apps/houseloop-crm/lib/workflows/execute-step.ts` (`fillSearchMatches`).
</Note>

## Inngest functions

All live in `apps/houseloop-web/lib/inngest/functions/saved-search-alert.ts` and are registered in
`apps/houseloop-web/app/api/inngest/route.ts`.

| Function ID | Trigger | Audience / role |
| --- | --- | --- |
| `saved-search-on-create` | event `houseloop/saved-search.created` | **NO-OP.** The *New Lead — Saved Search* door workflow owns the on-create email. |
| `saved-search-instant-check` | **event `houseloop/idx.event`** (a new/changed listing) | `alertFrequency = 'instant'` — fires the hour a matching home hits our feed |
| `saved-search-daily-alert` | cron `TZ=America/Chicago 0 8 * * *` (8am CT daily) | `alertFrequency = 'daily'` |
| `saved-search-weekly-alert` | cron `TZ=America/Chicago 0 8 * * 1` (Mon 8am CT) | `alertFrequency = 'weekly'` |
| `saved-search-monthly-alert` | cron `TZ=America/Chicago 0 8 1 * *` (1st, 8am CT) | `alertFrequency = 'monthly'` |

<Warning>
`saved-search-instant-check` is **event-driven, not a cron.** It runs on every
`houseloop/idx.event` (emitted by the Repliers webhook at
`apps/houseloop-web/app/api/repliers/webhook/route.ts` on `listing.created` / `listing.updated`).
For each instant search it checks for homes that arrived since the last send. A **never-sent**
search uses a 7-day catch-up floor for its first run; a sent search uses its `lastAlertSentAt`
watermark, so arrivals between checks are never missed and never double-sent.
</Warning>

### The digest gate

Every cron + the instant check first calls `digestGateActive()`, which reads the CRM's
`/api/workflows/digest-gate`. The gate **fails open** (treats unreachable as active).

<Warning>
🛑 **CORRECTED 2026-08-12 — PAUSING THIS WORKFLOW DOES NOT STOP ALERTS.** This section used to say that
pausing **Saved Search Listing Alerts** in Lead Flow makes every alert path go quiet. **That is wrong, and
acting on it means believing you have stopped emails to real clients when you have not.**

`sys_saved_search_digest` is **locked infrastructure** (mig `0347_workflow_infrastructure_lock.sql`:
`is_locked=true` means "NOT user-toggleable and always active"). The gate reads:

`app/api/workflows/digest-gate/route.ts:29` → `active: wf?.is_locked === true || wf?.status === 'active'`

So `is_locked` short-circuits `status` entirely. You can PATCH the workflow to `paused`, the row will
reload reading "paused", and **the digests keep going out** — measured at 81 sends since 8/03 while the UI
showed paused. To actually stop them today you must disable the crons or the gate, not the toggle. The
control itself is an open P0 in the
[Enterprise QA Findings Ledger](/command-center/enterprise-qa-findings) — it is either "locked means the
control is disabled and can never read paused", or "status gates everyone"; today it is neither.
</Warning>

## How a saved search is created

Three creation paths, each with its origin — and all end with the CRM sending the email:

**1. Client self-serve (`createdBy = 'client'`).** Buyer clicks **Save Search** on `/listings`.
`POST /api/saved-searches` creates the row (defaults: `alertFrequency = 'instant'`,
`deliveryEmail = true`, `createdBy = 'client'`), runs `sendSavedSearchAlert(skipSend, isConfirmation)`
to compute the first-look matches, and calls `pushLeadToCRM({ action: 'saved_search', ... })`. The
CRM's **New Lead — Saved Search** door workflow sends the branded confirmation + matches email, the
Myli personal email, and the text.

**2. Registration auto-seed (`createdBy = 'system'`).** When a lead registers and we have real
browsing signal, `seedStarterSavedSearch()` in
`apps/houseloop-crm/app/api/integrations/website/lead-intake/route.ts` derives a starter search
from the homes they actually viewed (`deriveSearchCriteriaFromPixel`) and raw-inserts an
`instant`, `createdBy = 'system'` row into the web `SavedSearch` table. It is a silent insert (no
on-create email) — the `saved-search-instant-check` (with its never-sent 7-day catch-up) delivers
the recent matches on the next `idx.event`, then real-time after.

**3. Agent-on-behalf (`createdBy = 'agent'`).** A HouseLoop agent clicks **Create Saved Search as
Agent** on the CRM lead-detail Searches section.
`GET /api/leads/[id]/agent-search-link` mints the client's magic link (`signMagicToken`, same
`MAGIC_LINK_SECRET` the website verifies) and returns
`/auth/magic?ml=<token>&next=/listings?sort=newest&asAgent=1`. Opening it logs the agent into
`houseloop.ai` **as the client** and lands on `/listings` in agent-on-behalf mode. The agent picks
filters like the client would; `SaveSearchButton` reads `?asAgent=1` → `SaveSearchModal` shows
agent-focused copy → `POST /api/saved-searches { createdBy: 'agent' }` saves the search FOR the
client (and fires the same confirmation + alert workflow).

## SavedSearch data model

```prisma
model SavedSearch {
  id               String    @id @default(cuid())
  userId           String
  name             String
  searchCriteria   Json      // { city, state, zip, minPrice, maxPrice, beds, baths, ... }
  searchUrl        String    // e.g. "/listings?city=Olathe&minPrice=400000&minBeds=5"
  alertFrequency   String    @default("instant")  // instant | daily | weekly | monthly | never
  deliveryEmail    Boolean   @default(true)
  deliveryPush     Boolean   @default(false)
  isActive         Boolean   @default(true)
  createdBy        String    @default("client")    // system | client | agent (Zach 2026-07-01)
  lastAlertSentAt  DateTime?                        // watermark — advances on every emit
  lastMatchCount   Int       @default(0)            // homes the LAST alert sent (the RECENT column)
  totalMatchesSeen Int       @default(0)
  lastOpenedAt     DateTime?                         // Resend engagement (the god-tier card)
  lastClickedAt    DateTime?
  lastEmailId      String?
  createdAt        DateTime  @default(now())
  updatedAt        DateTime  @updatedAt
}
```

`createdBy` values: **`system`** (auto-seeded at registration), **`client`** (self-serve),
**`agent`** (agent-on-behalf). Legacy `lead`/NULL rows read as `client`.

## The Saved Searches surface

`/saved-searches` (and the `/updates` view) render from
`apps/houseloop-web/app/api/saved-searches/enriched/route.ts`, which returns one card per active
search:

| Column | Source |
| --- | --- |
| **RESULTS** | live `totalCount` from the same query the card links to (parses `searchUrl`'s querystring so the count is byte-identical to the listing page) |
| **RECENT** | **`lastMatchCount`** — the homes the *last alert sent* (Zach 2026-06-28: "the recent has to be the homes that were sent"). Was a `daysOnMarket<=1` query that never reflected the email. |
| **STARTED** | `createdAt` |
| **FREQ** | `alertFrequency` |
| **LAST SENT** | `lastAlertSentAt` |

In the CRM, the same data drives the **Saved Searches** card on the lead (the "god-tier" card with
Resend opens/clicks/last-sent/frequency/match count), grouped by origin (Agent / Client / System),
with the **Create Saved Search as Agent** button at the top. The card's count = real saved-search
rows, never website *search* (pixel) events.

## Email template

The branded matches email is rendered + sent by the **CRM workflow** (`sys_saved_search_digest` /
the New Lead — Saved Search door). `{{search.matches}}` = the new-since-last homes (from the carried
`matches_json`, so count == cards); `{{search.match_count}}` = that same count; `{{search.other_results}}`
= the omit-zero "explore the rest" links (last 24h / coming soon / under contract / sold). The website
template `apps/houseloop-web/lib/email/saved-search-alert.ts` backs the legacy manual
`/api/saved-searches/alert` HTTP path only.
