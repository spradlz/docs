<Info>
**This is infrastructure, not decoration.** Zach runs four artifacts on two vertical screens — one per agent
(**Lee**, **Benji**, **Adam**, **Caleb**). Each one is that agent's entire working surface: the plan, the law,
the corrections, the progress bar, and the next thing to do. **The artifact is the session.** If a decision is
not in the artifact, it did not happen; if work is not on the artifact, it is not being done.

This page locks the structure so all four look and behave the same, and so a new agent can produce a correct one
on the first try.
</Info>

## The one sentence

**One agent, one artifact, one canonical numbered list — worked top to bottom until it is done.** When the work
turns out to be standing on something broken, that becomes an **orange rabbit hole** with its PRD *inside the
artifact*, the list is **re-ordered and renumbered**, and the agent continues. At every arc boundary the agent
writes state; at the end the agent reads the artifact back and updates the dev docs it touched.

## Why it exists

Four agents were each inventing their own format. Zach was telling them "go look at the artifact Lee built" —
which is a style reference, not a law, so it drifted. The same failure mode as every other drift we have killed:
**no single definition, so everyone wrote their own.** This page is the definition.

## The anatomy — in this order, every time

A conforming artifact has these blocks, top to bottom. Do not reorder them; do not skip the uncomfortable ones.

| # | Block | What goes in it | Required |
|---|---|---|---|
| 1 | **Header** | Eyebrow · title · date · **who owns it** · the master PRD path | ✅ |
| 2 | **Progress rail** | Sticky bar: `done / total · %` + a Reset button | ✅ |
| 3 | **How we got here** | The origin in plain English — the ONE thing that started it | ✅ |
| 4 | **The law — locked, do not re-litigate** | Zach's decisions, quoted. Nothing here is reopened without him. | ✅ |
| 5 | **Corrections on the record** | **Every mistake the agent made, kept visible on purpose.** | ✅ |
| 6 | **Already shipped** | Done and verified on prod, with migration numbers / commits | ✅ |
| 7 | **Gate** | "No code below this line until sign-off" — the decisions Zach still owes | when blocked |
| 8 | **Arcs** | The work, grouped into landable slices | ✅ |
| 9 | **🕳 Rabbit hole (orange)** | A discovered foundation problem + its PRD, inline | when hit |
| 10 | **Done means all N are true** | The acceptance test, written *before* the work | ✅ |

<Warning>
**Block 5 is not optional and it is not self-flagellation.** "Corrections on the record" is what makes the rest
of the artifact trustworthy. An artifact with no corrections block is an artifact nobody has audited. Every entry
is one line: what was claimed, what was true, what changed as a result.
</Warning>

## The numbering law

**Numbers are positional and DERIVED. They are never hand-typed.**

The artifact's script walks every checkbox in DOM order and stamps `1.`, `2.`, `3.` … as it goes. That is what
makes Zach able to say *"I have not signed off number 12"* and *"we are on 63 of 152"* and have it mean something
exact.

```js
boxes.forEach(function(b, i){
  var n = document.createElement('span');
  n.className = 'no';
  n.textContent = (i + 1) + '.';   // ← derived from position, always
  li.insertBefore(n, b);
});
```

**Why derived and not authored:** when a rabbit hole forces a re-order, every number downstream shifts. Hand-typed
numbers would instantly be wrong and someone would have to renumber 90 items by hand. Derived numbers are correct
the moment the DOM changes. **Same law as the event catalog: one source, generated, never a second hand-maintained
copy.**

<Warning>
**Identity must NOT be the number.** The number changes on every reorder — so persistence, task-manager sync and
Zach's sign-offs must key off a **stable slug**, never the index. See
[The state-loss bug](#the-state-loss-bug-we-actually-hit) below — we hit this for real.
</Warning>

## The ownership law

**Every item has exactly ONE responsible agent.** Not a team, not "Lee/Benji". One name, rendered as a chip on
the row.

- Default: the artifact's owner (set `data-owner="lee"` on the block).
- Override per item when it genuinely belongs to someone else: `<span class="own own-benji">Benji</span>`.
- **If two agents are needed, it is two items.** An item with two owners has no owner.

| Agent | Lane |
|---|---|
| **Lee** | infra · glue · deploy · cross-app · data model |
| **Adam** | CRM (`apps/houseloop-crm/**`) |
| **Benji** | Website (`apps/houseloop-web/**`) |
| **Caleb** | data · intel · scrapers · reconciliation |

## The rabbit-hole protocol

A **rabbit hole** is not a distraction and it is not a failure. It is what happens when you try to ship an item
and discover the floor under it is broken. **Zach's rule: it is not a detour, it is the floor.**

<Steps>
<Step title="Stop and name it">
The moment you find it, say so in the artifact — do not quietly fix it and do not quietly skip the item. Name the
item number that exposed it (*"opened Jul 27 evening, the moment #21 shipped"*).
</Step>

<Step title="Make it an ORANGE block, in place">
`style="border-color:var(--warn);border-width:2px"` on the block, `background:var(--warn)` on its header, and a
`🕳` in the label. **Orange means: this is foundation work that was not planned.** It is visually impossible to
miss on a screen across the room — which is the entire point.
</Step>

<Step title="Put the PRD INSIDE it">
Not a link to a doc nobody opens. The vocabulary, the schema, the diagrams, the laws, the benchmark — **inline,
in the orange block**. The artifact stays the one thing you read.
</Step>

<Step title="Re-order and renumber the whole list">
The hole changes what has to happen first. Rewrite the order so the list reads in true execution sequence, top to
bottom. **The numbers re-derive themselves.** Say plainly what moved and why.
</Step>

<Step title="Reconcile against what you already wrote">
If the hole overlaps an earlier plan, **publish the diff** — a table of *yesterday's plan · today's finding ·
resolution*. Mark laws that CHANGED in red, laws that HOLD in green. **Never silently rewrite a law Zach locked.**
</Step>

<Step title="Continue">
Work the new order. The hole is now part of the plan, not beside it.
</Step>
</Steps>

<Warning>
**Do not let rabbit holes multiply.** Three separate orange blocks accumulated in the Lead Engine artifact before
anyone noticed that **two were the same hole seen at different depths and one was never a hole at all** — it was a
phase of an arc. When you open a second hole, first ask whether it is the same hole. Merge aggressively; one
document means one hole per problem.
</Warning>

## The state protocol

The artifact is the plan. The state files are the **memory** — they are what survives a compaction.

| When | Write | What goes in it |
|---|---|---|
| **During an arc** | `.claude/state/<agent>.lock` | current arc, current item number, what is `🟡 in progress` |
| **End of every arc** | `.claude/state/<agent>-handoff.md` | what shipped, commit hashes, live URL, what is next and why |
| **End of every arc** | `.claude/state/wip/<agent>.md` | the public WIP list |
| **After a rabbit hole is opened** | all three | the new order, so a compacted session resumes correctly |

**The artifact URL goes in all three.** It is the first line of the handoff, so the next session's first action is
to open it.

<Info>
**Why this matters more than it sounds.** After compaction an agent has lost the conversation. If the handoff says
*"open artifact X, you are on item 64"*, the agent resumes exactly. If it says *"continuing the lead work"*, the
agent freelances — and freelancing after compaction is where the worst bugs come from.
</Info>

## Syncing to the Claude Code task manager

**The artifact is the source of truth. The task manager mirrors the CURRENT ARC ONLY.**

This is deliberate and it is the honest design:

- The task list is **per-session** and shows in the sidebar — it is a working set, not an archive.
- A 150-item artifact in the task manager is unreadable and instantly stale.
- **So: at each arc boundary, the agent clears the task list and re-creates it from the arc it is entering.**

| Artifact | Task manager |
|---|---|
| all 150 items, permanent, numbered, Zach-visible | the ~5–10 items of the arc in flight |
| checkbox ticked when Zach signs off | `completed` when the agent finishes + verifies |
| survives compaction (it is a file + a URL) | rebuilt at each arc boundary from the artifact |

**Task titles carry the artifact number** — `#64 Retire platform='inbox'` — so the two can never be confused
about which item is which. That number is the join key between the two systems, and it re-derives from the
artifact, which means the artifact always wins.

<Warning>
**Do not claim these are auto-synced.** They are synced *by protocol at arc boundaries*, by the agent, on purpose.
Any claim of live bidirectional sync would be a lie — the artifact renders in Zach's browser and the task list
lives in the session.
</Warning>

## The closeout — how an artifact ends

An artifact is **not** done when the last box is ticked. It is done when its knowledge has been moved somewhere
permanent, because **an artifact is a working surface, not a dev doc.**

<Steps>
<Step title="Read the whole artifact back, top to bottom">
With every note, correction and rabbit-hole finding. This is a real read, not a skim — the corrections block and
the rabbit-hole PRDs are where the durable knowledge is.
</Step>

<Step title="Update the dev docs the artifact touched">
For each section of the artifact, find the Mintlify guide that owns that topic and fold the finding in. **Docs
Section Discipline applies** — name the section first, edit the existing doc, never create a floating sibling.
</Step>

<Step title="Move laws into the rules, not the docs">
If the artifact locked a *law* (a constitutional "never do X again"), it belongs in `.claude/rules/*.md`, not
only in a guide. The artifact dies; the rule does not.
</Step>

<Step title="Write the final handoff and archive the artifact">
Last handoff entry names the artifact URL, the docs pages updated, and the rules added. Then the artifact is
reference, not a to-do.
</Step>
</Steps>

## The state-loss bug we actually hit

<Warning>
**Persisting checkbox state by ARRAY INDEX loses Zach's sign-offs on every reorder.** The original script saved
`{0:true, 1:false, …}` keyed by position. A rabbit hole re-orders the list — so item 64 becomes item 71, and it
inherits the checkbox state of whatever used to be 71. To avoid *silently wrong* checkmarks the agent bumped the
storage key, **which reset everything Zach had personally ticked.**

**The fix — key by a stable slug derived from the item's own title**, so the number can move freely while the
state stays welded to the item:

```js
function slug(li){
  var b = li.querySelector('.tx b');
  return (b ? b.textContent : li.textContent)
           .toLowerCase().replace(/[^a-z0-9]+/g,'-').slice(0,48);
}
// save:  o[slug(li)] = b.checked          ← survives any reorder
// load:  if (saved.hasOwnProperty(k)) b.checked = !!saved[k];
```

**Never bump the storage key to "fix" a reorder.** Bumping the key is data loss wearing a version number.
</Warning>

This is the same class of bug as everything else this protocol guards against: **identity was implicit
(a position) instead of explicit (a key).** Positions are for display. Keys are for truth.

## The build kit

Copy these verbatim — the four artifacts must look identical.

### Tokens

Use HouseLoop brand tokens only. **No raw hex.** Both themes required (`prefers-color-scheme` **and**
`:root[data-theme]`, because the artifact viewer has its own toggle).

| Token | Use |
|---|---|
| `--navy` `#1B3A8A` | page header — the only navy |
| `--blue` `#2D6DFF` | block headers · progress bar · stars |
| `--warn` `#A65B0B` | **rabbit holes only** |
| `--danger` `#C2263B` | broken / needs-a-decision |
| `--done` `#08674C` | shipped |

### Pills

| Class | Means |
|---|---|
| `p-live` | shipped and verified on prod |
| `p-soon` | in flight |
| `p-need` | needs Zach's explicit go |
| `p-block` | blocked on something else |

### Callouts

`note` (context) · `note warn` (a caution) · `note bad` (a live bug) · `note fix` (the resolution).

### The item

```html
<li>
  <input type="checkbox">
  <span class="tx">
    <span class="star">★</span> <b>The one-line headline</b>
    <span class="pill p-need">needs explicit go</span>
    <small>The evidence. File paths, row counts, migration numbers, the quote from Zach.
    Never "improve X" — always what is true, what is broken, and how you know.</small>
  </span>
</li>
```

**`★` marks a load-bearing item** — one that other items depend on. Use it sparingly; if everything is starred,
nothing is.

## 🧾 THE AUDIT RECEIPT — an item is not checked until it has one

<Warning>
**Locked by Zach 2026-08-03.** *"For every single thing you fix you have to audit and walk it like a user."*
A checkbox means **one** thing: the agent opened the product, used the feature as a human through Playwright,
and wrote down what the machine actually did. **Compiling is not evidence. Typechecking is not evidence. A
passing gate is not evidence.** The receipt is the evidence.
</Warning>

### Why this is not optional

On 2026-08-03 an agent reported the per-document Share modal as built, typechecked, committed and pushed.
It was all of those things. It was also **unreachable** — the modal had state, it was mounted in the tree,
and nothing anywhere called `setShareDoc`. Opening the page for the first time surfaced **three** defects
inside a minute:

| Defect | Caught by |
|---|---|
| The modal had no button — dead code | opening the page |
| The **Done** button was missing (a custom `footer` prop had replaced the submit) | trying to save |
| "Attach PDF to email" promised something the transport cannot do | reading it as a user |

**`tsc` was clean for all three.** That is the whole argument. The typechecker verifies the code you wrote;
only the screen verifies the product you shipped.

### The anatomy, revised

The artifact grows a third region. Same file, same URL, three bands top to bottom:

| Region | What it is |
|---|---|
| **① THE PRD** | The plan, the law, the corrections, the "done means" — everything already specified on this page |
| **② THE CHECKLIST** | One canonical numbered list, 1 → N. There is no cap; a real PRD runs to hundreds |
| **③ THE AUDIT RECEIPTS** | **At the bottom.** One receipt per checklist item, in item order, each carrying its screenshot and its machine evidence |

Item **17** in region ② links to receipt **17** in region ③. If a receipt has no item, it is orphaned; if a
ticked item has no receipt, **it is not ticked** — untick it.

### The seven fields — every receipt, no exceptions

Zach's list, verbatim, in the order you collect them:

| # | Field | What it must contain |
|---|---|---|
| 1 | **What I did** | The literal click path: *"Opened the loop → clicked People on document 2 → typed Dana Reed → chose Lender · Can sign → Done."* Not "tested sharing" |
| 2 | **What happened on the page** | The Playwright screenshot, embedded, plus the sentence a human would say about it |
| 3 | **The activity log row** | The `hl_lead_activity` row it created — `kind`, `title`, `actor_role`. **No row is a finding**, not an omission |
| 4 | **The table(s) used** | Every table written or read — `hl_tc_loop_document_share`, `hl_lead_activity`. Name them |
| 5 | **The variables** | The real values that moved: `permission='can_sign'`, `loop_status_key='lost'`, `meta.toLabel='Lost'` |
| 6 | **Schema-lock check** | The tables you touched, checked against `tools/schema/schema.lock.json`. New table → is it in the lock, the census AND `target-verdicts.json`? New kind → is it in the catalog **and** writable? |
| 7 | **Which item this proves** | The checklist number. A receipt that names no item is decoration |

<Note>
**Field 6 is the one people skip, and it is the one that bites.** Twice in one night a change was "done" while
a companion artifact was not: a catalog kind existed but had no `hl_trigger_events` row, so **every write was
rejected silently**; and migrations were applied while `schema.lock.json` lagged, blocking the whole branch.
Neither was visible in the UI. Field 6 is how you catch the half that the screen cannot show you.
</Note>

### Playwright, and only Playwright

**Use the MCP browser tools against real Chrome** (`mcp__playwright-*`). Never headless — headless is detected
and blocked on any human-facing site (`.claude/lessons/no-headless-browsers.md`).

**Drive it the way a person does.** Real clicks and real typing, because:

- **Scripted value-setting does not register in React.** Setting `input.value` from `browser_evaluate` updates
  the DOM and leaves component state empty — the form then submits **nothing** and looks like it worked. This
  cost a full false pass on 2026-08-03.
- **Navigating straight to a query URL trips bot detection.** Typing into the search box does not. The same
  session got a `403` for URL-hopping and recovered when driven like a human.
- If a control cannot be reached by clicking, **that is the finding** — write it down instead of routing around
  it with a direct API call.

**Verify with your eyes, then with the database.** A screenshot proves the render; a query proves the write.
A receipt needs both, because a UI can lie in either direction — it can show success on a failed write, or
hide a write that happened.

### Running the checklist — the `/loop` protocol

When Zach says **run in a loop**, the agent works the checklist top to bottom, and **one item is one full
cycle**:

<Steps>
<Step title="Build item N">Write the code. Typecheck the WHOLE app, never filtered to your own filenames — filtering hides the files your change broke.</Step>
<Step title="Walk it in Playwright">Open the page. Use the feature as a human. Click the real controls.</Step>
<Step title="Screenshot it">Capture what a user would see, including the failure if it failed.</Step>
<Step title="Collect the seven fields">Activity row · tables · variables · schema-lock check.</Step>
<Step title="Write receipt N at the bottom">Then, and only then, tick item N.</Step>
<Step title="Move to N+1">Never tick ahead. Never batch the walking to the end — that is how three defects hid behind a green typecheck.</Step>
</Steps>

**If the walk fails, the item does not advance.** Fix it, re-walk it, re-screenshot it. **Keep the failing
screenshot in the receipt** — a receipt showing "broken → fixed → proven" is worth more than one that only
shows the happy ending, and it is what makes the audit trustworthy.

### Publishing as you go

Re-publish the artifact after every few receipts — same file path keeps the same URL, so the tab on Zach's
second screen updates in place. He should be able to watch the receipts appear without asking.

Screenshots are inlined as data URIs (the artifact CSP blocks external hosts, so a linked image renders as
nothing). Compress before embedding — raw PNGs make the page unusable on a phone. Generate the receipts region
with a script that reads a manifest and inlines the images, so the payload never has to pass through the
agent's own context.

### The final gate — the screen-walk

The agent's receipts are **the agent's own testimony**. The [Screen-Walk](/how-to/screen-walk) is where Zach
walks the same screens after sign-off and forms his own verdict. It is the last step, it is his, and **it is
not a formality** — every defect in the 7/28 outage was found by Zach looking at a screen while every audit
was green.

Sequence: **agent builds → agent walks + receipts → agent signs off → Zach screen-walks → gate closes.**

## 🔁 THE LOOP TO FULL GREEN — how a PRD actually finishes (locked by Zach 2026-08-03, late)

Zach's words, the night the method was proven on the Lead Engine: *"you work in a loop fixing each item
as you go until the full PRD is signed off fully green."* This section is the exact operating procedure.

### The shape, restated as ONE sentence

**One PRD → ONE continuously-numbered checklist top to bottom → one audit receipt per item at the bottom →
a loop that FIXES as it walks — and the artifact is not done until every item is green or carries an
honest, evidenced state.**

### The exact instructions

<Steps>
<Step title="Write the PRD (band ①)">
The problem, the laws, the rulings, the corrections. Everything the checklist items will cite. History
stays here forever — superseded plans get a strike-banner, never a delete.
</Step>

<Step title="Build ONE checklist (band ②) — a single numbered list, top to bottom">
Not one list per phase. Not a numbered section and an unnumbered "walk". **ONE list in true execution
order**: proven work (checked, citing its receipt) → tonight's workable items → sequenced surgery eras →
decision items (red `p-need`) → team-parked items (owner chips). Duplicates collapse onto their canonical
number. Numbers derive from position; identity is the slug. *"We're on 63"* must mean something exact.
</Step>

<Step title="Work the loop — one item is one full cycle, and the FIX is part of the cycle">
**Fix the code first — a defect found is a defect fixed in the same cycle, never an audit note.**
(Zach's correction, 8/3: guarding a hazard inside your own module and reporting it "guarded" is a
band-aid — the DB/root cause gets fixed as you go. Only Rule-0/destructive changes pause for a typed
approval, and the ask surfaces immediately.) Then: walk it in Playwright as a human → screenshot →
collect the seven fields → write the receipt → tick → next. Never tick ahead. Never batch the walking.
</Step>

<Step title="Every receipt notates the machine truth">
**What table was touched** (every one, named) · **what activity-log row was written** (`hl_lead_activity`
kind — *no row is a finding*) · **what variable moved** (the real values) · the schema-lock check · the
click path · the embedded screenshot · the item number it proves. A new KIND discovered mid-loop is signed
through the ONE-write ceremony (a catalog INSERT — the autoseat trigger seats the automation row), then
the vocab + union regenerate before the writer lands.
</Step>

<Step title="Republish as you go; the loop survives interruption">
Republish every ~3 receipts (same file path = same URL — Zach's tab updates in place). Team consults are
handled and RETURNED from. The loop's state lives in the scope-lock + a battle ledger on disk, so a
compaction or restart resumes mid-list without re-discovery.
</Step>

<Step title="FULL GREEN — the only end state">
The artifact closes when **every item is either ✅ ticked-with-receipt, or carries an honest evidenced
state** (`p-need` waiting on a named decision · `p-block` sequenced behind named surgery — each with the
evidence of WHY). Then the closing count goes to Zach (N green / N receipts / what remains and exactly
why), he screen-walks, and the gate closes. A list with silent unticked items is not finished — it is
abandoned.
</Step>
</Steps>

### The client-state law (the bug that hid a night's work)

The artifact's own script must **never restore checkbox state from localStorage** (or any client store).
It happened twice: sign-off state keyed by position wiped itself on reorder (documented above), and on
8/3 a legacy restore **overrode a night of receipts and ticks on Zach's screen** — the file said done,
his browser said not. **The HTML file is the ONLY state.** Scripts may paint and count; they may not
remember.

## The rules that keep it honest

1. **One artifact per agent.** Not per feature. The agent's whole lane lives on one page.
2. **Numbers are derived, identity is a slug.** Never hand-type a number; never persist by position.
3. **One owner per item.** Two owners means split it.
4. **Every claim carries its evidence** — a row count, a file:line, a migration number, a commit. *"Fixed the
   filters"* is not an item; *"3 leads matched where 23 qualified — the rename left the filter querying old
   names"* is.
5. **Corrections stay visible forever.** Deleting a correction after fixing it destroys the audit trail.
6. **Silence is never a verdict.** Zero fires in beta measures the absence of users, not a broken feature — do
   not write "not working" when you mean "nobody has used it."
7. **Ticked means verified on prod, by the agent's own eyes.** Not "committed", not "works locally."
8. **Zach ticks his own sign-off items.** The agent never ticks a gate item on his behalf.
9. **Publish the artifact after every meaningful change** — same file path keeps the same URL, so the tab Zach
   has open on his second screen updates in place.
10. **The last step is always the docs.** An artifact that closes without a docs update leaked its knowledge.
11. **The fix rides the walk.** A defect found during an item's cycle is fixed in that cycle — root cause,
    not module guards. "Audited but not fixed" is not a state this method recognizes (Zach, 8/3).
12. **Client state never overrides the file.** No localStorage restore of checkbox state, ever — the
    published HTML is the single source of ticked-ness (see the client-state law above).
