<Info>
**This is infrastructure, not decoration.** Zach runs four boards on two vertical screens — one per agent
(**Lee**, **Benji**, **Adam**, **Caleb**). Each is that agent's entire working surface: the plan, the law, the
corrections, and the next thing to do. **The board is the session.** If a decision is not on the board it did not
happen; if work is not on the board it is not being done.
</Info>

## The one sentence

**One agent, one board, ONE permanent numbered list — and exactly one green Active Working Section that items are
pulled up into and dropped back down from.** An item is not ticked until it has an **audit receipt**.

## The five bands, in this order, always

| Band | What is in it |
|---|---|
| 🟢 **Active working section** | The items being worked *right now*, pulled up out of the list, with the PRD covering every one of them |
| **The list** | Everything, 1 → ∞, in permanent order. Ticked items stay exactly where they are. |
| **The record** | The law, the corrections, the findings. Everything that is reasoning rather than a task — and the half that gets silently dropped when a board is rebuilt from memory. |
| **Reference** | Every sub-artifact this board points at: locked wireframes, competitor references, linked artifacts. |
| **Audit results** | The receipts. **Last**, because it is the longest band and nothing should sit under it. |

<Warning>
**There is deliberately no "Completed" section.** A finished item does not move to a pile — it stays in its own
position in the list and goes green. A separate completed section immediately creates a second ordering, and two
orderings is how the last board reached 3.7MB with two competing "today's work" blocks.
</Warning>

Because these boards get long, **the sticky nav is not optional** — and it **scrolls, it does not hide**. One page,
end to end, with a scrollspy so the lit button always names the band you are looking at. Beside it: a **progress bar
of three real slices of one total** (done / active now / still to do) so the remainder is legible at a glance.

**When you restructure a board: MIGRATE it, never retype it.** Parse the old document, diff the result, and report
the percentage of fragments carried across. Rebuilding from memory silently drops the reasoning — which is the half
nobody notices is gone until they need it.

## ⭐ The numbering law — THE NUMBER IS PERMANENT

**An item's number is assigned once and never changes.** Item 34 means the same thing tomorrow, next week, and in
a message to another agent.

<Warning>
**This REVERSES the previous law on this page, which said numbers were derived from DOM position and re-stamped on
every reorder.** That was wrong, and the reason is worth keeping: derived numbers mean *"I have not signed off
item 12"* silently changes meaning the moment anything is inserted above it. A number whose meaning drifts is not
an identifier — it is a coincidence. Numbers are now **authored once, in the data, and frozen**.
</Warning>

- New work appends at the end. It never inserts in the middle.
- Re-prioritising does **not** renumber. You move an item into the active section; its number rides along.
- Numbers may have gaps. Gaps are fine. Renumbering is not.

## ⭐ The Active Working Section

**Exactly one, wearing a big green band.** Never two — if a second green block appears, the board has two "now"s
and neither is real.

**How an item moves:**

1. Zach names items — one, or a range: *"make 56, 72, 89 and 94 through 101 active."*
2. Each named item is **pulled up** into the active section.
3. In its home position it leaves a **placeholder** — dashed, with an ↑ and a link to the active section — so the
   list never develops holes and you can always see where an item went.
4. When it is done it **moves back down** to its own position, goes **green**, gets its **checkbox ticked**, its
   **completion date**, and a link to its **audit result**.

**Active can be a single item or a hundred.** It is a batch on purpose: that is what makes `/loop the active
section` a real instruction rather than a per-item conversation.

**The PRD covers EVERY item in the active section.** Not a summary of the theme — the reasoning for each item in
there, including what was rejected and why. An item in the active section without its reasoning is an item someone
will rebuild wrong in three weeks.

## ⭐ The audit — ten fields, and an item cannot be ticked without one

> **Compiling is not evidence. Typechecking is not evidence. A passing gate is not evidence. The receipt is the
> evidence.**

| # | Field | What it must contain |
|---|---|---|
| 1 | **Walked in Playwright** | The literal click path. Which URL, which buttons, in order. Real headed Chrome. |
| 2 | **Buttons actually pushed** | Not "the button exists" — it was clicked and something happened. |
| 3 | **What happened on the page** | The embedded screenshot + one human sentence. |
| 4 | **The table it wrote to** | Named. Every table touched, not just the interesting one. |
| 5 | **The event that was logged** | The activity kind. **"No row" is a FINDING, not a blank.** |
| 6 | **The variables that moved** | Real values, before and after. Not "the count updated". |
| 7 | **The code it wrote to** | The files. |
| 8 | **Against the current schema lock?** | Tables vs `schema.lock.json`; kinds vs the catalog **and writability**. |
| 9 | **Is it inventing something new?** | If yes, say so loudly. New table / new kind / new column gets signed before it ships. |
| 10 | **Reuse check** | Did you look for something already built? Name what you found and why it did or did not fit. |

<Warning>
**Field 8 is the one people skip, and it is the one that bites.** A kind can exist in the catalog and still have
its writes rejected silently because it was never seated. *Presence is not writability.* Probe it: insert, read it
back, roll back.
</Warning>

<Warning>
**Field 10 is the anti-drift field.** "I could not find one" is an acceptable answer only if you actually looked
and can say where. Most duplicate components in this codebase exist because nobody wrote this line down.
</Warning>

## The state lives in DATA, not in the HTML

**The board is GENERATED from a JSON file. It is never hand-edited as markup.**

```
.claude/reports/board.json                 ← the state: items, status, dates, the PRD
.claude/skills/project-board/build-board.mjs ← the generator (shipped IN the skill)
.claude/reports/<name>-board.html          ← the output, published as the artifact
```

<Warning>
**Why this is a law and not a preference.** The previous board reached **3.7MB and 203 list items** by accretion:
every session appended to the markup, nothing was reorganised, and it ended with two overlapping "today's work"
sections, a stale date, and two numbering schemes that did not reconcile. The cause was structural — **the state
lived in the HTML**, so moving an item meant surgery on markup and nobody ever did it. With the state in JSON,
pulling item 56 into the active section is a one-line edit.
</Warning>

`board.json` shape:

```json
{
  "title": "...", "owner": "caleb", "updated": "2026-08-04",
  "active": { "title": "...", "prd": ["...", "..."], "items": [31, 32, 33] },
  "items": [
    { "n": 31, "status": "active", "title": "...", "note": "...", "prd": "how this one gets done" },
    { "n": 30, "status": "done", "date": "2026-08-04", "title": "...", "receipt": "30" }
  ]
}
```

`status` is `done | active | future`. Nothing else.

## ⭐ The board is tied to the task list — STRUCTURALLY

> Zach 2026-08-04: *"make it structural and not you need to think to update the board — the board has to be
> tied to the task list."*

**The task list is a RENDERING of the active section, not a second system reconciled by hand.** They cannot
drift, because one derives from the other.

| | |
|---|---|
| `/board active 56,72` | writes `board.json` **and** creates the tasks, in one action |
| a task marked `completed` | a `PostToolUse` hook regenerates the board — no agent judgement involved |
| task title | always carries the item number: `#56 Retire platform='inbox'` — the join key |

<Warning>
**What is automatic and what is not, stated honestly.** ✅ Marking a task complete rebuilds `board.json` and
the HTML via `tools/hooks/board-sync.sh`. ⚠️ **Publishing is not automatic** — a shell hook cannot call the
Artifact tool. The hook writes a dirty marker and the `UserPromptSubmit` hook surfaces it every turn until
the agent republishes. **Never claim live bidirectional sync** — it is a derivation plus a nag, and claiming
more is the class of overstatement this protocol exists to stop.
</Warning>

<Info>
**This supersedes the older "sync at arc boundaries" protocol**, which was honest that it depended on an
agent remembering at the right moment. It worked exactly as often as someone remembered. The hook removes
the remembering.
</Info>

## The skill

Everything on this page is executable as **`/project-board`** (`.claude/skills/project-board/`). The skill
ships the SKILL.md law, `build-board.mjs`, and the hook. **The layout is not described to an agent — it is
generated**, so no agent can render the bands wrong, invent a sixth section, or renumber items. This page
stays as the human-readable explanation; the skill is what agents execute.


## Running it — the `/loop` protocol

Zach says **"loop the active section"** and the agent works every item in it without checking in between them.

For each item, in order:

1. **Read the item's PRD line.** If it does not have one, that is a bug in the board — write it first.
2. **Build it.**
3. **Walk it in Playwright.** Headed Chrome, real clicks. Never `curl` as a substitute for a walk.
4. **Write the ten-field audit.** If any field cannot be filled honestly, the item is not done.
5. **Move it back down, green it, stamp the date, rebuild and republish the board.**

**Republish as you go, not at the end.** Zach is reading the board while you work; a board that only updates at
the end is a board he cannot use to interrupt you.

**If a walk reveals the item was standing on something broken:** that is not a detour, it is a new item. Append it
at the end with its own number, note why it exists, and say so in the next message. **Never silently widen an
item's scope** — the number is a contract about what got done.

## The rules that keep it honest

- **Report what happened, not what you intended.** If a walk failed, the receipt says it failed.
- **A "no row" is a finding.** If an action wrote no activity row, that is the most interesting line in the audit.
- **Corrections stay on the record.** Every mistake stays visible in the item's note. A board with no corrections
  is a board nobody audited.
- **One owner per item.** If two agents are needed, it is two items. An item with two owners has no owner.
- **Never fake a control.** A button that writes nothing must say so on its face — the tour-notes box on the
  client dashboard reads *"Notes are coming"* rather than swallowing what someone types. Zach's rule: a wireframe
  that hides what does not exist is how we ship a button that goes nowhere.
