## 📌 Summary — what is true today

HouseLoop's data lives in **two databases**: the **WEB** database (the website — `Listing` ~355K
homes, users, visitors; Prisma, 39 models) and the **CRM** database (**219 tables ·
295 FKs**, all on the board below). Everything that *happens* is one of **197
signed activity kinds**; everything that *exists* is a row in a locked table. The **Spradling
Refinery** (Caleb's `hl_srg_*`/`sisu_*` reconciliation estate + the third Railway DB, `hl_txn`
schema) is a **separate section** on the board — it pours INTO the product tables and is never part
of the product schema. Config surfaces for humans: **Settings → Trigger Events** (every event kind,
trigger + notify toggles, both arms) and **Settings → Notifications** (who receives what, per
channel).

## THE CAGES — what physically stops drift

| # | Cage | What it blocks | Where it runs |
|---|------|----------------|---------------|
| 1 | **Migration numbering** | duplicate migration numbers (boot-runner loops) | pre-push, blocking |
| 1b | **Table laws** | non-`hl_` names · singular/plural twins · tables without a `-- GRAIN:` registration | pre-push, blocking |
| 2 | **Event-kind drift** | the generated TypeScript union disagreeing with the catalog — an invented kind **does not compile** | pre-push + compile time |
| 3 | **Catalog parity** | a kind that can be written but cannot render | pre-push, blocking |
| 4 | **SCHEMA DRIFT** | the live database differing from `schema.lock.json` in ANY way | pre-push, blocking |
| — | **DDL attribution** | nothing — it *names* whoever touched the schema (`hl_schema_ddl_log`) | always-on DB event trigger |

**The migration workflow** (the only legal way to change schema): write `06XX_*.sql` → apply with
`db/migrate.mjs` (hand-applied = ledgered SAME session) → `node tools/schema/schema-lock.mjs` →
regenerate this page + the board → commit migration **and** lock in ONE push. The cage rejects
anything else. Destructive DDL = Rule-0: typed Zach approval, live session, tables named.

## The two databases (+ the Refinery source)

| Database | Where | What it holds | Governance |
|---|---|---|---|
| **WEB** (`DATABASE_URL`) | centerbeam Railway | The website: `Listing` (~355K homes), users, visitors, saved searches | Prisma schema-as-code |
| **CRM** (`HL_CRM_DATABASE_URL`) | autorack Railway | People + everything that happens: **219 tables · 295 FKs** | schema.lock.json + the cage |
| *(source)* **TXN** (`HL_TXN_DATABASE_URL`) | Railway, `hl_txn` schema | The Refinery source: 11,639 transactions / 1,947 closed — feeds the commission build, never a product store | read-only mining (Caleb) |

The law that joins them: **the website is our Zillow, the CRM is our contact book** — home data lives
on the web `Listing` (keyed by HLID), the CRM points at it by `website_hlid` and never copies values.

## The signed models (quick reference)

- **Loan ladder** (config, `hl_loan_status`): contacting → contact_made → started_application → submitted → underwriting → pre_approved → fully_underwritten → on_hold → denied† → funded† → no_longer_active†

## 🌐 SIGNED RULING — THE WEBSITE DATA MODEL (8/7 · one source, everything derives · build/rename pending)

## 3.2 — Two status axes, and why one field could never hold both

| | **Loop status** — where the DEAL is | **TC work status** — what the FILE needs |
|---|---|---|
| how | **derived** from the stage's section while alive · **explicit** on a terminal exit | **explicit**, set by the coordinator |
| values | `pre_contract` · `pre_listing` · `under_contract` · `closed` · `archived`(+reason) | `processing` · `paused_blocked` · `waiting_for_closing` · `complete` |
| moved by | the agent, working the pipeline | the TC, working their board |
| default | derived from birth | **NULL until a TC is assigned**, then `processing` |

They are independent, and these four combinations prove it:

- `under_contract` + `waiting_for_closing` — deal live, TC done, waiting on the date
- `closed` + `processing` — house closed, TC still chasing commission docs
- **`pre_contract` + `processing`** — buyer agreement out for signature, Ana chasing it. **This is the case
  that broke the old single-field model** and produced a status that didn't match the stage.
- `archived` + `processing` — contract terminated, TC still releasing earnest money and filing the cancellation

<Note>
**`cancelled` was cut from the TC axis** (Zach). If the loop is archived, the TC isn't "cancelled" — the loop
is. Saying it twice is the double-write this whole exercise exists to kill.
</Note>

### Derived while alive, explicit when it dies — the correction

<Warning>
An earlier draft of this page said loop status is purely derived. **It is not, and it could not be** — if
every value came from the stage there would be no way to archive a loop at all. Nothing can compute
"we lost the listing" from a pipeline position.

```
loop_status_key IS NULL   → derive from the stage's section
                            pre_contract · pre_listing · under_contract · closed
loop_status_key IS SET    → a human ended this loop on purpose. The derivation stops.
                            listing_not_won · offer_not_accepted · fell_through
                            listing_expired · listing_cancelled · archived
```

The column lives on the LOOP (nullable). Only the terminal exits are ever written to it; the active path is
never stored, so it cannot drift. Corrected 2026-07-31 after Zach caught it.

**⚠ SUPERSEDED 2026-08-04/05 (the freeze, confirmed by Benji against the live DB):** loop status **IS
a stored column now** — `hl_transactions.loop_status_key → hl_tc_loop_status`, with `loop_status_at` /
`_by_user_id` / `_reason` attribution beside it. Zach's ruling ("i dont need those weird derived stuff,
it should just be a simple drop down") and migs 0599 + 0620–0622 postdate this passage: the 45-line
derivation ladder died, the vocabulary became config rows with a UI. The paragraph above stays as the
dated record of the earlier model.
</Warning>

### The derivation is a FOREIGN KEY, not an if-statement

`hl_stages` gains `loop_status_key → hl_tc_loop_status(key)`. Loop status is **never stored on the loop** —
it is the stage's `loop_status_key`. It cannot drift, and a stage can be re-pointed in config without a
deploy.

```
working_buyer stages     → pre_contract
win_listing / list_prep  → pre_listing
under_contract stages    → under_contract
Closed (is_terminal)     → closed
```

### The archive exits — flat, one chip, `group` for rollup

Zach rejected parent-child twice and was right: the reason IS the status, so storing both is storing one
fact twice. `hl_tc_loop_status` carries a `group` column instead.

| key | label | side | group |
|---|---|---|---|
| `pre_contract` | Pre-Contract | buyer | active |
| `pre_listing` | Pre-Listing | seller | active |
| `under_contract` | Under Contract | both | active |
| `closed` | Closed | both | closed |
| `offer_not_accepted` | Offer Not Accepted | buyer | archived |
| `listing_not_won` | **Listing Not Won** | seller | archived |
| `listing_expired` | Listing Expired | seller | archived |
| `listing_cancelled` | Listing Cancelled | seller | archived |
| `fell_through` | Fell Through | both | archived |
| `archived` | Archived | both | archived |

- **One dropdown, one chip.** `Listing Not Won` — status and reason are the same fact.
- `WHERE group = 'archived'` gives the rollup without a second field.
- `side` scopes the dropdown; a seller loop never offers "Offer Not Accepted".
- **`archived` is the plain catch-all** — a buyer who changed their mind isn't ghosted, but the loop still ends.

<Warning>
**`listing_not_won` closes a hole that exists right now.** The seller pipeline runs
Listing Appointment Met → Listing Agreement Sent → Listing Agreement Signed with **no exit**. Lose the
listing and there is nowhere to put it — Lawrence Guenther's listing has no disposition today. Without it,
listing-presentation win rate cannot be computed at all.
</Warning>

### Why "lost" is a loop status and never a stage

A buyer is never lost — they are still a person, possibly buying next spring. A TC is never "in a lost
stage." **The transaction is what's lost**, along with every document in that loop.

**A loop is one attempt at one deal.** One buyer can carry four archived loops (offer rejected, offer
rejected, fell through) and a fifth that closes, while their pipeline stage never moves backwards. A lead
has one stage; a lead has many loops. That is the whole argument.

## 3.3 — Milestones, tasks, and what a loop actually holds

**Status is one value → a column. Milestones are a dated checklist → rows.** Measured on a live loop: 16
milestones, 81 tasks.

```

☐ Photos / Media Complete     ☐ On-Market (Live)
☐ Under Contract              ☐ Earnest Money (EMD) Received

☐ Title Commitment            ☐ Appraisal Received
☐ Clear to Close              ☐ Final Walkthrough
☐ Closing                     ☐ Funded                    ☐ Possession
```

Each needs its own date (the TC overrides them constantly — inspections extend, closings move), its own
completion, its own completed-by. That cannot be a column.

### Ana's ruling: tasks nest under MILESTONES. Phases are retired.

Tasks already hang off milestones — just only 4 of the 30:

```
 57  start           → (not a milestone)
 38  closing         → closed
 18  effective       → under_contract
 14  inspection_end  → inspection_period_ends
 12  on_market       → on_market
```

`phase` was a *second* grouping that said nothing the anchor didn't already say, and made 81 tasks look
like they lived in two hierarchies. **Retired.**

`start` — 57 of 139 tasks, the biggest bucket — becomes a real milestone, **`loop_started`**. Then every
task nests under a milestone with zero special cases.

```
hl_tc_loop_milestone_catalog   31            hl_tc_loop_milestone    ~16 per loop
  └── hl_tc_loop_task_catalog  139             └── hl_tc_loop_task   ~81 per loop

```

Migration is 1:1, no guessing: `closing→closed` · `effective→under_contract` ·
`inspection_end→inspection_period_ends` · `on_market→on_market` · `start→loop_started`.

### Two species of milestone — which is why Under Contract → Close is its own beast

```
CHECKPOINTS  (anchor=start, no offset)      COMPUTED DATES  (anchored + offset)
buyer_agreement_sent                        under_contract          KEY DATE
buyer_agreement_signed                      emd_due                 effective +3
listing_agreement_signed                    inspection_period_ends  KEY DATE
pre_listing_packet                          title_commitment        effective +10
                                            clear_to_close          closing −3

```

The top group answers *did it happen*. The bottom group are **dates with timing rules** — business-day
math, holiday rolls, 139 tasks hanging off them. Only the second group has anything to configure, which is
why it earns its own section.

## 🧹 THE DATA HYGIENE LAW (Zach, 7/31 PM — constitutional, delegated to Lee end-to-end)

The four rules, enforced:
1. **ONE PATH PER ANSWER.** Two columns/routes to the same fact = one dies. No exceptions.
2. **DERIVE, DON'T STAMP.** A fact computable from the run log / another table is a QUERY (or a
   DECLARED regenerable cache) — never a hand-maintained stamp that can disagree with the source.
3. **NO SPECULATIVE SCHEMA.** A column/table for an idea that isn't built yet does not exist — it gets
   NAMED in the plan and BUILT when its feature is. Unused/empty now → dies now (with judgment: a live

# PART 2 — THE PAYOUT POLICY (Zach, 8/3/2026)

## 2.1 — The waterfall. The order IS the policy.

| # | Step | Detail |
|---|---|---|
| 1 | **GCI** | `(sale price − price deduction) × commission rate`. The **actual** rate — 2.5%, 2.8%, 3%. **Never assume 3%.** |
| 2 | **Referral off the top** | team-provided leads only, computed on GCI → **adjusted GCI** |
| 3 | **Tier split** | `adjusted GCI × the agent's tier %` — which table depends on lead status |
| 4 | **Add** | flat fee + ISA bonus |
| 5 | **eXp fees** | the cap logic (§2.4) |
| 6 | **Stock** | 5% withheld |
| 7 | **Net to agent** | what lands |

## 2.2 — Lead status is the first fork

- **Team-provided** — the team supplied it. Zillow, Google PPC, and going forward **HouseLoop**. A referral
  fee comes off the top.
- **Agent-provided** — the agent brought it. **No referral fee, ever.**

## 2.3 — The tier ladder, measured in CLOSED VOLUME

| Tier | Closed volume | Agent keeps — **team lead** | Agent keeps — **own lead** |
|---|---|---|---|
| 1 | \$0 – \$2.5M | 50% | 75% |
| 2 | \$2.5M – \$5M | 55% | 80% |
| 3 | \$5M – \$7.5M | 60% | 85% |
| 4 | \$7.5M – \$10M | 65% | 90% |
| 5 | \$10M+ | 70% | 95% |

The stored plan's `agent_pct` (0.75 → 0.95) and `group_pct` (0.50 → 0.70) match these two columns exactly.
**`group_pct` is misleadingly named** — it is the *agent's* share on group-provided leads, not the group's.

### ⭐ THE TIER FLOOR — the rule that will bite any implementer

> *"closed volume resets every january 1 for the tier structure, but they keep the previous deals
> percentage they gained for the entire year but they have to earn it again."* ·
> *"floor is always set by the previous year."* — Zach

Two things happen on January 1: **the volume counter resets to zero, and the payout tier does not.**

```
tier(deal) = MAX(
    floor    = tier EARNED by volume in the previous calendar year,
    current  = tier reached by volume so far in THIS calendar year
)
```

**Worked example (Zach's own).** An agent closes \$6M in 2026 → Tier 3. On Jan 1 2027 volume resets to
zero, but their **first closing of 2027 still pays Tier 3**. To reach Tier 4 they must close **\$7.5M of
new volume** in 2027 — no credit carries.

**The floor RATCHETS DOWN.** It is set by volume *earned*, never by what they were *paid at*. If that agent
then closes only \$2M in 2027 — paid at the Tier 3 floor all year but earning Tier 1 by volume — their
**2028 floor is Tier 1**. Status is kept for a year, not forever.

**Without the floor, every agent's January and February deals compute at Tier 1**, understating a strong
producer at the start of *every single year*.

## 2.4 — eXp fees: the cap flips which fees apply

| Fee | **Before cap** | **After cap** |
|---|---|---|
| eXp company split | **20% of gross** | **\$0** |
| Capped transaction fee | \$0 | **\$75** |
| Risk management | \$60/deal | \$0 |
| Broker review | \$25 | \$25 |
| Stock | 5% | 5% |

**The cap is per-person, by role — not one number:**

| Who | eXp cap |
|---|---|
| **Team agent** | **\$4,000** |
| **Team / team leader** | **\$16,000** |

✅ **CONFIRMED BY ZACH 8/3:** *"i do confirm the 4,000 and the 16K for caps for agents vs team."*

✅ **THE CROSSING DEAL — CONFIRMED 8/3:** *"the cap cross a deal does cap at 4,000 to the pennies."*
A deal that takes an agent past their cap charges **exactly to the cap and not a cent more** — the 20% is
prorated to land on \$4,000 (or \$16,000) precisely, and the remainder of that deal is treated post-cap.
Same rule for the \$750 risk-management ceiling: the deal that crosses it charges only the room left.

**Risk management has its own annual ceiling: \$750.** \$60 per deal until the agent has paid \$750 that
year, then it stops.

## 2.5 — Three running totals force the order of calculation

| Running total | Threshold | Controls | Resets |
|---|---|---|---|
| Closed volume | \$2.5M steps | which tier | Jan 1 — **carries the floor (§2.3)** |
| eXp paid | \$4,000 / \$16,000 | when 20% becomes flat \$75 | Jan 1 |
| Risk management paid | \$750 | when the \$60 stops | Jan 1 |

**Therefore every deal must be computed in close-date order, per agent, per year.** A deal cannot be
calculated in isolation — its numbers depend on everything that agent closed before it. An agent who closed
in November was on a different tier than the same agent in February. **Compute in any other order and every
number is wrong.**

## The shape in one breath

**One truth spine, everything else is evidence or a pointer.** `hl_srg_canonical` (one row per DEAL: client × house × side, keyed `pc_id:hlid:our_side` — never MLS in the key) is THE deal record. `hl_srg_past_clients` (one row per PERSON) carries who they are and their bucket. `hl_srg_past_client_homes` (one row per person × home) carries the relationship to each rooftop. ## ZACH'S SEVEN RULES — signed 2026-07-30 (eyeball catches that became law the same day)

1. **THE SOURCE HIERARCHY LAW.** Canon = `hl_srg_mls_deals` + `hl_mls_property_history` (the MLS-UI harvests). Rank-2 = real `Listing` rows, dates cross-checked against canon. **`Listing.priceHistory` (Zillow, address-glued) is BANNED from the book pipeline** — it carried the neighbor's history and falsely flagged the Frittz. A weak source raises a QUESTION; only canon writes an ANSWER.
2. **THE SELF-CONSISTENCY TEST.** A price history that does not contain the house's OWN sale is not that house's history (61 contaminated carriers found).
3. **THE CONDO UNIT GUARD.** A harvest/building event joins a unit-keyed home ONLY when it NAMES that unit (shared parser — handles the MLS's `UNIT##2002` double-hash). An ambiguous, unit-less event NEVER counts.
4. **THE IDENTITY KEY BEATS THE COLUMN.** A home's unit reads from `identity_key`'s middle segment; the `unit` column is a cache that goes NULL. Key-vs-column drift is a red-flag sweep (Guardian Tier 5).
5. **ROSTER MATCHING NEEDS THE INITIAL.** A surname match requires a first-initial match with a roster member of that surname — no more Blaire-via-Jordan Lawrence.
6. **DISPOSITION = SISU DATES + THE MLS SHEET + THE HARVEST** (the Mettman rule): the sheet's `close_date` beats the web listing's `soldDate`; the client's own later sell deal beats everything.
7. **THE CONFIRMATION STANDARD.** Every buy disposition carries a chip — canon ✓ / listing-only / no-harvest / mismatch. Unconfirmed SAYS SO; gaps are filled by harvesting, never substituted.

## The rulings (the lock session's verdicts)

### 1. ONE disposition vocabulary — and it is NOT transaction status
The child table's four words are canonical: **`owns` · `sold_moved` · `lost_listing` · `lost_buy`** (matches the deterministic disposition engine). The canonical table's synonyms (`still_owns`/`sale_side`/`lost_opportunity`/`sold_repped_by_us`) MAP onto these — one migration, alias-documented.
**Deliberately NOT merged into the transaction ladder**: `transaction_status` (pending → closed → lost) answers *"what happened to a deal"*; disposition answers *"what is this rooftop's relationship to us now."* Two questions, two vocabularies — forcing them together would be a false merge (the interchangeability test).

### 2. The `verified` gate values — SIGNED
`PASS · WARN_NO_ADDRESS · WARN_UNIT_DROPPED · FAIL_WRONG_UNIT · FAIL_WRONG_HOUSE · FAIL_NOT_SOLD · FAIL_PRICE`

### 3. `identity_key` format — LOCKED
**`street::unit?::zip5`** — unit is the optional MIDDLE segment. The **columns are the source; the key derives** — when a column repair (like the 7/27 zip fix) makes key and column disagree, the KEY regenerates by migration, collisions resolve oldest-wins with the quarantine trail. # 📎 Activity Card Design Lock (folded 8/5)

## What this is

On 2026-07-30 Zach locked the universal design for **every card in the lead-detail feed** — messages, notes,
emails, calls, inquiries, registrations, website activity, appointments, tasks, documents, deals, AI actions,
system moves. It was designed the constitutional way (`UI_ITERATION_HTML_FIRST`): iterated as an HTML
wireframe, signed, then ported node-by-node and refined live on real leads the same day.

**The pinned wireframe:** `Docs/wireframes/card-chrome-locked-2026-07-30.html` (repo, version-pinned).
This page carries the FINAL law including the same-day refinements Zach ruled during the live walk.

## THE SENTENCE LAW — the one grammar

Every card is: **[family icon in a colored circle] + a plain-English sentence "[Who] [did what] [· the facts]"**
(+ a VIA chip when it came from a portal) · **date+time top-right, always** · **hover actions below the date,
star first** · **click the card → its family's tab**.

The verb phrase is **DATA — a column on the signed activity catalog** (`hl_activity_catalog.sentence`,
migration 0513, 127 kinds authored): "created a note", "changed the stage", "requested a tour". The renderer
is one dumb line: `who + the catalog's sentence + the payload facts`. A new kind writes its sentence in its
catalog row — no code, no pills, no drift. NULL sentence = the label renders atomically (insight/system kinds).

### Who is the "Who" (all Zach's exact rulings)

- **Full names, always**: "Msale Olongo requested a tour", "Zach Spradling created a note".
- **The WHO comes from the actor lane** (lead / agent / Myli / System) — never guessed from message direction.
- **Users ACT, strangers ARRIVE**: a known system user reads active ("Ana Spradling sent an email");
  an outside sender reads "Email received from John Nelson". The email thread API resolves the sender
  against `hl_users` (`sender_is_user`) so the card knows which grammar to speak.
- **The machine never takes a person's credit**: "System opened a document" was the SIGNER opening their
  e-sign link — the writer credits the lead (mig 0514 re-credited history). The multi-party completion
  event reads atomic: "Document fully executed" — a system observation, not a signature.
- **Pink #EC4899 (`--hl-ai-pink`) = Myli/AI only.** Purple is retired from the feed (email = teal #0F766E).
  System moves wear the mechanical Settings icon in slate.

### Every card names its OBJECT

- **Appointments**: title from `hl_appointments` + the schedule line —
  "Wednesday, Jul 29, 2026 · 11:00 AM – 1:00 PM · 116 se 8th street, Lees Summit MO · with Zach Spradling".
  Meta fallback keeps history when an appointment is deleted.
- **Email engagements**: "Bradley Bengel opened an email · *subject*". Engagement rows key on the SEND
  PROVIDER'S id (Resend), which the send log never stored — the thread API triangulates it (same lead,
  same recipient, provider sent-event within ±2 min). Lesson from the walk: a "missing" record is
  usually the right row in the wrong table — check the id's LANGUAGE before declaring data deleted.
- **Documents**: "Zach Spradling sent a document for signature · Exclusive Buyer Agency Contract" (0515) ·
  "Bradley Bengel signed a document · *name*" · "Bradley Bengel opened a document · *name*".
  The document NAME links to the **sealed PDF** (our R2 archive — never rots), and the whole card jumps
  into the **TC loop** (`?view=tc`). The multi-party COMPLETION event ("fully executed") is internal
  machinery — it drives transaction status and never renders on the feed; the signer's row is the story.
- **Stage moves**: "changed the stage · First Appointment Set → First Appointment Met".
- **Calls**: "Outbound call to Msale Olongo · from your line · 1:52" — the person by NAME, number as fallback.
- **Myli's facts**: "Myli captured a new fact — Search Criteria", the slot underneath, the evidence quoted.
  Never the raw payload salad.
- **Comms provenance**: the from→to line ("from Msale · (816) 756-9634 → Zach Spradling") rides every
  message card, FUB-style.

## NO pills — not for users, not for kinds

The actor is plain bold text in the sentence. Kind pills ("Note Added", "Stage Changed", "Phone Call
Logged") are dead — **the icon IS the kind; VIA (source) is the only chip a card may wear.** Per-user
colors are whack-a-mole and banned forever.

## The chrome (top-right, every card)

- **Row 1, always visible**: date + time, ONE token (`CARD.date`), one format, same corner on every card
  type — compact rows, notes, emails, heroes.
- **Row 2, hover, below the date**: action icons, **☆ ALWAYS FIRST**; per-family extras follow
  (note: ✏ edit · 🗑 delete).

## Click-through — every row leads somewhere

Clicking any feed card opens its family's tab: note → Notes · appointment → Appointments · text/in-app →
Messages · call → Calls · task → Tasks · inquiry → Inquiries · home view → Website. A guard skips real
controls (links, buttons, the audio player) so they keep working.

## The email card — Gmail's grammar (Zach's ours-vs-Gmail ruling)

- **ONE icon** (the left-rail mail circle). The avatar double-icon is dead.
- Line 1: **the sentence** ("Email received from John Nelson" / "Zach Spradling sent an email").
- Line 2: "to Trish.redenbaugh, zach, bradleybengel, Ana **▾**" — the triangle opens the Gmail details
  block: from / to (every full address) / date / subject.
- Chrome: date + ☆ top-right only. **Reply · Reply All · Forward · ⋯ (Delete/Block) at the BOTTOM** of the
  expanded message.
- **Full expansion** — no height cap, no inner scroll; the feed scrolls.
- **Sender names are captured at sync** (mig 0512 `from_name`) and resolved from-name → `hl_users` → bare
  address; old rows self-heal as new mail arrives.
- **Attachments**: paperclip row per genuine file (name + size + View + Download) riding
  `GET /api/email/attachment`. **Inline signature images** (cid: parts) are rewritten to the attachment
  endpoint so signatures render like Gmail — inline parts never clutter the file list.
- **FUB twin dedupe**: FUB mirrors the same email as a `[CONTENT HIDDEN]` row; redacted fub rows are
  dropped only when the native capture exists within ±2 minutes.
- **All-feed match**: activity rows may reference an email by `gmail_message_id` — the email map keys BOTH
  ids so the real card always renders, never a fallback; the fallback itself is atomic and can never
  invent a speaker.

## The locked pieces that must not be touched

- **Home-card links**: Zillow-origin → `Look up on HouseLoop · View on Zillow`; HouseLoop-origin →
  `View on HouseLoop` only.
- **In-app Zillow messages always wear the little round Zillow circle** — hero included.
- **Registrations are ALWAYS hero** with a big round SOURCE icon (HouseLoop / Zillow / generated
  color+initial for unbranded sources).
- **Hero shapes** for inquiries/tour requests (icon chip on photo, quote box, VIA chip).
