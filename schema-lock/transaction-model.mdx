## The one-sentence problem

**We have three different concepts crammed into one status list, and no vocabulary at all for document
categories or folders.** A-Frame — the system we reverse-engineered — keeps them deliberately separate and
its own doc warns *"A-Frame has both; don't conflate."* We conflated them.

## The status dropdown today — three concepts in one list

```
0  Processing
1  Paused
2  Waiting for Closing
3  Preparing Documents
4  Document Sent
5  Buyer Signed
6  Showing Agreement Signed
```

Read it again and the seam is obvious:

| Rows | What they actually are | Belongs |
|---|---|---|
| Processing · Paused · Waiting for Closing | **TC processing state** — is the coordinator working it? | a TC status field |
| Preparing Documents · Document Sent · Buyer Signed · Showing Agreement Signed | **document lifecycle events** — things that HAPPEN | the activity log + document state |
| *(missing entirely)* | **the loop's own stage** — active, under contract, sold, archived | the loop spine |

The four document rows are not statuses at all. They are events, already written to
`hl_lead_activity` (`document_sent`, `document_signed`), and the webhook *also* advances this dropdown —
so the same fact is stored twice, in two shapes.

**The loop stage Zach asked about does not exist yet.** Nothing in the system can answer "is this loop
active, under contract, sold, or archived."

# PART 2 — WHAT IS PLANNED

## The approved target model (Zach signed 2026-07-30)

From [The Table Sitting](/schema-lock/target-model), the TRANSACTIONS family:

| Table | What it is |
|---|---|
| `transactions` | **one SIDE of one deal** — the financial record. The catalog section is **Transactions** (Zach renamed it from "Deals", mig 0528 — sections speak the TABLE noun; "deal" survives only as prose). |
| `loops` | **the TC workspace** — its own lifecycle, born at Appointment Set, **can exist before a transaction** |
| `loop_milestones` | milestones inside a loop |
| `loop_tasks` | tasks inside a loop |
| `loop_participants` | every party on a loop — **becomes the signer registry** |
| `documents` | ONE document table — loop docs, transaction docs and contract fills merge |
| `document_signatures` 🆕 | per-recipient signing state — 3-party signing finally has a home |
| `commission_forms` | the DA + splits + adjustments |

**Phase C of the pour:** *"`hl_transactions` splits into `loops` + `transactions`."*

That split already answers the structural half of Zach's question. What it does **not** yet specify is the
vocabulary: the loop's stages and statuses, the folder structure, and the document categories.

## A-Frame's model — the pattern worth copying

A-Frame separates exactly what we merged:

**Stages — a fixed system enum:**
```
PRE_ACTIVE · ACTIVE · UNDER_CONTRACT · SOLD · NOT_SOLD
```

**Statuses — user-built, each bound to a stage:**

| Status | Stage | systemType |
|---|---|---|
| Coming Soon | PRE_ACTIVE | — |
| Active | ACTIVE | `SYSTEM_ACTIVE` |
| Under Contract | UNDER_CONTRACT | — |
| Pending | UNDER_CONTRACT | — |
| Closed | SOLD | `SYSTEM_CLOSED` |
| Expired | NOT_SOLD | — |
| Cancelled | NOT_SOLD | `SYSTEM_FELL_APART` |
| Draft | PRE_ACTIVE | `SYSTEM_DRAFT` |

<Note>
**The `systemType` trick — copy it exactly.** Statuses are renamable and recolorable by the user, but a few
are *bound* to system behavior. The user can rename "Closed" to anything; the engine still knows which one
is closed via the bound type. Customizable words, stable logic.
</Note>

Also on their transaction: **`xactionSide` = `BUYER | SELLER`**, and attachments are grouped in folders
seeded per transaction from a team-level `defaultXactionFolders` list.

And critically, A-Frame keeps a **separate** team-defined field for processing state
(Processing · Paused · Waiting for Closing · Closed · Cancelled) — the same words we put in our one list.
Their own doc says: *"distinct from the structural Status→Stage spine above. A-Frame has both; don't
conflate."*

# PART 3 — WHAT WE SHOULD LOCK IN

Everything below is **PROPOSED**. Three vocabularies, each needing a signature.

## 3.1 — Loop stage (fixed spine)

Zach's words, mapped onto A-Frame's spine:

| Zach said | Proposed `loop_stage` | A-Frame equivalent |
|---|---|---|
| Active loop | `active` | ACTIVE |
| Under contract loop | `under_contract` | UNDER_CONTRACT |
| Sold loop | `sold` | SOLD |
| Archived loop | `archived` | NOT_SOLD |

Zach: *"An archived loop would have a type lost."* So `archived` needs a reason — `hl_transactions`
already has `lost_reason` and `lost_at_stage_id`, which is where that lives.

**Open:** A-Frame carries a fifth, `PRE_ACTIVE`, for drafts and coming-soon. Our loops are *born at
Appointment Set*, before any transaction — that is arguably a pre-active loop. **Do we want a `draft`/
`pre_active` stage, or is a loop `active` from birth?**

## 3.2 — Loop status (user-editable, bound to a stage)

The renamable layer, each row bound to one stage, a few bound to system behavior:

```
hl_loop_statuses(key, label, loop_stage, color, sort, system_type, is_active)
```

`system_type` ∈ `SYSTEM_ACTIVE · SYSTEM_UNDER_CONTRACT · SYSTEM_CLOSED · SYSTEM_LOST` — bound, so renaming
a label never breaks the engine.

**The four document rows in today's dropdown do NOT become statuses.** They are already activity kinds
(`document_sent`, `document_signed`) and document state on `hl_tc_loop_document.status`. Keeping them as
loop statuses is the double-write.

**Open:** Processing · Paused · Waiting for Closing — A-Frame keeps these as a *separate* TC processing
field, not on the stage spine. **Same for us, or fold them in as statuses under `active`?**

**What the bucketing exposes — three findings, not one taxonomy:**

1. **Category and folder are not the same thing.** A buyer disclosure and a buyer agency both file under
   *Showing & Touring Agreements*, but they behave differently: one is the contract, the other is welded
   to it by law. Category carries behavior; folder is where it lands.
2. **"Rides with" is a real relation.** Ana's two state disclosures must go out *in the same envelope* as
   the agency. That is a link between forms, not a category value.
3. **Side is not always known from the form.** 13 addenda serve both sides. Side comes from the LOOP, not
   the form — which argues that `loop_side` is the parent and category is scoped beneath it.

## 3.5 — The contract catalog (Lee already ruled)

Lee approved on 2026-07-31:

- **EXTEND `hl_contract_template`**, do not add a table: `dotloop_document_id`, `dotloop_folder_id`,
  `category`, `folder`, `field_map`, `page_count`, `imported_at`. Same grain, no twin, no fork.
- **`field_map` lives in the JSONB column** — an opaque geometry blob read whole and never queried into,
  `pdf_b64`'s sibling, so Gate B does not bite. A file on disk would be scratch-file truth.
- **Recommended, pending Zach:** `hl_contract_categories(key, label, folder_label, sort)` as a pure config
  table, FK from the template. Reason: labels like `"eXp - Writing the Offer Documents"` are not
  mechanically derivable from a key, so a CHECK constraint would force them into a hand-kept TS map.
- **ONE vocabulary:** the filled document's loop folder DERIVES from the template's category. Category and
  folder must not become two vocabularies for one concept.

Two mandates riding along:
1. **`SIGNATURE_ANCHORING` applies in full to imported maps.** dotloop's coordinates are a better *source*,
   not a pass on verification — every imported map gets the overlay check before it touches a contract.
   "58 imported" is a count, not proof.
2. **The import runs as a registered Inngest function** — manual trigger, no cron, visible in the dashboard
   and Run Log.

## 3.6 — The transaction kind catalog

Per the [Activity Catalog](/schema-lock/activity-catalog) law, verbs live in ONE signed dictionary. The
transaction-side kinds that already exist and fire today:

```
document_sent · document_opened · document_signed
```

**Open:** stage and status moves are verbs too. A loop going `active → under_contract` should be an
activity with a signed kind, the same way lead stage moves are. **Does that need new kinds, or does it
fold onto an existing one via `hl_trigger_event_alias`?** Under the kind gate, only Lee signs — this goes
to him with Zach's approval, not into code.

## Open questions — the decision list

### Lee ruled (2026-07-31) — four of the seven are settled

| # | Question | Ruling |
|---|---|---|
| 6 | Do stage moves need new activity kinds? | **YES — ONE new kind: `transaction_stage_changed`** ("moved the transaction to &lt;stage&gt;"), section **Transactions**. Do NOT fold onto the lead stage kind — different noun. On Zach's nod list. |
| 7 | Does `loop_kind` survive the split? | **NO.** It encodes the FORM, which is the template category's fact. The loop carries `loop_side`; the 13 both-side addenda prove side belongs to the loop. Retire at the split with a data migration. |
| — | Where do the document rows go? | **OUT of the dropdown — approved.** They are verbs masquerading as states. **Sequencing: its own Phase-B fold, NOT Phase C** — additive stage-spine columns first, dual-carry, repoint the dropdown reads, retire the doc rows last, Zach's eyes on the TC screen before and after. |
| — | Is "rides with" a category or a relation? | **A RELATION.** Self-referencing link table `hl_contract_template_companion(template_id, companion_template_id, reason/jurisdiction)`. Never a TS array (unqueryable, hand-kept) and not a column (a form can ride with many). |

## What must NOT happen

- **No migration until 1–7 are answered.** Guessing a taxonomy onto legal paperwork is how the folder
  free-text mess happened in the first place.
- **No new kind in code.** The kind gate blocks it, correctly. Signed vocabulary or nothing.
- **No third vocabulary for the same concept.** Category → folder derives; it does not duplicate.
