## 🔗 HOW A LEAD CONNECTS TO A DEAL — the one map (Zach's 8/5 question, answered in one place)

**`hl_transactions` IS the deals table** — one row per deal. The whole correlation, today:

```
hl_leads (the PERSON, 55 cols)
   │  1 ────── many
   ▼
hl_transactions.lead_id  →  hl_leads.id     (real FK, ON DELETE CASCADE)
   │                                          one lead owns many deals
   ├── website_hlid      →  the HOUSE        (the website Listing — the house holds the value)
   ├── transaction_type  →  hl_tc_transaction_type   (purchase | sale — ONE family since the 8/5
   │                        fork collapse: 22/23 typed; the untyped 1 shows loudly, never filtered)
   ├── transaction_status_key →  hl_tc_transaction_status  (where the deal stands — renamed 8/5, mig 0632)
   └── transaction_id ←── the TC estate hangs OFF the deal:
         hl_tc_loop_task (719) · milestones (via milestone_key) · documents · participants
```

**Today's limit, and the signed fix:** `lead_id` is SINGULAR — one person per deal. That is why
splitting a glued couple ("Michael & Katherine") without more machinery makes the second person
unservable. The signed fix is **`hl_transaction_party`** (8/4, unbuilt): each person on the deal gets a
row with a role (co_buyer / co_seller / other), exactly ONE flagged primary, and a party can be a named
entity (a trust holding title) instead of a person. `lead_id` then remains as the primary-party mirror.
**The value queries repoint from "which deals does this person OWN" to "which transactions is this
person a PARTY to"** — that repoint is atomic with the couple-split (board 239+241+247).

**The refinery side** (the pour's source): `hl_srg_canonical` (1,964 deals, key `pc_id:hlid:side`) has
NO FK to anything — the pour copies it into `hl_transactions` where the FK to the person is real.

## A-Frame's model — the pattern worth copying

A-Frame separates exactly what we merged:

**Stages — a fixed system enum:**
```
PRE_ACTIVE · ACTIVE · UNDER_CONTRACT · SOLD · NOT_SOLD
```

**Statuses — user-built, each bound to a stage:**

| Status | Stage | systemType |
|---|---|---|
| Coming Soon | PRE_ACTIVE | — |
| Active | ACTIVE | `SYSTEM_ACTIVE` |
| Under Contract | UNDER_CONTRACT | — |
| Pending | UNDER_CONTRACT | — |
| Closed | SOLD | `SYSTEM_CLOSED` |
| Expired | NOT_SOLD | — |
| Cancelled | NOT_SOLD | `SYSTEM_FELL_APART` |
| Draft | PRE_ACTIVE | `SYSTEM_DRAFT` |

<Note>
**The `systemType` trick — copy it exactly.** Statuses are renamable and recolorable by the user, but a few
are *bound* to system behavior. The user can rename "Closed" to anything; the engine still knows which one
is closed via the bound type. Customizable words, stable logic.
</Note>

Also on their transaction: **`xactionSide` = `BUYER | SELLER`**, and attachments are grouped in folders
seeded per transaction from a team-level `defaultXactionFolders` list.

And critically, A-Frame keeps a **separate** team-defined field for processing state
(Processing · Paused · Waiting for Closing · Closed · Cancelled) — the same words we put in our one list.
Their own doc says: *"distinct from the structural Status→Stage spine above. A-Frame has both; don't
conflate."*

## 3.2 — Two status axes, and why one field could never hold both

| | **Loop status** — where the DEAL is | **TC work status** — what the FILE needs |
|---|---|---|
| how | **derived** from the stage's section while alive · **explicit** on a terminal exit | **explicit**, set by the coordinator |
| values | `pre_contract` · `pre_listing` · `under_contract` · `closed` · `archived`(+reason) | `processing` · `paused_blocked` · `waiting_for_closing` · `complete` |
| moved by | the agent, working the pipeline | the TC, working their board |
| default | derived from birth | **NULL until a TC is assigned**, then `processing` |

They are independent, and these four combinations prove it:

- `under_contract` + `waiting_for_closing` — deal live, TC done, waiting on the date
- `closed` + `processing` — house closed, TC still chasing commission docs
- **`pre_contract` + `processing`** — buyer agreement out for signature, Ana chasing it. **This is the case
  that broke the old single-field model** and produced a status that didn't match the stage.
- `archived` + `processing` — contract terminated, TC still releasing earnest money and filing the cancellation

<Note>
**`cancelled` was cut from the TC axis** (Zach). If the loop is archived, the TC isn't "cancelled" — the loop
is. Saying it twice is the double-write this whole exercise exists to kill.
</Note>

### Derived while alive, explicit when it dies — the correction

<Warning>
An earlier draft of this page said loop status is purely derived. **It is not, and it could not be** — if
every value came from the stage there would be no way to archive a loop at all. Nothing can compute
"we lost the listing" from a pipeline position.

```
loop_status_key IS NULL   → derive from the stage's section
                            pre_contract · pre_listing · under_contract · closed
loop_status_key IS SET    → a human ended this loop on purpose. The derivation stops.
                            listing_not_won · offer_not_accepted · fell_through
                            listing_expired · listing_cancelled · archived
```

The column lives on the LOOP (nullable). Only the terminal exits are ever written to it; the active path is
never stored, so it cannot drift. Corrected 2026-07-31 after Zach caught it.

**⚠ SUPERSEDED 2026-08-04/05 (the freeze, confirmed by Benji against the live DB):** loop status **IS
a stored column now** — `hl_transactions.loop_status_key → hl_tc_loop_status`, with `loop_status_at` /
`_by_user_id` / `_reason` attribution beside it. Zach's ruling ("i dont need those weird derived stuff,
it should just be a simple drop down") and migs 0599 + 0620–0622 postdate this passage: the 45-line
derivation ladder died, the vocabulary became config rows with a UI. The paragraph above stays as the

</Warning>

### The derivation is a FOREIGN KEY, not an if-statement

`hl_stages` gains `loop_status_key → hl_tc_loop_status(key)`. Loop status is **never stored on the loop** —
it is the stage's `loop_status_key`. It cannot drift, and a stage can be re-pointed in config without a
deploy.

```
working_buyer stages     → pre_contract
win_listing / list_prep  → pre_listing
under_contract stages    → under_contract
Closed (is_terminal)     → closed
```

### The archive exits — flat, one chip, `group` for rollup

Zach rejected parent-child twice and was right: the reason IS the status, so storing both is storing one
fact twice. `hl_tc_loop_status` carries a `group` column instead.

| key | label | side | group |
|---|---|---|---|
| `pre_contract` | Pre-Contract | buyer | active |
| `pre_listing` | Pre-Listing | seller | active |
| `under_contract` | Under Contract | both | active |
| `closed` | Closed | both | closed |
| `offer_not_accepted` | Offer Not Accepted | buyer | archived |
| `listing_not_won` | **Listing Not Won** | seller | archived |
| `listing_expired` | Listing Expired | seller | archived |
| `listing_cancelled` | Listing Cancelled | seller | archived |
| `fell_through` | Fell Through | both | archived |
| `archived` | Archived | both | archived |

- **One dropdown, one chip.** `Listing Not Won` — status and reason are the same fact.
- `WHERE group = 'archived'` gives the rollup without a second field.
- `side` scopes the dropdown; a seller loop never offers "Offer Not Accepted".
- **`archived` is the plain catch-all** — a buyer who changed their mind isn't ghosted, but the loop still ends.

<Warning>
**`listing_not_won` closes a hole that exists right now.** The seller pipeline runs
Listing Appointment Met → Listing Agreement Sent → Listing Agreement Signed with **no exit**. Lose the
listing and there is nowhere to put it — Lawrence Guenther's listing has no disposition today. Without it,
listing-presentation win rate cannot be computed at all.
</Warning>

### Why "lost" is a loop status and never a stage

A buyer is never lost — they are still a person, possibly buying next spring. A TC is never "in a lost
stage." **The transaction is what's lost**, along with every document in that loop.

**A loop is one attempt at one deal.** One buyer can carry four archived loops (offer rejected, offer
rejected, fell through) and a fifth that closes, while their pipeline stage never moves backwards. A lead
has one stage; a lead has many loops. That is the whole argument.

## 3.3 — Milestones, tasks, and what a loop actually holds

**Status is one value → a column. Milestones are a dated checklist → rows.** Measured on a live loop: 16
milestones, 81 tasks.

```
☐ Listing Agreement Sent      ✓ Listing Agreement Signed (ERTS)
☐ Photos / Media Complete     ☐ On-Market (Live)
☐ Under Contract              ☐ Earnest Money (EMD) Received
☐ Inspection Period Ends      ☐ Inspection Resolution (ROUC)
☐ Title Commitment            ☐ Appraisal Received
☐ Clear to Close              ☐ Final Walkthrough
☐ Closing                     ☐ Funded                    ☐ Possession
```

Each needs its own date (the TC overrides them constantly — inspections extend, closings move), its own
completion, its own completed-by. That cannot be a column.

### Ana's ruling: tasks nest under MILESTONES. Phases are retired.

Tasks already hang off milestones — just only 4 of the 30:

```
 57  start           → (not a milestone)
 38  closing         → closed
 18  effective       → under_contract
 14  inspection_end  → inspection_period_ends
 12  on_market       → on_market
```

`phase` was a *second* grouping that said nothing the anchor didn't already say, and made 81 tasks look
like they lived in two hierarchies. **Retired.**

`start` — 57 of 139 tasks, the biggest bucket — becomes a real milestone, **`loop_started`**. Then every
task nests under a milestone with zero special cases.

```
hl_tc_loop_milestone_catalog   31            hl_tc_loop_milestone    ~16 per loop
  └── hl_tc_loop_task_catalog  139             └── hl_tc_loop_task   ~81 per loop
      milestone_key + offset                       due = milestone date + offset
```

Migration is 1:1, no guessing: `closing→closed` · `effective→under_contract` ·
`inspection_end→inspection_period_ends` · `on_market→on_market` · `start→loop_started`.

### Two species of milestone — which is why Under Contract → Close is its own beast

```
CHECKPOINTS  (anchor=start, no offset)      COMPUTED DATES  (anchored + offset)
buyer_agreement_sent                        under_contract          KEY DATE
buyer_agreement_signed                      emd_due                 effective +3
listing_agreement_signed                    inspection_period_ends  KEY DATE
pre_listing_packet                          title_commitment        effective +10
                                            clear_to_close          closing −3
                                            final_walkthrough       closing −1
```

The top group answers *did it happen*. The bottom group are **dates with timing rules** — business-day
math, holiday rolls, 139 tasks hanging off them. Only the second group has anything to configure, which is
why it earns its own section.

## 3.4 — Sections become data, with a `source` column that owns the redirect
