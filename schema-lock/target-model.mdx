## ⚖️ THE ACTOR-AGNOSTIC VOCABULARY LAW (Zach, 7/31 PM — constitutional)

**"The whole CRM is designed so that if a human can do it, the AI can do it — so an ai_ prefix on an
action is REDUNDANT."** One vocabulary of ACTIONS; the WHO (human · AI · clone, name, role) is carried
ENTIRELY by the user on the row — never by the kind. There is no `lender_looked_up`, no
`tc_looked_up_document`, no `ai_<anything a human could also do>` — a lookup is `property_searched`
whether Ana did it or Myli did; a text is `sms_sent` whether Zach typed it or his clone did.
**THE TWO-SIDED TEST (Zach's full statement, ratifying Adam's carve-out, 7/31 PM): "If anyone can do
it, there's NO prefix. But if it's genuinely a thing only the AI can do, it NEEDS the ai_ prefix."**
Both directions are requirements, not permissions: an action a human could take never forks by actor
(no prefix, the user carries the WHO) — AND an AI-machinery event with no human equivalent (the memory
engine's own operations: `ai_context_built`, `ai_fact_captured`, `ai_send_blocked`) MUST wear the
prefix, because there the prefix names the ACTION's nature, not the actor. Receipts from today: `ai_search` deleted (was `property_searched` + an AI user) ·
`ai_clone_stepped_in` deleted (was the real channel kind + an AI user) · `property_looked_up` folded
(was `property_searched` + Myli's id). New kind proposals are tested against this law FIRST.

## The pour — how we get there without the software ever stopping

   columns + sha256 · `hl_lead_custom_value` · `hl_lead_activity.website_hlid` · message thread ids /
   attachments / draft status · run-log cost columns · the loop↔transaction link.
2. **B · REPOINTS (one fold per push, alias-closure pattern)** — email → `hl_messages` · phone assignments →
   `hl_phone_numbers` · tokens → `hl_oauth_connections` · settings documents → `hl_settings` · segments merge ·
   the stage_id dual-write dies with its four writers in one commit.
3. **C · CUTOVER SURGERY (Zach in the room, ONE-COMMIT-RENAME)** — the person merge · trigger-events →
   catalog succession + the kind FK move · the `hl_transactions` split into `loops` + `transactions` ·
   FK-ghost drops (hl_agents, hl_channels, hl_conversations) · **the actor→user vocabulary rename**
   (Zach 7/31: "we don't have actor anymore, it's user and user_type") — lands as `user_name` /
   `user_type` / `user_id` (bare `user` is a Postgres reserved word), 58 files, ONE commit; until then
   the `hl_lead_conversations` view is the adapter — its OUTPUT already speaks the new names, so readers
   never migrate twice. **✅ THE CLONE IDENTITY RULING — SIGNED BY ZACH 7/31 PM**
   (his words: "clone gets its own user row, zach_ai_clone, user type=ai, linked to the user, so EVERY
   user can have an ai clone and it's distinguished if it does an activity"): **every clone is a REAL
   `hl_users` row** — `user_type='ai'`, its own id + name (`<user>_ai_clone`), `clone_of_user_id` → its

   SPEAK as the owner (the product's replies-as intent) via the clone_of link. **The standing constraint
   (guides/ai-agents, carried verbatim): a clone NEVER holds a service seat and NEVER owns a comms
   identity — identity yes, capabilities no.** This unblocks the rename: `actor_kind`'s distinction

   dies in the same pass). **ALSO SIGNED 7/31 PM — THE LEAD CATEGORY**: `lead_created` ("created a lead")
   + `lead_edited` ("edited a lead") join the catalog beside the `user_*` family — the kind-level
