## What it is

The vocabulary for **where a loop stands** (Processing, Waiting for Closing, Complete, …). Until mig
0599 this was **derived** by a 45-line read-time precedence ladder — you could not set a status, only
cause one. Zach's ruling ("i dont need those weird derived stuff, it should just be a simple drop
down") made it one stored column whose legal values are **rows on this page**.

## Where the data lives

| | |
|---|---|
| Vocabulary | `hl_tc_loop_status` — `key` · `label` · `color` · `icon` · `sort_order` · `is_active` · `is_terminal` · `transaction_type_key` · `section_key` |
| Sections | `hl_tc_loop_status_section` — the group bands the table displays (flat vocabulary since 0622) |
| Stored value | `hl_transactions.loop_status_key` FKs to `key` |
| API | `/api/tc/loop-statuses` |

## What the page does

- **Add, rename, recolour, reorder, section** statuses — the same shared builder as every other TC
  config surface (one builder, five identical pages by construction).
- **Scoped by transaction type**: a status can belong to Purchase or Sale, so a coordinator only sees
  the statuses that make sense for the loop they are on (the Transaction Types page owns that
  vocabulary).
- The **LOOPS column** counts live loops on each status, and the delete guard refuses to remove a
  status while loops still point at it — the count shows before you try.
- `is_terminal` marks the statuses that end a loop's life (the reporting layer reads it).
