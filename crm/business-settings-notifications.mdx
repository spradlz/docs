Settings → Notifications controls every alert that goes to **you** (or the team). Client-facing messages
(tour confirmations, welcome emails, listing alerts) are **not here** — those are workflows managed per
trigger event in [Registration Trigger Events](/settings/lead-platform).

## The two panels

| Panel | Who it's for | What it controls |
|---|---|---|
| **How I get notified** | Each agent, personally | Where your alerts land, which events ping you |
| **Sent from** | Admins only | The outbound email + SMS identity for system alerts |

---

## How I get notified

### My Channels

The phone numbers and email addresses where YOUR alerts land. Add a phone → you get text pings. Add an
email → you get email pings. You can have multiple of each. Each recipient controls their own channels;
no agent can configure another agent's.

### Event toggles (BELL / TEXT / EMAIL)

Every notification event has three independent delivery toggles:

| Toggle | What it does |
|---|---|
| **BELL** | In-app bell (always records regardless of TEXT/EMAIL) |
| **TEXT** | Sends an SMS to each number in My Channels |
| **EMAIL** | Sends an email to each address in My Channels |

**TIMING** shows either "Instant" (fires immediately) or an "Nh" delay chip (Agent Nudges only — fires
after N hours of silence). **SENT** is a live count of deliveries; click it to see the drill-down log of
who got what and when. **VIEW** (eye) opens the notification template. **CONFIG** (gear) opens the
per-event timing rule.

#### The Connected Phone rule

**Text / Missed Call / Voicemail are always locked ON for SMS.** A lead reaching you always texts your
cell — the TEXT toggle for these three events is disabled (you can't turn it off). This matches how
`ALWAYS_SMS_CLASSES` works in the dispatch layer (`dispatch.ts`).

---

### Event sections

#### New Lead Activity

One class: **New Lead** (`lead_created`). Fires on any first-time registration from any source
(HouseLoop, Zillow, Realtor.com, etc.). The message body shows what the lead did — saved a search,
requested a tour, shared a home — plus their CRM link.

#### Existing Lead Activity

Per-activity classes for leads already in the CRM. Grouped by channel:

| Sub-group | Events |
|---|---|
| **Website activity** | Home liked · Home saved · Home shared · Saved search · Tour request · Contact request · Seller request · Home value report · Property viewed |
| **Calls** | Call received · Missed call · Voicemail |
| **Text** | New message (always SMS, locked ON) |
| **Emails** | Email received |

The Calls / Text / Emails sub-groups were folded into Existing Lead Activity on **2026-07-14** (Zach) —
the old standalone "Communications" section is gone. Each event toggles independently.

#### Lead Lifecycle

Stage changed · Lead assigned · Added as collaborator · AI clone activated · Lead reassigned ·
Appointment scheduled · Appointment completed.

#### Agent Nudges ⏰

Time-based reminders that fire when a human drops the ball:

| Nudge | Fires when |
|---|---|
| **Acknowledge Handoff** | Myli hands the lead to you and you haven't introduced yourself within the configured delay |
| **Response Needed** | A lead messaged you (text / email / call) and you haven't replied within the configured delay |

Each nudge has a **timing rule** (CONFIG gear) — threshold hours + on/off per channel. The default is
Instant. If AI Failover is on, the clone steps in when Acknowledge Handoff fires.

#### AI Follow-Up 🤖

Pings when the AI does something: AI Phone Calls · AI Messages Sent · AI Facts Captured · AI Homes
Searched · AI Stages Advanced · AI Appointments Set. Off by default — opt in to the ones you want.

#### Website Activity 🌐

**Daily website digest** — a morning email summarizing the last 24h on houseloop.ai (real humans,
registrations, homes viewed, searches, requests). **Bot/crawler breakdown** — include the crawlers &
bots section in the digest.

#### Transaction Deal Notifications 📁

Loop created · Under contract · Document signed by client · Milestone reached · Transaction closed ·
Transaction lost · Status changed · TC assigned · Key date approaching.

Fires to the deal's assigned agent and the TC coordinator.

#### System Alerts

Live health badges for: Gmail disconnected · BlueBubbles disconnected · Phone / Twilio disconnected.

#### Inbox Notifications

Subscribe to any inbox (an agent's personal inbox or a shared line) to get pinged on every text, call,
and email that hits it — even for leads not assigned to you. This is the "watch my wife's inbox"
control. Stacks with the notification scope below.

## Admin-only controls

### Global delivery master switches

Account-wide kill switches that sit **on top of** everyone's personal prefs:

- **Email off** → no notification email sends to anyone on the team, regardless of their per-event
  setting. The in-app bell still records.
- **SMS off** → no notification text sends to anyone.

Use these to silence a channel account-wide in one flip. Only visible to admins (`canEdit = true`).

### Which leads notify me (scope)

Admins can choose:

| Scope | Behavior |
|---|---|
| **Only leads assigned to me** | Default — you hear about a lead when it's yours |
| **All leads — any agent** | Every registration + activity across the whole team |

Regular agents always see only their assigned leads; the scope card is hidden for non-admins.

## Sent from

Two outbound identities for **internal / team alerts**:

| Sender | Key | Used for |
|---|---|---|
| **Email sender** | `team_alerts` | All system + team email notifications |
| **SMS sender (INTERNAL)** | `outbound_sms` | All system + team text notifications (agent alerts) |

These are **not** the addresses leads see — see [Brand line (public)](#brand-line-public) below.

### Brand line (public)

A dedicated public identity the **HouseLoop brand** uses when texting or emailing a lead:

| Sender | Key | Used for |
|---|---|---|
| **Brand SMS line** | `brand_public_sms` | Listing alerts, saved-search digests, registration texts |
| **Brand email sender** | `brand_public_email` | Same — every branded lead email sends from this one address |

Promote a number from the pool in [Phone Provider](/settings/phone-provider). Keep this separate from
the internal `outbound_sms` alert line so leads don't see your internal (913) 800-4470 number.

## Architecture notes (for builders)

- **`createNotification`** (`lib/notifications/create.ts`) fans out to the lead owner + every
  `notif_scope='all'` admin. The 5-min dedup keys on `(entity_type, entity_id)` — each distinct
  inbound signal fires its own notification; reprocesses are dropped.
- **`dispatch.ts`** gates SMS on `ALWAYS_SMS_CLASSES` (new_message, missed_call, voicemail) regardless
  of pref. Email/SMS prefs are per-agent per-event; the global master sits above them.
- **Inbound Twilio SMS → notification:** the SMS webhook (`app/api/phone/webhooks/sms/route.ts`)
  inserts into `hl_bb_events` (channel='sms') and calls `notifyInboundMessage` with the row's UUID `id`
  (NOT the raw `SM…` MessageSid — that string can't cast to the `uuid` column in `hl_notification`).
- **Inbound iMessage → notification:** same path via the BB webhook
  (`app/api/bb/inbound/route.ts`); BlueBubbles GUIDs are UUID-formatted so they pass directly.
- **Notification scope** persisted in `hl_users.notif_scope` ('assigned' | 'all'). Admins can change
  it; non-admins are always clamped to 'assigned' server-side.
- **Per-event timing** (Agent Nudges delay) stored in `hl_agent_nudge_rules` and read by the Inngest
  nudge function at fire time.
- **Sent counts** come from `/api/notification-sends` (run-log source='notification'). Click the count
  → drill-down modal with who + when.

## ⚠ THE SILENT-BELL BUG — `inAppOnly` defaulted your alerts to bell-only (found 2026-07-28)

**Symptom.** Zillow in-app messages — including live tour requests — created a bell card and **never reached
Zach's phone or inbox**. Every gate read GREEN: `_global` on, `in_app_message` Notify on for both arms, per-user
prefs `{sms:true, email:true}`, two channels configured, not muted. The only evidence anywhere was
`hl_notification.channels_sent = []`.

**The proof that killed every "check your settings" theory** — two rows, same recipient, same `event_key`,
same prefs, minutes apart:

```
"Unknown Caller texted back"   pref {sms:true,email:true}  #chan 2  →  channels_sent ["sms","email"]
"💬 Evelyn Morales sent a…"    pref {sms:true,email:true}  #chan 2  →  channels_sent []
```

**Root cause — an inherited default two layers away.** `createNotification` only dispatches inside
`if (!args.inAppOnly)`. `notifyLeadEvent` (`lib/notifications/lead-events.ts:69`) defaults
`inAppOnly: opts.inAppOnly ?? true` — correct for incidental CRM chatter nobody asked to be paged about. But
`routeFubNotification` called it **without passing the flag**, so it inherited `true`:

- A lead **with an assigned agent** → `notifyLeadEvent` → `inAppOnly: true` → **bell only, forever.**
- The native text path (`notifyInboundMessage`) calls `createNotification` **directly** → dispatches → sms+email.

So the two paths diverged on a default, not on a decision. Every FUB-routed notification for an **owned** lead
was silently bell-only.

**Fix.** `routeFubNotification` now passes `inAppOnly: false` explicitly. The rule it encodes:

> **If the gates said FIRE, we DELIVER.** The router runs *after* the `_global` master and the per-type Notify
> toggle have already decided. Channel choice belongs to the recipient's own prefs in `dispatchNotification` —
> never to a default inherited from a helper two layers up.

**Second fix — a thrown dispatch now names itself.** `dispatchNotification`'s outer `catch` only did
`console.warn`, so a throw produced a bell row with `channels_sent = []` and **zero database trace** —
indistinguishable from "the gates said no". It now writes a `dispatch-error` row to `hl_run_log`
(source `notification`), alongside the existing `dispatch-drop` rows that record pre-send gate reasons
(`channel_master_off` · `prefs_off` · `no_channel` · `no_template` · `muted`).

<Note>
**Debugging a missing notification — the order that actually works.** `channels_sent = []` means *nothing was
delivered*, not *nothing happened*. Read `hl_run_log WHERE source='notification'` for that minute:
`sms-dispatch`/`email-dispatch` = an attempt (success or failed) · `dispatch-drop` = a gate blocked it, with
the reason · `dispatch-error` = it threw · **nothing at all** = the dispatcher was never called, so look for an
`inAppOnly` upstream. Do **not** start by re-checking the user's toggles — that was the wrong first move here
and it cost days while real tour requests went unanswered.
</Note>

## 🔴 THE IN-APP NOTIFY PASS HAD NEVER RUN — NOT ONCE (found + fixed 2026-07-28)

Fixing the silent-bell bug above made delivery work — but **only for notifications someone fired by hand.**
The automatic path that is supposed to notice a new Zillow in-app message and notify you had **never worked,
and reported `"notified": 0` + SUCCESS on every run since it was built.**

Zach's words when he realised: *"I got those alerts from FUB and Premier Agent and my own software that I work
18 hours a day on for the past year refuses to notify me."* Four tour requests from Bradley Bengel for the next
morning sat un-sent.

**Two silent layers, stacked — each one alone enough to hide the other:**

| # | Layer | Why nothing failed |
|---|---|---|
| ① | **The ledger column was on the wrong database.** `fub.text_messages.notified_at` existed on the **Railway mirror**, never on **Camp David** — and the sweep reads Camp David. | The query threw `column "notified_at" does not exist`, hit a bare `.catch(() => ({ rows: [] }))`, and became an empty list. No DDL for that column exists anywhere in the repo — it had been added to Railway by hand. |
| ② | **`HL_INTERNAL_SECRET` was absent from pm2's environment.** | Once ① was fixed, the POST hit `[notify] HL_INTERNAL_SECRET unset — POST skipped` — **and the run still printed `"notified": 0` and exited SUCCESS.** `FUB_API_KEY` in that same file already resolved from the sibling `.env`; the secret did not. |

<Warning>
**⚠️ THE LANDMINE — a hand-run check queries a DIFFERENT DATABASE than the running process.**

```
/Users/lee/.env        DATABASE_URL → yamabiko.proxy.rlwy.net:40035/railway   ← RAILWAY (mirror)
pm2 fub-body-recovery  DATABASE_URL → localhost:5432/bossloop                 ← CAMP DAVID (ground truth)
```

Debugging with `. ./.env && psql "$DATABASE_URL"` reads **Railway**, while the sweep reads **local**. That is
how *"I verified 4 rows are eligible, the sweep should have sent them"* got reported as fact — twice — when the
sweep was querying a table that did not even have the column.

**To reproduce what a pm2 process sees, take its env from the PROCESS, never the .env file:**
```bash
ps eww $(pgrep -f fub-body-recovery-consumer | head -1) | tr ' ' '\n' | grep '^DATABASE_URL='
```
</Warning>

**The fix:** `notified_at` added to **Camp David** (ground truth per the `fub-relay` header — the relay reads
its column list from CD's `information_schema`, so it flows to Railway automatically); **402,346 rows
backfill-marked notified** so the first working sweep could not blast 13,461 historical messages (`pending = 0`
verified first); `HL_INTERNAL_SECRET` given the same `.env` fallback `FUB_API_KEY` already had; and **both
failure modes now log loudly** — a query that cannot RUN is an outage, not "nothing to do."

**Proof:** run with pm2's exact environment, nothing sourced → `"notified": 1` and
`hl_notification.channels_sent = ["sms","email"]`.

<Note>
**The pattern behind all four notification bugs found this night** — the silent bell, the thrown dispatch, the
missing column, the missing secret — is identical: **an error swallowed into a green result.** `"notified": 0`,
`channels_sent = []`, and `{ok:true}` all meant "nothing happened" and "everything is fine" at the same time,
and nothing in the system could tell them apart. When auditing this pipeline, the only trustworthy question is
*"can I name a message that reached the phone?"* — never *"did the job report success?"*
</Note>

**Known-open (next):** Zillow in-app messages still resolve to the generic `new_message` notify class
(`lib/notifications/router.ts` → `FUB_EVENT_CLASS`), whose subline is `{{event.time}}`. That is why the card
reads *"💬 Evelyn Morales sent a message"* with no property and no body, while `property_inquiry` renders
`{{listing.address}}`. A dedicated `in_app_message` class needs a row in `hl_notify_classes` **and** seated
email/SMS templates — switching the class without seating templates makes `dispatch` log
`NO TEMPLATE REGISTRY ENTRY` and send nothing, so the two must land together.
