## The three layers, one sentence each

| layer | what it is | may it be edited? |
|---|---|---|
| **THE TAPE** — `fub.*` | The verbatim mirror of Follow Up Boss: people, events, notes, calls, emails, team members. | **Never.** It is evidence, not an answer. |
| **THE STAGING LAYER** — the subject of this PRD | One PRE-DERIVED row per FUB person carrying every answer the CRM needs, computed by re-runnable jobs. | Regenerated by its jobs, never hand-edited. |
| **THE IMPORT** | A dumb copy from staging into the CRM through the sanctioned writers (the pour for past clients; any future lead import). | It reads staging ONLY — never the raw tape, never derives. |

## Why (the disease this kills)

Every import that "thinks" at import time re-litigates the same questions — identity, agent
history, household, DNC — and two imports can answer them differently. That is the circles Zach
named on the resolver (two months of re-resolving). The cure is structural: **all derivation runs
BEFORE import, lands in staging where a human can read it, and the import copies what staging
says.** A wrong answer is fixed by fixing the staging job and re-running it — visibly — not by a
smarter import.

## The staging person row (the target shape)

One row per FUB person. Every column is DERIVED by a named, re-runnable job, with provenance:

| column group | carries | derived from (the job) |
|---|---|---|
| **identity** | resolved person verdict (`household-resolved` / `identity-confirmed` / `wrong-human` / `unresolved`), the evidence citation | the triangulation method (ledger 304): dotloop client parties → SISU → `fub.notes` → the contact census |
| **contact census** | EVERY email + phone on the record, each tagged person-vs-household (an email names a person; a phone names a household) | `fub.people` parse + the household artifact rules (ledger 311) |
| **agent relationship history** | the parsed history from tags — any other agent's tag supersedes the Ana Spradling / Ben Freshel distribution tags; team-exit marks the departure; current agent = Zach | the tag parser (Zach's 8/15 rules; ledger 314 — this is a COLUMN here, never its own twin table) |
| **household** | spouse/partner edges to other FUB persons, with the source (note, dotloop party, shared closing) | the same triangulation evidence |
| **relationship class** | past_client / lead / vendor / agent-peer, with the closing evidence for past clients | SISU spine + the book |
| **compliance** | the explicit-DNC flag (ONLY the named set: Harrisons · Burdett · Radke · Suzana Lewman), never derived from tags/stages | the named DNC ruling (ledgers 299/313) |
| **readiness** | import/pour readiness verdict + what blocks it, per person | the pour matrix |

**Standing laws that bind this table:** one answer table (a fact lives here once — the era/source
is a column); the tape is never edited; staging is derived and disposable; the import is
idempotent through the sanctioned writers; `is_backfill` never rings a bell.

## What already exists (honest status, 2026-08-17)

- **Events: DONE and LIVE.** `hl_event_mapping` + the FUB staging adapter translate tape events
  into catalog kinds — a live lead's Zillow views and tour requests render as HouseLoop cards
  today through this exact path.
- **Identity: DERIVED for the whole held set.** The 31 triangulation verdicts (ledger 311) are the
  first real rows of the identity column — 22 household-resolved, 9 identity-confirmed, 0 wrong
  humans, every verdict with its dotloop/SISU/notes citation.
- **The pour (past-client import): BUILT and pilot-proven** — stage-at-mint, hlid forwarding,
  honest dry-run accounting. It currently derives some answers at run time; under this PRD those
  derivations MOVE into staging and the pour reads them.
- **NOT built yet:** the staging person TABLE itself (the shape above), the tag parser job, the
  contact-census job, and the readiness projection reading staging instead of computing.

## The order of work

1. **DDL for the staging person table** (staging shelf, desk-gated) — columns above, provenance on
   every derived group.
2. **The jobs**, one per column group, each a registered Inngest function with a run-log receipt
   (Inngest or it doesn't exist): identity-fill (seeds from the 31 verdicts + extends book-wide),
   contact-census, tag→agent-history parser, household edges, readiness.
3. **A readable surface** — Zach can open a FUB person and SEE the staged answers before anything
   imports (the agent-history dropdown/column he asked for reads THIS).
4. **Repoint the pour** to read staging for identity/household/agent-history instead of deriving.
5. **The ratchet:** any import that reads `fub.*` directly for a DERIVED answer goes red.

## The three requirements

<Warning>
**PROVENANCE, said plainly:** these three are the DESK'S wording, not Zach's. They compress a day of
his live rulings (each rule below carries its own source and date), and they extend the one law he
did sign verbatim on 2026-08-17: *"we should not be deriving anything without it already derived and
structured properly in the fub mirror… the fub mirror should be a staging table for the houseloop
crm."* If you need Zach's exact words for a specific rule, they are in that rule's row — not here.
</Warning>

**R1 — A staged lead lands in a FINISHED SCHEMA.** Every answer the CRM needs is a typed column with
provenance, computed before import. The import copies; it never derives, parses, guesses or reaches
back into the tape for a derived answer. The nearest thing to a Zach quote is his 8/21 01:36Z
question, which is really this requirement asked as a question: *"WHAT IS THE TABLE THAT GETS
POPULATED WHEN WE PULL A LEAD INTO HOUSELOOP CRM FROM FUB AND DO WE FREEZE THAT TABLE AND TIME STAMP
IT AS FOLLOW UP BOSS LEGACY… so if this happens again its just a simple delete lead, and restore
lead and it comes back perfect."* **That is the acceptance test: trash a staged lead, re-import it,
and it comes back identical.**

**R2 — The staged HISTORY reads as CATALOG CARDS, not as raw tape.** Every historical event a staged
lead carries is already resolved to a catalog kind with its actor, its venue and its sentence —
i.e. it is a card before it is imported, and the import files it through `logActivity` rather than
inventing a second writer. A staged history that still needs the render layer to figure out what
happened has not finished staging.

**R3 — The item that TRIGGERED the pull is marked and timestamped on the record.** Not the import
job, not "backfill": the actual co-temporal event that caused this person to become a lead, named
honestly and carrying its own timestamp. This is the true-trigger rule (below), and it is the one
of the three that Zach signed word for word.

## The rules the build must honor

Each rule is here because a real lead was wrong without it. **A rule with no verbatim quote is a
desk ruling and says so** — do not upgrade it in a later retelling.

### 1. THE TRUE-TRIGGER RULE — signed by Zach 2026-08-22 (verbatim)

Zach, ratifying the desk's proposal in his own message (19:56Z), with James Wisner's card as the
worked example:

> *"the pull card's reason must be the TRUE co-temporal trigger — even when that trigger is a
> machine inference — honestly labeled. So Wisner's card would read: ▎ Lead created in HouseLoop via
> the Follow Up Boss integration ▎ Action: pulled in on a FUB automation note — "Buyer has started
> searching again after being inactive…", June 30 — this is the correct fix."*

**A machine-inference reason is SELF-INDICTING by design and is never dressed up as a human action.**
Live in `apps/houseloop-crm/lib/leads/arrival-trigger.ts`; staging inherits it rather than
re-deriving it.

**THE REASON-RESOLUTION LADDER** (desk wording, ruled 2026-08-22 downstream of the signature above):

| rung | what it is | renders as |
|---|---|---|
| ① | a co-temporal **qualifying** action (a kind whose `creates_lead` is true) | the action, with its venue |
| ② | a co-temporal **non-qualifying** source event with SUBSTANCE | its honest family — "a FUB automation note", "a Zillow insight" |
| ③ | manual | a person pulled this lead in |
| ④ | **unexplained = a filed defect** | drawn, never hidden — `unrecorded`, in warning colour |

Four mechanics the staging build must carry, not re-invent:

- **The window is MEASURED, not chosen:** 3 days back, 10 minutes of forward grace. 33 of 50 stamped
  lags land within 89 minutes, then hours, then 2.4 days — and the next one is 30 days. The gap is a
  factor of twelve, which is what makes 3 days a boundary rather than a preference.
- **Rung ② prefers SUBSTANCE over NEAREST.** Nearest-wins on Wisner picks a contentless
  `virtually_toured` and renders "took a virtual tour"; substance picks the insight and renders the
  card Zach actually signed.
- **Candidates are source-side only** (an `archived_from` stamp or a `fub.*` source table). Without
  that fence, rows written three minutes AFTER the pull get cited as its cause.
- **The qualifying set is read live from `hl_event_mapping.creates_lead`** — never a list in code
  (Bedrock D5: the toggles are DATA).

The defect this cures, measured 8/22: the earlier correction pass searched only qualifying kinds and
reached backwards, so Wisner's 2026-06-30 pull cited an `sms_received` from 2026-04-25 — **65 days
stale**. Nine real leads carried that shape, up to 351 days.

### 2. THE FILING-SIDE GENERATION PREFERENCE — desk ruling 2026-08-22 ⚠ GATES the cohort rehearsal

When one `(person, body, timestamp)` fact exists in both generations, **the API row files and the
scraped twin never does.** The scraped generation disagrees with the API generation on message
DIRECTION in **19,764 of 58,854 twin pairs**; on the API generation the actor is trustworthy.

⛔ **This must be LIVE BEFORE any cohort rehearsal.** Importing 49k through a reader that believes
111k lying rows replays the disease at scale — the cleanup is not a substitute for the rule, because
the next pull mints the twins again.

### 3. THE MACHINE-NOTE ACTOR RULE — ordered by Zach 2026-08-22 (verbatim), shipped

Zach, on finding his own name on a Zillow sync note:

> *"Zach Spradling created a note, wants to view a property, wants to be contacted by text.
> **I DIDNT DO THAT.**"*

(and on 8/21: *"it says zach spradling created a note… THAT IS A FUCKING ZILLOW SYNC NOTE FROM FUB"*)

⚠ **Scale for staging: 1,155 machine notes are latent on the tape across 36 agent names** (largest

thousand robot notes in human clothes. Note the arithmetic drift in the record — the day card queues

### 4. THE VENUE RIDES WITH THE VERB — signed by Zach 2026-08-22 (verbatim, iterated live)

The action sentence names **where the action happened**, never the pipe: *"made a general inquiry on
Zillow."* This is Bedrock **D2 in a single field** — Zillow is a SOURCE, Follow Up Boss is a PIPE.
Passing the carrier here would put *"made a general inquiry on Follow Up Boss"* on a card, which
asserts that somebody browsed our CRM vendor.

The hero card Zach signed, in his words (20:04Z): *"bottom left badge should be follow up boss icon
and the right of it should be the source… zachary bell, imported via follow up boss integration, no
fub signal [up top], we keep the fub signal at the bottom left, and the rest of the card stays the
same."* And on timeline events (19:58Z): *"the fub logo rides the EVENT."*

The three grammar lines live as DATA in `hl_settings.arrival_grammar`, drafted by Zach at 13:24Z:

```
Lead created in HouseLoop [via the Follow Up Boss integration]
Lead source: <bucket>
Action: <signal> — <payload>
```

Staging supplies the venue and the payload as COLUMNS. It never hands the renderer a carrier name.
⚠ Open, not shipped: the venue-logo law on timeline event cards (parked as its own measured pass —
`avatarFor` precedence touches every legacy card).

## What staging must NOT reintroduce — the six named diseases

The 8/21–8/22 inventory run reduced the whole episode to six causes. Every one of them is a
staging-layer failure mode, which is why this PRD exists:

1. **Contaminated stamps** — a backfill dressing re-imports in campaign clothes.
2. **False-legacy masking, in BOTH directions** — native rows masked as legacy, legacy rows unmasked.
3. **The twin generation** — the scraper's direction-blind second copies (rule 2 above).
4. **Fabricated participants** — the assigned-agent recipient rule; FUB auto-notes wearing human
   actors (rules 3 and 7).
5. **Unwired truth** — grammar and reasons built with zero render callers. A staged column nothing
   reads is not progress.
6. **Mint floodgates** — cured by rule 9.
