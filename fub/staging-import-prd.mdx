## The three layers, one sentence each

| layer | what it is | may it be edited? |
|---|---|---|
| **THE TAPE** — `fub.*` | The verbatim mirror of Follow Up Boss: people, events, notes, calls, emails, team members. | **Never.** It is evidence, not an answer. |
| **THE STAGING LAYER** — the subject of this PRD | One PRE-DERIVED row per FUB person carrying every answer the CRM needs, computed by re-runnable jobs. | Regenerated by its jobs, never hand-edited. |
| **THE IMPORT** | A dumb copy from staging into the CRM through the sanctioned writers (the pour for past clients; any future lead import). | It reads staging ONLY — never the raw tape, never derives. |

## Why (the disease this kills)

Every import that "thinks" at import time re-litigates the same questions — identity, agent
history, household, DNC — and two imports can answer them differently. That is the circles Zach
named on the resolver (two months of re-resolving). The cure is structural: **all derivation runs
BEFORE import, lands in staging where a human can read it, and the import copies what staging
says.** A wrong answer is fixed by fixing the staging job and re-running it — visibly — not by a
smarter import.

## The staging person row (the target shape)

One row per FUB person. Every column is DERIVED by a named, re-runnable job, with provenance:

| column group | carries | derived from (the job) |
|---|---|---|
| **identity** | resolved person verdict (`household-resolved` / `identity-confirmed` / `wrong-human` / `unresolved`), the evidence citation | the triangulation method (ledger 304): dotloop client parties → SISU → `fub.notes` → the contact census |
| **contact census** | EVERY email + phone on the record, each tagged person-vs-household (an email names a person; a phone names a household) | `fub.people` parse + the household artifact rules (ledger 311) |
| **agent relationship history** | the parsed history from tags — any other agent's tag supersedes the Ana Spradling / Ben Freshel distribution tags; team-exit marks the departure; current agent = Zach | the tag parser (Zach's 8/15 rules; ledger 314 — this is a COLUMN here, never its own twin table) |
| **household** | spouse/partner edges to other FUB persons, with the source (note, dotloop party, shared closing) | the same triangulation evidence |
| **relationship class** | past_client / lead / vendor / agent-peer, with the closing evidence for past clients | SISU spine + the book |
| **compliance** | the explicit-DNC flag (ONLY the named set: Harrisons · Burdett · Radke · Suzana Lewman), never derived from tags/stages | the named DNC ruling (ledgers 299/313) |
| **readiness** | import/pour readiness verdict + what blocks it, per person | the pour matrix |

**Standing laws that bind this table:** one answer table (a fact lives here once — the era/source
is a column); the tape is never edited; staging is derived and disposable; the import is
idempotent through the sanctioned writers; `is_backfill` never rings a bell.

## What already exists (honest status, 2026-08-17)

- **Events: DONE and LIVE.** `hl_event_mapping` + the FUB staging adapter translate tape events
  into catalog kinds — a live lead's Zillow views and tour requests render as HouseLoop cards

- **Identity: DERIVED for the whole held set.** The 31 triangulation verdicts (ledger 311) are the
  first real rows of the identity column — 22 household-resolved, 9 identity-confirmed, 0 wrong

- **The pour (past-client import): BUILT and pilot-proven** — stage-at-mint, hlid forwarding,

  derivations MOVE into staging and the pour reads them.
- **NOT built yet:** the staging person TABLE itself (the shape above), the tag parser job, the

## The order of work

1. **DDL for the staging person table** (staging shelf, desk-gated) — columns above, provenance on
   every derived group.
2. **The jobs**, one per column group, each a registered Inngest function with a run-log receipt

4. **Repoint the pour** to read staging for identity/household/agent-history instead of deriving.
5. **The ratchet:** any import that reads `fub.*` directly for a DERIVED answer goes red.

## THE REQUIREMENTS — dictated by Zach, 2026-08-22

### R1 — COMPLETE SCHEMA, NO HOLES (Zach, verbatim, 2026-08-22)

> *"the schema has to match. There cannot be holes in anything."*

Every staged row lands with **every destination field either resolved or explicitly recorded as
absent — never silently null.** A NULL that means "we could not derive this" and a NULL that means
"this person genuinely has none" are different facts, and a column that cannot tell them apart is a
hole. Absence is a recorded verdict with a reason, the same way a derived value is a recorded
verdict with a basis.

The acceptance test is Zach's own from 8/21 01:36Z, which is this requirement asked as a question:
*"WHAT IS THE TABLE THAT GETS POPULATED WHEN WE PULL A LEAD INTO HOUSELOOP CRM FROM FUB… so if this
happens again its just a simple delete lead, and restore lead and it comes back perfect."* **Trash a
staged lead, re-import it, and it comes back identical.** If anything was derived at import time
rather than read from staging, it will not.

### R2 — EVERY MESSAGE CARRIES ITS ACTOR; DERIVATION IS LICENSED (Zach, verbatim, 2026-08-22)

> *"the actor who was the agent that sent the message. That can be derived. It doesn't have to be
> perfect. It can be derived from the tags that we find, team exit / agent name, or by reading some
> of the messages to see who sent the message and then inferring that to the other messages."*

⭐ **This licenses IMPERFECT derivation for staging attribution — on one condition: the provenance
rides along.** Every derived rung stamps WHAT it derived from. Unstamped inference stays banned; an
actor with no `actor_source` is a hole under R1, not an answer.

**THE STAGING ACTOR LADDER** — tried in order, first hit wins, the rung recorded on the row:

| rung | `actor_source` | how it decides | confidence |
|:-:|---|---|---|
| ① | `witnessed` | the tape names the sender (`user_name` on the row) | the tape's own claim |
| ② | `assignment_derived` | `fub.assignment_history` — who held this person AT THE MESSAGE'S TIME | high |
| ③ | `tag_derived` | the agent-relationship tags (any other agent's tag supersedes the Ana Spradling / Ben Freshel distribution tags; team-exit marks the departure) | medium |
| ④ | `content_inferred` | a signed message body naming its own sender, propagated to its thread neighbours | medium-low, and it says so |
| ⑤ | `degraded` | nothing decided it — recorded as unresolved WITH the reason | none, and never dressed up |

Four things the ladder must not do:

- **Never re-derive at render time.** The staged actor is the answer; surfaces read it (the actor
  canon, one door).
- **Rung ② is time-aware or it is wrong.** "Who is assigned NOW" attributes a 2024 message to the
  current owner. The join is against the assignment interval containing the message's `occurred_at`.

<Warning>
**⚠ RUNG ② CAVEAT — measured by builder-mask, 2026-08-22, and it changes what the rung can claim.**
`fub.assignment_history` has **`changed_at` NULL on all 22,449 rows.** So the custody ORDER is real,
but the **boundaries are bounded by OUR SCRAPE OBSERVATIONS, not by the actual handoffs** — we know
who held a person in what sequence, not the minute custody changed. A message near a boundary can
land on the wrong side of it.

**The rung therefore carries its honesty number, not a claim of correctness.** Control measurement
against 126,281 witnessed rows (where the tape names the sender, so rung ① could grade rung ②):
**88.3% exact, 4.13% wrong-person.** That 4.13% is the price of the rung, it is a KNOWN price, and
it is exactly what R2's licence covers — *"It doesn't have to be perfect"* — **on the condition that
`actor_source='assignment_derived'` rides along so a downstream reader can see it was inferred.**

Two consequences the build must honor: **never let rung ② overwrite rung ①** (the witnessed row is
the grading key — overwriting it destroys the only instrument that can measure the ladder), and
**re-run the control whenever the ladder changes.** A ladder whose error rate is unmeasured is back
to unstamped inference no matter what column it writes.
</Warning>
- **Rung ④ propagates within a THREAD, never across a person's whole history.** One signed message
  licenses its neighbours, not every message that person ever received.
- **The machine-note actor rule outranks all five rungs** (rung ZERO, below) — a robot note never
  reaches the ladder to be dressed in a human name.

⚠ **Rung ① is the tape's claim, not the truth.** The recipient-fabrication revert (rule 7 below) is
the standing proof that a confident override of the tape can be pure, tested, green and wrong. Rung
① beats rungs ②-④ because the tape is evidence and they are inference — not because it is infallible.

### R3 — FULL TIMESTAMP PROVENANCE: THREE CLOCKS (Zach, verbatim, 2026-08-22)

> *"there has to be a timestamp when it got filled in, when it got pulled into BossLoop, when the
> lead got pulled in via the integration."*

Every staged fact carries **three first-class clocks**, never one collapsed field:

| clock | column | what it answers |
|---|---|---|
| **the event's own time** | `occurred_at` | when the thing actually happened, in the world |
| **the staging fill** | `staged_at` / `filled_at` | when WE derived this row — so a re-run is visible and a stale derivation is findable |
| **the lead's pull moment** | `lead_pulled_at` | when this person became a HouseLoop lead through the integration |

The third clock is already law: **`created_at` is the HouseLoop pull date** (rule 6 below) — Renita
Ford's 7/14 was correct and the 50-lead restamp was killed over exactly this. Keeping the three
apart is what makes a wrong date a *fixable derivation* instead of an argument.

## The naming convention — FOUND, not invented

The question "what prefix does a FUB staging table take" was already argued and signed in migration
`0726_staging_event.sql`, and its four reasons transfer to the person grain unchanged: the shelf is
carried by the **noun** (`staging`), a human reads the review queue so `ONE_ANSWER_TABLE` test 4
answers PRODUCT `hl_*`, it is a standing conveyor rather than a one-pour scaffold, and there is no
`srg_`-style name collision needing the prefix trick. **The integration is a COLUMN** — there is no
`hl_fub_staging_event` and there must be no `hl_fub_staging_person`.

So: **`hl_staging_person`**, keyed `(integration_key, fub_person_id)`. The draft DDL is
`apps/houseloop-crm/db/migrations/DRAFT_fub_staging_person.sql` — `DRAFT_` is outside the boot
runner's `^\d{4}_` pattern, so it structurally cannot self-apply, the same protection `HOLD_` gives.

## The absence-verdict vocabulary (R1, typed out)

Every derived group on `hl_staging_person` carries a verdict from **one** closed set, and a CHECK
makes a NULL-without-a-verdict unrepresentable:

| verdict | means | R1 reading |
|---|---|---|
| `resolved` | a value was derived, and `*_source` names the rung that did it | the answer |
| `absent_on_tape` | the tape genuinely carries none | **a KNOWN answer, not a failure** |
| `unresolvable` | we could not decide; the reason is in `review_reasons` | never dressed up |

That distinction is the whole of R1: *"a NULL that means 'we could not derive this' and a NULL that
means 'this person genuinely has none' are different facts, and a column that cannot tell them apart
is a hole."* The pattern is not invented here — `hl_staging_event` already ships it as
`CHECK ((recipient_source = 'none') = (recipient_name IS NULL))`.

## What this map does NOT decide

The two open decisions from this PRD stand, unresolved, and the DDL carries **both as parameters**:

1. **The qualifying window, July 1 vs July 7.** Never a baked predicate — it travels as
   `trigger_window_spec` text on every row, so a re-run under the other answer is a visible
   re-derivation and rows from the two runs are distinguishable.
2. **The Google source bucket.** `source_raw` holds the tape's spelling verbatim; `source_key` holds
   only the bucketed answer, versioned. Re-bucketing changes one column and touches nothing else.

⛔ **Neither a source allow-list nor a date literal belongs in the DDL.** Either one converts an open
product decision into schema, which is exactly what makes it expensive to reverse.
