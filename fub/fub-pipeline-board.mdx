## Chapter 1 — Why FUB exists for us

**Follow Up Boss is a PIPE. Zillow is the SOURCE. Never conflate the two.** That is Bedrock decision
**D2**: the integration layer is first-class and multi-adapter; FUB is the permanent Zillow conduit for
the 49k book, and a future Zillow-direct connection would be adapter #2 — not a replacement for the
model. ([BEDROCK_LAW](/bedrock-prd))

### Why we built a scraper instead of using the API

Zach, verbatim (2026-08-18):

> *"I created the Camp David scraper… because FUB hides text message bodies and email bodies… we just
> call Camp David as a dumb job… agents don't work out of [FUB] daily — that was a huge one-time
> backfill — then we use it because FUB has a direct sync to Zillow users' behavior and in-app messages
> which I can't get through a normal API."*

The acquisition question is **closed**, ruled the same evening: *"going direct to zillow doesn't work…
we have to scrape."* The scrape is the primary road, and it gets hardened rather than replaced.

### FUB's three remaining jobs — and nothing else

1. **Zillow in-app messages** — a client's message inside Zillow, which has no API.
2. **Zillow behavior** — views, saves, searches, the insight notes Zillow writes into FUB.
3. **The preserved 49k history** — the one-time backfill of the book.

Everything else FUB once did for us is retired by ruling. Its own screens are gone: *"Its FUB screens
are dead to me — retire them."* Agents do not work out of FUB daily. We do not read FUB's dashboards,
and we do not treat its UI as a system of record. It is a pipe carrying Zillow's signal to our tape.

### What that buys, and what it costs

The signal is real and it is unavailable anywhere else — which is why the estate exists at all. The
cost is that the road runs through someone else's product, over a browser we do not control, into a
mirror that has to be watched. Chapters 4 and 5 are the whole answer to that cost.

## Chapter 2 — The five roads in (the 28-signal arrival map)

derived 2026-08-19 from the live `hl_event_mapping` table (CRM DB) — the registry the triggers UI, the
classifier, and the signal-set cage all read. The 28 signals are the MENU; beneath them the engine
holds 42 active recognition rules + 8 deliberate drop rules (trash filters).

## Chapter 3 — The two tapes (only ONE is live)

| | RAILWAY (`FUB_RAILWAY_DATABASE_URL`) | CAMP DAVID (`192.168.1.211/bossloop`) |
|---|---|---|
| **Role** | **THE LIVE TAPE** — the CRM's only FUB source, via the one chokepoint `lib/fub-import/fub-db.ts` | The scraper's browser host + staging hop (until slice 3 removes the hop) |
| **Webhook-fed tables** (people, notes, emails, events, calls) | Minutes-fresh — FUB webhooks write it DIRECTLY | **Frozen 2026-07-09** (the cutover). `fub-sync` retired permanently. |
| **Scraper-fed tables** (in-app texts, home activity, saved searches) | Arrives via the relay (home activity writes direct since 6/27) | Captured here FIRST by Chrome |
| **Backups** | Nightly dump, byte-exact offsite, **KEEP FOREVER** (Zach 8/18) | Nightly, plus the whole-DB dump |

⚠ **THE NAME TRAP:** `DATABASE_URL` means **three different databases** depending on how a process
started. Operations assert `current_database()` — never the env-var name.

### Three tables that read as outages and are not

Each of these is frozen on purpose. Each has been misread at least once, and one of them was filed as
a 41-day P0 on a feed that had never stopped.

| table | frozen at | why it is not an outage |
|---|---|---|
| `fub.webhook_event_log` | 2026-07-09 19:36:25Z | Its only writer was the retired `realloop.co` receiver (`apps/dashboard/server/fub-webhooks.ts:1212`). FUB's subscriptions moved to the CRM receiver the same hour — the road never stopped, the endpoint moved. The live arrival record is `hl_run_log` where `fn='fub-webhook-router'`. |
| `fub.sync_log` | 2026-07-09 19:36:25Z | Same writer, same HTTP handler — which is why both die in the same 78ms. |
| Camp David's `fub.zillow_home_activity` / `fub.zillow_insights` | 2026-08-16 (the ENOSPC) | The live truth is the **Railway** copy, current to the minute. This is the intended post-7/09 shape — but any surface still reading Camp David's `fub.zillow_*` is reading a corpse that will never advance again. |

Both `webhook_event_log` and `sync_log` carry a `COMMENT ON TABLE` tombstone saying exactly this.
⚠ **A tombstone in `pg_class.obj_description` is invisible to every `max(created_at)` query and every
table listing** — which is precisely how the same table got filed as an outage twice. Read the
tombstone before you file a freshness P0:
`SELECT obj_description('fub.sync_log'::regclass)`.
Full autopsy: [the arrival-log receipt](https://github.com/spradlz/BossLoop-Gold/blob/houseloop-app/.claude/reports/arrival-log-165/RECEIPT.md).

## Chapter 4 — The fleet (what runs, where, and what must NOT be restarted)

**The standing law of this chapter:** a pm2 status field cannot testify about a process pm2 has
forgotten — only the process's own FACT column can. The 8/16 ENOSPC killed the pm2 *daemon* while its
already-forked *children* kept writing, so "pm2 says down" and "it stopped working" turned out to be
two different claims. Every verdict below is a FACT-column measurement, not a status field.

### Camp David — the five that run (reboot-survivable, `dump.pm2` Aug 19 05:51)

| process | its FACT column | note |
|---|---|---|
| `fub-body-recovery` | drains `fub.body_recovery_queue` | the 3-min in-app sweep + hidden-body jobs |
| `fub-relay` | Camp David `fub.*` → Railway `fub.*`, 30s cursor loop, upsert-only, never deletes | measured lag: milliseconds |
| `fub-chrome-guard` | the Chrome the other roads depend on | |
| `fub-webhook-scraper` | `fub.webhook_scraper_heartbeat.last_beat` **on RAILWAY** | ⭐ see the correction below |
| `fub-home-refresh` | `fub.zillow_home_activity` on the Railway mirror | healthy; wrote 85s before measurement 8/19 |

⭐ **CORRECTION (8/19, `factcheck-168`): `fub-webhook-scraper` is UP and working.** The earlier
"deny-by-default, stays down" verdict measured the **wrong database**. Its heartbeat is unconditional —
it beats every 30s from the daemon loop whether or not there is work — and the row is on **Railway**,
where it was 40 seconds old at measurement. Camp David's copy of that same heartbeat is a **dead
sentry stuck at `polling` since 2026-05-30**; reading it is how the process gets declared dead while it
is running.

### Down, and staying down — with the reason, because the reason decides the risk

| process | status | why it stays down |
|---|---|---|
| `fub-watchdog` | ⛔ **DOWN since the 8/16 ENOSPC** (last log line 03:36:56) | ⚠ **Not merely deny-by-default — UNSAFE TO RESTART AS WRITTEN.** Restarting it points a self-described page-killing probe at the one Chrome that four live processes depend on, and arms a resurrection trigger for the backfills Zach ordered dead. The only behavior lost is the `partial → rehydrated` promotion sweep, which is scraper bookkeeping no surface renders. A rebuilt relaunch guard is tracked separately. |
| `fub-sync` | ⛔ **DOWN PERMANENT** | The ventilator: its `ON CONFLICT … synced_at = NOW()` re-stamped freshness onto a mirror frozen since 7/09. A dead job is visibly dead; a job that fakes its own pulse is worse than no job. |
| `fub-backfill-a` / `fub-backfill-b` | ⛔ down by order | the one-time backfill is finished |
| `fub-webhook-sink` | ⛔ down, one worker is enough | ⚠ **It was never a receiver.** The pm2 name is not the process: `sink` and `fub-webhook-scraper` point at the *same file*, so "sink" was a **second scraper worker** (the queue uses `FOR UPDATE SKIP LOCKED`, so two workers was intentional). Retiring it because "FUB no longer posts to it" would be the right call for an entirely wrong reason, and would leave the record claiming a receiver where a duplicate worker stood. |
| `hl-photos-redfin` | ⛔ retire candidate | Outside this estate — it writes no database at all (a JSON file), its queue is exhausted, and photo refresh on houseloop.ai is **not** broken. |

### CRM side — Inngest

`fub-webhook-router` (one run per webhook resource — the live arrival record) · `fub-lead-import` ·

## Chapter 5 — The sentries

`system-health-scan` runs every 10 minutes and pages Zach's cell on a NEW red.

| Sentry (probe key) | watches | FACT column | thresholds |
|---|---|---|---|
| `inbound_email_capture` — global | any inbound at all vs demonstrated volume | `hl_inbound_emails.received_at` | quiet &gt;24h = RED |
| `inbound_email_capture` — per mailbox | each of the 8 boxes via `synced_mailbox` | same | 24h RED; no/sparse history = AMBER, never paged |
| `inbound_email_capture` — the watch | Gmail watch renewal per box | `hl_oauth_connections.watch_expiry` | &lt;24h left = RED |
| `fub_feed_freshness` — per feed | every tape feed's arrival age | per-table latest rows | per-road windows |
| `fub_feed_freshness` — scrape roads | saved-search + home-activity capture | `scraped_at` (deliberate capture-time exception) | 6h ⚠ / 12h RED · 3h ⚠ / 6h RED |
| `fub_feed_freshness` — filing lag | captured-but-never-filed on real leads | tape vs `hl_activity_log` | any = RED |
| `body_recovery_consumer` — live rows | is the Camp David consumer draining at all | `fub.body_recovery_queue.requested_at` (pending) / `.claimed_at` (claimed) — AGE, never depth, and never the consumer's heartbeat | sentinel 10m ⚠ / 30m RED · everything else 20m ⚠ / 45m RED · claimed 15m ⚠ / 30m RED |
| `body_recovery_consumer` — the enqueuer | whether a quiet queue means anything | newest `fub-inapp-sweep-tick` run in `hl_run_log` | 15m ⚠ / 30m RED (silence makes the row above vacuous) |

First real catches, both within 24h of going live: the hung consumer loop that was holding
Jovanna Zarco's message (8/19) and the honest stranger-amber design on fresh mailboxes.

**Why the queue got its own probe key (8/19, watchdog lane).** The queue check moved OUT of
`fub_feed_freshness`. Three reasons, all measured that morning: (1) tickets in
`hl_system_health_issue` are keyed on **probe_key**, and the pager only fires on a NEWLY-opened ticket —
so while the 14-signal probe is red for any other reason a queue stall opens no ticket and pages
nobody (that probe held a red FILING ticket 8/18 17:40→21:10, ten hours before the 07:20 queue stall);
(2) the old thresholds were in **rounded hours**, so a 3h RED could not trip until 3.5h; (3) the
predicate read `status='pending'` only, and a consumer that CLAIMS then wedges leaves the row
`claimed` — invisible, because the reaper that would rescue it runs inside the process that hung. The
RED text now names the runbook (`pm2 restart fub-body-recovery` on Camp David).

⚠ **A sentry can be swallowed downstream of a correct red.** Health pagers were found suppressed by
the lifeline gate (5 health-class drops in 7 days). A probe going red is not the same claim as a human
being told — the escalation path is its own tracked estate.

## Chapter 6 — The registry as data

Everything in chapters 2, 4 and 5 used to live as prose in this file and as constants in code — which
is the exact D5 disease: a hand-kept map that drifts the day nobody re-reads it.

- **The signal → kind mapping** has been DATA since the catalog: `hl_event_mapping` (CRM DB, 42 active
  recognition rules + 8 deliberate drops). `tools/schema/signals.lock.json` is GENERATED from it.
- **The ROAD, its capture process, its tape table and its sentry thresholds** are now data too:
  `hl_signal_channel` — one row per road (`webhook` · `chrome_scrape` · `note_parse` · `native_gmail` ·
  `email_scrape`), carrying `capture_kind` / `capture_ref` / `capture_host` / `tape_db` / `tape_table` /
  `sentry_probe_key` / `thresholds`, with `hl_event_mapping.channel_key` referencing it. Migration
  `0786_hl_signal_channel.sql`, desk-signed shape, 14 columns matching the signed diet exactly.

The end state (board slice 8): **this page's tables are GENERATED from those two tables**, so the
documentation cannot disagree with the system it documents. Until that generator ships, the tables
above are hand-derived from a live read on the date in the frontmatter — accurate the day it was
written, which is not the same promise.
