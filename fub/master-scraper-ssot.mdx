## The architecture in five lines (the part everyone gets wrong)

**Webhooks do NOT go to Camp David. They go to Railway. Railway then hands Camp David a job.**

```
FUB  ──webhook──►  crm.houseloop.ai/api/fub/webhook        (RAILWAY — the CRM)
                        │  fubWebhookRouter sorts into 3 lanes
                        │  Lane 2 (masked body) writes a job row ↓
                   fub.body_recovery_queue                  (RAILWAY MIRROR — because Railway
                        │                                    cannot reach Camp David's LAN postgres)
                        │  Camp David POLLS that Railway queue
                        ▼
              CAMP DAVID scraper  ── does the job (reads the one hidden body / sweeps the inbox)
                        │  writes fub.*  (Camp David = ground truth, where the scraper WRITES)
                        │
                   fub-relay  ──30s cursor loop, upsert-only, NEVER deletes──►
                        ▼
              RAILWAY MIRROR fub.*   ── THE ONLY THING THE CRM READS
```

**Why this matters:** the scraper is a **dumb helper**. It never decides what's new. It takes a job and does
it. The webhook (on Railway) is what decides *what happened*. So "is the scraper running?" and "are webhooks
arriving?" are **two different questions with two different answers** — check both.

## ✅ HOW TO CHECK IT — in this order, stop when one answers you

**1. Is the pipeline alive?** (the ONE health law — fresh data landing in `fub.*`)
```bash
node tools/fub-scraper/scraper-health.mjs
```
GREEN = alive, done. It prints per-table freshness so you can see *what* is landing. The
`mcp__camp-david__fub_scraper_status` MCP tool now **delegates to this exact script** (fixed 2026-07-30 — see
the conflicts below), so the two can no longer disagree.

**2. Are webhooks actually arriving?** (this is NOT the scraper — it is Railway)
```sql
-- CRM database (HL_CRM_DATABASE_URL)
SELECT fn, count(*) FILTER (WHERE started_at > now()-interval '2 hours') AS h2,
       to_char(max(started_at),'MM-DD HH24:MI') AS newest
FROM hl_run_log WHERE fn ILIKE '%fub%' GROUP BY 1 ORDER BY h2 DESC;
```
Healthy reading (measured 2026-07-30 18:15): `fub-webhook-router` **57/2h** · `fub-lead-import` **62/2h** ·
`fub-inapp-sweep-tick` **40/2h** (= exactly every 3 min) · `fub-activity-sweep-tick` **40/2h**.

**3. Is the 3-minute in-app sweep really cycling?** (the tick that catches Zillow in-app messages)
```bash
# on Camp David
tail -20 /Users/lee/.pm2/logs/fub-body-recovery-out.log
```
You want `[JOB] #NNNN inbox_sweep` lines **~3 minutes apart**, each ending `in-app sweep complete`, with
`"notify_query_failed": false`. `0 in-app people to extract` is **normal and healthy** — it means it looked and
there was nothing new.

**4. Are the right processes up?** (LAST — pm2 is the least trustworthy signal)
```bash
sudo -H -u lee bash -lc 'pm2 list'
```

## ⭐ THE MINT LAW — who is allowed to become a lead (board #241, signed by Zach 2026-08-20) 🔒

**A HouseLoop lead is created from Follow Up Boss data in exactly two circumstances, and no others.**

Zach, verbatim (State of the Union, 8/20):

> *"the fub captain has to freaking respect the fub automation triggers for bringing a new lead in"*
> *"its only for inbound any type of communication or registration or property tour request etc."*

| # | The only two ways a FUB person becomes a lead |
|---|---|
| **1** | **A human named them.** The single-person "Pull in", the bulk import wizard, or the PCSOI reconciled import. An operator choosing one person IS the consent (Zach 2026-07-18), so these mint regardless of the board and regardless of age. |
| **2** | **A fresh inbound signal arrived on a live road** whose kind maps to a `creates_lead = true` row in `hl_event_mapping` — the Trigger Events board, read LIVE at decision time. |

**Everything else refuses.** A swept, replayed, backfilled or stale event never mints, and — carrying no
dispatch stamp — never bells either.

### The gate

One decision, one file: `apps/houseloop-crm/lib/fub-import/mint-gate.ts` (`mintVerdict`, a pure function).
It is a **ladder**, and the order is load-bearing — a disabled parent always wins, and the **road** is
asked before the **age**:

| order | check | refusal code |
|---|---|---|
| 0 | Did a human name this person? (Pull-in · wizard · PCSOI) → **MINT** | — |
| 1 | Is the `_global` master breaker on? | `global_off` |
| 2 | Is this a catch-up/backfill road? → a replay is not an arrival | `backfill_never_mints` |
| 3 | Does an `hl_event_mapping` rule exist for this kind? (fail closed) | `no_rule` |
| 4 | Is the signal's **Sync** toggle on? | `signal_disabled` |
| 5 | Is the signal's **Creates Lead** toggle on? | `creates_lead_off` |
| 6 | Does the signal carry a timestamp of its own? (fail closed) | `no_event_anchor` |
| 7 | Is it inside the freshness window? | `stale` |

The refusal code and its sentence land in the Inngest run output (`mintRefusal`, `mintRoad`,
`mintAgeMinutes`), so "why did this person not become a lead?" is answerable without reading code.

### The two clocks — and why the road is asked first

`dispatchedAt` (when the router fired) and `eventAt` (FUB's own `created` on the record) are **different
facts**. A replay mints a brand-new dispatch stamp for a year-old event, so the dispatch stamp may gate a
**bell** but must never gate a **mint**. The mint gate reads `eventAt`, which the router now stamps on
every dispatch; when it is absent the gate refuses.

Two of Zach's rulings look like they collide, and the road is what reconciles them. On **7/30** he ruled
*"what if the system is down and pulls it in 3 days later? I don't want it to silently fail… a lead must
never be punished for our downtime."* On **8/20** he ruled that a swept or replayed event never mints. An
event's AGE cannot tell a genuinely-late real inquiry from a replay — at three days old they are the same
number. The ROAD can: a webhook that just fired is an arrival; a sweep re-reading the tape is a replay.

### The freshness window — 72 hours, and where that number comes from

`MINT_FRESHNESS_MINUTES` = **4320** (72 h), overridable by `FUB_MINT_FRESHNESS_MINUTES`. It lives in one
place with its justification attached, because a threshold buried in a handler has cost us three times
(#139, #177, #188). Measured live 2026-08-20 — **re-run before quoting, never from memory**:

- **The live arm** (`fub.events` whose own `created` falls inside 30 days, n = 133): **131 captured within
  one minute**, 132 within 60 minutes; p50 lag 0.04 min, p95 0.26 min. The single outlier is person
  **50546 at 3,499.9 min (58.3 h)** — Zachary Bell, the July outage Zach's 7/30 ruling was written about.
- **The 8/20 flood:** the *least* stale of the 14 bad mints was **45.0 days**; the worst 538.5 days.

72 h is the only value that satisfies both rulings at once: 15× the worst honest lag ever measured, and
15× smaller than the least-stale replay. The choice is pinned to the rulings, not to the gap.

### Where the gate sits — all three mint paths

A gate on one of three mint paths is not a gate. Every path that can `INSERT INTO hl_leads` from FUB data:

| path | file | gated by |
|---|---|---|
| The import (webhook · rebackfill · wizard · Pull-in · voice) | `lib/inngest/functions/fub-lead-import.ts` → `lib/fub-import/import-fub-lead.ts` | `mintVerdict` on the resolved road |
| FUB-native inbox seat, inbound **text** | `lib/inngest/functions/fub-webhook-router.ts` | the seat's `creates_lead` **and** the same freshness bound |
| FUB-native inbox seat, inbound **call** | `lib/inngest/functions/fub-webhook-router.ts` | the seat's `creates_lead` **and** the same freshness bound |

The past-client **pour** (`pastclient-pour.ts`) is a separate estate and is out of this gate's scope by
design — it is a human-run import of named people.

### What this changed, deliberately

`backfill: true` used to set `adminFlow`, and the mint condition ended `&& !adminFlow` — so **the
Creates-Lead toggle was unreachable on every backfill road.** Three roads dispatch backfill with no human
behind them: `/api/fub/rebackfill` (the scrape road), `fub-high-intent-sweep`, and `/api/fub/import`.

- **`/api/fub/rebackfill` still works exactly as documented** for a person who is already a lead —

### ⭐ The scrape-on-entry doctrine — the real-time per-lead intercept (THE entry mechanism) 🔒
**This is how every new lead's full history reaches us, in ~half a second.** The moment a new Zillow inquiry fires
the FUB `eventsCreated` webhook, the handler **spins up a per-lead scrape on Camp David** that intercepts FUB's own
authenticated SPA call `GET /api/v1/events?hasProperty=true` and walks the lead's **entire** timeline — grabbing
**every home the lead ever touched: the Zillow URL, zpid, MLS, price, and the photo** — in one shot (242 → 534 homes
on the test lead James Ross). It writes each home keyed by FUB's stable `fub_event_id` into `fub.zillow_home_activity`
via `saveZillowHomeActivity` (`tools/fub-scraper/fub-scraper-lib.mjs`). Trigger paths: the webhook auto-enqueues it
(`fub.rehydration_queue` → `fub-webhook-scraper`); on demand, **`mcp__fub-scraper__fub_scrape_lead` /
`mcp__camp-david__fub_scrape_person`** re-run the full intercept for one person. **It is deployed + LIVE.** This
scraper is the front door for ALL new lead data — when a lead's cards look wrong, re-running it is the first move.

### 🗄️ TWO databases — and `zillow_home_activity` is OFF the relay (read this before any photo/home-card debugging) 🔒
There are **two** FUB stores, and they are NOT kept in sync the same way for every table:
- **Camp David `fub.*`** (`DATABASE_URL` on the box) — where the scraper WRITES. Ground truth for scraped data.
- **Railway mirror `fub.*`** (`FUB_RAILWAY_DATABASE_URL`) — **what the HouseLoop CRM READS** (`fubQuery`,
  `LeadContextPanel`, the import, the card minter). The CRM never reads Camp David directly.

Most tables reach the mirror via the **relay** (`fub-relay`, upsert-by-id). **`fub.zillow_home_activity` is the
exception — it is OFF the relay (Zach 2026-06-27).** The **scraper is its SINGLE WRITER to the mirror**: right after
`saveZillowHomeActivity` writes Camp David, it does a **per-person FULL REPLACE to the mirror**
(`syncPersonHomeActivityToMirror` — `DELETE person rows + INSERT the fresh set`). So a home's photo reaches the CRM
**only when the scraper runs for that person.** If the scraper hasn't re-run since the photos were captured, **Camp
David has the photos but the mirror does not** — and the CRM, reading the mirror, shows blank.

### ✅ The blank-photo bug — ROOT CAUSE FOUND + FIXED (2026-06-28)
Every blank photo + stale lead traced to **ONE bug**: `mirrorUrl()` in `fub-scraper-lib.mjs` resolved its `~/.env`
fallback with **`require('node:fs')` — but that file is an ES module, so `require` is undefined and threw**, silently
returning `null`. The per-person mirror sync then no-op'd on **every on-demand scrape** (which doesn't set
`RAILWAY_DATABASE_URL`). pm2 scrapers "worked" only because their env sets the var. So a scrape wrote Camp David
perfectly but **never updated the Railway mirror the CRM reads** → blank. *Proven:* Alberto Camp David **199/199**
photos, mirror **829 rows / 0 photos** — until the fix flipped it to **207/207**.

**Fixed (shipped):**
- `mirrorUrl()` uses the ESM-imported `fs` (no `require`).
- `syncPersonHomeActivityToMirror` now **sources the FULL set from Camp David** (not the flaky in-memory scrape
  result, which the intercept returns non-deterministically — 0/4/199 on the same lead), **always runs**, **never
  shrinks** the mirror below Camp David, and **fails LOUD** (`✅ mirror replaced: N` / `❌ mirror sync FAILED` — never
  silent). The loud log is what surfaced the `require` bug on the first run.
- **Card heal:** `resyncHomePhotos` + `stampActivityPhoto` (the sanctioned append-only exception) stamp photos onto
  already-minted cards (all `evt`/`zpid`/slug source_id variants); for leads minted from the old broken mirror,
  **re-import** (`fub/lead.import {backfill}`) mints clean `evt`-keyed cards, then a Rule#0-approved delete removes the
  stale `fub_home:` non-evt duplicates. **Junk guard** in `convertHomeActivity`: an address that is a URL / agent-page
  (`realscout.com/users/...`) / doesn't start with a street number **never mints a card**.

> **One-line debug rule:** blank home card → check the **Railway mirror** (`FUB_RAILWAY_DATABASE_URL`), not Camp
> David. 0 photos there → re-run `fub_scrape_lead` (now mirrors loud); cards stale → re-import the lead.

### 🔑 Where property VIEWS actually come from — the internal feed, NOT the notes (Zach 2026-06-28)
FUB has **no property-view webhook** (the public "Viewed Property" event died May 21). Your **"Property Viewed" note

42729, James Ross 50308):

1. **Source** — a Zillow in-app message / inquiry lands in FUB (e.g. "interested in touring 15111 E 44th St S on
   Jun 26 at 12pm", source **Zillow Preferred**, MLS# 2626844). FUB fires an `eventsCreated` webhook.
2. **Pull-in decision** — the **native webhook router** (`fub-webhook-router.ts`) classifies the signal

3. **The import mints (the key steps):**
   - **2.6 — the canonical request card** — `kind` from `classifyFubEvent(message, source)`,
     `source_table='fub_request'`, `source_id='fubreq|<fub.events.id>'`, ONE per inquiry, home resolved by MLS# →
     photo + `/home` link. **The card we keep.** (`fub.events` is now stored **unconditionally** by the router's
     `storeRecord`, so inquiries/tours always land for this step — 2026-07-10.)
   - **2.7 — behavior + comms backfill** — `backfillFubBehavior` mints the lead's FUB behavior history
     (views/saves/searches/insights); `backfillFubComms` bridges texts/calls/emails. Both are **watermarked
     FORWARD-ONLY** (floored at the lead's `created_at`) — a pulled-in lead starts CLEAN, and only new comms flow
     into the feed; old comms stay context-only under the FUB tab (2026-07-10). Idempotent.
   - **2.8 — Myli context is NOT built on import.** `buildLeadContext` was removed from the import path (2026-06-29):
     facts refresh **before Myli communicates** (the conversation path / a pre-outreach workflow step / on-demand
     when the lead is opened), never on a data pull-in. See §6.
   - **3 — registration door log** — `kind='registration'`, `source_table='fub_lead_import'`, source "VIA HouseLoop".
     **This currently DUPLICATES the request card** (tracked issue I2, §7).
- **Link + source + owner:** `hl_leads.fub_person_id`; lead source = `Zillow.com`, platform = `follow_up_boss`; a
  lead is **never ownerless** — `ensureLeadAiOwner` falls back to the platform default AI agent (Myli) when no human

### Pulling in a FRESH person — the mirror lag + the scrape front door (Lee, 2026-07-22) 🔒
**The problem:** the CRM reads only the Railway mirror (`fub.people`), which the scraper populates — so it **lags
the FUB API**. A person created minutes ago (proven: **Kenneth Eugene Hunt, FUB 50544**, while the mirror's newest
was 50543) is **in FUB but not yet in the mirror**. The single-person **find people** search (`import/search`) and
the **Pull in** (`import/person` → `importFubLead`) both read only `fub.people`, so a fresh person was invisible
AND un-importable (`importFubLead` threw *"not found in fub.people"*).

**The fix (doctrine-aligned — the scraper stays the front door, the CRM never reads FUB data direct):**
- **Search** (`app/api/integrations/fub/import/search/route.ts`) merges a **live FUB API** lookup
  (`fubGet('/people?name|email|phone=…')`, current `FUB_API_KEY`) with the mirror rows — de-duped by id, API-only
  rows flagged **`notInMirror`**. A FIND aid only: it surfaces the person so the operator can pull them in; it does
  not ingest data.
- **Pull in** (`lib/inngest/functions/fub-lead-import.ts`, `importMode:'single'` only) — when the person isn't in
  `fub.people`, it **enqueues a `person_rescrape` into `fub.body_recovery_queue`** (the SSOT lock-step mechanism)
  → the live Camp David CDP scraper (logged into FUB as Zach — it **sees** them, no REST key needed) walks their
  FUB page → **upserts `fub.people` + full browse/comms history** → `POST /api/fub/rebackfill` fires
  `fub/lead.rehydrated`. The import `waitForEvent`s on it (3-min timeout, soft *"pull in again in a moment"* on
  timeout) THEN mints from the populated mirror. So **pulling in a fresh lead scrapes them and brings in
  everything** — via the front door, no parallel CRM→FUB-API data path. Human `single` pull-in only; the
  fail-closed webhook mint gate is untouched.

### ⭐ The Watermark Law — read-once, merge-forward (universal) 🔒
Governs **every** LLM rollup (dossier, facts, Hot Buyers, any summary): **never re-process data already consumed.**
The dossier stores its text + a `source_cursor` (high-water mark). Each regen: read only the delta
(`WHERE synced_at > source_cursor`) → merge into the existing dossier (don't re-summarize) → advance
`source_cursor = max(synced_at)`. First pull = full history (Sonnet, cursor = now); every pull after = the delta,
merged with Haiku. **Tokens paid once per row, ever.**

<Warning>
**The gotcha:** watermark on **`synced_at` (when WE ingested the row), NOT the event's own date.** A 2-year-old
home view the scraper *just* backfilled is **new to us** — `synced_at > cursor` catches it. Watermark on the event
date and you'd silently skip every freshly-backfilled historical row.
</Warning>

# ═ SIGNAL CAPTURE + THE TOGGLES (absorbed from fub/trigger-events, 2026-07-17 — the EVENT CATALOG moved to /guides/trigger-events) ═

## The principle (LOCKED 2026-07-09 by Zach)

**Notifications are the source of truth. The scraper is a dumb, on-demand grabber of HIDDEN content only.**

The native HouseLoop webhook is what decides *what happened*; when the thing that happened has content FUB hides
(a masked message body), the notification layer *tells the scraper* to go recover exactly that one body — nothing
else. The scraper never decides what's new, never crawls, never re-scrapes on a record edit. This replaces the
old "push for speed, pull for truth" dual-path / differential-reconciler design, which is **dead** (it read the
lagging mirror and flooded Zach with 2022-era activity — see the post-mortem below).

## Vocabulary (LOCKED 2026-07-07)

- **Integration** = the *pipe* a lead flows through — **HouseLoop.ai** (our website pixel) or **Follow Up Boss**
  (the Zillow-connected CRM). Managed at **Settings → Lead Integrations** (`/settings/lead-platform`).
- **Lead Source** = the *brand* on the lead — Zillow, Referral, etc. A source lives *under* an integration.
- **Trigger Event** = a *door* — a thing that can happen (a tour request, an inbound text, a property save) that
  can start a lead, run a workflow, and/or fire a notification. One row in **`hl_fub_webhook_settings`**,
  configured at `crm.houseloop.ai/settings/trigger-events`.

## The four independent toggles (this is the model)

Each FUB trigger event carries **four independent switches** — none implies another:

| Toggle | Column | What it controls |
|---|---|---|
| **Sync** | `enabled` | Do we ingest/process this FUB signal at all. Off = we don't even mirror it. |
| **Creates Lead** | `creates_lead` | Does firing this door mint (or match) a HouseLoop lead. |
| **Workflow** | `workflow_id` + `workflow_active` | Which workflow the door runs, and whether it runs. |
| **Notify** | `notify` | Fire an owner-only HouseLoop notification when this door fires **for a person who is not yet a HouseLoop lead** (the leadless ping, and the fresh mint) — **independent of Creates Lead.** ⚠ It does **not** govern a signal arriving on someone who is **already** a lead; see the note below. |
| **Notify (Existing arm)** | `existing_notify` | The Existing-Lead arm. ⚠ **Live only on the body-recovery road** (in-app / text messages, via `routeFubNotification`). For every signal that files through `logActivity`, this column gates nothing. |

<Warning>
**THE NOTIFY COLUMN IS NOT THE WHOLE ANSWER — TWO TABLES DECIDE, ONE PER ROAD (measured 2026-08-19, task #196).**

Whether a FUB signal rings depends on whether the person is already a HouseLoop lead, and a **different table
governs each case**:

| the person is… | who decides the bell | where |
|---|---|---|
| **not a lead yet**, or this event mints them | `hl_event_mapping.notify` — the toggle on this page | `fub-lead-import` leadless + fresh-mint branches |
| **already a HouseLoop lead** | `hl_activity_catalog.notify` — the catalog, via the `logActivity` weld (`notifyClassForKind`) | `lib/activity/log-activity.ts` |

The consequence, live today on five signals: `property_saved`, `property_viewed`, `property_shared`,
`saved_search_created` and `virtually_toured` all read **Notify = OFF** on this settings board, and all five are
**`notify = true` in the catalog** — so a known lead's save or view still rings. Measured over 90 days:
**961 `property_saved` bells and 232 `property_viewed` bells** fired while the board showed those toggles off
(most recent: 2026-08-19). The board is not lying about its own column; it is showing one road's answer to a
two-road question. `tools/schema/signals.lock.json` now publishes **both** values per signal (the `governing`
block) plus a `notify_divergence` chapter, and `signals-lock.mjs --check` reports any new divergence.

**Turning a toggle OFF here does not silence that signal for existing leads.** To silence one everywhere, its
catalog `notify_class` must also be cleared (`/settings/activity-catalog`). Converging the two into one answer
table is an open desk item — see the receipt at `.claude/reports/notifytwin-196/`.
</Warning>

<Note>
**Notify is decoupled from Creates Lead (Zach 2026-07-08).** You can turn ON a notification for a FUB trigger
event **even if you do not create a lead** — a "heads-up, this happened" ping with no lead minted. The card then
renders "**HouseLoop — no lead created**" (no HouseLoop link) alongside the always-present FUB person link. The

## The 3-lane architecture

Every FUB event enters the native webhook and `fubWebhookRouter` sorts it into exactly one lane:

### Lane 1 — Visible activity (~95 percent): router notifies directly, scraper never touches
Home saved/viewed (`notesCreated`), inquiries (`eventsCreated`), visible SMS, call metadata, appointments,
tasks, deals. (In-app messages are NOT here — they are the inbox-app sweep lane below.) The API hands us clean
content → the router classifies it and fires
the owner-only notification immediately.

### Lane 2 — Masked comms: the ONLY thing that wakes the scraper
The three masked cases — masked SMS bodies, email bodies, and call notes. The flow is a **surgical body-fetch**,
never a re-scrape:

```
masked textMessagesCreated / emailsCreated  →  fubWebhookRouter writes metadata + enqueues ONE job
      ↓ fub.body_recovery_queue (on Camp David — the relay is CD→Railway one-way, so the job lives CD-side)
      { person_id, resource_type: 'text' | 'email', resource_id, requested_at }
      ↓ the scraper drains the queue — reads THAT ONE body from the FUB UI
      ↓ writes the recovered body → flips content_status  hidden → visible
      ↓ trg_fub_new_message fires  (now AFTER INSERT OR UPDATE, transition-guarded, text + email)
      ↓ pg_notify('fub_new_message') → the native notify path
   →  HouseLoop notification fires WITH the body
```

**No metadata-only notify for a masked body** — a card with no message is useless, so we hold the notify until
the body is recovered. Born-visible content (in-app, visible SMS) is Lane 1 and notifies on the INSERT.

### Lane 3 — Record edits: update the person, never scrape
`peopleUpdated` / `peopleStageUpdated` / `peopleTagsCreated` / `peopleDeleted`. These update the person record
only. **They never enqueue a scrape.** (A stage change may fire `stage_changed` if the Notify toggle is on; that
is a notification, not a scrape.)

## ⭐ How an in-app (Zillow Messages) message becomes a trigger event

Zillow in-app chat is the ONE signal FUB does **not** expose through its API or webhooks (proven 2026-07-09 on
James Ross: his in-app messages carry synthetic ids and never appear in `GET /v1/textMessages`; no
`textMessagesCreated` fires). They live in FUB's **"Zillow Messages" inbox app** (`inboxApp id 1`, created by
the original account owner's seat — `createdById 1`, which is why a departed owner's Zillow connection still
fronts these leads). So capture is: find the people via the REST API, scrape their pages for the bodies — all
lawful, gated, and Inngest-visible:

1. **Detect — the REST API, not the inbox SPA (proven 2026-07-09):** message BODIES aren't in the API, but WHO
   has in-app activity IS: **`GET /v1/people?sort=-lastInboxAppMessage&fields=id,lastInboxAppMessage`** returns
   every person ordered by their last in-app message, with the timestamp. Reliable, no browser, cursor-pageable.
   (The FUB inbox web endpoint `/api/v1/inbox/…/conversations` **hangs** on any direct/replay fetch and its
   virtualized list won't page on scroll — only the app's own live XHR ever fires; the people-sort is the robust
   surface.) **Incremental compares each person's FUB `lastInboxAppMessage` against OUR newest message for THAT
   PERSON** (a per-person watermark), walking back a `LOOKBACK_DAYS` (45d) floor; backfill takes all.
   The registered Inngest cron **`fub-inapp-sweep-tick`** (Run Log `comms` lane; cron `*/3` ARMED since
   2026-07-09 sign-off) enqueues one sentinel `inbox_sweep` job into the Railway FUB mirror queue —
   `UNIQUE(resource_type,resource_id)` = at most one sweep pending (no pile-up).

   <Warning>
   **⚠ NEVER re-introduce a GLOBAL watermark here.** From 2026-07-09 to 2026-07-28 discovery used ONE cursor —
   `max(fub_created)` across ALL people — and **broke out of the walk at the first person at/below it**. Because
   the API is sorted `-lastInboxAppMessage`, one person's fresh message raised the bar for **everyone**: Evelyn
   Morales' Jul 28 message made Shamyah Matthews' Jul 23 tour interest permanently undiscoverable, and the sweep
   printed `0 in-app people to extract` while three leads sat invisible. A person who falls behind can never be
   caught up by a cursor that only moves away from them. **The watermark is per-person, or it is broken.**
   </Warning>
2. **Extract (reuse, never reinvent):** the Camp David `fub-body-recovery` consumer claims the job and runs
   **`tools/fub-scraper/fub-inapp-sweep.mjs`**, which — for each discovered person — reuses the proven extractor
   in `fub-scraper-lib.mjs` (`scrapePersonFull` + `matchAndUpdateMessages`: `scrapeTextContainers` classifies a
   timeline row `zillow_inapp` by its **`zillow.png`** circle-icon; the synthetic id
   **`900000000 + personId*1000 + seq`** dedupes against the existing rows, `ON CONFLICT (id) DO NOTHING`). The
   relay carries the new born-visible rows Camp David → Railway.
3. **Notify (native, gated — one notifier):** for each NEW inbound in-app message the sweep POSTs
   `/api/fub/body-recovered`; **`fub-body-recovered`** maps `message_type='zillow_inapp'` → `in_app_message` →
   a card, through the gate stack: **existing-lead gate** (no HouseLoop lead ⇒ store-only, NO card, NO mint) +
   `_global` on + `in_app_message` Notify on + recency. The legacy realloop `notify-scraper` Twilio path is
   retired (behind `REALLOOP_SCRAPER_NOTIFY`, off) so there is exactly ONE notification per message.
4. **Backfill is silent:** `fub-inapp-sweep.mjs --backfill` pulls every in-app message into the mirror + All
   feed with **zero** notifications (no 1,198-card flood). `--measure` prints **`people_behind`** — how many
   people FUB has newer in-app activity for than we do. (It used to print `gap_people = fub_people −
   mirror_people`, which clamped to 0 forever because our mirror holds 2,806 in-app people historically vs FUB's
   1,307 current. It answered a question nobody asked and read "no gap" through an 11-day outage.)

<Warning>
**⚠ THE 11-DAY SILENT OUTAGE — 2026-07-17 → 2026-07-28 (read before touching this pipeline).**

Zach missed **17 inbound Zillow in-app messages, 11 of them tour requests**, and nearly lost two deals. Every
health signal we had stayed GREEN throughout. Four defects compounded — each one alone was enough to hide it:

1. **The jam.** The sweep blew the consumer's 8-min `JOB_TIMEOUT_MS` 3× (a full `scrapePersonFull` costs
   60-90s/person). The reaper marked the sentinel `status='error'`. Because `UNIQUE(resource_type,
   resource_id)` carries **no status predicate**, that dead row owned the `('inbox_sweep', 0)` slot forever —
   nothing in the system clears a terminal sentinel. **The anti-flood property became a permanent deadlock.**
2. **The lying heartbeat.** `fub-inapp-sweep-tick` hit `ON CONFLICT DO NOTHING` and returned
   `{ok:true, enqueued:'already pending (no-op)'}` — **~5,300 consecutive green runs while zero sweeps ran.**
   The signal measured *the tick firing*, not *the sweep running*. Every prior investigation concluded "the
   scraper is fine" because **by that metric it was fine**. A health check that can't tell working from jammed
   argues against the truth.
3. **The unreachable notifier.** `if (!persons.length) process.exit(0)` sat *above* the decoupled `notified_at`
   notify pass — the very mechanism built 2026-07-14 so notification could not depend on scrape timing. Since
   discovery is empty on most healthy runs, the good code was unreachable almost always.
4. **The global watermark** (see the Warning above) — which meant even an unjammed sweep found nobody.

**The invariants now enforced in code — do not soften any of them:**
- The tick **DELETEs** any `error`/`done` sentinel on sight, so a jam cannot persist past one tick.
- The tick **THROWS (run goes RED)** when the sentinel has sat undrained > 20 min. Green now means *a sweep is
  cycling*, not *the tick fired*.
- Capture and notify are **independent**; neither may short-circuit the other. No early return above the
  notify pass, ever.
- A **wall-clock budget** (5 min) + count backstop (6 people) keeps a backlog from blowing the job timeout —
  the run finishes on its own terms and clears its own sentinel. Both **log what they defer**; the result JSON
  carries `behind_total` / `deferred`. **No silent caps** — a truncated run must never read as full coverage.
- The sweep's notify lookback (48h) is aligned to the CRM's `FUB_NOTIFY_RECENCY_HOURS`, so the two gates can't
  disagree and silently drop a lead.

**The one-line lesson:** *every instrument pointed at this pipeline was measuring the wrong noun.* When
diagnosing it, verify the **data** (is a message we can name actually in the mirror and in the CRM?) — never
the status of the thing that reports on itself.
</Warning>

## Native capture — the webhook that severs realloop.co

## The recency gate + the flood post-mortem

## The login (this is what "stuck / can't log in" means)

FUB's real login is **"Log in with Google"** as `zach@spradlingrealtygroup.com`. The persistent Chrome profile
holds a live Google session, so navigating to the app **auto-completes SSO** — no password prompt in the normal
case. If the Google session itself has lapsed, `fub-login-bot.mjs` drives the SSO by hand: **email → password →
account-chooser → consent**, in that order, using `FUB_WEB_GOOGLE_PASSWORD` (→ `FUB_WEB_PASSWORD` fallback). Only a
**genuine 2FA challenge** — a real code box or a phone push, with nothing else the bot can fill — alerts a human via
`notify.sh`. **Option text alone ("Try another way", "use a passkey", "verify it's you") is NOT a 2FA wall** — those
appear next to the normal password field and the bot must ignore them (see the 2026-07-08 incident below).

When the session expires, the scraper's **startup session-check** navigates fresh to `/2/people`; if it lands on
the login page it **delegates to `fub-login-bot.mjs` (Google SSO)** and re-verifies. (Before 2026-07-08 it clicked
a `input[type=submit].u-bigBlueButton` — the DEAD legacy FUB email/password form button. FUB is Google SSO now, so
that click always failed → an instant 10-minute cooldown → the "scraper down / won't log back in" symptom. The
delegation to the real login bot fixed it.)

**The `fub-watchdog` self-heals a real logout AUTONOMOUSLY — a human should almost never touch it.** Every 60s it
checks Chrome A (18800). If a login tab is up, it runs the login-bot; on a persistent real logout it does a HARD
relaunch (kill + fresh-profile launch + re-login), same as `fub_chrome_restart`. It only alerts a human via
`notify.sh` if even that can't re-auth (a genuine 2FA/password wall).

<Warning>
**The watchdog must WATCH, never HARM (Caleb 2026-07-08 — the "watchdog was the killer" fix).** Its health probe
`isCdpConnectable()` used to `connectOverCDP()` then `browser.close()` — and on this Chrome build that close
**tore down the browser's live pages.** So every 60s the watchdog killed the actively-scraping worker, mis-read
the wreckage as "WEDGED," and hard-relaunched Chrome — **568 relaunches**, an endless self-inflicted crash loop
that looked exactly like "the scraper won't stay logged in." Two guards now prevent it, permanently:
1. **Passive probe** — a raw DevTools websocket open/close (Node global `WebSocket`) that never calls
   `browser.close()`, so probing a healthy Chrome is harmless.
2. **Fresh-log guard** — if the `fub-backfill-a` log is fresh (the worker wrote scrape output seconds ago), the
   watchdog **never probes or relaunches**: an actively-producing worker is definitive proof CDP is healthy.

Rule for anyone touching the watchdog: a monitor may **look** but must never **close/relaunch a browser that has a
live worker.** Code: `fub-backfill-watchdog.mjs` — `isCdpConnectable` + the `workerFresh` guard in `check()`.
**Known gap (audit F9, 2026-07-09):** a Chrome whose DevTools websocket has wedged (HTTP alive, ws hangs forever)
can hide behind the fresh-log guard, because the empty-queue exit loop keeps writing "Nothing to scrape" — a log
write, not real scrape output. The freshness signal must key on *scrape output*, and CDP connects need an
external timeout, not an in-process race.
</Warning>

## The scrape-on-entry doctrine

The moment a new Zillow inquiry fires the FUB `eventsCreated` webhook, the handler spins up a **per-lead scrape**
that intercepts FUB's own authenticated SPA call `GET /api/v1/events?hasProperty=true` and walks the lead's **entire
timeline** — every home they ever touched (Zillow URL, zpid, MLS, price, **photo**) — in one shot, keyed by FUB's
stable `fub_event_id` into `fub.zillow_home_activity`, then **full-replaces** that person's rows in the Railway
mirror. On demand, re-run it with **`mcp__fub-scraper__fub_scrape_lead`** or **`mcp__camp-david__fub_scrape_person`**.
This is the front door for all new lead data — when a lead's cards look wrong, **re-running the scrape is the first move.**

### The real activity time — `activity_at` (2026-07-12)

Each home row carries **`activity_at timestamptz`** — the REAL moment the lead viewed/saved the home, lifted
from FUB's browse-list `occurred` field. It exists because `activity_date` is **date-only and UTC-sliced**, so
an evening view (e.g. Jul 11 9:24pm ET) rolled its date forward a day and the CRM feed fell back to
**scrape-time** for the timestamp (Austin Banh's 6303 N Bellefontaine showed "Jul 12 5:46am" — the scrape — vs
FUB's Jul 11). The CRM converter (`homeOccurredAt`) now uses `activity_at` first, so the feed + the FUB Context
view render FUB's real time 1:1.

Two gotchas: **(1)** after scp'ing a new `fub-scraper-lib.mjs`, **pm2-restart the worker** — a running worker
holds the old lib in memory, so `activity_date` populates while `activity_at` stays NULL (the tell). **(2)** a
lead minted BEFORE the fix keeps scrape-time `occurred_at` — `logActivity` is `DO NOTHING` on conflict and the
heal path never touches `occurred_at` (write-once identity), so the per-lead fix is a **re-scrape + purge/re-mint**
(`scripts/austin-remint-loop.ts`); a fleet-wide `occurred_at` heal needs Zach's sign-off.

## What it can't recover

**If a FUB user sets their emails private/hidden in the FUB UI, the DOM scraper cannot recover them** — they read
`[CONTENT HIDDEN]` in the actual UI, so there is nothing to scrape. This is a FUB privacy feature, not a scraper
failure (concrete case: Aaron Foster's UI-hidden emails store `[CONTENT HIDDEN]` permanently). So a large `hidden`
count is **largely expected** and must not be "fixed." What it **can** recover: anything visible in Zach's FUB UI,
including the newest message body via the intercepted timeline API (`lastEmail.bodyHtmlVisibleClean`; a direct
public-API fetch returns `401`).

## 🔁 THE RESTORE DRILL — proving the backups are backups (FUB-17, live 2026-08-22)

**One sentence: a backup nobody has restored is a rumour.** The nightly job
(`~/houseloop-backups/run-backup.sh`, 03:30 daily) proves a dump was *written* and is big enough.
The drill proves the dump *restores* — into a real database, with the rows counted.

<Warning>
**`pg_restore --list` CANNOT tell you a dump is complete.** A custom-format dump keeps its table of
contents at the FRONT of the file, so a dump truncated halfway through still lists perfectly. Four
truncated dumps survived that way on Camp David 2026-08-15..17 when the disk filled mid-write; each
one looked like a backup and would have restored like a lie. Size plus a real restore are the only
honest evidence. That is why this drill exists.
</Warning>

### Running it

```bash
# on Camp David
bash ~/houseloop-backups/restore-drill.sh                 # the drill — takes about a minute
bash ~/houseloop-backups/restore-drill.sh --keep          # leave the scratch DB to poke at
bash ~/houseloop-backups/restore-drill.sh --dump <path>   # drill a specific (e.g. older) dump
```

Source of truth for the script: `tools/houseloop-backups/restore-drill.sh` in the repo. Camp David
runs a deployed COPY at `~/houseloop-backups/restore-drill.sh` — edit the repo, redeploy, never
hand-edit the copy:

```bash
scp tools/houseloop-backups/restore-drill.sh lee@192.168.1.211:~/houseloop-backups/restore-drill.sh
```

**DEPLOYED 2026-08-22 16:49** — verified byte-identical to the repo (md5 `005684e2…` on both sides).
⚠ Nothing SCHEDULES it: the drill is a command you run, not a cron. A backup proof that depends on
somebody remembering to run it is the same shape as the SISU mirror nobody refreshed for three
months — putting it on a cadence is open work, not done work.

Exit 0 = PASS, exit 1 = FAIL. Every run appends one line to
`~/houseloop-backups/restore-drill.log`; a failed restore leaves its full stderr at
`~/houseloop-backups/restore-drill-last-errors.log`.

### What it checks, in order

| # | Gate | Fails when | Why it is a gate and not a warning |
|---|---|---|---|
| 1 | **the file** | no `houseloop_crm-*.pgdump`, or the newest is a `.partial` | a failed dump is renamed `.partial` on purpose; restoring one would launder a corpse into a receipt |
| 2 | **freshness** | newest dump older than 36h | the nightly runs at 03:30 — 36h means it is broken, and a drill that passes on a stale dump is a green light for a dead backup |
| 3 | **size** | under 200 MB (measured 370,915,150 B on 8/22) | the shrink guard; a near-empty dump is the 2026-07-18 failure mode (it dumped an empty LOCAL database nightly and logged "complete") |
| 4 | **disk** | under 12 GB free | the restored CRM is ~2.7 GB; an ENOSPC mid-restore is how Camp David lost four dumps in August |
| 5 | **the restore** | any `pg_restore: error:` that is not known version noise | see the version-skew note below |
| 6 | **the sentinels** | any of five tables under its floor | the actual proof — the only check that a dump which restored also CONTAINS the estate |

**The five sentinels** — five different estates, so a partial restore cannot hide behind one healthy
table. Floors are SHRINK guards (these tables only grow; trash is a flag, never a delete), set well
under the live counts measured 2026-08-22:

| sentinel | estate | floor | live 8/22 | in the 8/22 dump |
|---|---|---|---|---|
| `hl_leads` | people | 100 | 216 | 229 |
| `hl_activity_log` | THE activity log | 30,000 | 65,802 | 70,265 |
| `hl_messages` | comms | 15,000 | 16,719 | 16,897 |
| `hl_srg_past_clients` | the past-client SSOT | 1,700 | 1,779 | 1,779 |
| `hl_user` | website users | 200,000 | 210,221 | 210,234 |

Raise a floor only when it has gone uselessly low, and say why in the commit. **Never lower one to
make a drill go green** — that turns the drill into decoration.

### The two safety properties

- **THE NAME GUARD.** Every `createdb`/`dropdb` goes through one function that refuses any name not
  matching `^hl_crm_drill_[0-9_]+$`. `houseloop_crm`, `bossloop`, and the kept snapshots
  (`hl_crm_0818_snapshot`) are unreachable from this script by construction, not by carefulness.
- **NO RESIDUE.** The scratch database is dropped on the way out — on success, on failure, and on
  Ctrl-C — unless you asked for `--keep`, which says so loudly.

<Warning>
**VERSION SKEW: the dumps are PostgreSQL 18, Camp David's local server is PostgreSQL 16.13.** Every
PG18 dump opens each section with `SET transaction_timeout = 0;` — a parameter that did not exist
before PG17 — so a *perfectly clean* restore here still exits 1 with a handful of those lines and a
`errors ignored on restore: 2` summary. The drill classifies exactly that pattern as benign and lets
the row counts decide. It works today because nothing in the schema uses PG17+ syntax; the day
something does, the restore breaks HERE first, which is the point. **Do not widen the benign list to
make a future error go away.**
</Warning>

### The gap this does not close

bytes** against a real 370 MB dump — four orders of magnitude too low to catch anything — and the
off-box R2 copies have never been restore-tested at all.

# ═ THE FUB FOLLOW-UP WIDGET (absorbed from fub/follow-up-widget, 2026-07-17) ═


<Note>
**Quarantined FUB section.** Part of the **FUB system** on RealLoop infrastructure
(realloop.co, future ConvertLoop) — **not** HouseLoop web/CRM. Documented here only because FUB
leads migrate into HouseLoop eventually. The one shared touch-point with the CRM (inbound call/text
routing) is described under [Inbound routing](#inbound-routing-one-number-two-systems) and is
deliberately the only crossover.
</Note>

## What it is

A Follow Up Boss **embedded app** ("Houseloop") that renders in the right column of every FUB
person view. It loads the lead's **recovered** history (the bodies the [FUB scraper](/fub/master-scraper-ssot)
unmasked), acts as the agent's AI clone, and lets them **text or call the lead** without leaving
FUB. Served from `https://realloop.co/fub-widget`.

- **Auth:** FUB passes a `context` (base64 JSON) plus an HMAC `signature`; the widget verifies
  `HMAC-SHA256(context, FUB_EMBEDDED_APP_API_KEY)` before rendering. No `X-Frame-Options` (it's an iframe).
- **Freshness:** every panel re-reads the database on open (`Cache-Control: no-store`) so it always
  reflects the latest activity.

## The three tabs

| Tab | Shows |
|---|---|
| **Actions** | Claude "what should I do?" — summary, intent, single best next step, a channel-aware drafted reply, **Approve & Send**, **Call lead**, Regenerate. |
| **Activity** | Texts / Calls / Emails / Homes — the real recovered content, homes are clickable Zillow links. |
| **Context** | The living brain — who the lead is + buying intent, regenerated from live data. |

The AI reads a **single unified, timestamped timeline** across *every* channel — texts, emails,
calls, team notes, and home-activity events — with the most-recent line flagged, so suggestions
reflect what just happened rather than a stale early message.

## First-touch outreach mode

When a lead has a **team-exit / prior-agent tag** (e.g. `Team Exit - April Atkinson`), no recent
outbound from us, and a real in-market property to anchor on, the widget switches to a cold
first-touch script:

1. **Who** — "Zach Spradling, team lead at The Spradling Group in Overland Park — the local Zillow
   team that runs showings in your area."
2. **Bridge** — names the prior agent: "April's moved on from our team, so I'm personally looking
   after your search now."
3. **The property** — the most-recently-viewed home **in the lead's primary market** (out-of-state
   browsing noise filtered out), pulled from the notes.
4. **The ask + open door** — "Saw you checking out `[address]` — want to go see it? Happy to set up
   that one or any others you've got your eye on."
5. The exact Zillow URL is appended deterministically (the model never edits the link).

## Sending — text and call

There is **no FUB API that sends a message** (`POST /v1/textMessages` only *logs*; it never
transmits). So the widget sends through a number we control and logs into FUB for the timeline.

- **Number:** `+1 (913) 286-1761` "Zach AI Outbound" on our Twilio account — A2P brand **approved**,
  campaign **verified**, in a Messaging Service.
- **Text** — `POST /fub-widget/send` sends via the Twilio Messages API (`From` = the AI-outbound
  number **and** `MessagingServiceSid` together, for A2P compliance), then logs to the FUB timeline
  via the registered-system API (gated on `FUB_SYSTEM_KEY`).
- **Call (click-to-call bridge)** — `POST /fub-widget/call` rings the agent's cell first, then
  `/fub-widget/voice/outbound` returns TwiML that dials the lead with the AI-outbound number as
  caller ID and bridges the two. The agent talks on their normal phone; the lead sees the
  AI-outbound number.

<Note>
Logging sent/received texts onto the **FUB timeline** requires registering the system at
`apps.followupboss.com/system-registration` and setting `FUB_SYSTEM` + `FUB_SYSTEM_KEY`. Sending,
calling, and inbound routing all work without it — only the FUB timeline row waits on that key.
</Note>

## Inbound routing — one number, two systems

A lead lives in **exactly one** system — FUB (this widget) or HouseLoop CRM — never both, and keeps
the same number when they graduate FUB to HouseLoop. Inbound to the AI-outbound number therefore
routes by **ownership = does an `hl_leads` row exist for that phone** (HouseLoop-first, FUB-fallback):

```
Lead texts/calls the AI-outbound number
   -> CRM webhook (front door) checks hl_leads by phone tail-10
        - HouseLoop lead          -> handled in the CRM (unchanged)
        - not a HouseLoop lead     -> forwarded to the FUB widget:
             SMS   -> POST realloop.co/fub-widget/sms/inbound  (X-HL-Forward-Secret + MessageSid dedupe)
             Voice -> TwiML Redirect to realloop.co/fub-widget/voice/inbound (whisper "call from <lead>")
```

Graduation is automatic: the moment an `hl_leads` row exists for that number, the next inbound
resolves to HouseLoop and the widget stops receiving it — **no double-send, no flag to flip.** The
shared `FUB_FORWARD_SECRET` guards the SMS forward; `MessageSid` / `CallSid` dedupe Twilio retries.

<Note>
True lead caller-ID on a forwarded inbound call is **not possible on raw Twilio** (anti-spoofing /
STIR-SHAKEN). The agent's phone shows the AI-outbound number; a spoken **whisper** announces who's
calling instead.
</Note>

# ═ FUB IMPORT NOTIFICATIONS — the 2026-07-29/30 pass (Adam) ═

Four defects, found by Zach on real leads, all in the seam between **a FUB signal arriving** and **Zach being
told about it**. Every one is the same shape: **an absence read as a decision.**

## ① `peopleCreated` carried no `webhookType` — the MINT arm could never notify

`fub-webhook-router` dispatched `{ trigger: 'new_lead' }` with **no `webhookType`** — the only branch in the
router that omitted one. The dispatch drops falsy fields, and `fub-lead-import` gates its **entire** notify
block on `if (!backfill && webhookType && notifyOn)`. **The import that MINTS a brand-new lead was structurally
incapable of notifying.** Not gated off by a toggle — silently skipped.

It bites hardest on the highest-intent signal, because a new Zillow tour fires **two** webhooks in the same
second: `peopleCreated` (no type) and `eventsCreated` (`tour_requested`). The registration import wins the race
and mints; the tour import then sees an *existing* lead. Zach's words: Bradley Bengel requested **four homes**
and he was told someone *registered*, never that they wanted a showing.

**Reproduced, then proven fixed, on real `POST /v1/events` traffic:**
```
BEFORE  19:58:42  lead MINTED · nativeNotified=FALSE · notifications: ZERO
ISOLATE 02:41:45  same tour event on an EXISTING lead → class 'tour_request' → SMS   (chain is healthy)
AFTER   02:55:06  router webhookType='registration'  ← the field that was empty
        02:55:15  'MintArm Test500632 — 4410 Mint Arm Way' → SMS
```
**Fix:** `{ trigger: 'new_lead', webhookType: 'registration' }` — a real board row, so it stays
catalog-driven and Zach-controllable.

## ② The 48-hour recency gate is GONE — age no longer decides anything

> Zach: *"Recency going back 48 hours is dumb. What if the system is down and pulls it in 3 days later — I
> don't want it to silently fail. It needs to be the date, the time, of the registration event, then dedupe and
> not send any more after it sends that one. But after it pulls in, it has to continue firing for future events."*

The gate asked *"is this OLD?"*; the real question is *"have I TOLD him yet?"* Age is a proxy that fails in
precisely the case that matters — **our own outage**.

**The case:** Zachary Bell (FUB 50546) inquired 2026-07-27 — a funded investor with a buy box. He was dropped
by ③ below, and when re-driven on 07-30 he minted correctly and then went **silent at 58h**. Not even a bell.

**What replaced it (mig 0498 + `createNotification`):**

| Mechanism | Job |
|---|---|
| `hl_leads.notify_anchor_at` | The **registration event's own timestamp** — *not* our mint time. (Bell minted 07-30 06:24 but registered 07-27 20:25; anchoring on the mint would still have silenced him.) Activity at/after it is news; before it is history and stays context. |
| `hl_lead_activity.notified_at` | Per-signal delivery stamp. Stamped = never fires again. |
| Exact-signal dedupe now **FOREVER**, not 5 minutes | The 5-min window was sized to beat the webhook/poller race, so *any* later re-drive re-fired the identical card. The title-heuristic branch **keeps** its 5-min window on purpose — titles legitimately repeat, and an unbounded title match would swallow a genuine second event. |

**Why dropping it is safe:** the 2026-07-09 flood was mirror-reading **pollers** treating re-scraped old rows
as new. Those pollers were **ripped**; the webhook is the sole trigger and fires on genuinely new activity, and
historical import comes through `backfill`, which never notifies. The gate guarded a door that no longer
exists while silencing real leads through the one that does. The **dispatch-freshness** suppressors STAY —
they ask a different, still-valid question: was this *dispatch* live, or a queued backlog draining through?

<Warning>
**The flood guard is the whole safety of this change.** 17,006 of 17,556 existing activities were older than
48h and had **never** been notified — flipping the rule bare would have sent ~17,000 notifications. Mig 0498
stamps **all** existing activity delivered FIRST; `pending = 0` and zero null anchors were verified immediately
after apply. Same sequence that made the Zillow in-app fix safe (402,346 rows marked, pending 0, then correct
delivery). **Never enable a "fire what hasn't been delivered" rule without seeding the ledger first.**
</Warning>

## ③ The config lookup asked for a name the board doesn't store

the miss as *"Zach turned this off."* His toggles were ON the whole time. Run log, verbatim:
```

```

# ═ THE 1000-BLOCK SYNTHETIC-ID SCHEME IS DEAD (2026-07-30, Zach-approved) ═

> Zach, verbatim: **"yes clean the rows and get rid of the 1000 block bullshit."**

## What the scheme was, and why it had to die

A message we **scrape** (Zillow in-app, group SMS — anything not fetched from FUB's API) has no FUB id, so we
mint one. The old scheme gave every person a private block of exactly **1,000 slots**:
`900000000 + personId × 1000`.

**Message #1,001 landed inside the NEXT person's block.** And because the insert is
`ON CONFLICT (id) DO NOTHING`, the collision was **swallowed with no error** — the message simply never
existed. Same silent-loss shape as everything else this week.

<Warning>
**Widening the block would NOT have fixed it.** Any fixed per-person capacity is a bet on how much a person
will ever say, and when the bet loses the failure is silent. 10,000 slots just moves the cliff. **A monotonic
pool has no cliff** — ids only go up, collisions are impossible by construction, and `id` is int4 (max
2,147,483,647) against a pool based at 1.2B: ~947M slots, versus ~150k synthetic rows after five years of
scraping.
</Warning>

## ⚠ THREE TRAPS — read before touching synthetic ids again

**① CRM `source_id`s are PREFIXED.** They look like `inapp:950454003`, not `950454003`. A `^[0-9]+$` regex
matches **nothing** and returns a confident, wrong **zero references** — which would have green-lit a re-ID
that orphaned live message history. Re-measured correctly: 316 `inapp:` refs exist, zero touch an affected
person, and that was confirmed a *second* way by sampling 25 **real** misplaced ids and searching for them
verbatim. **Always sample real ids; never trust a pattern you haven't proven matches.**

**② The relay upserts BY ID — changing an id creates a duplicate, not a move.** `fub-relay` carries CD → RW
keyed on `id`, and it **never deletes**. Re-ID on Camp David alone ⇒ the relay INSERTs the new id on Railway
while the old row stays ⇒ 5,192 duplicates ⇒ a bulk DELETE to clean up (Rule #0). **Stop the relay for the
write.** This job performed zero deletes because of it.

**③ The verification predicate is the trap.** The obvious check —
`id >= 900000000 AND (id - block) NOT BETWEEN 0 AND 999` — counts the **overflow rows as misplaced**, because
they are outside every person block. That is the *point*, but it reads as total failure. The correct test is:
```sql
id >= 900000000 AND id < 1200000000 AND (id - (900000000 + person_id*1000)) NOT BETWEEN 0 AND 999
```
A wrong success test is as dangerous as a wrong fix — it nearly reported a clean run as a failure, and could
just as easily do the reverse.

## The rule now

`fub-scraper-lib.mjs` allocates **every** new synthetic id from the monotonic overflow pool (`OVERFLOW_BASE =
1200000000`). `baseId` and the per-person offset cursor are **deleted**. Per-person blocks are frozen legacy —
existing ids stay valid, nothing is ever minted into a block again.
